# 速度の参考チェック（PR #1686、2026-10-10）

画面ごとに5回を順番に測り、指標ごとの中央値を比較する。結果の `samples` に5回の生の値、`policy` に環境・回数・時間倍率を残す。読み込みに失敗した回は再試行で置き換えず、測定を失敗にする。

## CIの余裕の根拠

修正前の [CI run 38040188674](https://github.com/skmtmst/line-harness-oss/actions/runs/38040188674/job/114178841250) は3回の中央値で、受信箱の反応84ms（基準67ms）、2,000人の長時間処理63ms（目標50ms）だった。比率はそれぞれ1.254・1.26。観測した最大比率を切り上げ、CIの時間倍率を1.30とした。機械差と測定の揺れの両方に対する暫定的な余裕であり、複数のCI実行から機械の性能比を確定した値ではない。

- 手元: 従来の基準×1.20。CI: 基準×1.20×1.30＝1.56。2倍の悪化は落ちる。
- 2,000人の絶対目標: 手元1,000ms・50ms、CI1,300ms・65ms。
- longtaskの基準0は、観測対象となる処理時間の境界50msを比較の下限とする。0への倍率計算で、1回のlongtaskをすべて悪化にしない。
- JSの量には倍率を付けず、従来の1KBの許容だけを使う。既存の基準表は更新しない。

`V8_SPEED_PROFILE=ci` をCIから明示する。未指定なら `CI=true` のときCI、通常は手元の条件。未知の環境名は失敗する。

## 必須と参考の分離

列車12までの `codex/development` では速度予算は `continue-on-error: true` だった。列車14で追加された2,000人の絶対速度目標だけが必須になっていたため、両方を別ステップの参考チェックにそろえた。レイアウト・仮想表の操作と配置、および判定道具自体の対照試験は必須のまま。

測定CLIと絶対目標CLIは、超過・測定失敗時に終了コード1を返す。結果には `complete: false` とエラーを記録する。絶対目標は `complete: true` がない途中結果を拒否する。報告ステップは `steps.*.outcome`（実際の成功・失敗）を使い、「測定未完了」「測定完了・超過」「合格」を区別してActionsの警告と概要へ出す。結果ファイルは従来のartifactへ保存する。参考ステップのためjob自体が緑でも、未測定を合格と報告しない。

## 確認命令

CIと同じモックAPIと、本番形式の書き出しを配る静的サーバーを先に起動する。

```sh
V8_SPEED_PROFILE=ci node apps/web/scripts/v8-guard/speed-budget.mjs http://127.0.0.1:4310 /tmp/v8-guard/speed.json
V8_SPEED_PROFILE=ci node apps/web/scripts/v8-guard/stress-targets.mjs /tmp/v8-guard/speed.json
node --test apps/web/scripts/v8-guard/speed-budget.test.mjs
```

実ブラウザの負の対照は同じ測定命令へ `SLOW_MS=2000` を追加する。標準10画面と2,000人の場面の表示に2秒を加え、予算CLI・絶対目標CLIがともに1で終わることを確認する。数値の対照試験では全4時間指標の2倍、CI実測84ms・63ms、欠測・途中結果・警告、JSの増加、必須/参考のworkflow設定を検査する。
