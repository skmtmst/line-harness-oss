## Uber Eats の現在の提供範囲（2026-10-23）

- 接続設定の完了と注文の連携は別。注文の取り込みと注文ごとの操作は、接続とサーバー側の利用条件がそろった場合に受注画面へ表示する。この設定画面では可否を推測せず「受注画面で確認」と案内する。営業状態の変更とメニュー同期はまだ利用できない。
- 設定画面の Uber Eats はログイン・店舗選択に加えて接続確認と解除も実際のAPIへつなぐ。確認はサーバーが確定した状態だけを反映し、解除は共通Dialogで利用者が確定した1回だけ送る。解除結果が不明な場合は直前に表示していた接続先を確認用に残し、接続操作を止めて「送り直さず musubo へ」と案内する。再認証が必要な場合は「Uber Eats にログインし直す」を出し、再認証から戻った後は店舗選択や解除を自動実行せず、接続確認が完了してから利用者が解除をもう一度確定する。
- 店舗の接続先またはメニュー連携に確認が必要な保存状態は、通常の「つなぐお店を選ぶ」案内へ戻さない。接続先を確認用に残し、安全な「接続を確かめる」だけを使えるようにして、店舗選択と解除を止める。
- 受注画面の接続の札は設定画面と同じ保存済みの接続APIを読む。この読み口はオーナー・管理者専用なので、閲覧のみ・権限の読込中は照会せず「接続未確認」とする。失敗・未取得は「接続未確認」、結果不明は異常として表示し、別の店の遅い応答を混ぜない。
- Uberの注文は一覧・詳細・履歴・CSVで確認できる。一括受付と停止の対象からUberを除く。他社の受注・停止・再開は維持する。
- 品切れのAPIは商品に紐付いた全サービスへ送るため、Uberを含む商品の選択・切替は止める。他社だけの商品は従来どおり。保存済みの商品・販売状態は消さない。
- 閲覧のみでは変更操作を隠す。Worker・DB・通信APIの実装、署名・権限・別店の境界・送信停止旗・上限は変更しない。

以下の既存の送信仕様は、Uber以外の操作と保持している実装の説明。Uberを利用可能とする記載には使わない。

## 1. 社名のあとの半角の空き → 作りを直した

絵の本文は「Uber Eats での許可をいただきました。Uber Eats に登録されているお店が2件…」。
英数字で終わる名前のうしろだけ半角の空きを入れる決まりで、`docs/v8-design-rules.md` の
「単位は数字の後ろに半角の空き」と同じ考え方。この画面の `SERVICES` も前から
Uber Eats は「Uber Eats に入った注文を…」、出前館は「出前館に入った注文を…」と書き分けていた。

直したのは文字をはめ込んでいた9か所。`withParticle(name, particle)` を1つ置いて、
英数字で終わる名前のときだけ空きを足す。出前館・ロケットナウは今までどおり空きなし。
DL-3 の題と本文（Codex が調べていない窓）にも同じ間違いがあったので、あわせて直した。

## 2. 窓の左のボタン「やめる」 → 「キャンセル」のまま

`docs/v8-design-rules.md` B-146：
「入力をやめる＝「キャンセル」、窓を閉じるだけ＝「閉じる」。「やめる」は使わない
（予約のキャンセル窓の「やめる」も「閉じる」）」。

これはオーナーの決まり（順位2）で、Pencil の板（順位3）より上。
同じ §1 に「絵と食い違う時は決まりが勝つ。コードは決まりどおりにし、絵と写しを直してから
その板を測り直す（B-240）」とある。よって作りは「キャンセル」のままにし、**絵の側を直す**。

v03 の DL-3 `a3W4B`／DL-4 `K3aIxK` の両方が「やめる」なので、この板だけの写し間違いではない。

## 3. 右上の× → 消さない（絵の側を直す）

共通部品 `components/shared/dialog.tsx` は右上の×を必ず出す。止める入口（prop）は無い。
部品の中にも「閉じ方は必ず右上の×。フッターの「閉じる」ボタンは置かない（UI-25）」と書いてあり、
`components/shared/dialog-close-ui25.test.tsx` が見張っている
（標準・確認・危険操作の3つすべてに `aria-label="閉じる"` が出ること）。

`docs/v8-design-rules.md` 20〜21行目：
「見た目を変えるときは Pencil を先に直す。コードだけ直すと、次に絵を見た人が元に戻す。」
「…ただし **LINE の決まり・安全・見張りに反する絵は、今の作りに合わせて絵を直す**」。

×を消すと見張りが落ちるので、この但し書きのとおり**絵を直す**側になる。
v03 は DL-3 `k9HHE`／DL-4 `wU4HH` のどちらも窓の頭に題だけで×が無い。

> 注：UI-25 はコードと試験にしか書かれておらず、`docs/` の markdown には記録が無い
> （`grep -rn "UI-25" docs AGENTS.md` で0件）。だから絵を描くときに漏れた。
> 正本 `docs/v8-design-rules.md` への追記は**司令塔の枝の仕事**で、この枝からは触れない
> （`docs/v8-*` は司令塔の持ち物で、lane の PR から変えると `required-pr-gate` が落ちる）。

## 4. 窓の高さ 396 と 451 → 数字を合わせ込まない

幅は絵も作りも 480（共通の `small`、決まりの「窓の幅は 480／560／720／960」どおり）。
高さが違うのは、絵の余白と間隔が共通部品の値と違うから。

| ところ | 絵（v03） | 共通部品 | 出どころ |
| --- | --- | --- | --- |
| 窓そのものの余白・段の間隔 | 0 | **0** | `dialog.module.css:334`（層の外） |
| 窓の頭 | 47（上下10） | 20 / 24 / 8＋×のボタン36 | 同 341行目 |
| 中身の余白 | 上12・左右24・下20 | 24（四方） | 同 396行目 |
| 中身の間隔 | 12 | **12**（差は無い） | 同 430行目 |
| ボタンの段 | 60（上下12） | 14＋区切り線1px | 同 404行目 |

窓そのものについて、`.confirmationPanel { gap:16px; padding:24px }`（42行目）と
層の中の `:root .panel { padding:24px }`（257行目）は、**332行目で `@layer components` が閉じた
あとの** `:root .panel { padding:0; gap:0; overflow:hidden }`（334行目）に負ける。
層の外の決まりは、層の中のどの決まりよりも強い。だからこの窓は**頭・中身・区切り線・ボタンの段が
隙間なく積み重なった一枚の箱**で、内側の下げ幅も段と段の間隔も無い。
`padding:24px` が効くのは `[data-design-layout='stacked']` など別の型を渡した窓だけで、
この2枚はどれも渡していない。

「中身の間隔 16」は前の版のこの表の書き間違いだった。16 は `--tpl-e1-dl-gap` で、
画面本体（`delivery.module.css` の `.body`）にだけ使う値。窓の中身は 12 で、絵と同じ。

v04 で共通部品の値へそろえ直して測ると、**DL-3 `s7FM2` が 480×281、DL-4 `xnZpf` が 480×431**。
内訳も部品の計算と一致する（頭 114＝上下の余白28＋いちばん高い子86／
DL-4 の中身 252＝余白48＋お店の群138＋間隔12＋注記54／ボタンの段 64＝ボタン36＋上下28）。

Codex の実測 451 とはまだ 20 の開きがある。原因は本文や住所が実際の文字で何行に折り返すかで、
絵の側では確かめられない。4 の決着どおり**数字は合わせ込まない**ので、ここは合わせずに残す。

`docs/v8-design-rules.md` 161行目「作る画面の細かい違い（閉じるボタンの枠・欄の高さ 36・
右の欄の幅）は共通部品の値にそろえる」。
部品には板ごとに余白を変える入口（`designHeaderPadding` など）もあるが、
使っているのは窓を出す165ファイルのうち29ファイルだけで、既定値がこのアプリの標準。
この板に標準から外れる理由（オーナーの決まり）は無いので、**絵を標準の値へ直す**。

## 本線取り込み後の動作と安全対策（2026-10-19）

- v04 の店舗選択（DL-4）は実際の候補取得・確定APIにつながる。解除の確認窓（DL-3）の文章・幅・共通Dialogの構成もv04を保つ。
- 閲覧のみでは変更操作を隠し、閲覧のみの帯を出す。OAuthから戻っても候補取得と変更窓を自動で開かない。項目と値は共通CustomerInfoRowsを使い、長い項目名を重ねない。
- 出前館・ロケットナウの申し込み・取り消し・接続確認・解除は、対応するAPIが未接続のため共通の準備中案内を出す。Uber Eats の接続確認と解除はオーナー・管理者だけが実行でき、選択中のLINE公式アカウントや権限が変わった後に古い応答を反映しない。どの操作も失敗や曖昧な応答を成功扱いして状態や日時を書き換えない。保存対象のない下部の保存・キャンセルは置かない。
- 店舗選択の候補取得とPOS有効化はA06のboundedHttpRequestへ通し、1回の通信を10秒・応答1MiBに制限する。SDK内の自動再送はしない。
- 有効化前に既存接続の版・アカウント・候補を照合し、対象と送信開始を保存する。同時操作の片方だけが送信できる。通信断・5xx・外部成功後の保存失敗は結果不明とし、候補取得・押し直し・再ログインで開始印を消さない。画面は送り直しを勧めずmusuboへの確認を案内する。
- 完全なA06の永続journal・複数Worker間の共有遮断・結果照合の自動化はこの実装に含まない。既存の欄だけの保守的な停止で守り、共有遮断の新表はA06の番号案727として司令塔へ渡す（未予約・作成なし）。
- エラーは既存の共通fail/inputErrorを利用し、入力項目storeIdを返す。S03本体は指定まとめ土台に未包含のため、S03との最終統合時に共通のエラー正規化・相関ID・コード一覧を同じ版で再確認する。別のエラー形式を画面やWorkerへ作らない。
