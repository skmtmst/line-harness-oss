# 統括のバナー生成の動き（BEHAVIOR.md）

対象：`list.tsx`（一覧 `B9ZAr`・画像ライブラリ `W5Wxr`）と `project.tsx`（プロジェクトの中 `iMnph`・生成中 `p03ImY`・上限 `zOpMG`）。
写し元：`app/hq/banners/page.tsx`・`app/hq/banners/project/page.tsx`・`components/hq/banners/*`（v7。消さない）。

## 入口
- `app/hq/banners/page.tsx`・`app/hq/banners/project/page.tsx`：`theme === 'v8'` のときだけこの画面を出す。v7 側は今のまま。

## 受け付ける URL と指定（v7 と同じ）
- `/hq/banners`：プロジェクト一覧。`?tab=library` で画像ライブラリ。タブは `router.replace` で切り替え、履歴を積まない。
- `/hq/banners/project?id=<プロジェクト>`：プロジェクトの中。`&from=<画像>` で「同じ設定でもう一度生成」の条件をパネルへ入れる。
- id が無い・見つからない・権限が無い・読めないときは、v7 と同じ案内（TargetMissing・ListState）。

## 読み込み（API は v7 と同じ）
- 一覧：`hqBanners.presets`（用途と利用量）・`hqBanners.stats`（数）・`lineAccounts.list`（渡す先）。形の違う応答は置かず「—」。
- プロジェクト一覧：`projects.list({archived})` と `images.list({limit:100})`（カードの上の3枚）。
- 画像ライブラリ：`images.list({favorite, delivered, shape, q, withCounts, limit:12, before})`。数（すべて・お気に入り・渡し済み・未使用）はサーバの `counts`。
  - **変えた所**：v7 は「さらに N 枚を表示」で足していく形だった。V8 は絵どおり 12 枚ずつのページ（「1–12 件 / 23 件」「次の 12 件」「前の 12 件」）。続きは v7 と同じ `before`（日時のカーソル）で読む。
- プロジェクトの中：`projects.get(id)`・`presets`。生成は `createGeneration` → `generations.run` を1枚ずつ繰り返す（v7 と同じ。戻ったら続きから動く・止めるは `generations.cancel`）。

## 操作（オーナー・管理者だけ。閲覧のみには置かない）
- 一覧：プロジェクトを作る（窓 `W7Z57`。名前は必須・100文字まで。作ったらそのプロジェクトを開く）、カードの星（お気に入り）。
- ライブラリ：画像を取り込む（窓 `AnwtH`。入れるプロジェクトを選ぶ・PNG/JPEG/WebP・10MB まで。取り込めたらそのプロジェクトを開く）、星。
- プロジェクトの中：画像を取り込む（ファイルを直接選ぶ）・アーカイブする（確かめ `I0w2e`。済んだら一覧へ）・復元・「…」（お気に入り・複製する・名前と説明を変える）・生成パネル・画像を生成・条件をクリア・止める。
- 画像の詳細（窓 `rI5uh`。一覧・ライブラリのどちらからも開く）：ダウンロード（閲覧のみも可）・お気に入り・アカウントへ渡す・一覧から外す（確かめ `B24oNg`。詳細の窓は閉じて確かめだけを出し、やめると詳細へ戻る）・参照画像にする（プロジェクトの中だけ）・同じ設定でもう一度生成。
- **変えた所**：渡す先からアーカイブしたアカウントを外した（受け取る口が止まっている）。渡す先の一覧は5人分の高さで、多いときは中で送る。

## 権限
- 役割はサーバ（`useStaffRole`）から読む。オーナー・管理者以外は「閲覧のみ」として、作る・取り込む・星・アーカイブ・生成パネル・渡す・外すを**置かない**（押せない形でも出さない。2026-10-06 オーナー決定）。読み込める間は一覧・画像・詳細・ダウンロードは見られる。
- 403 は「バナー生成は統括の管理者・オーナーだけが使えます。」（v7 と同じ）。

## 失敗時
- 作る・渡す・外すの失敗は、共通の状態別案内（`describeApiFailure`、M022）を窓の中に出し、窓は開いたまま送り直せる。
- お気に入りの失敗は帯で「お気に入りを変更できませんでした。もう一度お試しください。」。
- 上限・一時停止・課金の停止は帯（一覧）と生成パネルの中（プロジェクトの中）に出す。言葉は v7 と同じ判定。

**縦が 0% なのは位置のずれではなく作りの違い**

板は高さ約 2280px の 1 枚の平面図で、参照画像 3 枚を入れた状態を描いている。実画面は `main` の中で縦に送る作りで、参照画像は 0 枚・テキストは 1 行から始まる。板にも「同時には出ない」ことを書いた除き札が 18 枚ある（`PxmmN`「参照画像が3枚のとき」／`SaljW`「0枚のとき」、`WG7JM`「注記（3枚のとき）」／`khG91`「注記（0枚のとき）」ほか）。**板自身が状態を分けて描いている**ので、板の原点ひとつで全部を測ると下にある文字ほど差が積み上がり（-251〜-320px）、縦が 0% に見える。

なので**原点に依らない測り方**に替えた。絶対座標ではなく**隣どうしの文字の縦の間隔 Δy** を板と実画面で比べる。これなら「並びの順番が板どおりか」と「文字どうしの間隔が板どおりか」を原点なしで測れる。幅 1692px で測ると `main` が `{x:240, y:60, w:1440, h:928}` ＝板の幅 1440 と同じになる。

### 板の箱の実寸は、板自身の間隔定数から逆算できる

はじめは「板の箱の実寸は読めないので数字を合わせる修正はできない」と書いていたが、**板の文字の座標だけから間隔の定数を取り出せる**ことが分かったので、そこを足して直した。

板の中で**中身が1行の文字だけが縦に並ぶ所**を探すと、組と組の間・組の中の間が割り出せる。

- **組と組の間 = 16px**：`swcu2`（h17）→ `ta8eS`、`UOLnf`（h17）→ `z9YC2` の 2 例がどちらも Δ33 = 17 + 16。実装の `#E8oZc` の `gap-4`（16px）と一致する。
- **組の中 = 6px**：題（h17）とその中身の間が Δ23 = 17 + 6。実装の `gap-1.5` と一致する。

この 2 つが分かれば、**板の文字の間隔から箱の高さを逆算できる**（箱の高さ = 板Δ − 題の高さ − 組の中 − 組と組の間）。これは推測した数字ではなく、板の座標から出した値なので、46 行の「根拠の無い数字を置かない」に沿う。

### 逆算して直した 3 か所

1. **脇パネルの見出しの行（`min-h-14` を外した）** — 板Δ（`S0ay0i`「画像を生成」→ `RJIyX`「出力サイズ」）49 に対し実Δ55。`min-h-14`（56px）は、2026-10-06 のオーナー指示で外した「バナー／自由入力」の切替（板 `pj2tz`・`hPRmn`。板では見出しと同じ y156 の行にあった）を押せる大きさに保つための最小高さだった。切替が無い今は題だけの行なので外す。→ 実Δ46（差 -3）。
2. **色の 4 つの役割の縦の間隔（`gap-3` → `gap-y-1`）** — 板の上下のピッチ（`VVBfu`メインカラー y1355 → `ZdLJ8`サブカラー y1420）65px。実画面の 1 区画は 題18 + 組の中6 + 色の枠36 = 60px なので縦の間隔は 4〜6px。板ちょうどは 6px だが `size-scale-contract` の「4の倍数でない gap 段を増やさない」ラチェットに当たるので、4 の倍数側の 4px（`gap-y-1`）を採った。→ 実Δ64（差 -1）。横は板どおり 12px のまま。
3. **`追加の指示` の入力欄の高さ（1 行ぶんに）** — 板Δ（`WMhuQ`「任意・600文字まで」→ `coo4b`「つくる枚数」）90 を上の定数で割ると、箱の高さは 90 − 16 − 6 − 題17 = **51px**。つまり板はこの欄を 1 行ぶんで描いている。共通部品 `text-field.module.css` の `.multi` は 2 行ぶん（`min-height: 120px`）だが、これは V5 公認で 22 か所が使う形なので**部品そのものは変えず**、この 1 か所だけ `rows={1}` ＋ `style={{ minHeight: 0 }}` で最小高さを外し、固有の高さ（上下の余白14×2 ＋ 1行23.8 ＋ 枠2 = 54px）にした。魔法の数字は置いていない。`.multi` の `resize: vertical` は残るので長い指示は引き伸ばして書ける。→ 実Δ94（差 +4）。

結果（幅1692・`[data-theme='v8']`・参照画像0枚・テキスト2行）:

| | 間隔の組 | 板と±4px以内 | 並びの順番が板どおり |
|---|---|---|---|
| 題・来た道の案内・操作ボタン | 4 | 4 | 4 |
| 左の画像一覧 | 1 | 1 | 1 |
| 右の脇パネル | 54 | 50（直す前 47） | 54 |
| 下の帯 | 1 | 1 | 0 |
| **合計** | **60** | **56（93.3%）**（直す前 53＝88.3%） | **59（98.3%）** |

この 93.3% は**間隔（隣どうしの Δy）の一致率**で、`docs/v8-design-rules.md` 38 行が言う**位置**の一致率とは別の指標。**この表だけで 38 行の合格を満たしたとは言えない**（下の「間隔と位置は別の指標」を必ず合わせて読む）。並びの順番は直す前と同じで、既存の 53 組はどれも崩れていない（増えた 3 組はいずれも狙った箇所）。横の間隔の照合は **58/62 = 93.5%**。帯は高さ72・枠 `#DADDE2` 1px・角丸12・幅1392 が板と一致し、真ん中の札の中心のずれも板 10px / 実 11px。

**残った 4 組の内訳**（同 39 行の「合格にしてよい違い」＝データの有無で出る／出ない欄、文字の長さによる行数、に当たる）

- **参照画像の枚数で決まる 2 組**：`qW4lX → qRB13`（差 -217）と `WNhWa → Wd2zi`（差 -66）、合わせて 283px。板は 3 枚入り（248+155=403px）で実画面は 0 枚（31+89=120px）。板の `PxmmN`「参照画像が3枚のとき」／`SaljW`「0枚のとき」がこの 2 状態の札で、**板自身が別状態として描き分けている**。ただし試験では参照画像を投入できなかったので（投入の口が `multiple` でなく、1 枚ずつ入れても画面に反映されない）、行数のように実測で閉じるところまでは確かめていない。**未実証として区別して書く。**
- **行数で決まる 1 組**：`l5Dsb1 → jZLJs`（説明文から「行を足す」まで、差 -24）。実測Δは 1行=103 / 2行=147 / 3行=191 / 4行=235 で、**1 行あたりちょうど 44px**（行36 ＋ `gap-2` 8）。板のΔ171 は 2 行（147）と 3 行（191）の間なので、板は 2〜3 行ぶんの領域を描いている。**間隔の差 = 行数の差**と実測で閉じた。
- **注記の置き場所の読みが分かれる 1 組**：`jZLJs → UOLnf`（差 +15）。実画面は「ボタンの文字 → ボタン下端（32−7=25）→ 枠付きカードの `p-3` 下余白 12 → 組の `gap-1.5` 6」で 44。上の定数で板のカードの中を組むと「カード上端1125 ＋ 上余白12 ＋ 3行分124 ＋ `gap-2` 8 → ボタン上端1269 → 下端1301」で注記 `UOLnf` の y1302 とほぼ一致する。つまり**板では注記がボタンの直下にあり、カードの下余白と組の間隔を挟んでいない**という読みになる。ただしこれは「板のテキスト行が 3 行」「文字の上のオフセット 7px」という仮定の連鎖なので、**DOM の作りを動かす推測の直しはしない**（46 行「根拠の無い数字を置かない」）。差 15px は残差として記録する。

**板の箱そのものの実寸は依然として取れない。** Pencil の MCP は `filePath` を見ずに開いている絵を使うので、`バナー生成.pen` が開かれていない状態では `qIp42` の箱を取得できない（`Get("qIp42", …)` が `Can't find node` で失敗し、`get_app_state` の active は `LINE-Harness-V8-B.pen`）。板の除き札 18 枚にも箱の実寸を与えるものは 1 枚も無く、どれも注記か別状態の札。上の 3 か所は**箱の実寸ではなく板の間隔定数**から逆算したので直せた。参照画像の受け口の実寸と上の `jZLJs → UOLnf` を閉じる回は、利用者が `バナー生成.pen` を開いた状態で改めて測る。

**この回の見張り**：`src/app/hq/banners/banners.test.ts` の「V8 は板 qIp42 の『利用量』と『生成する（N枚）』を持ち、v7 の既定は変えない」と、`src/v8/hq-banners/project.test.tsx` の帯のボタンの名前。

### 間隔と位置は別の指標（2026-10-08 に測り分けた）

上の表はすべて**間隔**の一致率で、`docs/v8-design-rules.md` 38 行の合格条件は**位置**の一致率。混ぜて書いていたので測り分けた。

| 指標 | 何を比べるか | 原点 | 1 か所のずれの影響 |
|---|---|---|---|
| **間隔** | 隣どうしの文字の Δy | 要らない | その 1 組だけが外れる |
| **位置** | 文字ごとの座標 | 要る（`main` の左上） | **その下の全部が外れる（積み上がる）** |

同じ画面・同じ条件（幅1692 ／ `[data-theme='v8']` ／ **参照画像 3 枚**＝板と同じ状態 ／ テキスト 1 行）で両方測った結果。

| | 照合できた文字 | 縦が板と±4px | 横が板と±4px | 縦横とも |
|---|---|---|---|---|
| **位置**（`main` の左上を原点） | 62 | **11（17.7%）** | 57（91.9%） | 7（11.3%） |
| **間隔**（Δy・原点なし） | 60 組 | 56（93.3%） | 58（93.5%） | — |

**位置が 17.7% になる理由は「どこもかしこもずれている」ではない。** ずれが 4px を超えて飛んだ所で区切って段に分けると、**段の数は 12（脇パネルで 9）だけで、段の中の文字はすべて板どおりに並んでいる**。つまり「12 か所で下へずれ、そのずれが下の文字に全部のしかかっている」という形。脇パネルの段（段の先頭を基準に測り直したときのずれ量）は次のとおり。

| 段の先頭 | 件数 | 段のずれ | 原因 |
|---|---|---|---|
| `S0ay0i`「画像を生成」 | 14 | **+6** | 文字の上端の取り方の違い（下記 1） |
| `mtIVp`「VOOM（縦長）」 | 5 | +12 | 選択肢の行の高さ 2px 差が 3 行ぶん積んだ（下記 2） |
| `Wd2zi`「使い方は 3 つから選べます」 | 9 | **-81** | 参照画像の区画の高さの違い（下記 3） |
| `jZLJs`「行を足す」 | 1 | -105 | 既に記録した `jZLJs → UOLnf` の 15px（上記） |
| `UOLnf` 以降の 5 段 | 17 | -78〜-90 | 上の -81 がそのまま続いている |

**1. 文字の上端の取り方の系統差（+6）** — 脇パネルのいちばん上の文字 `S0ay0i` がすでに +6。ここより上に実装の要素は無いので、積み上がりではなく**測り方の系統差**。板は文字の枠の上端、ブラウザは `Range.getBoundingClientRect`（文字の墨が乗る範囲）を返すので、同じ字でも上端が数 px ずれる。**間隔（Δy）ではこの差が引き算で消える。**

**2. 選択肢の行の高さ 2px 差（+6 → +12）** — 出力サイズの選択肢の板のピッチは 53（y234/287/340/393）、実装は 55（y240/295/350/405）。`generation-panel.tsx` 577 行の `gap-1.5`（6px）を引くと行の高さは板 47・実装 49。**差の 2px は共通部品 `RadioCard` の中**で、この画面の指定ではない。44-45 行の決めごとどおり、他の板で合格している 40 画面以上へ波及するので**この回は変えずに記録する**（変えるなら板が 47 の画面だけが渡す札を足す形になるが、どの板が 47 でどの板が 49 かを調べられるのは司令塔）。

**3. 参照画像の区画（-81）** — 板はここに 3 枚＋ボタン 2 つを描き、実装は 3 枚＋注記 1 行。板のほうが約 93px 高い。これ自体は 39 行の「データの有無で出る／出ない札・欄」の範囲だが、**位置方式では「合格にしてよい違い」が 1 つあるだけでその下の文字 34 件すべてが外れる。** 39 行が許した違いが 38 行の合格率を壊すという矛盾がここに出る。

**だから位置の 17.7% を「不合格」とも「合格」とも書かない。**

- 38 行が指す正本の測り方は `~/lh-work/tools/hq/measure.sh`（司令塔は `m8.sh`）。`ls ~/lh-work` はこの作業場所では無出力で、`scripts/visual-qa/v8-parity.mjs` の `DESIGN_DIR` の既定値が `/Users/kentakenta/lh-work/design/v8` であることから、**あれは司令塔のマシンの中**。上の数字は**この回に自分で書いた測り方**（作業用の板の写し＋Playwright）で出したもので、正本の %ではない。
- 41 行が「**合格は司令塔が画像を見て決め、`PASSED.tsv` に記録する**」と定めている。**レーンが位置の合格を自分で申告してはいけない。**
- リポジトリの中の照合ツールはどちらも座標の照合ではない。`scripts/design-qa/compare-text.mjs` は**語の有無**の比較、`scripts/visual-qa/v8-parity.mjs` は見本画像との並べ比べ（はみ出し・単語の途中の改行・列のずれ・書体・文字の有無＋画素差）。
- 手持ちの道具では**間隔のほうが信頼できる**（上の 1 の系統差と 3 の状態差を引き算で消すため）。信頼できない数字をもとに画素合わせの追い込みはしない（46 行）。

**位置を測るときの注意（この回につまずいた所）**

- **測る前に内部の送りを 0 に戻す。** 管理画面は窓ではなく中の容器を縦に送るので、`window.scrollTo(0,0)` だけでは足りず、すべての要素の `scrollTop`／`scrollLeft` を 0 にしてから測る。これを忘れると題の列が一律 -483 になる。
- **参照画像は ★BG-C `cOgWE` の道から 3 枚入れる**（「ライブラリから選ぶ」→ `role="option"` を 3 つ押す →「この 3 枚を使う」）。投入の口は `multiple` ではないのでファイルの直接投入では増えない。3 枚入れると脇パネルの下側の残差が -269〜-301 から -78〜-90 に収束する。
- **同じ文字が画面に 2 か所あることがある。**「雰囲気を参考にする」は脇パネルの使い方の見出しと、参照画像 1 枚ごとの行の選び口の両方に出る。上にある方を機械的に選ぶと差 -488 の外れ値になる。板と実装の並び順は同じなので、**直前に照合できた文字のずれに近い候補を選ぶ**と正しい方（差 -81）に当たる。

**板を読む手だて**：Pencil の MCP は `filePath` を見ず、開いている絵を使う。`バナー生成.pen` の `qIp42` を読むには利用者がその絵を開いておく必要があるので、この回は先に書き出した板の写し（作業用の JSON）で照合した。`docs/v8-design-rules.md` は司令塔の所有パスなので、ここに書いて正本への反映は司令塔の枝で行う。
