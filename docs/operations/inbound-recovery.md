# 受信処理の再開と入力不足時の停止

既存の保存だけで再開できる範囲と、入力が足りず人の判断を要する範囲の説明。受信全体の完全再実行が実装済みとは扱わない。新しい永続表の提案や当時の検査記録は[外部保管](../document-archives.md#s05)。

## 結果と制限

受信箱の本文を再処理用にコピーせず、工程の結果にある受信箱のIDから元の保存へ戻る。本文・時刻から似た受信を推測して結び付けない。保存SQLだけ確定して親工程が未完になった場合も、確定済みSQLの結果とIDから再開する。取り消し、顧客削除、別アカウントへの移動、停止した契約は再開しない。

既存のSQL計画には保存時の引数（本文を含む）が残る場合もある。本修正はそこへWebhook全文や返信鍵を追加せず、確定した保存IDだけを取り出す。本文は現在の受信箱を正とし、取消後に古いSQL計画から復活させない。

管理者の `POST /api/line-webhook-events/:id/retry` と、5分ごとの内部回収（frequentHeavy、1-56/5、上限20件・順次）が同じ再開処理を使う。実行中の貸出と工程別の完了記録で競合と重複を止める。成功は200、要確認は409、処理中は409、一時失敗は503。安全な工程が成功しても残りの入力が不足すればイベント全体を成功にしない。回数上限・送達不明・要確認は自動回収しない。

| 新しい表なしで回復できる工程 | 条件・重複防止 |
|---|---|
| text/non-text受信の保存完了記録 | 親工程の結果、または確定済みのINSERTの結果から正確な保存IDを取得。INSERTを二度しない |
| メッセージ受信のマイル | 元の友だち・メッセージID・種類・時刻、工程別SQL記録を使用 |
| 友だち追加・ブロック解除の初回登録マイル | 完了した友だち登録工程の友だちID・初回時刻を使用。振り分けと配信は再開しない |
| text/通常postbackのスコア | 元の受信ID・所属・友だち・時刻で同じ採点工程を使う。返信の評価が不足していても採点だけは回復する |
| 受信箱の未読化 | 自動応答の評価結果が判明している場合だけ。完了した受信箱更新は再実行せず、担当者の解決状態を戻さない |
| 非テキスト受信・ブロックの分析記録 | 元の出来事時刻と不変IDを使う。非テキストは元の返信評価が判明している場合だけ |
| text/通常postback/unfollowのイベントバス | 入力・返信評価が足りる場合。完了した採点・各アクション・自動化起動を飛ばして再開 |
| 旧自動化のタグ付け/外し・情報更新・シナリオ登録 | 元の本文で条件判定、各アクションの工程とSQL完了を同じ取引にする。未完分だけ。postbackは通常dataに限る |
| 新自動化の起動、既存送信Webhook待ち行列 | 元の受信IDを使う既存の冪等な起動・配送記録を使用。既存の送信不明停止を保つ |
| unfollowの分析・自動化 | ブロックの状態保存工程に固定した友だちIDと時刻を使用。ブロック回数を増やし直さない。旧式の外部送信は要確認 |
| 工程全体成功後の受信台帳更新 | 台帳更新だけ失敗した場合、全体の成功記録から補完し、工程は再実行しない |

返信の評価結果は新しく `auto_reply` 工程へ保存する（本文・鍵は持たない）。旧受信についても、元の受信箱IDと一致する既存の自動応答評価が完了/スキップなら再利用する。評価前に失敗した受信は、当時の「応答ルールも代わりの返信も無かった」という真偽値が保存されている場合だけ、返信不要と判断する。後日の設定を見て返信不要だったと推測しない。ルールのある未評価受信は、静かな応答ルールであっても未実行の動きが判定できないため要確認に止める。

旧自動化の `send_message` は返信の鍵が必要だったかを復元できないので、自動回収では要確認に止める。旧式の直書きWebhookやメニュー変更も受理結果が保証できないため要確認に止める。その後にある安全なタグ等は続ける。鍵を省略してpushへ切り替えることはしない。最初からpushを使う新自動化の動きは、既存の宛先・工程・送信結果の台帳で守る。

## LINEの200応答の後へ回る全工程と入力

対象は `routes/webhook.ts` の `processLineWebhookEvents` へ渡す処理全体。Promiseは200を返す前に走り始めるが、完了を待たず `waitUntil` へ渡すので、以下は200後に失敗し得る。署名検査・アカウント解決・最終受信時刻の更新は応答前で、この表の対象外。

表の「済SQL」は `workflow_steps` のSQL結果・固定した計画、「工程」は親工程の結果。受信台帳 `line_webhook_events` にあるのは受信ID・所属・種類・状態・失敗分類・時刻で、本文・reply token・LINEユーザーIDはない。

## それでも残る工程・頻度・運用者の行動

実環境の失敗率は測っていない。以下の頻度はコードと入力の期限に基づく見込みで、件数の推定値ではない。

| 残り | 足りない入力/理由 | 発生の見込み | 運用者ができること |
|---|---|---|---|
| 保存前のmessage・友だち登録前・確認コード分岐 | 受信IDと利用者/本文/時刻の対応。200前の確実な入力保存なし | DB障害・Worker中断時。割合未測定 | 元のトークと受信履歴を照合。必要なら顧客へ再送を依頼 |
| 自動応答の未評価/未完、返信を含む旧自動化 | reply token、完了した評価・送達結果。一部静かな応答の未実行アクションも保留 | 返信が必要な失敗を回収する度に発生。内部回収は5分間隔なので鍵の通常期限を超える | マイル/採点は回復済み。応答の実行結果・トークを確認し、必要なら担当者として返信（manual付き） |
| 保存済み画像以外の元コンテンツ、位置情報/ファイル詳細 | R2へ保存前のバイナリ、詳細の原データ | Content API/R2障害・期限経過時。比率未測定 | 元のトークを確認し、必要なら添付を再送してもらう。回収はラベルから本物の中身を推測しない |
| 追加/解除・流入の振り分け/初回配信/クーポン | 当時の分岐・候補・配信の結末・reply鍵。一部の途中状態は個別台帳にしかない | 追加処理の途中失敗時。マイル回復後も全体は要確認 | 友だち追加の実行/配信/クーポンの履歴を確認。対応が決まるまで一括で送り直さない |
| 印付きメニュー・カルーセル・質問・調査・クーポン・予約確認 | 元postback dataと受信IDの対応、選択肢/エリア/版、一部返信鍵 | 該当のボタン処理の途中失敗時 | 各機能の既存実行結果で済んだ物を確認。専用回収がある機能はそちらを使う |
| 取消/顧客削除/所属移動後 | 意図的に消された本文/顧客、元の所属 | 取消・削除・所属変更の対象となった未完受信で毎回 | 再開しない。必要な手対応だけを元の所属/権限で判断 |
| 古い工程の無い受信・回数上限・送信不明 | 済んだかどうかの証拠、入力、外部の受理結果 | 旧受信のretry時、繰り返す障害、通信断時 | 履歴を照合。自動でunknown/exhaustedを解除しない |
| 他アカウント体験通知 | 当初の宛先一覧と宛先別送達結果 | 特殊語による通知中断時だけ | 送信済み相手を確認。まとめて再送しない |

画面の担当は司令塔。今回UIファイルは変更していない。LINE受信台帳APIの一覧へ `recoveryStatus`・`recoveryLabel=要確認`・`recoveryReasonCode`・`recoveryReason` を追加し、retryの返事にも同じ理由と運用者の行動を返す。既存V8画面はこのAPIを参照していないので、**画面への接続は未実施**。司令塔が状態の札と理由の表示を接続し、要確認に自動再送ボタンを置かず、★V8との照合を行う必要がある。APIの中身に本文/鍵を出さないことは試験で確認する。
