# 飲食店向け（テスト）分離設計

## 目的

Penの `R-1`〜`R-8` を正本として、飲食店向けの統合業務管理を検証する。
現行の然-NEN LINE/EC運用を壊さず、画面と機能が固まった時点で新しいサーバーへ
切り離せる構成にする。

## 分離境界

| 領域 | 飲食店向けテスト | 既存機能 |
|---|---|---|
| 画面URL | `/restaurant-test/*` | 既存URL |
| API | `/api/restaurant-test/*` | 既存API |
| DB | `rt_*` | 既存テーブル |
| 機能スイッチ | `restaurant_test` | 既存キー |
| 外部通信 | 無効 | 既存設定に従う |

既存の左メニューは変更しない。検証中は `/restaurant-test/*` のURLを直接開き、
既存運用のメニュー構成から完全に分離する。

## 画面

1. 店舗ダッシュボード（Pen R-1）
2. 組織・権限（Pen R-2）
3. 承認ワークフロー（Pen R-3）
4. 予約台帳（Pen R-4）
5. 座席・卓管理（Pen R-5）
6. 予約枠・在庫（Pen R-6）
7. メニュー管理（Pen R-7）
8. Google・口コミ（Pen R-8）
9. LINE来店フォロー（予約前、来店後、口コミ、会員証、1タップ予約）

## 予約媒体の検証方針

- レストランボードを中心ハブとする。
- ハブで取得できない媒体は、媒体別受信アダプターを追加する。
- 検証中の同期方向は `inbound_only` だけである。
- 予約、席在庫、キャンセルを外部媒体へ書き戻すコードは持たない。
- 受信イベントは店舗・媒体・外部イベントIDで冪等化する。
- 予約は店舗・媒体・外部予約IDで上書きし、重複登録を防ぐ。
- 予約メールのcatch-all取り込みは `docs/restaurant-email-intake.md` の分離境界に従う。

## 排他制御

現行の検証基盤はCloudflare Workers/D1であり、Redisを持たない。このため検証版は
`rt_resource_locks` の10秒リースで、同一店舗・同一時間帯の手動予約を排他する。

切り離し後は次の契約を保ったままRedis実装へ交換する。

- キー: `reservation:{storeId}:{startsAt}`
- 所有者: 操作ごとのランダムトークン
- TTL: 10秒
- 所有者一致時だけ解放

## 権限

- `SuperAdmin`: 全店閲覧、契約・全設定
- `StoreManager`: 担当店舗の設定・承認
- `Staff`: 台帳閲覧、手動予約、配席

現行管理画面の `owner/admin/staff` を入口の認証に使い、飲食店向け領域内では
専用メンバーシップの役割と店舗スコープを持つ。新サーバーではこの専用モデルを
認証基盤へ移す。

## 外部接続を有効にする前の条件

1. 検証用のLINE公式アカウント、Google OAuth、各予約媒体の検証資格情報を用意する。
2. Webhook署名、トークン暗号化、店舗スコープ、監査ログを確認する。
3. 読み取りだけで取得範囲と更新頻度を確認する。
4. 双方向更新は別の開発・承認・切り戻し計画として扱う。
5. 本番の然-NEN環境へは接続しない。
