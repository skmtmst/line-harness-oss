# Lステップ・Liny 実機調査 — V4 設計の一次資料

Lステップの管理画面を実際に操作して採取した仕様と、Liny の公開情報、現行実装との差分。
**V4 の画面仕様を決めるときの参照元**として使う。

- 調査日: 2026-08-22
- 対象: Lステップ `manager.linestep.net`（meauty渋谷店・スタートプラン）**実機操作 25画面**
- 操作範囲: 閲覧・設定画面の開閉・プルダウン展開のみ。**保存／配信登録／送信／テスト送信／削除は一切実行していない**
- 顧客の氏名・連絡先・トーク本文は本書に含めない
- 比較: Liny 公開資料（機能紹介ページ・第三者比較記事）
- 自社側: `apps/web` のルート100件・`src/lib/menu.ts`・`packages/db` 177マイグレーション・Pencil V4 設計86ノード

## 0. 実装判断のサマリ

| 指標 | 値 |
|---|---|
| Lステップ32機能のうち現行で実装済み | **30 / 32** |
| 残る中核ギャップ | **2**（変数挿入UI・フォームビルダー） |
| 両社に無い自社独自の機能領域 | **12** |
| サイドバー項目数 | 現行 **43**（9区分） ／ Lステップ **24**（6区分） |
| V4 設計が届いている現行画面 | **30 / 98** |

**機能はほぼ追いついている。残る2つは「作る手間を減らす仕掛け」で、
どちらも運用を現場に渡せるかどうかの分かれ目にあたる。**

**UI の課題のほうが深刻。** ただし原因は機能数ではなく構造にある。
Lステップは「アクション」という1つの部品を全画面から呼び出せる形にすることで、
機能を増やしながら24項目に収めている（§2-11）。

## 2. 実機採取した仕様

以下はすべて**画面から直接読み取った値**。V4 の画面仕様に落とすときの一次情報として使える。

### 2-1. 変数挿入UI（テンプレート編集・一斉配信・カルーセル共通）

本文入力欄の上にツールバーとして配置。

```
[↶] [↷] | [名前] [友だち情報▾] [共通情報▾] [回答フォーム▾] [配信日▾] [その他] [😀]
```

**4階層のカスケードメニュー:**

| 階層 | 内容 |
|---|---|
| 1 | カテゴリ（名前 / 友だち情報 / 共通情報 / 回答フォーム / 配信日 / その他） |
| 2 | **友だち情報欄のフォルダ**（例: 01_基本情報 / 02_健康・医療情報 / 03_お悩み・ご要望 / 04_生活習慣 / 未分類） |
| 3 | 項目（例: お名前（漢字）／お名前（フリガナ）／電話番号／生年月日） |
| 4 | **日付型のみ: 表示書式8種** |

**日付の表示書式 8種（そのまま実装対象）:**

```
月日と曜日                          M月D日(W)
年月日と曜日                        YYYY年M月D日(W)
月日                                M月D日
年月日                              YYYY年M月D日
月日と曜日（スラッシュ区切り）      M/D(W)
年月日と曜日（スラッシュ区切り）    YYYY/M/D(W)
月日（スラッシュ区切り）            M/D
年月日（スラッシュ区切り）          YYYY/M/D
```

**「その他」= カウントダウン変数（2種）:**

```
配信日から [目標日(date)] までの日数          → [+挿入]
配信日から [N(number)] 日後の日付（書式: ▾）  → [+挿入]
```

**カルーセル内の変数挿入は簡略版**（名前 / 友だち情報▾ / 共通情報▾ / 絵文字 のみ）。

> **現行の状況**: `friend_fields` `folders` `common_vars` はすべて存在する。
> **データは揃っていて、入口だけが無い。** 実装は UI 層のみ。

### 2-2. 友だち情報欄の型（7種）

`/line/var/new` の登録フォーム。

| 種別 | 画面の説明文（原文） |
|---|---|
| 標準 | 友だちの名前やメールアドレスなど、短いテキスト情報を登録できます |
| 長文 | 志望動機やプロフィール文など、長いテキスト情報を登録できます |
| 画像 | 友だちから送信された画像を登録できます |
| PDF | 履歴書や同意書など、PDFファイルを登録できます |
| 年月日 | 誕生日・最終来店日など、友だちごとに異なる日付を登録できます |
| 日時 | 来店日時など、時刻も含めた情報を登録できます |
| 選択肢 | 担当者や選考段階など、選択肢を作成して友だちに割り振れます |

その他のフィールド:

- **フォルダ名**（プルダウン）
- **種別**（ラジオ、**「※新規登録後は変更できません」**と明記）
- **既定値**（200字）— **「※友だち情報が空欄の場合に送信されます」**
- `[name]を使用` ボタン

> **既定値の意味**: 変数を差し込んだとき値が空の人には、この既定値が代わりに送信される。
> `{お名前}様` が「様」になる事故を、**テンプレート側ではなくデータ定義側で防いでいる**。
> 変数挿入UIとセットで実装しないと意味が出ない。

### 2-3. 条件ビルダー（15軸）

**同じビルダーが3箇所で使われる**: 友だちリストの詳細検索 / アクションの動作条件 / 一斉配信の配信先絞り込み。

**構造:**

```
「すべて満たす」必要がある条件 (and条件)
  [条件行] [条件行] ...
  絞り込む項目を更に追加できます → [15個のボタン]
+ 「いずれか1つ以上を満たす」必要がある条件(or条件)を追加
[カスタム検索からコピー]
```

**条件軸 15種:**

```
名前 / 個別メモ / ステータスメッセージ / 友だち登録日 / 対応マーク /
タグ / 友だち情報 / シナリオ / イベント予約 / カレンダー予約 /
共通情報 / リマインダ / 回答フォーム / 最終反応日 / その他
```

※呼び出し元で変わる。友だちリストの詳細検索は「共通情報」が無く **14軸**。

**軸ごとの演算子:**

| 軸 | 演算子・オプション |
|---|---|
| 名前 | テキスト（半角スペース区切りでOR）＋ 検索対象チェックボックス `LINE登録名` `本名` `システム表示名` |
| タグ | `いずれか1つ以上を含む` / `全て含む` / `1つ以上含む人を除外` / `全て含む人を除外`<br>＋ ☐`タグフォルダで指定` |
| 友だち情報 | `完全一致` `部分一致` `登録あり` `登録なし` `完全一致除外` `部分一致除外`<br>`以上(≧)` `より大きい(＞)` `以下(≦)` `より小さい(＜)` **（10種）** |

**友だちリストの詳細検索モーダルには、条件ビルダーに加えて2ブロック:**

```
友だちの絞り込み
  表示設定: ☑表示中 ☐非表示 ☐ブロックした人
  友だちの状態: [このアカウントをブロックしていない ▾]
並び替え・表示数
  表示順: [友だち追加の新しい順 ▾]   表示数: [50人ずつ ▾]
[決定する]
```

> **既存資料 A-3 の答え。** 想定では6軸だったが実物は15軸だった。

### 2-4. アクション（動作8種＋動作ごとの条件）

`/line/action` の「新しいアクション」モーダル。

```
保存するアクション名 [必須]        フォルダ [▾]
行う動作を選択してください
[テキスト送信][テンプレート送信][タグ操作][友だち情報操作]
[シナリオ操作][リマインダ操作][対応マーク・表示操作][イベント予約操作]
☑ 発動2回目以降も各動作を実行する
[この条件で決定する]
```

動作を追加すると、行として積まれる:

```
1. タグ操作                      [条件OFF] [↑] [↓] [🗑]
   タグ操作: ◉タグを追加 ○タグをはずす      ☐タグフォルダで指定
   タグ選択: [タグ名を入力 ▾]
   　　　　　「タグ名を入力することで新規追加・検索ができます」
```

**重要な仕様:**

- 動作は**何行でも積める**
- **各動作行に `条件` ボタン**があり、押すと §2-3 の15軸ビルダーが開く
  → **1つのアクション内で「条件Aを満たす人にはこの動作」を並べられる＝実質の分岐エンジン**
- **「発動2回目以降も各動作を実行する」** チェックで再発動時の挙動を決める
- タグ選択欄で**その場で新規タグを作れる**
- タグは**フォルダ単位でも指定できる**

**マニュアル記載は10種だが、実機（スタートプラン）では8種。**
`メニュー操作`（リッチメニュー切替）と `通知` が出ない。上位プランかオプションと思われる。

### 2-5. フォームビルダー（12ブロック）

`/line/form/:id`。

**画面構成:**

```
[フォーム名] [フォルダ▾] | デザイン[デザイン設定] オプション[オプション設定] | プレビュー [フォームを保存]
────────────────────────────────────────────────
                              [共通ヘッダ] [セクション1 ⊗] [＋]
  ライブプレビュー            ブロック設定  ↶ ↷ | 上に移動 下に移動 複製 削除 | [＋ブロックを追加▾]
  （スマホ幅）                ┌ 1 見出し ────────────┐
  ①②③④⑤ の番号バッジ       ├ 2 単一行入力 ────────┤
                              └ ...                     ┘
```

**選択中のブロックが左右で連動ハイライトされる。番号が両側に同じ数字で振られる。**

**ブロック種別 12種:**

| グループ | ブロック |
|---|---|
| 表示 | 画像 / 見出し / テキスト / ボタン |
| 入力 | 単一行 / 複数行 / ラジオボタン / チェックボックス / プルダウン / ファイル / 日付 / 都道府県 |

**入力ブロックの構造:**

```
タイプ[単一行▾]   タイトル[...]              ☐非表示
回答の登録先（複数可）
  [友だち情報] [本名] [システム表示名] [個別メモ]     ← トグルボタン群
  友だち情報欄: (お名前（漢字） ×) [友だち情報欄名を入力 ▾]
☐説明文 ☐初期値 ☐プレースホルダ ☐入力制限 ☑必須 ☐非表示
```

- オプションは**チェックボックス列**で、**チェックした人にだけ入力欄が開く**
- **日付ブロックには `リマインダを設定`** がある（回答日を起点にリマインダ起動）
- `見出し` ブロックには `タイプ[見出し1▾]`
- セクションはタブで追加（ページ分割）

**デザイン設定:**

```
[カスタマイズ] [テーマ]        簡単設定 ⇄ CSS設定（トグル）
テーマカラー: ●メイン ○サブ ○アクセント ○エラー ○テキスト    [🔀おまかせテーマ]
背景色 / 背景色（2色目）
背景画像: [なし]        透明度: ━━━━━ 100
フォント: [明朝体▾]
[閉じる] [保存する]     ※左のライブプレビューに即時反映
```

> **色を役割で5つに割り当てている**（メイン／サブ／アクセント／エラー／テキスト）。
> 利用者に色は選ばせるが、**役割の枠は運営側が決めている**ので破綻しない。
> そのままデザイントークンの設計として使える。

**オプション設定（6ブロック）:**

```
回答設定
  回答後アクション      [⚡アクション設定]   ← §2-4 のモーダルが開く
  サンクスページURL     [https://...]
                        [ありがとうございました…]
                        ※サンクスページURLを設定しない場合の文章を設定します
  2回目以降の回答       ☐ 前回の回答を復元する（初期値は無視されます）
                        ※別のフォームの回答や、回答した端末が異なる場合は復元できません
ページタイトル設定      ページタイトル名 [回答フォーム]
ボタン設定              送信ボタン文言[送信] / セクション移動ボタン文言[前へ][次へ]
                        ボタンスタイル[デフォルト▾] / 色
セクションヘッダ        表示スタイル[ページ番号▾]  ※複数セクション時に表示されます
確認ダイアログ          ☐ 使用する
回答期限                ☐ 使用する
1人1回に回答を制限      ☐ 使用する
```

### 2-7. 一斉配信の作成（番号付き5段）

```
1. 管理用タイトル      タイトル / フォルダ
2. 配信先設定          ○友だち全員に配信する
                       ○友だちを絞り込んで配信する → [絞り込み]（§2-3の15軸ビルダー）
                       ※ 配信対象を選択してください（赤字）
3. 配信日時設定        ◉登録後すぐに配信する  ○配信日時を指定する
4. 開封数の取得設定    ◉取得する  ○取得しない
                       「取得する」を選択するとメッセージを閲覧した友だち数を測定できます
5. 配信メッセージ設定  [テキスト][スタンプ][画像][質問][カルーセル][位置情報][紹介][音声][動画]
                       本文 + 変数挿入UI + ツール（PDFアップロード / URL読み込み）
                       約4,500文字を超えた場合は複数のメッセージに分割されます   0/22500
                       ☐このメッセージではURLを短縮しない
                       URLごとのクリック計測テーブル（サイト名 / 訪問時）
                       公式アイコンで送信（変更不可）

☐ テンプレートとして保存
[配信登録] [下書き保存] [テスト送信]
```

> **「4. 開封数の取得設定」の設計意図**: LINE の `customAggregationUnit` は**月1,000種類まで**。
> Lステップは**配信ごとにユーザーへ取捨選択させる**ことでこの上限を回避している。
> 技術制約を設定項目として素直に開いた例。

**一覧の列とフィルタ:**

```
[新しいフォルダ] [新規配信] [テンプレート配信]
☐配信予約中のみ  ☐非表示のみ   配信日 [📅]-[📅]  [🔍]
タイトル │ 配信日時 │ 配信条件 │ 内容 │ 開封数ⓘ（開封率）│ 配信数ⓘ
```

### 2-11. 「アクション」は全画面から呼び出せる1つの部品

今回の調査で最も重要な構造的発見。

タグ付与・シナリオ開始・情報欄の書き換え・リマインダ起動・対応マーク変更・イベント予約操作を
**「アクション」という1つの単位に束ね**、以下すべてから**同じモーダル**で呼び出せるようにしている。

| 呼び出し元 | 呼び出し方 |
|---|---|
| カルーセルのボタン | 挙動 = `アクション実行` → [⚡アクション設定] |
| 質問メッセージの選択肢 | 選択後の挙動（7種） |
| 回答フォームの送信完了 | オプション設定 → 回答後アクション → [⚡アクション設定] |
| 自動応答 | ルールに紐づくアクション |
| 友だち追加時設定 | ⚡その他のアクションを設定する |
| 友だち詳細 | アクションタブ → アクション実行 |
| 友だちリスト | 一括操作 |
| アクション管理 | マスタとして登録・スケジュール実行 |

**機能を横に増やすのではなく、1つの部品を全画面に埋め込む。**
これが「機能が多いのにサイドバーが24項目で済んでいる」構造上の理由。

## 4. Liny との差分

**両社に共通する弱点** — Liny は第三者記事に

Lステップも管理画面に教育コンテンツを4本常設している。
**機能で並んだうえで「教育しなくても使える」を実現できれば、それが最も明確な差別化になる。**

## 5. すでに超えている領域（V4 で落とさない）

| 領域 | 意味 |
|---|---|
| **メール統合インボックス** | 両社は LINE のみ。問い合わせ窓口の一本化は構造的な優位 |
| **外部連携（Webhook）標準** | Lステップは有料オプション |
| **複数人オペレーション標準** | Lステップはオペレーターが有料オプション。スタートプランはスタッフ1人 |
| 重複検出・名寄せ | 両社に無い。長期運用で必ず出る問題 |
| アカウントプール | 多店舗・多ブランド展開の基盤 |
| 運用状態（緊急停止） | 配信事故の被害を止める手段 |
| EC連携 | 顧客データが LINE 外から入る |
| ウェビナー / アフィリエイト / 写真審査 | 両社に無い |
| 飲食店向け9画面 | 業種特化の別プロダクト級 |
| 自己更新機能 | OSS配布を前提とした構造 |

**これらは同時に「サイドバーが43項目に膨らんだ原因」でもある。**

## 6. UI 原則（V4 設計の指針）

実機観察から導いた、そのまま設計ルールにできる型。

### 6-1. アクションを部品化し、全画面から呼べるようにする

**最優先。** §2-11 の通り、これが Lステップが24項目で収まっている構造上の理由。
**画面を増やさずに機能を増やす唯一の方法。**

### 6-2. 「作りに行く」を無くす

| Lステップの実装 | 解いている問題 |
|---|---|
| アクションのタグ選択欄でその場で新規タグを作れる | タグ管理画面への往復 |
| シナリオ編集のヘッダ4項目がインライン編集 | 設定変更のためのページ遷移 |
| カルーセルのボタンからアクション設定モーダル | 分岐を作るための画面移動 |
| 質問メッセージで2択＋挙動＋返信が1画面 | 簡単な分岐に大掛かりな設定が要る |
| 友だち詳細から情報欄マスタを新規作成 | 「この項目も要る」と気づいた瞬間の往復 |
| フォームのオプションに回答後アクション | フォーム完成後にアクション画面へ行く手間 |
| 情報欄フォルダを増やすとカルテのタブが増える | 項目追加のたびに画面を作り直す |

### 6-3. 一覧に「何が起きるか」を書く

§2-12 参照。**編集画面を開かずに設定を確認できる**状態を目指す。

### 6-4. オプションはチェックボックス列に畳む

`☐説明文 ☐初期値 ☐プレースホルダ ☐入力制限 ☑必須 ☐非表示` のように並べ、
**チェックした人にだけ入力欄が開く**。初期状態の情報量を抑えつつ、上級者の機能を消さない。

### 6-5. エディタとプレビューを番号で対応させる

フォームビルダーの左右に同じブロック番号を振り、選択中を連動ハイライト。
**説明文を一切書かずに関係を伝えている。**

### 6-6. 事故を仕組みで防ぐ

| 手法 | 防いでいる事故 |
|---|---|
| 既定値によるフォールバック | 「{お名前}様」が「様」になる |
| 未設定の明示警告（⚠アクションが未設定です） | 押しても何も起きないボタンを配る |
| 自社集計であることの明記 | 課金トラブル |
| 空状態をオンボーディング導線に | 使い始められない |

現行の**配信前チェック**（テスト送信・過剰配信・20人未満の集計制限）は
Lステップより一段進んでいる。この方向を維持する。

### 6-7. サイドバーの再設計

- 現行43項目 → 業種テンプレートによる初期表示の絞り込み（機能設定の仕組みは既にある）
- 「飲食店向け（テスト）」9項目を分離すればメニューが21%短くなる
- 括りを「機能の種類」から「誰と何をするか」へ寄せる
- 「成果と分析」「自動化」は日常的に開く場所ではない。設定と同階層に落とせる

### 6-8. 密度の基準

`friend-attributes-v3-static.module.css` が社内で唯一 V4 の見た目に到達した実装。
Tailwind の標準スケールでは表現できない値（`font-weight:750`、`border-radius:9px`、行高46px）を
実測値で持っている。**V4 画面では Tailwind クラスを使わず、`module.css` ＋ CSS変数で組む。**

Lステップの情報密度は現行より高い（1行に7つの操作ボタンを並べても破綻していない）。
**「シンプル＝要素を減らす」ではなく「シンプル＝迷わない」と定義する。**

## 7. 優先順位

### Tier 1 — 連鎖を繋ぐ（これだけで中核体験に並ぶ）

Lステップの強さは、次の5点が1本に繋がっていること。**現行に欠けているのは実質1箇所。**

```
① 友だち情報欄をフォルダ付きで定義        ← 現行：実装済み
② フォームの各ブロックに「登録先」を指定  ← 現行：登録先は実装済み／ビルダーが無い
③ 友だち詳細で情報欄フォルダがタブになる  ← 現行：要確認
④ 条件ビルダーが情報欄を15軸の1つとして扱う ← 現行：実装済み
⑤ テンプレートの変数挿入UIから差し込む    ← 現行：ここだけ無い
```

実装対象:

1. **テンプレートの変数挿入UI**（§2-1）
2. **友だち情報欄の「既定値」**（§2-2）
3. **ブロック型フォームビルダー**（§2-5）
4. **日付ブロックからのリマインダ起動**（§2-5）
5. **顧客カルテ（友だち詳細）**（§2-10）— 連鎖の出口。①〜④の投資がここで初めて画面として現れる

### Tier 2 — UI で差をつける

1. **アクションの部品化**（§6-1）
2. サイドバーの再設計（§6-7）
3. 「その場で作れる」の徹底（§6-2）
4. 一覧に「何が起きるか」を書く（§6-3）
5. オプションの畳み方（§6-4）
6. 空状態をオンボーディング導線に（§6-6）

### Tier 3 — 運用の穴を埋める（低コスト中心）

質問メッセージ / 友だち予約履歴URL / 送信後一時停止 / トーク内システムイベント /
配信ごとの開封取得ON-OFF / 送信者アイコン / CSVレポート書き出し

### Tier 4 — V4 の適用範囲を広げる

V4 設計は10機能群・30画面にしか届いていない。**残る68画面が未着手。**
ただし全部を描く必要はない。**Tier 1・2 で触る画面を優先して V4 化**する。
順序は連鎖に対応する「情報欄 → フォーム → 友だち詳細 → テンプレート」を1本の帯として設計する。
