# 反映履歴（アップデート履歴）の設計

状態: **決定済み・実装済み。**
対象バージョン: 0.23.0
書いた人: kenta

---

## 1. 何を作るのか

管理画面に「この画面に、いつ、何が反映されたか」を表示する。
運用側が「先週から予約の画面が変わったのは何だったのか」を自分で確認できる状態にする。

## 2. 既存の「アップデート履歴」との違い

**同じ名前の機能がすでにある。** これを潰さずに分ける、というのがこの設計で一番大事なところ。

| | 既存（041 `update_history` / `/updates`） | 新規（反映履歴） |
|---|---|---|
| 記録するもの | self-update の**実行**（v0.19→v0.20 を実行した、成功した、切り戻した） | **変更の中身**（何ができるようになったか） |
| 出どころ | 実行時にWorkerが書き込む | リポジトリに人が書く |
| 認証 | `x-admin-api-key`（スタッフ認証を通らない） | スタッフ認証 |
| 然の環境での中身 | **常に空**。self-update ではなく wrangler で配っているため | 実データが入る |
| 画面 | `/updates` | `/settings/changelog`（新規） |

**分離方法**: テーブルも経路も画面も共有しない。既存の `/updates`・`update_history`・`/admin/update/*` には一切触れない。
サイドバーの「アップデート履歴」の行き先だけを新画面に変え、既存画面へは
新画面の下部から「システム更新の実行記録」として控えめに導線を残す。

> 既存画面をそのまま残す理由: CLI で入れた環境（OSS利用者）では実データが入り、
> 切り戻し期限の表示という実用の役割がある。然で空だからといって消してよいものではない。

## 3. 記録方法 — 3案と選定

### 案A: リポジトリのファイルをビルド時に同梱（**採用**）

`docs/release-log/` に1リリース1ファイルの Markdown を置き、
ビルド時に JSON へ変換して管理画面に同梱する。

```
docs/release-log/
  0.21.0.md
  0.22.0.md
  0.23.0.md
```

```markdown
---
version: 0.23.0
released: 2026-08-20
---

## 追加
- タグに親分類を付けられるようにした（#32）
- 予約メニューに同時受付数と受付期限を追加（#33）

## 修正
- 予約の詳細画面で、入力済みの内容が表示されていなかった（#28）
```

- 利点: **マイグレーション不要**、実行時のネットワークアクセス不要、秘密情報不要。
  そして何より、**表示される履歴が、いま動いているコードの履歴と必ず一致する**
  （同じビルドに同梱されるため、ずれようがない）
- 欠点: 反映のたびに人が書く。書き忘れると空欄になる
- 書き忘れ対策: PRゲートに「`docs/release-log/` の未リリース欄に1行あるか」の確認を足す。
  ただし**最初は警告のみ**にする。いきなり必須にすると、緊急の修正が出せなくなる

### 案B: DBに記録し、CIから書き込む

- 欠点: 本番D1への書き込み資格情報をCIに持たせることになる。
  履歴を出すためだけに、**本番DBを書き換えられる鍵を1本増やす**のは割に合わない
- 欠点: 表示中の履歴と動いているコードがずれうる（デプロイ失敗時など）
- 却下

### 案C: 実行時に GitHub API を叩く

- 欠点: 管理画面がリポジトリの公開状況に依存する。private リポジトリではトークンが要る
- 欠点: 外部APIが落ちると画面が落ちる。レート制限もある
- 欠点: PRのタイトルは開発者向けの言葉であって、運用者に読ませる文ではない
- 却下

**結論: 案A。この場合マイグレーションは不要になる。**
当初 097 以降を割り当てる想定だったが、DBに持たない設計にしたため使わない。
（097 は friends の索引に使用済み。098 以降は空いたまま）

## 4. 記録タイミング

| 時点 | 誰が | 何を |
|---|---|---|
| PRを出すとき | 実装者 | `docs/release-log/unreleased.md` に、運用者に伝わる言葉で1行足す |
| リリースするとき | リリース担当 | `unreleased.md` を `<version>.md` に改名し、`released` に日付を入れ、空の `unreleased.md` を作り直す |

「PRを出すとき」にしたのは、**変更した本人が、変更した直後に書くのが一番正確**だから。
リリース時にまとめて書くと、後から差分を読んで推測することになり、内容が薄くなる。

`unreleased.md` は画面上「次回反映予定」として、リリース済みの履歴とは分けて表示する。

## 5. 表示項目

一覧（新しい順）:

| 項目 | 例 | 備考 |
|---|---|---|
| バージョン | 0.23.0 | |
| 反映日 | 2026-08-20 | `unreleased` は「次回反映予定」と表示 |
| 区分 | 追加 / 変更 / 修正 | 色は状態色を使う（追加=success、修正=warning） |
| 内容 | タグに親分類を付けられるようにした | **運用者の言葉で書く。テーブル名や関数名は書かない** |
| 参照 | #32 | 任意。あれば PR へのリンク |

いま動いているバージョンを画面上部に出し、そのバージョンより新しい行には
「未反映」の印を付ける。バージョンは既存の `/admin/version` から取る。

**書かないもの**: コミットハッシュ、ファイル名、内部の識別子。
運用者が読む画面であって、開発の記録ではない。

## 6. 権限

閲覧のみ。更新系のAPIは作らない（ファイルはリポジトリで管理するため）。

- 全役割が閲覧可（読み取り専用の人も含む）
- 「次回反映予定」はオーナー／管理者のみ。まだ出ていない機能を全員に見せる必要はない

## 7. 作るもの

| ファイル | 内容 |
|---|---|
| `docs/release-log/unreleased.md` ほか | 履歴の実体 |
| `apps/web/scripts/build-release-log.mjs` | Markdown → JSON。`prebuild` で走らせる |
| `apps/web/src/app/settings/changelog/page.tsx` | 画面 |
| `apps/web/src/components/layout/sidebar.tsx` | 行き先の変更（1行） |
| `.github/workflows/*` | 記載漏れの警告（必須にはしない） |

マイグレーション: **なし**
新規API: **なし**
既存ファイルへの変更: サイドバー1行のみ

## 8. 決定事項

1. 案A（リポジトリのファイルをビルド時に同梱）を採用する
2. 反映履歴のためのマイグレーションは使わない
3. 既存の `/updates` は、OSS利用者のシステム更新記録として残す
4. 「次回反映予定」はオーナー／管理者だけに表示する
5. 記載漏れのPRゲートは警告から始める
