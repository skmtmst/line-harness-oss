## 1. 目的・効く目標・ライバルとの差

- 目的：本部が予約メニュー（カット＋トリートメント 90 分 ¥8,800 など）とマイルの景品を 1 回作って全店へ配り、直したら配り直せる。店ごとの手作りと食い違いを無くす。
- 効く目標：① 引き継ぎ（本部の型が正本）・③ 作り込める（店は直してよい・直した所は守られる）・② 直感的（今のひな形と同じ作る→配る）。
- ライバルとの差：多店舗の予約ツール（STORES 予約・RESERVA の本部機能）はメニューの一括登録があるが、LINE の配信・マイルと一体ではない。Lステップ・エルメに本部の型は無い。musubo は今のテンプレートの配り方と同じ形で、予約・マイルまで配れる。

### 2-5. 状態と言葉

- ひな形：下書き（保存だけ）／配った（12 店）／一部できなかった（11/12）。
- 店の物：統括から／この店専用（統括から）／本部の新しい版があります。
- 配る前の確かめの失敗：「確かめに失敗しました」［もう一度確かめる］。確かめから 30 分で切れる（今の preflight の期限）「確かめの期限が切れました。もう一度確かめてください」。
- 言葉：「ひな形」「配る」「配り直す」「取り込む」「統括から」「この店専用」。使わない：「テンプレートを同期」「上書き」（店に見せる言葉として）。

## 3. データと API の形（案・Codex）

- 今の仕組み（`hq-templates` の registry に adapter を足す）を使い、新しい表は作らない見込み：
  - adapter `booking_menu`：配ると店に予約メニュー（今の表）を作る。予約メニューに `hq_template_id`・`hq_template_version_id`・`hq_customized`（店が直したか）の欄が無ければ足す（マイグレーション・小）。
  - adapter `mileage_reward`：配ると `mileage_rewards`（下書き）と版を作る。同じく `hq_template_id`・`hq_template_version_id`・`hq_customized`。
- 口（今ある口の種類を増やすだけ）：
  - `POST /api/hq/templates`（`kind: 'booking_menu' | 'mileage_reward'`）・`PUT /api/hq/templates/:id`。
  - 配る前の確かめ（今の preflight）の応答に店ごとの `warnings`：`same_name_exists`・`payment_downgraded_to_store`・`booking_not_used`・`reward_codes_required`。
  - 配る（今の distribution）・配り直し（Q-33：直していない店は上書き、直した店には知らせ）。
  - 店の側：`POST /api/booking/menus/:id/hq-adopt`・`POST /api/mileage/rewards/:id/hq-adopt`（［取り込む］）・`.../hq-dismiss`（［今のまま］・その版の知らせを消す）。
