# 24 LINE通知 操作と挙動（受け入れ）

要件の正本：[V6 24 LINE通知 要件定義](../../v6-requirements/v6-24-line-notification-requirements-draft.md)。共通の動き・権限は [共通基盤](../../v6-requirements/v6-shared-platform-requirements.md)（§3 権限、§6-2 再試行、§9 未取得の表示、§11 応答コード、§15 進み・トースト）と [30 ログインユーザー](../../v6-requirements/v6-30-login-users-requirements-draft.md) §7〜§8。EC の出来事の受け取りそのものは [23 EC連携 操作と挙動](./23-ec-integration.md)。

2026-10-16 B-333。画面は「LINE通知」（タブの順：顧客へのお知らせ／運用者へのお知らせ／送れなかったもの／記録）、「運用者へのお知らせを作る・なおす」、ヘッダーの「通知」（管理画面の中のお知らせ一覧）。

- 顧客へのお知らせ＝注文・発送・定期便などの取引のお知らせをお客さまの LINE へ。運用者へのお知らせ＝予約・フォーム・注文などをお店の人（スタッフ）の LINE・メール・管理画面へ。
- 本当の送信はしない前提。検証環境では、試しの LINE アカウントと試し受信者（スタッフ自身の LINE・試しの友だち）だけで確かめる。メールは検証用の送り先だけ。
- 「自動：単体」は Worker・DB の試験、「自動：画面」は画面の試験、「手」は検証環境で人が操作して見ること。
- LINE について「届きました」「開きました」は出さない。出してよいのは「送信処理中」「LINE API受付済み」「送信対象外」「再試行予定」「送れなかった」まで（要件 §4-4）。

## 連携とエラーが出そうな所

| 相手 | 何が起きうるか | 画面の出し方 | 復旧 |
|---|---|---|---|
| LINE Messaging API（お客さま・スタッフへの送信） | 429・5xx・時間切れ | 記録「再試行予定」、理由と次の再試行時刻 | 自動で送り直す（同じ再試行キー）。上限後は店長が「再試行」 |
| LINE Messaging API | 送った後の結果不明 | 「送信処理中」または「届いたか不明」 | 同じキーで確かめる。新しく送り直すのは理由つきの別操作（API のみ。食い違い参照） |
| LINE Messaging API | トークン切れ・未設定 | 「LINEの接続設定を確認してください」 | アカウント設定で直してから再試行 |

## 日々の操作の手順

毎日：
1. LINE通知 → 顧客へのお知らせ。数のカードで「今日送った」と「送信枠の残り」を見る。送信枠が月の残り日数に対して少なければ、一斉配信の予定を見直す。
2. 送れなかったもの を開き、宛先「顧客」で今日の分を見る。理由ごとに：
   - 一時的な失敗（再試行予定）→ 次の再試行時刻を過ぎても残っていれば店長が「再試行」。
   - 「LINEの友だちが見つかりません」「現在フォローしていません」→ 受信箱やメールなど別の手で連絡し、「対応済みにする」。
   - 「この通知は設定で停止されています」→ 止めたままでよいか確かめる。
3. 運用者へのお知らせの一覧で「受け取る人がいない」ルールが無いか見る（スタッフの退職・LINE の解除で0人になる）。
4. ヘッダーの「通知」で未読を片づける。

毎週：
1. 記録で、きっかけ別の受付済み・送信対象外・失敗の数を前の週と比べる。
2. 運用者へのお知らせの「同じ知らせを重ねない時間」が短すぎて同じ知らせが続いていないか見る。
3. お知らせの文面を直したときは、公開前にテスト送信で試し受信者の LINE を見る。

異常の気づき方：「今日送った」が注文があるのに 0／「再試行予定」が減らない／送信枠の残りが急に減る／運用者の知らせが同じ内容で何度も届く。

## 要件と今の作りの食い違い

コードを読んで確かめたものだけ。直していない。

1. 運用者へのお知らせの「送る時間（営業時間だけ・翌朝にまとめる）」「どれくらいたまったら（3件・10件）」「勤務中の人だけ」は保存されるが、送る処理は使っていない。画面は「営業時間外のものは翌朝 10:00 にまとめて送ります」と書くが、実際はその都度送る。送る処理が使うのは重ねない時間・重要度・送る手段だけ。根拠：`apps/web/src/v8/line-notifications/operator-edit.tsx:326-339`・`637`、`apps/worker/src/services/operator-notification-dispatch.ts:618-700`（`schedule`・`threshold`・`onlyAvailable` を読む所は Worker に無い）。
2. 公開中の運用者ルールを「下書きを保存」で直すと、同じ行が書き換わり、公開中の動きがすぐ変わる（新しい版を作って公開し直す形ではない。要件 §4-6「公開済みルールは版を固定」）。根拠：`apps/worker/src/routes/notifications.ts:655-660`、版は行の番号を使うだけ `apps/worker/src/services/operator-notification-dispatch.ts:127-130`。
3. 運用者ルールの「公開」に版の確認が無い（顧客へのお知らせの公開は版を確かめる）。根拠：`apps/worker/src/routes/notifications.ts:238-276`（本文は lineAccountId だけ）。
4. 「同じ知らせを重ねない」は、時刻を時間の幅で区切った枠で数える。例えば10分なら 10:09 と 10:11 の2件は別の枠になり、2回届く（「10分のあいだは1回だけ」とずれる）。根拠：`apps/worker/src/services/operator-notification-dispatch.ts:203-205`。
5. 送れなかったものの「再試行」が一時失敗で「5分後に再試行」になっても、顧客向けの記録を時刻で拾う定期の回収は無い（定期の回収は運用者向けだけ。EC の出来事のやり直しが残っている間だけ、そちら経由で送り直される）。根拠：`apps/worker/src/routes/line-notifications.ts:729`、`apps/worker/src/services/operator-notification-dispatch.ts:773`。
6. 「新しくもう一度送る」（理由つきの新規再送）の口はあるが、画面に入口が無い。記録の詳細にあるのは「再試行」と「対応済みにする」だけ。根拠：`apps/worker/src/routes/line-notifications.ts:831`、`apps/web/src/v8/settings/line-notifications/runs-tab.tsx:44`・`282-286`。
