# 07 リマインダ 操作と挙動（受け入れ）

要件の正本：[07 リマインダ](../../v6-requirements/v6-07-reminder-requirements-draft.md)・[共通基盤 §3・§6-2・§6-3・§11・§15](../../v6-requirements/v6-shared-platform-requirements.md)・[30 ログインユーザー §7〜§8](../../v6-requirements/v6-30-login-users-requirements-draft.md)。この文書は「操作したらどう動くか」を試験が書ける形にしたもの（2026-10-16 B-333）。食い違ったときは要件が勝つ。

前提の言葉：
- 「基準日」＝予約日時・イベント日時・友だち情報の日付など、案内を数える起点。
- 「通」＝1つのリマインダの中の1回分の案内（例：3日前の10:00、1時間前）。
- 時刻はすべて**日本時間**で決める。配信の見回りは 5 分ごと（cron `*/5 * * * *`）なので、予定の時刻から最大 5 分ほど遅れて届く。
- 友だち情報の日付からの登録は、日本時間の毎時 01 分に見回る。

## 連携とエラーが出そうな所

| 相手 | 何が起きうるか | 画面の出し方 | 復旧 |
|---|---|---|---|
| LINE Messaging API（push） | 時間切れ・5xx・429・トークン切れ（401）・月の送信上限 | 実行履歴に「再試行待ち」「失敗」と言葉の理由。秘密値や LINE の生の返事は出さない | 一時失敗は 1・5・30 分で最大 3 回。恒久失敗は手で再実行。トークン切れは LINE 連携の画面へ |
| LINE の再試行キー | 送ったかどうか分からないまま期限が切れる | 「要確認」 | 自動で送らない。人が LINE で届いたか見て手で送る |
| cron（5 分ごと） | 見回りが遅れる・止まる・2 本重なる | 次回予定より遅れて届く。運用状態の画面の見回り時刻 | 貸出期限（5 分）で他の回が拾い直す。重なりは一意制約で 1 本だけ送る |
| cron（毎時 01 分・友だち情報） | 1 回に見る人数に上限（4,000 行）。超えると次の時間へ持ち越し | 登録が数時間遅れる | 続きから読む（カーソル）。「3 日前」の通は基準日の 3 日以上前に登録されないと間に合わない |
| D1 | 書込の失敗・競合 | 保存の失敗の帯／409 | 読み直してやり直す。送る前に登録の状態と基準日を読み直す |
| 予約・イベント・Meet 相談 | 日時の変更・取消が送信とほぼ同時 | 実行履歴に「取消」 | 送る直前に予約の版・日時・本人を照らす。古い版は送らない |
| 課金・機能オフ・緊急停止 | 送れない期間がある | 一覧・実行結果に止めている理由 | 緊急停止・課金は解除後に続きから届く。アカウント停止中に過ぎた通は送らない |

## 日々の操作の手順

毎日：
1. 一覧の上の数を見る：「24 時間以内の予定」「要対応の失敗」。失敗が 0 でなければ実行履歴を開く。
2. 実行履歴を「失敗」「要確認」で絞る。理由を読む：
   - ブロック・友だち解除 → 何もしない（正常）。
   - トークン切れ・権限 → LINE 連携を直してから［再実行］。
   - 要確認（結果不明）→ 受信箱でその人のトークを見て、届いていなければ手で送る。
3. 今日・明日に予約・イベントがある人が「登録者と予定」に入っているか、数で照らす（予約の件数と登録中の件数）。
4. 予約の取消・日時変更があった人の予定が止まった・動いたかを見る。

毎週：
1. 「次回予定」が空のまま「登録中」の人がいないか見る（基準日が過去・日付不正）。
2. 友だち情報（誕生日など）が空・不正の人の数を見る（対象外の理由）。
3. 使っていない下書き・停止中のリマインダを片づける。

異常の気づき方：
- 「24 時間以内の予定」があるのに直近成功が増えない → 見回り（cron）・緊急停止・課金停止を疑う。
- 同じ人に同じ案内が 2 通届いたという問い合わせ → 実行履歴の LINE 要求 ID を見て、2 行あるか確かめる（あれば不具合として報告）。
