## 連携とエラーが出そうな所

| 相手 | 何が起きうるか | 画面の出し方 | 復旧 |
|---|---|---|---|
| LINE Webhook | 署名が合わない | 何も起きない（200 を返して捨てる） | チャネルシークレットを見直す。運用状態の「Webhook が届いていない」警告で気づく |
| LINE Webhook | 同じイベントの再送・遅延・順番の入れ替わり | 実行結果は1行 | 2回目以降は捨てる。古い follow は後から来ても無視 |
| LINE Webhook | 同じ友だちの follow が同時に2つ | 片方は「抑止（重複）」 | 予約を持つ側だけが送る |
| LINE Messaging API | 応答トークンの期限切れ・使用済み（4xx） | 1通目は「送れなかった」 | 定期の配信処理がプッシュで送る |
| LINE Messaging API | 時間切れ・429・5xx | 「送達不明」・要対応 | 友だちのトークで確かめ、人が判断 |
| LINE プロフィール取得 | 失敗 | 名前が空のまま | 友だち登録は続ける。後で取り直し |
| 流入リンク（18） | リンクが削除・停止 | 設定に「削除済みリンク」 | 受け皿が動く。設定を直す |
| 流入の確定（OAuth と follow の競争） | follow が先に届いて経路がまだ無い | 経路不明 | 約1秒待って取り直す。それでも無ければ受け皿 |
| シナリオ（05） | 選んだシナリオが停止・未公開 | 最終確認で警告 | シナリオを公開・再開してから有効にする |
| D1 | 台帳・予約が書けない | 送らない・失敗を記録 | 次の follow から通常に戻る。届かなかった人は手で送る |

## 日々の操作の手順

1. 毎朝、一覧の数の帯（今日の友だち追加・経路が取れた人数・経路が分からなかった人・失敗）を見る。経路不明が急に増えたら、流入リンクではなく素の QR が配られていないかを疑う。
2. 実行結果を「要対応」で絞り、一部失敗は原因を見て「失敗した処理をもう一度」。送達不明はトークで届いたかを見る。
3. 新しい流入リンクを作ったら、その日のうちに設定を作り、テスト→試しアカウントで実際に追加して実行結果に1行出るかを確かめる。
4. 毎週、同じ流入リンクを複数の設定が持っていないか（最終確認の競合表示）と、優先順位を見直す。
5. キャンペーンが終わったら設定を止める（受け皿が代わりに動くことを確かめる）。

### 仕様が無い
> 2026-10-16 オーナー「おすすめで」（B-337）で下の項目は全部決まった。各行の → が決定。問いは design/v8/review/SPEC-QUESTIONS-1016.md。

- 受け皿を止めるときの「代替先」に何を選べるか（別の設定・何も送らない など）。 → 決定 B-337 Q-69：「別の設定」か「何も送らない」から選ぶ。
- 送達不明（1通目が届いたか分からない）を、人が確かめたあとにどう送り直すか（実行結果からの再送の口が要るか）。 → 決定 B-337 Q-46：人が確かめて［この 1 通を送り直す］で送り直す。
- 再追加でシナリオが既に読み終わっていた（完了）ときの「前回配信した次から」の扱い（送る先が無いので何もしないのか、最初から流すのか）。 → 決定 B-337 Q-46：何もしない。
- 同じ友だちが短時間に追加・ブロックを繰り返したとき、何回目まで案内を送るか（再送制限の既定値）。 → 決定 B-337 Q-46：24 時間に 1 回まで。
