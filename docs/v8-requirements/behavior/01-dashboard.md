# 01 ダッシュボード 操作と挙動（受け入れ）

要件：[V6 1 ダッシュボード 要件定義](../../v6-requirements/v6-01-dashboard-requirements-draft.md)（動きの正本）。共通の動き・権限は [共通基盤](../../v6-requirements/v6-shared-platform-requirements.md)（§3 権限・§6-2 再試行の既定・§9 未取得の表示・§11 応答コード・§15 進み・トースト）、権限の正本は [30 ログインとユーザー](../../v6-requirements/v6-30-login-users-requirements-draft.md) §7〜§8。見た目は ★V8 の板（WQmep・編集 mcOqK）と [V8 の決まり](../../v8-design-rules.md)。

作成：2026-10-16（B-333）。業種別のダッシュボード（B-294・B-304・B-305・B-309・B-313・B-318）は、今の作りに無い物は §4・§5 に分けて書いた。

前提の言葉：

- 「運用者」＝管理画面を使う人（オーナー・管理者・スタッフ）。「閲覧のみ」＝読み取り専用の人（変える操作が無い人）。
- 「未取得」＝取れなかった数（`—` と「未取得／取得失敗／未接続」）。「0件」＝数えて 0 だった数。この 2 つを混ぜないのが一番大事な決まり（要件 §0-1）。
- 検証環境での確かめは、点検専用のアカウントと壊してよい見本のデータ（B-292 の 3）で行う。本当の配信・決済はしない。

## 日々の操作の手順

毎朝（始業時、5 分）：

1. ホームを開き、板の頭の「動きの状態」が「正常に動いています」かを見る。「確かめることがあります」「止まっているところがあります」なら運用アラート→運用状態へ。
2. 数の帯「対応が必要な受信」の件数と「最長 ◯ 前」を見る。最長が半日を超えていたら最初に受信箱を開く。
3. 「今日の予約」の件数と「次の予定」を見て、予約の一覧（日の表示）で今日の流れを確かめる。
4. 写真審査・出荷予定がある店は、件数が 0 でなければ押して片づける。
5. 「今月の送信枠」の残りを見る。残り 10% 以下（赤）なら、大きな一斉配信を止めるか枠を足す相談をする。

昼・夕方：

6. 受信一覧の段は 30 秒ごとに読み直されるので、開きっぱなしでよい。「最新の状態に更新できませんでした」が続いたら接続を疑う。
7. 「最近の動き」に配信の失敗が出ていれば、行を押して配信結果へ。

毎週（月曜）：

8. 期間を「過去7日」にして、友だち数の推移（前日比・ブロック）・流入経路TOP3・最近の成果を見る。ブロックが急に増えた日は、その日の配信を確かめる。
9. ファネル要注意・オートメーション失敗が 1 以上なら分析・実行状況へ。

異常の気づき方：

- 数が `—`（未取得）なのに 0 と勘違いしない。`—` は「取れなかった」。0件は「本当に無い」。
- 「更新 HH:MM」が古いまま進まないとき・2 つのカードの時刻が大きくずれているときは、数をうのみにしない。
- 推移の表に「推定」が多いときは、日ごとの記録（cron）が止まっていないかを運用状態で見る。
