# 27 予約管理 操作と挙動（受け入れ）

要件の正本：[27 予約管理](../../v6-requirements/v6-27-booking-management-requirements-draft.md)・[v8-booking-additions.md](../v8-booking-additions.md) §1・[飲食の融合1](../restaurant-fusion-contract.md)（予約盤）・[共通基盤 §6-2](../../v6-requirements/v6-shared-platform-requirements.md)。この文書は「操作したらどう動くか」を試験が書ける形にしたもの（2026-10-16 B-333）。食い違ったときは要件が勝つ。

- 前提の言葉：「運用者」＝ログインした店の人。「閲覧のみ」＝予約の権限が見るだけの人。「統括」＝本部の画面から店を選んで開いた人。「代理ログイン」＝運営が店の画面に入っている状態。
- 本当の LINE 送信・Google への書き込みはしない。検証環境は送信止めの LINE チャネルと試験用カレンダーで確かめる。検証環境には cron が無い（`wrangler.staging.toml` に triggers が無い）ので、時刻で動く物は手元の workerd の試験で確かめる。

## 日々の操作の手順

- 朝：予約管理の「日」の今日→数の帯の未承認・要対応・同期失敗を 0 にする（承認・断る、同期失敗は［もう一度］）。
- 来店のたびに：盤の予約に［✓ 来店］。開始から 15 分過ぎて印が無い予約は要対応に上がる。
- 電話が来たら：［電話の予約を入れる］→確認→完了画面で送る物の予定を確かめる。
- 夕方：明日の予約を「日」で確認。リマインダの予定時刻が入っているかを詳細で見る。
- 週に 1 回：「週」で稼働率・空き・休みを見て、勤務表・休みを予約設定で直す。
- 異常の気づき方：同期失敗が 0 にならない（Google の共有切れ）、リマインダの失敗が増える（LINE のトークン・ブロック）、要対応が溜まる（来店の印の付け忘れ）。

## 要件と今の作りの食い違い

コードは `~/lh-work/lh-claude-f`（2026-10-16 時点）。直していない。

1. **指名なしの自動割り当てが先頭の担当に偏る**：`apps/worker/src/routes/booking.ts:696-710` は空いている担当の一覧の先頭を選ぶだけ。B-306 の均等・優先順・ランダムは API 組3 の枝（未取り込み）にある。
2. **リマインダの再試行が共通基盤と違う**：`apps/worker/src/features/booking/booking-reminders.ts:229` と `REMINDER_MAX_RETRY = 3`（`event-booking-types.ts:107`）で初回を含め 3 回・間隔は 5 分ごとの cron 任せ。§6-2 は 1・5・30 分の最大 3 回（初回を含め 4 回）、429 は Retry-After 優先。
3. **ブロック中・友だち解除を区別しない**：同ファイル `:95-103` は友だちのフォロー状態を見ずに送り、失敗として数える。27 §7「ブロック中、友だち解除、送信先なしを区別する」と違う。
4. **競合の候補はある**：管理の代理予約は 409 に候補を返す（`booking.ts:4690-4697`）。LIFF の申込は 422 `slot_not_available` で候補なし（`booking.ts:857`）。LIFF に候補を返すかは要件に書いていない（仕様が無い）。 → 決定 B-337 Q-56

仕様が無い：LIFF の申込で枠が埋まっていたときに候補を返すか。検証環境で cron の動き（リマインダ・キャンセル待ち）を手で確かめる方法（検証の Worker に cron が無く、手で動かす口も無い）。 → 決定 B-337 Q-56：LIFF で満席なら近い空きを 3 つ返す。 → 決定 B-337 Q-75：検証環境だけに「今すぐ動かす」口を作る（本番には無い）。
