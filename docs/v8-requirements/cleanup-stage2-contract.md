## 2. 店舗の機能設定と署名の契約（B-358・A02・A03）

### 2-1. はじめの質問と店舗の切り替え

予約・クーポンを使うかの正本は **店舗ごとの `rt_store_feature_flags`（683）**。`account_styles.answers_json`（649）は最初の値を決める回答であり、二つ目の稼働設定にしない。

| はじめの質問のキー | 店舗の feature | 初期化する回答 |
|---|---|---|
| `booking` | `reservation` | `mode=configured` の boolean の `value`（true→1、false→0） |
| `coupons` | `coupon` | 同上 |

- 回答を保存した時、所属を確かめた同じ LINE アカウントの対象店舗へ、まだ設定のない項目の初期値を**1回だけ**書く。対象店舗が確定できなければ、別店舗や全店舗へ推測で広げない。`manual`・`later`・未回答をオンとみなさず、後で明示回答できる状態を保つ。ほかの回答や delivery 系の flag は写さない。
- 店舗が先に設定した値はオフも含めて優先する。再保存・スタイル変更・初期セットの配り直しで上書きしない。店舗が後からできる場合も保存済みの明示回答を初期値にできるが、既存の店舗設定を優先する。
- 同時保存でも初期化は1回。回答保存の版確認と初期化の完了を整合させ、途中失敗を完了扱いにしない。店舗側の変更と競合したら店舗側が勝ち、ほかの店舗・アカウントへ広げない。初期化したかを現在のオン・オフだけで推測しない。
- API・自動処理は実行直前にも現在の店舗設定、権限、停止を検査する。質問の回答やキャッシュで上書きしない。予約の承認方法・支払い方法など、既存の版付き設定はこの2項目の初期化とは分けて守る。
- 受け入れ：初回 true/false、未回答・manual・later、同時保存、再保存、店舗の先行設定、後から店舗作成、別店舗・別アカウントを確認し、2回目の上書きがないこと。

### 2-2. x-nen の署名

## 3. 再試行の契約（B-365①・A06）

回数と期間の正本は [共通基盤 §6-2](../v6-requirements/v6-shared-platform-requirements.md#6-2-execution)。外部 API は **1分・5分・30分の最大3回の再試行（初回込み4回）**、送信 Webhook だけ最大8回・24時間。B-365 の共通化を理由に上限を増やさない。機能別の要件で決定済みの、もっと厳しい回数・期限・結果不明時の停止は維持する。コードだけの差を新しい仕様の例外にせず、差を記録して担当へ渡す。

- LINE・Stripe・Google・Slack などの外部呼出しを、timeout、指数バックオフ、`Retry-After`、サーキットブレーカーを持つ一つの共通方針へ通す。外部ごとの認証・応答の解釈は adapter が担う。外部をまたぐ業務の進行は §5 が担う。
- 指数待ちを導入しても既存の業務ジョブの1分・5分・30分の予定を黙って変えない。**既存の固定した待ち列は互換の待機ポリシーとして渡し、指数待ちを使う経路も同じ実行器と予算を使う**。全経路の待ちを一律の等比数列へ変更する意味ではない。送信 Webhook は既存の指数待ち＋jitter を保つ。通信層・SDK・業務ジョブで別々に再試行を掛けず、実際の外部要求を一つの回数・期限の予算で数える。長い待ちは `next retry` として記録し、Worker の sleep で占有しない。
- 429 は `Retry-After` より早く再送しない。既存の1回の待機上限に収まらない時は期限を記録して次回へ送り、全体の回数・期限を超えたら要対応。短く切って即再送しない。
- 入力不備・認証/権限の失敗・宛先なしは自動再試行しない。5xx・時間切れ・切断も、副作用を起こす操作はまず §4 で分類する。HTTP の番号だけで再送を決めない。
- 再試行は同じ業務の冪等キー・対象・本文 snapshot を使う。成功済みの操作を再実行せず、認証情報や送信者を替えて別の操作にしない。既存の安全な照合や認証の更新は adapter の契約に従う。
- 障害で遮断（open）した範囲への外部要求は0回。店舗・接続先の境界を守り、別の店の障害で混線しない。再開を試す半開（half-open）は同じ遮断範囲で同時1回、失敗なら再遮断、成功なら段階的に再開する。待機の理由・次回・回数を残す。
- 自動再開で停止スイッチ、同意、ブロック、版、送信上限、静かな時間、遅れの上限を飛ばさない（共通基盤 §6-3）。認証の失敗を自動復旧とみなさない。
- 受け入れ：429/5xx/時間切れ/切断、`Retry-After`、遮断中0回、半開の同時1回、認証失敗の再送0、同じ冪等キー、予算の二重消費・増加0、秘密ログ0。時計と外部応答は模擬にする。

予約リマインダの「初回込み3回・5分cronごと」という実装の差は [外部失敗の食い違い2](behavior/integration-failures.md#3-要件と今の作りの食い違い) に残す。共通の既定を3回へ弱めず、既存のコードの上限もこの整理だけで4回へ増やさない。A07 はこの差の解消が要る箇所を司令塔へ返し、上限の判断と分けて既存予算内の共通化・不明時の停止を進める。

## 4. 結果不明の契約（A06・A07）

| 分類 | 判断 | 次の動作 |
|---|---|---|
| 成功確認済み | 受理・支払い等を外部の参照 ID や検証済み通知で確認 | 結果を記録して次の段へ。同じ段を再実行しない |
| 未実行/失敗確認済み | 副作用が起きていないことを確認できる | 一時失敗だけ §3 の予算内で再試行。恒久失敗は要対応 |
| 結果不明 | 要求後に時間切れ・切断、または外部成功後に結果保存が失敗 | 新しい要求を自動で出さず、外部 ID・同じ冪等キー・通知の台帳で照合する |

- 結果不明を通常の「失敗」や「成功」に読み替えない。既存の状態名を利用する場合も不明の理由を保存し、通常の再試行の対象から外す。画面は成功表示や即時の［もう一度送る］で二重操作を誘わない。表示語の正本は [terms](terms.md)。
- 同じキーでの照合に外部への再要求が必要な方式は、provider が同一操作の重複を防げる有効期間内で、当該機能が許す場合だけ行う。**結果不明を自動再送しないと定めた機能は、その停止を優先**する。保証期間を過ぎた物・照合できない物は要対応で止める。
- 再起動・lease の期限切れ・手動再試行でも「送信を始めた」印は消さない。新しいキーや新しい job を作って不明の操作を再送しない。人が新規の送信を選ぶ別操作には理由・確認・権限・監査が必要。
- LINE の同じ retry key が受理済みであることを示す応答は、provider の根拠を確認して扱う。一般の 409 は成功ではない。署名付きの決済通知も、所属・金額・通貨・試験モード・外部 ID を照合する。
- 受け入れ：外部受理の直後の切断、結果保存の直前/直後の停止、lease 再取得、二重通知、キーの保証期限切れを模擬し、二度課金・二度返金・二重予約・二重通知を起こさない。不明の記録と要対応が残ること。

## 5. サガの契約：予約・支払い・通知（B-365②・A07）

外部サービスと D1 は一つの transaction にはならない。サガ（外部をまたぐ処理を段ごとに記録し、再開・補償できる手順）は **記録 → 実行 → 結果で更新** にそろえる。

1. 予約・申込の正本、版、所属、金額/通貨、期限、冪等キー、入力 snapshot と各段の実行予定を、外部を呼ぶ前に永続化する。既存の台帳・outbox を使い、過去の履歴を消さない。
2. 条件付き更新（CAS）と lease で実行者を一つにし、現在の権限・店舗設定・停止を再検査して、未完了の段だけ実行する。成功済み・結果不明の段を取り直して再実行しない。
3. 外部の参照 ID と各段の結果を記録し、次の段へ進める。外部成功後に D1 が失敗したら §4 で照合する。補償（返金・枠/券の復元など）も元操作に結び付く一意な記録→実行→結果で更新とし、補償自体の失敗・不明も回収できるようにする。
4. 通知・カレンダーの失敗だけで正本の予約や確認済み入金を消さない。予約には同期失敗・未完了/要対応を見せる。お金や枠が片側だけ動いた処理を完了にせず、補償または照合・再開が終わるまで追えるようにする。

- 返金・券を戻す条件は [予約の追加 §5](v8-booking-additions.md#5-決定-b-3372026-10-16-オーナーおすすめで)（B-337 Q-19〜Q-22）のまま。取り置き後の入金は、枠が空いていれば復元、埋まっていれば全額返金。予約の取り消し・期限切れ・遅着・二重通知でも回数や金額を二重に動かさない。
- Google カレンダーが読めない担当の枠は閉じる。書き込み失敗は予約を保持して同期の回収対象にする。B8 の入口は作らない。
- Google Meet の個別相談の確定・変更はカレンダーだけで終えず、`POST /api/meet-consultations` に event ID・LINE friend ID・日時・Meet URL を登録し、前日・1時間前の LINE をセットにする。キャンセルは `DELETE /api/meet-consultations/:externalEventId` も実行し、古い日時の通知を送らない。
- 自動通知に `X-Line-Harness-Source: manual` を付けない。担当者の1対1返信には付ける。模擬の支払い・返金・通知は実際の成功と分け、本番の送信・課金を有効化しない。
- 受け入れ：予約/決済/カレンダー/LINE の各境界の停止→再開、並行 CAS、重複/遅着通知、補償の失敗→再開、履歴保持と所属・権限を試す。必要な表・列が既存にない場合は新 migration を作らず、表・列・未使用番号案・理由を司令塔へ返して該当部分を止める。

## 6. cache の契約（B-365③・A10）

- 対象は dashboard・style-analytics・style-schedule・store-comparison の重い**表示用の読み取り集計**。既存の日次集計を再利用し、正本の業務データをキャッシュへ移さない。
- 認証と現在の所属・権限の確認を先に行う。キーは少なくとも LINE アカウント/店舗、統括の閲覧可能店舗の集合、権限/マスク・担当の範囲、スタイル、期間・timezone、絞り込み、集計の版を区別する。別店舗・権限・時刻帯・期間の値が混じらないようにする。
- 有効期間（TTL）は短い期限付きにする。A10 は対象ごとの TTL と失効条件を実装差分に示し、既存の鮮度の条件（共通基盤 §9、01 §6-2）を延ばさない。キャッシュを読んだ時刻で元データの `as_of` を更新せず、古い・一部・未取得を区別する。
- 予約/支払い/出欠/集計/設定など、値に影響する更新では対象を失効させるか版を変え、更新前に始めた集計が後で戻って古い値を再登録しないようにする。店舗設定・権限の変更後は古い許可やデータを使わない。
- 予約の空きの確定、課金・返金、送信の対象と同意、権限、機能のオン・オフ、停止の判断には使わない。盤の表示がキャッシュでも、予約確定の直前は正本と外部カレンダーを再検査する。
- 取得失敗や未設定を0として保存しない。期限切れを無期限に延ばさず、最後に取れた値を出す場合も古い時点・状態を明示する。cold/warm で応答の意味・表示の権限を変えない。
- 受け入れ：cold/warm、失効、期限切れ、同時更新/古い集計の戻り、2店舗、権限縮小、timezone の境目、未取得を試す。同じ入力・同じデータで SQL 数と待ち時間を比較し、機能や安全の省略で速くしない。
