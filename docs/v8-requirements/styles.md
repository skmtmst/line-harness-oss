# 6つのスタイルの要件

2026-10-18、B-391。対象は `standard`・`ec`・`restaurant`・`salon`・`consult`・`lesson`。本書は「使える状態」の受け入れ条件であり、実装済み・公開済みの宣言ではない。不足と接続先の実装状況は [styles-gaps.md](styles-gaps.md) に分ける。

## 1. 正本と適用範囲

- B-391 により、整理の段2で6つとも登録から日々の操作までつなぐ。B-381 の「初めは飲食に絞る」は販売の方針として残り、他スタイルを未実装のままにする理由にしない。
- 言葉は [terms.md](terms.md) §5・§6、既存のスタイル・お金の動きは [style-and-money](behavior/style-and-money.md)、予約の条件は [予約の追加](v8-booking-additions.md) が正本。本書は6業種の組み合わせと入口を具体化する。食い違いは要件を先に直す（B-337）。
- [段2の共通契約](cleanup-stage2-contract.md) の権限・別店・送信停止・結果不明・サガ・cacheを引き継ぐ。B8「Google で予約」と提供側の会話AIは、準備中の表示も含め入口なし。Google カレンダーと手で設定する会議URLは別機能として残す。
- [B2 回数券・月謝](gap-features/B2-tickets-monthly.md)、[B3 振替](gap-features/B3-makeup-lesson.md)、[B7 面談・カレンダー](gap-features/B7-online-meeting-calendar.md)、[G6 EC自動LINE](gap-features/G6-ec-auto-line.md) の既存画面と口を再利用する。実装のない機能を新しい同名画面で代用しない。
- 飲食店の登録手順・席予約・台帳・媒体連携・初期セット・文面・店舗設定を変更しない。本書の飲食節は現在の契約を保つための条件。飲食の不具合や別束の未完了をT00で直したことにしない。
- 実決済・実返金・カードの継続課金、会議の自動発行、Outlook等の未提供の外部連携はB-381どおり「準備中」。既存の試験操作は本当の請求・送信と区別する。G6は現行の模擬設定・確認をつなぎ、実送信を開始しない。
- 管理画面の形は [V8の決まり](../v8-design-rules.md) と [V8の置き場](../../apps/web/src/v8/README.md) に従う。実装時は共通の型・部品を使い、1152・1440で操作・全状態とはみ出しを確かめる。LIFFは375も含む。本書の文書変更だけを画面の合格に数えない。

## 2. 全スタイルに共通する始め方

### 2-1. 登録から保存まで

1. LINEアカウントの登録で6つを同じように選べる。表示名はTM-V01の「標準／EC／飲食店／サロン／面談・相談／教室・レッスン」。保存する値は上記の正式キーだけ。面談を `meeting` として保存しない。
2. LINEの接続・本人の所属・権限を確かめてアカウントを作り、選んだスタイルを同じアカウントの設定へ保存する。はじめの質問で選び直させず、保存したスタイルを初期選択にする。飲食を選んだ時だけ既存の店舗追加へ進む。
3. アカウント作成とスタイル保存が別操作なら、後半の失敗を「登録完了」にしない。作成済みのアカウントを表示し、同じアカウントで［もう一度保存する］へ。二重に登録せず、勝手に標準や飲食へ戻さない。作成済みアカウントを消す補償もしない。
4. 設定の読み込みに失敗したら「読み込めませんでした」と［もう一度読み込む］。未取得を未設定・標準・0件とみなして初期化しない。
5. スタイルと見た目の次に、各節の質問を1問ずつ出す。すべてに「あとで設定する」「手動で設定する」と、後から変える実在の場所を示す。質問の順序は各節の順。質問は設定の説明であり、答えただけで送信や課金を始めない。
6. オーナー・管理者だけが保存・初期セットの有効化をできる。スタッフ・閲覧のみには操作を隠し、APIも元の権限で拒否する。代理ログインで送信やお金の制限を外さない。

### 2-2. 初期セットと完了条件

- 既存の初期セット定義・最後の一覧・リッチメニューの見本は同じ定義から出す。「見本だけ6ボタン、保存した物は別の3ボタン」を許さない。6ボタンは見本の最大であり、未設定の機能を埋めるために増やさない。
- テンプレートは「【見本】」を付けた下書き、リッチメニューは未公開、予約メニューは停止、自動処理・リマインダは停止で入れる。予約確定の通知は既存の1通だけ。初期セットに2本目の予約確定の自動送信を入れない（B-335）。
- `content=false` なら文面・リッチメニューの見本を入れない。`later`・`manual` は未完成の自動処理を作らず、設定先を残す。「使わない」と答えた任意機能は未完了としていつまでも残さない。
- 再保存・スタイル変更でも同じ見本を二重に入れず、店が編集した物を上書きしない。予約・友だち・回答・券・支払い・送信履歴を消さない。
- B-358の飲食の `booking → reservation`・`coupons → coupon` は初期化1回だけ。店舗が後から変えた値（オフも含む）が正本。ほかのスタイルの表示設定で飲食の店舗flagを上書きしない。
- 予約の承認方法など既存設定を変える回答は、変えた項目と影響を確認してから版付きで保存。古い版は409、入力を残して読み直せる。初期化やスタイル変更を競合回避に使わない。
- ［まとめて動かす］は既存の対象項目と権限の範囲だけ。項目別の成功・失敗を表示し、リッチメニューの公開・G6の有効化・カレンダー同期・実課金を一緒に始めない。
- はじめにやることの完了は、LINE接続・選んだ質問の保存・使う機能の実設定・必要な見本の確認で判定。1人で使う契約はログインユーザーの招待を必須にしない。最初の1通と［テストを送る］は同じ完了条件にし、模擬結果を実送信完了にしない（SELL-04・12・13）。

### 2-3. 読み取り・数字・言葉

- 取れない数字は「—」、取得済みの0は0。分母不足と未設定・取得失敗を分け、集計時点と式を示す。予約の数は来店日・面談日・クラスの日、新しく入った件数は「新着予約」。
- 数の帯・一覧・分析・CSVは同じ期間・担当・対象と式を使う。権限のない金額や人は数からも除く。金額の未取得を0円にしない。
- 管理画面・LIFF・送るLINEは、サーバーで所属を確かめた同じスタイルを使う。URLの任意の `style`、文面の名前、端末に残った前の店の値から業種を推測しない。別アカウントへ切り替えた直後に前の言葉・URL・数を表示しない。
- LIFFの公開情報に正式スタイルが無ければ、既存の本人向け読み取りへ最小のスタイル情報を追加する（T01）。秘密値・管理者の回答・店舗内部のflagを一緒に公開しない。未取得中は中立語、読取失敗は再読込。中立語への変更だけで業種対応完了にしない。
- TM-C01〜16を守る。LIFFはです・ます、主語を省く。面談で「ご来店」「お店」、教室で「施術」「生徒」を固定表示しない。状態の「確定／キャンセル／期限切れ」「未払い／支払い済み／返金済み」は共通語のまま。
- 送信予定の文・対象・日時・URL・送り手は元の予約等と結び付く。不明な送信を新しいキーでやり直さない。手動の1対1返信だけ `X-Line-Harness-Source: manual`、自動通知には付けない。

## 3. 左メニューの出す物・隠す物

## 4. standard（標準）

### 4-1. 登録とはじめの質問・初期セット

目的は配信と問い合わせから始めること。登録時に `standard` を保存する。質問は **スタイル → 見た目 → メッセージの見本（content）**。予約・券・EC接続を答えないと進めない形にしない。

初期セットは、ごあいさつ・問い合わせの文・汎用の案内の文と、設定済みの行き先だけを持つリッチメニュー。予約確定・来店のお礼を標準のおすすめの中心にしない。予約メニュー・リマインダ・EC自動LINEを自動で作らない。予約等を後から有効にしたら、その共通機能の既存画面を使う。

### 4-2. ダッシュボード・メニュー・言葉

今の共通ダッシュボードを保ち、「はじめにやること／受信箱の対応待ち／配信の状況」と共通の友だち・配信分析を出す。ECの数・注文・定期便・EC連携カードを出さない（B-304）。来店の盤や業種専用のタブを新設しない。左メニューは§3のstandard列。

題は「ダッシュボード」。人は「お客さま」、予約を追加で使う場合は「予約／メニュー／担当／来店日」（TM-V02・04・05・07・10・12）。LIFFは共通の言葉で、問い合わせはこのLINEのトークへ。予約未提供時に標準のリンクを汎用予約へ勝手に転送しない。

### 4-3. 申込の流れとリッチメニューの見本

**案内を見る → 回答フォームで希望を送る → 受け付けた表示 → 担当が受信箱で確認・返信**。予約も使う時だけ、設定済みメニューを選んで汎用予約へ。フォーム送信の成功と担当者の対応完了を混ぜない。

| ボタンの見本 | お客さまの行き先 | 運用者の設定先・未設定の扱い |
|---|---|---|
| ご案内 | 公開済みの案内テンプレートの表示・応答 | `/templates`。選んだテンプレートがなければ公開不可 |
| お申し込み | 同じアカウントのLIFF `/forms/:id` | `/form-submissions` で公開済みフォームを選ぶ。IDを推測しない |
| よくある質問 | 設定したキーワードの自動応答 | `/auto-replies`。会話AIを起動しない |
| マイページ | LIFF `/mypage` | 既存のLIFF設定がある場合だけ。個人の情報は本人だけ |
| お知らせ | 公開済みの案内テンプレートの応答 | `/templates`。配信の管理画面を開かせない |
| お問い合わせ | このLINEのトーク | `/chats` は運用者用。顧客URLにしない |

## 5. ec（EC）

### 5-1. 登録とはじめの質問・初期セット

`ec` を保存する。質問は **スタイル → 見た目 → クーポン（coupons）→ メッセージの見本（content）**。EC接続・サイトの読み込み・友だちとEC会員のつき合わせは、既存のEC連携画面への「はじめにやること」で案内する。未対応の回答キーを勝手に追加して保存成功にしない。

初期セットは、ごあいさつ・商品のお知らせ・購入へのお礼・再入荷の見本と、買い物用のリッチメニュー。予約メニューと来店リマインダは作らない。G6のカゴ落ち・閲覧落ち・再入荷は全て止めた状態。既存のルールや専用のNEN設定を上書きしない。サイト・商品のURLは店が選んだ実在のものを使う。

### 5-2. ダッシュボード・メニュー・言葉

今ある共通ダッシュボードとECの集計・注文・定期便・再購入の情報を組み合わせる。新しい6業種共通のEC集計基盤は作らない。注文やつき合わせの入口は既存EC連携へ。ECの値が未接続・未取得なら「—」と接続先、模擬G6の数字は模擬と表示する。定義しかない `ec-orders`・`ec-repeat` を出しただけでは完成ではない。

左メニューは§3のec列。NEN専用画面はEC全契約に公開しない。題は「ダッシュボード」、人は「お客さま」。商品・注文・発送の既存の言葉を使い、ECだけで始めた店に「本日の来店」「ご予約ありがとうございます」を出さない。予約を併用する時は標準の予約語を使う（terms §5）。

### 5-3. 買い物の流れとリッチメニューの見本

**商品を見る → 店のECサイトで購入 → 既存の署名付き受信で注文を取り込む → 本人への通知・マイページ**。カートや購入のできごとの受信、友だちとのつき合わせ、同意がそろった時だけG6の模擬確認へ進む。musuboに新しいカート・実決済画面を作らない。

| ボタンの見本 | お客さまの行き先 | 運用者の設定先・未設定の扱い |
|---|---|---|
| 商品を見る | 店が登録したECサイトのURL | `/ec-commerce?tab=connector` と既存リッチメニューのURL設定。未設定URLは公開不可 |
| お買い物を続ける | 店が設定した商品一覧のURL | `/rich-menus`。G6で送るカートURLは対象の記録から作り、共通URLで代用しない |
| マイページ | LIFF `/mypage`（本人に使える既存の情報）または設定したEC会員ページ | `/rich-menus` で行き先を明示。ECの注文履歴専用LIFFがあると仮定しない |
| クーポン | 設定・公開したクーポンの既存リンク／応答 | `/templates` と既存のクーポン設定。使わない時は出さない |
| ご利用ガイド | 店が設定した案内URLまたは公開テンプレート | `/templates`・`/rich-menus`。未設定なら出さない |
| お問い合わせ | このLINEのトーク | 運用者は `/chats` |

**運用者のG6への入口**は `/ec-commerce?tab=auto-line`。一般客のリッチメニューからG6の管理画面を開かせない。サイトの読み込み前は同タブの案内と入れ方だけ、模擬結果の確認は現在の権限・条件のまま。

題「教室」、タブ「クラス／会員／体験／分析」。今日のクラス・定員／残り・出欠待ち・最近来ていない会員・体験からの入会・継続の状況を既存の式で示す。オンラインと教室の定員は区別し、無制限と未取得を混ぜない。クラスから名簿を開き、出席・欠席・振替の確認まで操作できる。

### 9-3. 申込・欠席・振替の流れとリッチメニューの見本

**公開クラスの開催回 → 日時・残り・料金 → 本人の情報・券 → 申込／確定 → 本人の予約一覧 → 出席／欠席**。欠席は振替先を選ばなくても確定できる。対象なら振替を1回渡し、後から **振替の残り・期限 → 同じ種類・期限内・空きのある開催回 → 確認して予約**。券を戻す処理と振替の付与を二重に行わない。

| ボタンの見本 | お客さまの行き先 | 運用者の設定先・未設定の扱い |
|---|---|---|
| クラスを予約する | LIFF `/events/:id` の公開クラスと開催回 | `/events`・作成／編集。公開イベントIDを保存し、`?page=event` だけで汎用予約へ転送しない |
| 予約の確認 | LIFF `/events/me` の本人のクラス申込 | `/events/bookings`（運用者）。汎用の `/booking/history` と取り違えない |
| 回数券と月謝 | LIFF `/mypage` の残り・期限・今月の利用 | `/booking/menus?tab=passes`・`/booking/passes/new`・友だち詳細（B2） |
| 振替 | LIFF `/events/me` の振替の残り・期限と振替先を選ぶ操作 | クラスの作成／編集の振替の決まり、名簿・友だち詳細（B3）。運用者の `/events` を顧客URLにしない |
| スケジュール | LIFF `/events/:id` の公開開催回 | `/events` の同じ公開クラスを選ぶ。複数クラスは公開済み案内に各クラスのリンクを設定 |
| お問い合わせ | このLINEのトーク | 運用者は `/chats` |

既存LIFFに「すべてのクラスを並べる `/events`」は無い。存在しない一覧を行き先として登録しない。複数クラスの案内は既存のテンプレート／リッチメニューの選択で解決し、新しい一覧が必須なら別の不足として正本化する。

## 10. ボタン・見本を保存するときの共通条件

- 上の顧客向けパスはLIFF内部の画面を示す。送るURLは同じアカウントの実在するLIFF IDと選択先から既存の生成処理で作る。`liffActionUrl` が対応する4種類（予約・予約履歴・フォーム・スタンプ）はそのまま利用する。教室・マイページは実在ルートに合わせたURLを使い、生成処理の許可種別を勝手に増やさない。
- 管理画面のパスは運用者の設定先。顧客のURIへ流用しない。トーク・テンプレート応答・URLは既存のリッチメニューの動作で表し、新しい許可先の一覧を足さない。
- 「スタイル写真／資料／会社のこと／商品を見る」は、具体的な公開テンプレート・公開URL等を選んで保存する。リッチメニュー編集画面へ戻すだけ・ボタン名をトークに送るだけでは、その機能の完了にしない。
- 設定前は運用者の見本に未設定を示し、その項目を公開しない。公開済みの古いボタンは、元の準備判定で安全な案内とトークへの連絡を出し、白い画面・別店の内容・別機能への自動転送を出さない。準備判定のAPI失敗を「準備中」で隠さない。
- 機能を使わない回答ならボタンを外す。任意のボタンを隠した場所に別の未設定ボタンを自動追加しない。設定済みの行き先はスタイル変更だけで上書きしない。
- 文面の `【日時】`・`【URL】` 等は本書の説明用記号。新しい差し込み構文ではない。実装は既存の対応する差し込みと、予約／開催回／注文に属する確認済みデータを使う。共通情報を直しただけで個別予約の日時が入ると表示しない。必須値が無い文をそのまま送れないよう、公開前・送信前に確認する。
- 各文の目的（取引／宣伝）・対象・同意・静かな時間・停止・上限を既存の契約で検査する。送信先0・テスト・模擬・結果不明を「全員に送信済み」と表示しない。
- B2の実購入やB7の自動発行は準備中のままでも、手で付与する券・本人の残り表示・手動固定URLへの参加は使える。実装済みの操作に一律の準備中をかぶせない。
