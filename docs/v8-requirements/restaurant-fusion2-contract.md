# 飲食の融合2：来店・退店・共通のできごと・来店スタンプ・待ち

2026-10-10／Codex／B-181〜189・B-214。飲食1と列車16の上に追加する。正本は司令塔の `restplan/PLAN.md` §1 04・13・14・15・24、§2 625・628・632、§3 飲食2、§4 D2・D3。本書はその実装の受け渡し契約。

## 保存と版

- `POST /api/restaurant-test/reservations/:id/attendance?accountId=...` に `action`、`expectedVersion`、`requestId` を渡す。action は `visited / late / no_show / undo_visit / depart / undo_departure`。遅刻には `lateMinutes`。旧来店 POST・DELETE もこの処理へ渡す。
- 来店は既存の実来店記録、退店は実際の UTC 時刻と監査に保存する。予定の終了時刻を変えない。旧予約の予定から実来店時刻を作らない。
- 同じ依頼の再送は再実行しない。同じIDで動作・遅刻時間を変えたら409。新しい依頼の古い予約版は409。成功した予約版は1増える。
- 退店後も来店済みの状態を残し、`departed_at` がある予約は占有から外す。結合卓の全卓、LINE人数在庫、仮押さえ、待ち、空き候補の判定を合わせる。退店訂正には停止・休業・全卓の競合・人数在庫を再検査し、失敗時は監査も戻す。退店後の来店取消は禁止。
- 店の組織に属する owner/admin/staff が操作できる。閲覧のみは403、他組織の予約は404。来店・退店の各入口は同じ版付き処理を使う。

## D2：回転の式

`GET /api/restaurant-test/rotation?accountId=...&storeId=...&date=YYYY-MM-DD`。店のタイムゾーンの日付で集計する。

- 回転＝その日に実際に退店した組数÷その日に営業時間がある有効卓数。結合卓の予約も1組。
- 滞在＝実来店から実退店までの平均分数。日をまたぐ組は退店した日に数える。
- 稼働率＝実際に使われた卓ごとの時間÷卓ごとの営業時間。重複時間は合併し、卓別の臨時休業を除く。来店中は現在時刻まで。日付の境界で切る。
- 営業時間や実来店が無い場合は推測せず `null`（画面は「—」）。無断取消率は当日の取消・仮押さえを除く予約を分母にする。旧記録の不明数も返す。

## 共通のできごとと再実行

予約作成・変更・取消、来店・来店取消、退店・退店訂正、待ちへの空き案内の8種類。予約更新とできごと記録は同じD1書込に入る。予約ID＋版＋種類で一意。待ちは案内の再試行キーを使う。旧予約を過去のできごととして補充しない。

発生時の店・LINEアカウント・友だちを固定し、必要最小限の情報だけを保存する。氏名・電話・秘密値はpayloadに入れない。後日アカウントが変わった友だちには配送しない。

受取先は既存の共通できごと処理（オートメーション・シナリオ）、マイル、来店スタンプの既存キュー。受取先別の記録と共通workflowの工程記録・所有者の柵を使う。完了後の応答喪失は工程を使い直し、加算済みのSQLを繰り返さない。未完了は毎分の処理で再実行し、失敗は60秒後から最大50回。完了記録を失ってもworkflowの完了から修復する。機能の停止・友だちの所属を既存の共通処理で検査する。外向きWebhook・広告の変換通知は発火させない。飲食3の承認付きフォロー送信はこの束に含まない。

## D3：台帳とQRの同じ来店

- 台帳の来店の基本押印は1個。既存の初回ボーナス・倍率・カード制限は維持する。来店と押印処理は別だが、キューで再実行でき、画面に押印の完了・待ち・対象外を返す。
- 予約のある本人には当日の自分の予約を選ばせる。来店前の予約は店員の来店記録を待つ。複数候補を自動で選ばない。台帳とQRは同じ `restaurant:<予約ID>` を使い、一度だけ押す。QRが先でも台帳のキューが先でも増えない。退店しても来店印は残す。
- 予約のないQR利用は従来の来店スタンプの財布・記録に保存し、新しい顧客台帳を作らない。店頭QRはJSTの同じ日1回まで、時間制限があるときは両方を満たす。店員QRの単独押印・紙の移行には店頭用の間隔制限を掛けない。手入力・台帳の元のカード制限は変えない。予約に結びつくQRも元のカード制限を使い、時間制限なら同じ日の次の実来店でも指定時間後に押せる。制限中の次回時刻を返し、店員QRは消費しない。

## QRの口と安全性

- `GET/POST /api/visit-stamps/cards/:id/storefront-qr`：店×カードに1つ。owner/adminが発行・交換する。発行依頼IDと旧QR IDの比較で交換し、古い紙のQRを無効にする。読むだけで発行しない。
- `POST /api/visit-stamps/cards/:id/staff-qr`：owner/admin/staff。個数または会計金額、session ID、発行依頼ID、前のQR IDを渡す。30秒で期限切れ、1人が読んだら使用済み。金額の換算と上限はサーバで計算する。
- `GET/DELETE /api/visit-stamps/staff-qr/:id`：発行者本人が状態を読み、閉じた際に失効する。再発行と読取が競ったら読取の結果を返し、明示的な「続けて出す」でだけ次を出す。
- `POST /api/liff/visit-stamps/qr/redeem?accountId=...`：LINE本人確認から友だちを決める。bodyはtoken・読取依頼ID・選んだ予約IDだけ。友だちID・押印数をクライアントから信用しない。
- ランダム256bitのtoken、アカウント・カード所属、カードの有効版、期限、実来店、友だち追加を検査する。押印と使用済み化を同じbatchで決める。設定変更・停止後の古いQRは使えない。
- QR小窓は `components/dashboard/qr-dialog.tsx` を共用する。店頭には保存・印刷、店員には残り時間・受取結果を出す。店員QRのコピー・保存を置かない。非表示になった後の発行結果も失効させる。LIFFは成功・制限・期限切れ・友だち追加・予約選択を表示する。

## 待ちと空き案内

新しい待ちの表を作らず、既存の人／席の先着処理を使う。先着、通常30分の仮押さえ、開始2時間前は10分、1人3件、開始1時間前締切を維持する。取消・退店・時間変更の後、対象店のLINEアカウントと店IDで席の待ちを処理する（組織アカウントで別店を処理しない）。結合卓・在庫・休業を同じDB制約で再確認する。
