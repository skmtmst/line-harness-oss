## API契約

共通の先頭は `/api/ops/staging-qa`。通常の認証と運営の編集権限が必須。`env-owner`・通常の統括・店・閲覧のみでは使えない。返事は `{ success, data }`（拒否時は `{ success:false,error }`）。全返事は `Cache-Control: no-store`。

| メソッド・末尾 | 入力 | 返す値 | 確かめたこと |
| --- | --- | --- | --- |
| GET `/safety` | なし | 環境名、送信停止、模擬LINE限定、実行可能な処理名 | 本番設定・旗不整合・権限の拒否 |
| POST `/runs` | `passwords: {hq,store,viewer,impersonation}`。各8〜128文字、英字・数字が必須 | 作成ID、統括ID、LINEアカウントID、組織ID、店ID、4役の利用者IDと合成メール、友だちID一覧、状態 | SQLiteの参照整合性を有効にして作成、通常の認証とスコープで4役を照合 |
| GET `/runs` | 任意の `after=<直前のrun UUID>` | 最大50件の台帳、`nextCursor` | 作成分の再取得、秘密の非表示、入力拒否 |
| GET `/runs/:id` | 作成済みのUUID | 上記の台帳 | 任意IDの拒否、秘密の非表示 |
| POST `/runs/:id/friends` | `count:1..20`。1試験あたり最大100人 | 作成した友だちID・模擬LINE利用者ID | 他のアカウントへ追加できない、実送信0 |
| POST `/runs/:id/session` | `role:hq|store|viewer|impersonation` | ID、役、統括ID。代理は `mode:read` も返す | 作成済み試験利用者だけの通常セッション。代理は本人の既存セッション＋通常の `ops.impersonation` 再確認が必須 |
| POST `/runs/:id/cron` | `job` と `requestId`（英数字・`_`・`-`、1〜64文字） | 処理名、対象アカウント、結果、終了時刻、送信停止、`replayed` | 作成対象限定、実際の仮押さえ解除と他店不変、同時起動409、同じIDの再送は保存結果だけを返す |
| DELETE `/runs/:id` | 作成済みUUID | `id,status:archived` | 試験利用者停止・セッション失効・代理終了・接続と店の停止・友だち非表示。他の利用者・店は変更しない |

Web側の接続口は `apps/web/src/lib/api-staging-qa.ts` の `stagingQaApi.safety/create/list/detail/friends/session/cron/remove`。画面は変更していない。

## 本番を閉じる条件と送信止め

開くには次の全条件が必要（本番設定ファイルは変更していない）。

1. `DEPLOY_ENV=staging`。
2. 検証Worker名、検証DBの識別子、検証の公開URLがコード中の許可値に完全一致。
3. `STAGING_QA_ENABLED=true` と `STAGING_QA_OUTBOUND_DISABLED=true`。

本番の実設定に両旗を無理に足しても拒否する。環境名だけを検証へ変えた本番設定も拒否する。HTTP入口では認証やDBより先に404を返す。検証設定の両旗は既定falseのまま。

検証環境でどちらかの旗がtrueなら、外向きHTTPをすべて遮断する。LINE・Google・メール中継・Slack・決済・自分の公開URLへのHTTPも例外にしない。SMTP/IMAPの生ソケット、メール/AI/送信キューのサービス束縛も止める。処理ごとに非同期の文脈へ持たせ、待機後の処理も同じ停止を引き継ぐ。本番ではこの文脈とfetchの差し替えを導入しない。

例外は、台帳にある有効な模擬接続のランダムなトークンで、台帳にある同じアカウントの試験友だちへ送るLINEのpush/multicast/broadcastだけ。ネットワークを呼ばずに模擬の受理を返す。未知のトークン、他の友だち、片付け済み試験は遮断する。実際のHarness Proxyを通したときは通常どおり試験用の送信履歴に残る。担当者の1対1返信は `X-Line-Harness-Source: manual`、自動処理には付けない。

本番設定の負例・並行する処理の隔離・実際のworkerdの通信境界を試験した。workerdの送信先役は手元の別Workerで、遮断/模擬時の到達0と、通常通信の対照時の到達1を確認する。外部サービスには接続していない。

## cronの範囲と安全な再実行

- `booking_waitlists`: 共通予約/席待ちの期限切れ・昇格・模擬通知。必ず試験のLINEアカウントIDを渡す。
- `restaurant_holds`: 台帳にある試験店の仮押さえ期限切れだけ。
- `restaurant_menu_prices`: 台帳にある試験店の承認済み価格変更だけ。

全体cronをHTTPから起動する口や任意の関数を指定する口は作っていない。時刻はサーバーの現在時刻を使い、世界の時計は変更しない。全アカウントの定期処理は送信停止中には動かさず、キューは再試行へ戻し、受信メールは拒否する。検証の `[triggers]` は追加していない。

試験ID単位の永続ロックを、友だち追加・セッション準備・cron・片付けで共用する。cronの同じ `requestId` は結果を再利用し、異なる処理への使い回しは409。実行中/失敗済みの同じIDを自動で再実行しない。途中終了したロックに自動失効は設けない（古い処理と重ねて動かさないため）。残った場合は、司令塔が元の処理の終了と影響を確認してから回復を判断する。

## 利用手順と制約

1. 司令塔が統合・必要な通常検査・検証配備を済ませ、DB/Worker/Pagesの版を照合する。この作業では配備していない。
2. 運営の通常ログインを確保してから検証の両旗を有効にし、`GET /safety` を確認する。送信停止中は外部のログイン検証も遮断されるため、試験の役は準備APIのセッションを使う。
3. `/runs` で隔離した統括と店・4役を作り、`/friends` で合成データを追加する。パスワードは呼出側が保持し、返事や監査へ出さない。LINEの秘密値は模擬であり、APIに返さない。
4. 統括=owner/全体、店=admin/作成店のみ、閲覧=staff/read_only/作成店のみ。代理用の合成利用者も閲覧のみ。代理の試験では運営本人のセッションのまま、実際の代理ログイン機構で試験統括へ入る。試験利用者を運営マスターへ昇格させない。
5. 普通の3役の `/session` は、そのブラウザ/クッキー入れのログイン先を切り替える。運営用のブラウザ/認証は別に保つ。秘密はJSONには返さず、通常のSecure/HttpOnlyのセッションCookieへだけ入れる。
6. 通し試験に必要な処理だけ `/cron` で1回実行し、履歴・台帳を照合する。Google等の実接続が必要な区間は、この模擬接続では試験完了に数えない。
7. `/runs/:id` をDELETEし、試験データは履歴を残して停止する。司令塔が旗を解除するまでは検証全体の送信止めを保つ。

新しい表・列・マイグレーションは不要。`platform_settings` の専用名前空間に作成ID、ロック、実行結果だけを記録する。DB適用・配備・push・PRは実施していない。
