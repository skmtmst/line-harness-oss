# 列車30：二段階認証・代理ログイン・書き出し監査

対象は `codex/kenta-train-30-1012` のローカル作業だけ。本番・検証環境のAPIやDBには接続していない。push・PR作成・本線への統合・配備・DB更新は行っていない。migration・schema の変更はない。

## 二段階認証（S02）

統括ごとに、既存の `platform_settings` の `auth.mfa.required:<tenantId>` へ保存する。未設定・壊れた値はOn。全統括を触れるオーナーと有効な運営だけが変更でき、Offには毎回、使い切りの本人確認が必要。変更権限は保存するSQLでも確認し、切り替えを監査に残す。Onへ変えたときは、その統括の既存セッションと代理ログインを終了する。

LINE・メール・人のAPIキーの認証後、登録済みなら確認、未登録なら初回登録の合言葉だけを返す。普通のセッションは確認後に発行する。Offでも個人で登録した人には確認を求める。以前発行した未確認セッションも、On／個人登録済みの場合は拒否する。招待受け入れも登録前に普通のセッションを出さない。

回復コードは初回登録時だけ表示する。既存の `totp_secret_enc` にTOTP秘密と回復コードのハッシュを暗号化して保存する。旧形式のTOTP秘密はそのまま読める。競合時に1人だけ消費できる更新を使い、再使用できない。確認済みセッションの証拠は同じ設定表の `auth.mfa.session:<session-token-hash>` に保存し、ログアウト・失効・認証取消で消す。確認は既存の挑戦表と試行制限表で5回／15分に制限し、TOTPの使用済み段を再使用できない。メールのパスワード再設定はTOTPを解除しない。

試験：`train30-mfa.test.ts`、`admin-auth-mfa-enforcement.test.ts`、`auth-email.test.ts`。Onの全役割で未確認セッションなし、Off、初回登録、回復コードの同時消費、TOTP使い回し、挑戦を作り直した試行制限、権限変更競合、Offの本人確認使い切り、統括別の失効、既存セッション／直接キーの拒否、設定不足時の拒否、再設定で解除されないことを確認。対照試験は一度、試験時の変換だけでMFAゲートを外し、default-Onの3役割すべてが落ちることを確認した（実装ファイルは変更していない）。

残り：反映前に司令塔が既存のTOTP暗号鍵の設定を確認する。今回は環境設定を読み出していない。旧登録者には新しい回復コードがまだないため、必要な人は本人確認付きの既存の運営リセットから再登録する。新しい暗号化形式へ登録後は旧コードへの単純な巻き戻しに注意する。ログイン失敗の監査には入力された秘密・メール本文を入れない。

キーの探索：通常の管理APIとLINE Proxyは共通の `authenticateApiToken` を使う。Onでは人の生APIキーでここを素通りできず、キーのログイン口で二段目へ進む。環境／旧式の緊急キーもOnでは拒否する。公開LIFF・チャネルごとの既存の狭い機械認証は変えない。更新専用の `ADMIN_API_KEY` 口は別のS05範囲。将来の機械利用には、用途・店舗・期限を限定したサービス認証への移行を司令塔が判断する。今回は新しい広権限キーを足していない。

## 代理ログインの伏せ（S03）

URLごとの列挙から、すべての認証済みAPIの項目分類へ変更した。名前（realName・systemDisplayNameを含む）、連絡先、住所・生年月日・銀行情報、本文・メモ、ファイルの場所を伏せる。metadata・自由回答は未知のキーにも個人情報を入れられるため全体を伏せる。深すぎる未走査の木も返さない。JSON以外の出口も既定拒否し、CSVと本人確認書類はルートに入る前から拒否する。

表示には同じ代理セッション・担当者・統括の理由記録が必要。許可・拒否した出口を監査に残し、応答は保存させない。運営コンソールは元の権限を保つが、代理中の連絡先は伏せ、対象統括の表示許可を全統括へ広げない。

既存の設定表 `auth.impersonation.session:<id>` で代理と不透明なログインセッションを結び付けた。ログアウト、認証取消、ログインの期限切れ、代理の1時間経過で終了する。別の新しいログインには持ち越さない。

試験：`train30-impersonation.test.ts`、`ops.security.test.ts`。友だち・予約・metadata・運営コンソールのJSON、CSV、書類、未知の非JSON、理由付き許可、理由のないフラグ、監査、深い木、ログアウト・取消・期限切れ・別セッションを確認。

残り：追加される個人情報の項目は、この分類と出口試験に追加する。伏せたデータの画面上での扱いは司令塔が絵と照合する。

## 書き出し・書類の取得記録（S06）

既存の監査表へ、担当者・日時・統括・店舗・対象・件数・結果を保存する。複数店舗では店舗ごとに記録し、共通の要求IDで結び付ける。拒否・失敗も記録する。監査保存に失敗した場合は書類・CSVを返さない。CSVと本人確認書類の応答に `Cache-Control: private, no-store` を付ける。

同種探索でCSVを返す14系統を確認・修正した：予約、共通アクション、自動処理、共通情報、分析、飲食店配達、スコア、成果、ウェビナー、統括配信、イベント、通知、友だち移行、紹介支払。本人確認書類の中身取得にも適用。友だち・共通情報・分析・銀行書き出しの生成要求も記録する。単なる書き出し履歴一覧は取得記録の対象にしない。個別の予約／書類ルーターで使う場合も同じ監査を通す。

試験：`train30-output-audit.test.ts`、`318_affiliate_payout_operations.test.ts`。CSV内の改行と注記・見出しを除いた件数、単一／複数店舗、書類、成功・拒否・失敗、PII層での拒否、監査保存失敗、保存禁止を確認。

残り：監査の成功はHTTP応答を許可した結果で、利用者が最後まで受信した証拠ではない。友だちCSVのストリームは全件をメモリへ読み込まず、取得開始時の件数を記録する。生成待ちの件数は未確定として保存し、0件と見せかけない。
