## 保存の形・migrationの判断

- 統括の必須設定：既存 `platform_settings` の `auth.mfa.required:<tenantId>`。店舗管理者が統括の安全設定を弱めないよう、全統括を触れるオーナーと有効な運営だけが変更できる。Offには毎回使い切りの本人確認。監査も同じ原子的な更新で残す。Onへ変える時は同じ統括の既存セッションと代理ログインを終了する。
- 個人の登録と回復コード：既存 `staff_members.totp_secret_enc` に、TOTP秘密と8個のSHA-256照合用ハッシュをAES-GCMで暗号化して保存。コードの元の文字はDBへ保存しない。従来の暗号化TOTP秘密だけの形式も読める。新しい8文字は32種類の英数字から暗号学的乱数で生成する（40bit／個、重複なし）。オンライン確認は既存の5回／15分の制限を維持する。
- 消費：保存された暗号化内容が読み取り時と一致する場合だけ更新する。同時に使っても勝者は1人。確認したTOTPの時間の段は既存 `totp_last_used_step` で再使用を拒否する。
- 作り直し：本人の現在のセッションに結び付いた操作専用の確認票を1回だけ消費する。同時更新を検出し、新しい8個のハッシュへ全部交換する。古いコードは全部無効。成功した応答でのみ新しいコードを返し、GETは登録日と残数だけ。監査を同じ更新に結び付け、応答を保存禁止にする。
- アプリの登録し直し：本人確認後に既存の保留列へ新しい秘密を入れる。6桁の確認が終わるまでは前のアプリを使える。開始時に本人確認したセッション・元の確認票の期限・保留内容の照合用ハッシュを既存設定表 `auth.mfa.reenroll:<staffId>` へ結び付ける。別セッション・期限切れ・同時変更では置き換えない。確認後に置き換え、監査と保留票の削除も原子的に行い、回復コードも新しくし、セッションを失効する。
- セッションの確認済み証拠：既存設定表 `auth.mfa.session:<session-token-hash>`。ログアウト・失効・認証取消で消す。コードの表示は画面のメモリだけで、URL・localStorage・sessionStorageへ保存しない。コピーとファイル保存は本人の明示操作。

既存の列・設定表・本人確認票で全て保存できた。新しい表や列は要らないため、migration番号・SQL案はない。旧登録者の回復コード残数は0個として表示でき、本人確認後に8個を発行できる。新しい暗号化形式を旧コードへ単純に巻き戻さない。

LINE・メール・人のAPIキーは、Onでは二段目の確認か初回登録の合言葉だけを返し、確認前に普通のセッションを出さない。Offでも個人で登録済みなら確認する。メールのパスワード再設定ではTOTPを外さない。以前の未確認セッションや人の生APIキー・環境の緊急キーも、Onの広い入口にはしない。公開LIFF・チャネルごとの機械認証は従来の限定した入口を維持する。更新専用の `ADMIN_API_KEY` は別のS05範囲で、将来の機械利用に必要な用途・店舗・期限を限定したサービス認証は司令塔の判断事項。

## 鍵不足の扱いと理由

鍵が未設定・短い・空白だけの場合、**未登録の人の二段階認証の必須はOff扱い**にする。鍵があれば未保存の設定はOn。保存値を勝手にOffへ書き換えないので、鍵を正しく設定すれば本来の設定へ戻る。鍵なしでOnを保存する操作は400。

全員の一次認証まで拒否すると、運営も管理画面へ入れず、設定不足の発見・復旧が難しくなる。未登録の人は元のLINE／メール／キーの認証を維持して入れる方を選んだ。一方、**すでに個人で登録した二段階認証や運営の強制確認は省略しない**。既存の保護を外すと盗まれた一次資格だけで入れるため。登録済みの人が新しく入るには元の暗号鍵の復元が必要。確認済みの既存セッションは引き続き元のセッション証拠で確認する。

設定画面と運用状態（読み取り・手動確認の両方）、一次ログイン時の秘密値を含まないログに「二段階認証の鍵が未設定のため、必須にできません」を出す。運用状態は秘密値を返さず、configuredとnoticeだけ。

試験は、鍵なし・短い・空白で一次ログインとセッション利用可／鍵なしOn保存400／鍵あり既定Onで確認前にセッションなし／登録済みは省略不可を確認する。

4. オーナーが配備後、設定と運用状態の注意が消えたこと、未登録者が初回QR登録できること、登録済みのLINE／メールログインで確認が出ることを確かめる。
5. 鍵なしを再現するのはローカルの試験だけ。確認のために検証・本番の既存secretを削除しない。
