# コメントの書き方

コードだけでは分からない制約や判断の理由を、次に読む人へ伝えるための決まりです。置き場・名前・公開入口は [コードの構成と名前](code-structure.md) に従います。

## 理由を書く

コメントには「なぜこの条件・順序・制限が必要か」を書きます。処理をなぞるだけの説明、名前から分かる説明、役目を終えたコメントは削除します。

```ts
// 同じ冪等キーで照合し、結果不明の送信を二度実行しない。
// D1 のバインド数上限を超えないよう、対象を分割する。
```

権限・別店舗の境界、秘密値の伏せ方、失敗時の扱い、課金、二重送信を防ぐ理由は残します。法令・規約・外部仕様の制約や、その版を特定する日付・URLも必要な情報です。番号を取り除くために、こうした理由まで消してはいけません。

## 経緯は履歴へ置く

作業番号、Issue・PR 番号、作業した日付、人の名前、「誰が言った」「前はこうだった」「指摘されたので直した」という経緯は、Git の履歴と PR に残します。コメントには、今の実装で守る条件と理由だけを残します。試験の題名・内部名・ファイル名にも作業の経緯を足しません。

決まりの主語は人ではなく、対象と条件にします。例えば「担当者の指摘で伏せた」ではなく「秘密値が応答へ漏れないように伏せる」と書きます。理由が長い場合は、実在する正本の文書へリンクします。番号だけの参照や、存在しない文書への参照は残しません。

## 日本語でそろえる

自分たちが書くコメントは日本語を基本にします。API 名・HTTP ヘッダ・識別子・外部仕様の正式名はそのまま使えます。元の OSS に由来する英語のファイルは、ファイル単位で英語のまま保ち、説明文の言語を混ぜません。ライセンス表記と道具が解釈する指示は保持します。

適用済みマイグレーションはコメントも書き換えません。設計図の照合 ID は照合に必要な間は保持し、切り替え後の所定の整理で扱います。

## 既存の検査で増加を防ぐ

`pnpm quality:check --base <比較元SHA>` の `history-comment`・`history-name`・`history-test-title` などが、経緯を含むコメント・名前・試験の題名を集計しています。同じ目的の見張りや除外一覧は新しく作りません。

既存の違反を減らした場合は、同じ比較元で `pnpm quality:update --base <比較元SHA>` を実行し、実測に合わせて基準値を減らします。上限や許可一覧を広げて通してはいけません。検出式に当たらない経緯も、レビューでこの決まりに従って確認します。
