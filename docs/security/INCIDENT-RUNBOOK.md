# 事故が起きたときの手順

対象：オーナー・マサトさん・司令塔。2026-10-16作成。最初の目的は**被害が増えるのを止めること**。原因が全部分かるまで待たない。障害と漏えいの疑いは両方あり得る。

## まず全員で守ること

1. 発見時刻を日本時間・タイムゾーン付きで記録し、本番／検証、起きた操作、影響が続いているかを確認する。秘密・顧客本文・URLのクエリをSlackへ貼らない。
2. ケンタさんとマサトさんへ直ちに連絡し、事故の判断役・操作役・記録役を決める。返事がなければ、非公開の連絡帳にある電話など別の連絡方法へ切り替える。
3. 司令塔は調査と安全な手順準備を進める。**本番のコード配備・巻き戻し・secret変更・DB復元は、マサトさんの明示承認と担当指定を得て行う。** この文書を読んだこと自体は実行の承認ではない。
4. ログや履歴を消さず、必要な証拠をアクセス制限した保管先へ保存する。GitHubも公開中なので、事故の詳細や証拠を公開Issueへ置かない。

実際の連絡先と、証拠・回復コード・復元点の実値の保管先は非公開の連絡帳に置く。この文書には名前と役割、情報の種類だけを書く。連絡帳と本手順の控えは、GitHubやmusuboへ入れない場合にも使えるようにする。

## 漏えいの疑いから復旧までの時間割（B-343）

以下は内部の目標。⚖ 法律上の報告・本人への通知の要否と期限は、気づいた時点で専門家に確かめる。調査が終わるまで相談を待たず、24時間・72時間を法的な猶予と考えない。[案内の型](CUSTOMER-NOTICE.md)と[気づき方](DETECTION.md)を使う。

| 段階 | 最初の15分 | 1時間まで | 24時間まで | 72時間まで |
| --- | --- | --- | --- | --- |
| 気づく | 事故ID・発見時刻・本番/検証を記録。ケンタ・マサトへ連絡 | 警告と操作記録を照合。確定と疑いを分け、判断役を決める | 他の同種の警告・過去の異常を確認 | 見落とした入口・監視の停止期間がないか確認 |
| 止める | 進行中の配信・公開・該当入口を止める案を判断役へ。手動送信にも中断を連絡 | 承認した担当が鍵の失効/作り直し・入口遮断・配信停止・必要なWorker巻き戻しを実施。実際の停止を読み直す | 迂回できる入口や別環境も確認。旧鍵が拒否されることを確認 | 不要な権限と連携を整理。安全が確かめられない範囲は停止維持 |
| 範囲を調べる | 「誰の・何が・いつから」を仮置き。不明と書く | 対象の店、情報の種類、人数の上限、期間、外部閲覧の可能性を調べる | DB・出力・ログ・Slack・外部サービスを照合し対象範囲を更新 | 判明分と未確定分、対象外と判断した根拠をまとめる |
| 証拠を残す | 元のログを消さない。安全な保管先と記録役を決める | 閲覧を限定してログ・監査・配備版・変更履歴を控える。取得者・時刻・取得元・保管先を記録 | 控えの読み取り可否・保存期間・閲覧者を確認。必要なら改変確認用のハッシュも別管理 | 調査資料・承認・操作の時系列を整理。証拠を消す掃除をしない |
| 直す | 推測で修正を重ねず、被害拡大防止を優先 | 原因候補と修正案、影響する機能を整理 | 原因の修正を専用枝へ。鍵・権限・依存・設定の種類別に下表で対処 | 再発防止と残るリスク、担当・期限を確定。未解決を完了にしない |
| もう一度確かめる | 停止に成功したか、送信が続いていないか確認 | 旧鍵・他店/他人のID・閲覧のみの拒否を確認する計画を作る | 架空データで正常動作と「わざと壊すと落ちる」試験を実施 | 承認後の限定再開を見張り、結果不明の配信・決済を照合。戻り先も確認 |
| 振り返り・案内 | 連絡責任者と次回の報告時刻を決める | ⚖ 専門家へ相談。対象の店へ確認済みの初報と次の連絡時刻 | 店・本人への案内と未達を確認。なぜ気づけたか/遅れたかを整理 | 対応の評価・監視の追加・練習日を決め、続報。長期調査はそのまま継続 |

停止・鍵・巻き戻しの具体的な注意と承認は、この下の各手順を使う。戻すコードに今回の穴がある場合は巻き戻さず、入口の停止を維持する。証拠の保全と緊急停止は可能なら並行し、証拠を集め終わるまで被害の停止を遅らせない。

## 原因ごとの対策と直しの手順

| 原因 | 直し方 | もう一度の確認 | 再発を防ぐ見張り |
| --- | --- | --- | --- |

| 権限の抜け | 認証・店/統括の所属・操作権限・閲覧のみをサーバー側で直す。画面のボタン非表示だけで済ませない | 他店/別人/代理ログイン/閲覧のみで読取・書出し・変更・削除を拒否。副作用なしも確認 | 権限変更、管理者追加、出力急増、全経路の境界試験 |

### 練習の終わり方

検証環境と架空データだけで、警告→15分以内の連絡→停止判断→範囲確認→証拠保全→修正→正常/故障対照→再開判断まで通す。実行者・時刻・所要時間・停止できなかった経路・通知未達・次の担当を記録する。本番で故障を起こさない。この練習をまだ行っていない場合、点検表S39を「済」にしない。

## 止める・戻す方法

### 配信を止める

入れる担当者が管理画面の「運用状態」（`/emergency`）を開き、対象アカウントと停止範囲を確認する。理由を入れて確認し、操作後に読み直して停止履歴と停止状態を確かめる。APIが失敗したら、ボタンを押しただけで止まったとは考えない。

一斉配信・シナリオ・リマインダ・自動処理・自動応答など、今回影響する範囲を選ぶ。個別の一斉配信は詳細から「停止」、予約済みは「取消」を使える。統括配信にも専用の停止・取消がある。再開・再試行は、事故の調査中は押さない。

**停止は全送信の一括遮断ではない。** 担当者の手動1対1返信など対象外の経路があり、LINEが受け付け済みの送信は回収できない。手動返信の担当にも中断を伝える。Proxyから担当者として1対1返信する場合だけ `X-Line-Harness-Source: manual` を付け、自動通知には付けない。事故対応中に自動送信をmanual扱いにして停止をすり抜けさせない。

管理画面やAPIが使えず送信が続く場合はマサトさんへ即時連絡する。最終手段として対象LINEチャネルのアクセストークン失効やWorkerの入口・実行の遮断を検討し、影響と承認を記録して担当者が実施する。トークンの再発行だけで旧トークンも止まったと判断しない。公式側で失効を確認する。Webhookを無効にするだけでは予約送信・cronは止まらない。cronを止めるだけでも手動API・Webhook経由の送信は残る。

根拠：`apps/worker/src/routes/operations.ts`、`apps/worker/src/routes/broadcasts.ts`、`apps/worker/src/routes/hq-broadcasts.ts`、`apps/worker/src/services/operation-send-paths.ts`。画面の根拠：`apps/web/src/app/emergency/page.tsx` と同フォルダの制御画面。配備先での停止練習は[点検表S39](SECURITY-CHECKLIST.md)で未実施としている。

### Workerを前の版へ戻す

先に正常だった**Version IDと元のGit SHA**を特定する。単に「1つ前」を選ばない。戻す版が現在のDB・secret・設定と一緒に動くか確認し、脆弱性を直す前の版へ戻して漏えいを再開しない。承認した範囲を配備ロックで守る。

次は読むだけの例。`<対象設定>` は本番なら `apps/worker/wrangler.toml`、検証なら `apps/worker/wrangler.staging.toml`。命令はリポジトリのルートで実行する。

```sh
git status --short --branch
pnpm exec wrangler deployments list --config <対象設定>
pnpm exec wrangler versions list --config <対象設定>
```

下は承認後に指定担当者だけが実行する変更操作。事前に両作業ツリーがクリーンで、ローカルHEADとGitHubの対象ブランチが完全一致していることを確認する（本番はmain、検証はcodex/development）。復旧元のVersion ID／SHAと、作業用checkoutのSHAは別々に記録する。

```sh
pnpm exec wrangler rollback <確認したVersion-ID> --config <対象設定>
```

Cloudflare画面では Workers & Pages → 対象Worker → Deploymentsから正常版を選べる。実行後は新しい配備が100%になったこと、版・health・ログイン・必要な読取が回復したことを確認する。**Workerの巻き戻しではDBやR2は戻らない。** secretの復旧も個別に扱う。使えない古い版しかなければ、停止を維持して修正版を準備する。

[Cloudflare公式の巻き戻し](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)、[CLIの引数](https://developers.cloudflare.com/workers/wrangler/commands/workers/)。承認・排他は[DEPLOY-GATE](../DEPLOY-GATE.md)、現在の司令塔運用は[AGENTS.md](../../AGENTS.md)に従う。

### 鍵を作り直す

漏れた鍵の種類・対象サービス・本番／検証・利用箇所を特定する。担当者が公式の管理画面で旧鍵を失効させ、新鍵を安全な保管先と対象環境へ設定し、旧鍵が使えないことまで確かめる。被害が進行中なら旧鍵の失効を優先する。値を引数、Git、Slack、Issueへ貼らない。

Worker secretはCloudflareの対象Workerの設定か、値を表示しない対話入力を使う。secret変更も本番の変更であり、別環境へ同じ値をコピーしない。StripeのAPIキーと通知署名用の鍵、LINEのMessaging APIの鍵とログイン用の鍵は、それぞれ用途が違うため混同しない。

**DBを暗号化する鍵は単純に上書きしない。** LINE認証情報の暗号化鍵や二段階認証の暗号化鍵を失うと、既存データを読めず全員が入れなくなる場合がある。マサトさんと再暗号化・鍵の安全な控え・失効対象の再登録を計画し、被害が広がる経路を先に止める。漏れた暗号化鍵を新しい鍵へ替えるだけでは、すでに持ち出されたデータを守り直せない。

根拠：[LINEの暗号化手順](../line-credential-encryption.md)、`packages/db/src/credential-crypto.ts`、`apps/worker/src/lib/mfa-config.ts`。

## 管理画面に入れない

- **0〜5分**：自分だけか全員か、本番か検証か、ログイン画面／認証後／二段階認証のどこで止まるかを確認する。時刻と秘密を含まないエラーの種類だけ記録。ケンタさん・マサトさんへ連絡する。
- **5〜10分**：別の権限ある人が入れるか、CloudflareとLINEの公式障害情報、直前の設定変更を確認。認証アプリの端末時刻と回復手段を本人が確認する。Cookieの許可元・SameSite・ドメイン設定を担当者が点検する。
- **10〜15分／止め方**：配信が危険なら、入れる担当者が上の配信停止を行う。全員入れない場合はマサトさんが外側の遮断を判断する。認証を外して入れるようにする処置は行わない。
- **戻し方**：個人の締め出しは[二段階認証の回復手段](TWO-FACTOR-SETUP.md)へ。直前のWorker変更が原因なら、承認後に正常版へ戻す。登録済み二段階認証の暗号化鍵がない場合は鍵の復旧を優先し、必須化を外すだけで済ませない。
- **知らせる相手**：ケンタさん・マサトさん・司令塔。継続して業務が止まる利用者には、確認できた影響と次の連絡時刻を案内する。

根拠：`apps/worker/src/middleware/admin-auth-config.ts`、`apps/worker/src/routes/admin-auth.ts`、`apps/worker/src/lib/mfa-config.ts`。

## Workerのエラーが続く

- **0〜5分**：発見時刻、固定のエラーコード、失敗している機能、直前の配備を控える。本文・秘密・クエリの付いたURL・生のスタックをSlackへ貼らない。マサトさん・司令塔へ連絡する。
- **5〜10分**：Cloudflare画面でエラー率とVersion IDを確認し、D1・外部サービス・配備のどこから始まったかを切り分ける。設定変更や配備を重ねず、送信結果が不明な処理を連打しない。
- **10〜15分／止め方**：配信・決済等へ誤った副作用が出るなら該当機能を止める。直前のコードが原因で正常版との互換性を確認できれば、承認後にWorkerを巻き戻す。
- **戻し方**：healthだけでなく、エラーが起きた操作、未処理件数、ログインを確認する。受信済み通知の再実行は重複防止の記録を照合してから行う。
- **知らせる相手**：ケンタさん・マサトさん・司令塔。影響する利用者、必要ならCloudflareや該当サービスのサポートへ。復旧見込みが不明なら次の連絡時刻を知らせる。

根拠：`apps/worker/src/index.ts`、`apps/worker/src/services/line-webhook-recovery.ts`、[DEPLOY-GATE](../DEPLOY-GATE.md)。

## 間違った配信を送った

- **0〜5分**：対象アカウント、配信の種類、送信が続いているかを確認し、上の配信停止を行う。ケンタさん・マサトさん・配信担当へ直ちに知らせる。
- **5〜10分**：送信済み・未送信・結果不明を分け、配信履歴を保全する。お詫びを急いで一斉送信すると被害を増やすため、追加送信は判断役が確認するまで止める。
- **10〜15分／止め方**：予約の取消、対象の一斉配信停止、関連シナリオ・リマインダ・自動応答の停止状態を読み直す。手動返信の担当にも中断を伝える。
- **戻し方**：送信済みのメッセージはWorkerを戻しても取り消せない。宛先と内容を修正し、架空データで再確認後、承認された分だけ再開する。結果不明を失敗扱いして再送しない。
- **知らせる相手**：ケンタさん・マサトさん・配信担当。お客さまへの説明・訂正の範囲と文面を判断役が決める。他人の個人情報を送った可能性があれば、次の「個人情報が漏れた」も同時に始める。

根拠：`apps/worker/src/routes/broadcasts.ts`、`apps/worker/src/routes/hq-broadcasts.ts`、`apps/worker/src/services/operation-send-paths.ts`。

## 秘密の値が漏れた

- **0〜5分**：漏れた可能性のある種類、利用環境、公開された場所、発見時刻を記録し、ケンタさん・マサトさんへ連絡する。値そのものを複写して連絡しない。
- **5〜10分**：判断役の下で旧鍵を失効し、不審なセッション・APIキーも止める。攻撃者が触れた可能性のあるPCや連携を切り離し、管理者は安全な端末から操作する。必要な証拠は非公開に保全する。
- **10〜15分／止め方**：上の「鍵を作り直す」で利用箇所を切り替え、旧鍵が使えないことを確認する。鍵が共有されていた環境は両方を調べる。Gitから行を消すだけで完了にしない。
- **戻し方**：新鍵・権限・二段階認証を確認し、使い捨ての検証で動作を確かめて再開する。履歴の書換えやforce pushは実施せず、公開履歴の扱いは司令塔・管理者へ引き継ぐ。B-332の非公開化だけで漏れた鍵が無効になるわけではない。
- **知らせる相手**：ケンタさん・マサトさん・司令塔と対象サービスの管理担当。LINE等の提供元への連絡、お客さまへの通知、個人情報保護委員会への報告の要否は、個人情報へのアクセスの可能性も含めて弁護士・専門家に直ちに確認する。

## 個人情報が漏れた（疑いを含む）

- **0〜5分**：公開・出力・誤送信のどの経路かを確認し、該当する公開範囲・共有リンク・アカウント・自動報告を止める。ケンタさん・マサトさんへ連絡する。証拠はアクセス制限した場所へ保全する。
- **5〜10分**：漏れた情報の種類、対象人数の見込み、期間、外部閲覧の可能性を分けて整理する。実際の氏名・本文・添付はSlack・公開Issue・この手順書へ転記しない。
- **10〜15分／止め方**：第三者の閲覧を止め、漏えい経路で使ったセッション・鍵を失効する。ログ・Slack報告が原因なら、その送信経路と共有範囲も止める。安全な控えを取った後の削除・非公開化は担当と範囲を記録して行う。
- **戻し方**：原因の修正、同じ経路の再点検、権限の見直しを行う。持ち出し済みの情報は、非公開化やDB復元で回収できたとは扱わない。
- **知らせる相手**：ケンタさん・マサトさん・弁護士・専門家。**お客さま本人への通知、LINEへの連絡、個人情報保護委員会への報告の要否・期限・文面は弁護士・専門家に確認する。** 判断依頼を原因調査の終了まで待たない。外部への説明は判断役が一本化する。

報告が必要な場合は速やかな対応が必要。[個人情報保護委員会の公式案内](https://www.ppc.go.jp/personalinfo/legal/leakAction/)を専門家と確認する。報告不要・通知不要を開発者だけで決めない。

## 決済の不具合

- **0〜5分**：二重決済、未反映、金額違い、支払い不能を分け、Stripe側と管理側の状態を確認。ケンタさん・マサトさん・決済担当へ知らせる。カード番号などを取得・転載しない。
- **5〜10分**：Stripeのイベントと内部の受信履歴、金額・通貨・本番／sandboxの別を、担当者だけが見られる画面で照合する。状態が不明なまま再請求・返金をしない。
- **10〜15分／止め方**：誤請求が続く場合は新しい決済の受付を担当者が止める。配信停止だけでStripeの決済や継続課金が止まるとは考えない。Webhookを止めると支払いと管理側の状態がずれるため、停止範囲と未反映分を控える。
- **戻し方**：署名鍵と処理済みのイベントを確認し、重複しない方法で未反映分を照合する。返金・再請求・サブスクリプション変更は金額と対象を人が承認して行う。
- **知らせる相手**：ケンタさん・マサトさん・決済担当、必要ならStripeサポート。影響するお客さまへの説明は実際の請求結果を確認して行う。漏えいの疑いがあれば専門家へ同時相談する。

根拠：`apps/worker/src/routes/stripe.ts`、`apps/worker/src/routes/hq-billing.ts`、`apps/worker/src/routes/booking-payments.ts`、`apps/worker/src/services/stripe-signature.ts`。

## DBを壊した

- **0〜5分**：書込みを増やす機能と配信を止め、マサトさん・ケンタさんへ即時連絡。発生時刻、直前の操作・変更番号を記録する。手当たり次第のSQLや再適用をしない。
- **5〜10分**：対象が本番か検証か、壊れる前の復元点が残るかを担当者が確認。現在の状態も安全に控え、戻す間に失われる予約・友だち・配信記録の範囲を見積もる。R2や外部決済の状態も別に控える。
- **10〜15分／止め方**：本番DBの復元はマサトさんの明示承認と担当指定を得る。対象・復元点・失う期間を2人で照合し、復元中に新しい書込みが入らない状態にする。準備が終わらなければ停止を維持する。
- **戻し方**：下のTime Travelの手順を使う。復元後、友だち・予約・配信履歴・権限を確認する。外部では送信や請求が済んでいるのにDBだけ過去へ戻るため、自動送信・決済の再実行をすぐに再開しない。
- **知らせる相手**：ケンタさん・マサトさん・司令塔。失われた／遅れた予約などの範囲が分かり次第、影響する利用者へ連絡する。漏えいや個人情報の滅失に関する報告・通知の要否は専門家にも確認する。

読むだけの復元点確認：

```sh
pnpm exec wrangler d1 time-travel info <対象DB名> --config <対象設定>
```

下はDBをその時点で上書きする変更操作。承認後に、作業ツリーのクリーン・対象ブランチのSHA一致、ロック、控え、対象DB名と復元点の二者確認を終えてから行う。

```sh
pnpm exec wrangler d1 time-travel restore <対象DB名> --config <対象設定> --bookmark=<確認した復元点>
```

**復元点のあとのDB更新は失われる。** 返ってきた復元前のブックマークも非公開に控える。Time Travelの保持はプランによって無料7日／有料30日であり、契約を確認する。D1の復元ではR2・secret・LINEの送信済みメッセージ・Stripe決済は戻らない。

[既存のDB手順](../migration-runbook.md)は復元方法の参考。ただし2026-08-16時点の件数・未適用番号・過去PRの命令例を今回の対象へ流用しない。適用状況は現物を読み取りで確認する。DB更新とコード配備は別工程にし、どちらも直前にクリーン状態と対象ブランチの一致を再確認する。[Cloudflare公式のTime Travel](https://developers.cloudflare.com/d1/reference/time-travel/)、[配備ゲート](../DEPLOY-GATE.md)も参照する。

## 再開してよいか

停止状態がある場合、原因の修正・同じ操作の確認・未処理と結果不明の照合が済んでから、判断役が再開範囲と時刻を決める。Workerのエラーが減っただけで送信・決済を一括再開しない。作業の承認記録と復旧後の確認を残し、影響した利用者へ次の案内を行う。

## あとで書く記録の型

秘密・個人情報を含む詳細は非公開の事故記録へ。公開IssueやSlackへは、事故ID・状態・担当・次の連絡時刻と、秘密を除いた要約だけを出す。

```text
事故ID：
発見日時（日本時間・+09:00）：
種類／本番・検証の別：
判断役／操作役／記録役（名前と役割）：
分かっている事実／まだ分からないこと：
影響した機能・期間・人数（不明は不明）：
停止した範囲／停止できていない範囲：
時系列（時刻・操作・担当・結果）：
変更前後のVersion ID・Git SHA／承認記録の場所：
鍵の種類と失効・更新の結果（値は書かない）：
DB復元点の保管場所と失われる期間（実値は非公開）：
送信済み・未送信・結果不明／請求済み・未反映の照合：
証拠の非公開保管場所／閲覧を許す役割：
連絡した相手・時刻／専門家への相談と判断：
お客さま・LINE・個人情報保護委員会等への連絡判断と根拠：
再開の承認・時刻・確認結果：
原因／再発防止の担当と期限：
次の連絡時刻／未完了の作業：
```
