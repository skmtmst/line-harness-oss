### S07/S15 残る開発作業

1. S07の結果表は共通認証とアカウントqueryの検査。全経路の資源IDへの認可を証明していない。メソッド・経路ごとに他店の実在する架空IDを用意し、queryを付けずに取得・出力・更新・削除を試験する。owner/admin/staffの役割と「統括／店」の所属範囲を別々に用意し、閲覧のみ・代理ログインも同じ資源で確認する。認可を外す故障対照が失敗し、副作用0まで確認できてからS07を済へ。
2. S15は予約の本人操作14経路を共通のチャネル検査へ絞った。公開メニュー/設定/通常の空き照会4経路は本人情報を返す操作とは分ける。フォームの回答/添付、イベント、ウェビナー、会員・ペット等も含む全入口を一覧化し、別人/別店/期限切れ/欠落を実在する架空データで確認する。既存のフォーム・本人予約変更・キャンセル待ち等の試験再実行だけで全LIFF合格にしない。
3. 旧スコア5経路は所属のない共通表を触るため、同じ問題を扱うbehaviorfixの停止処理と同じ2行をこの枝にも含めた（同側は確認時未コミット）。GET一覧/詳細・POST・PUT・DELETEは410、D1へ到達しない。5つの役割/統括/閲覧のみ文脈×5経路で試験。現行画面はアカウントを指定する`/api/action-scores/rules`を利用し、友だちのスコア参照は維持。司令塔はbehaviorfix統合時にこの同じ停止を保持する。

[LINE公式](https://developers.line.biz/en/reference/line-login/#verify-id-token)に従い、検証APIの`client_id`は期待するチャネルIDを渡す。JWT自身が名乗るaudから検証先を追加しない。

### S21 反映前に必要なこと

専用secret名は`GOOGLE_CALENDAR_CREDENTIAL_ENCRYPTION_KEY`。値は書かない。環境ごとに異なる32バイト鍵をbase64形式で安全に登録する。LINE用鍵の名前を流用せず、別のWorker secretとして管理する。既存のTEXT列へ`v1.`形式の暗号文を格納するため、表や列の追加は不要。アクセストークンはGoogleクライアントを作る直前に復号し、APIの応答には含めない。

既存平文をそのまま動かす切替は設けていない。このコードだけ先に配備すると既存接続は停止する。オーナーは、旧認証情報の失効・新しい接続の登録・既存予約の接続参照・旧行と控えの扱いを含む移行計画を別途承認する。今回DBの中身は照会していない。既存予約が旧connectionを参照したまま、接続を先に削除してはいけない。安全な移行が完了するまで点検表S21は未。
