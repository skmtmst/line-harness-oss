# 鍵が漏れたときの入れ替えと練習（B-351/13）

対象：運営担当者。これは手順書で、実行の承認ではない。本番の鍵・DBはこの作業では変更しない。
鍵の値はターミナルの引数、履歴、文書、Slack、スクリーンショットに入れない。

## 最初に決めること

事故の担当者と確認者を1人ずつ決める。気づいた日時、疑われるサービス、鍵の名前、最後に安全だった版だけを事故記録へ残す。
[事故対応の時間割](INCIDENT-RUNBOOK.md)に従い、影響する送信・入口を止める。停止する範囲と承認を記録する。
鍵が漏れたかもしれない場合は「旧鍵をしばらく使えるままにする」ことを原則にしない。利用停止による影響を確認者と決める。

| 種類 | 入れ替える順序 | 入れ替え後に必ず確かめること |
| --- | --- | --- |
| LINE・Slack・Google・Stripe等のサービスの鍵 | 相手サービスの正規画面で旧鍵を無効にする→新しい鍵を発行→対象環境のWorker secretに入力→必要な配備 | 新鍵の架空データの操作が成功、旧鍵は失敗。通知・予約・Webhookの受信も確認 |
| API_KEY・取得URLの署名鍵 | 入口と送信を止める→新鍵をsecretへ→旧署名・旧キーを拒否→必要な本人へ再ログインと取り直しを案内 | 古い添付の中身を返さず、LIFFの本人確認で取り直せる。不要なLEGACY_API_KEYを残さない |
| Webhook署名鍵 | 相手と時刻を合わせる→新鍵に変更→短い併用が必要なら終了時刻と対象を明記 | 新署名成功、旧署名/改ざん/時刻外は拒否。併用終了を忘れない |
| 保存内容の暗号化鍵（LINE・Google Calendar・TOTPなど） | 安全な復元点と既存件数を確認→対応する旧鍵と新鍵を安全な場所に保持→移行を承認された担当者が行う→全件復号を値なしの件数で確認→旧鍵を失効 | **secretを上書きするだけでは既存分が読めなくなる**。旧鍵対応のない実装では移行手順を先に作り、止めたまま専門担当へ渡す |

## 検証で1回まねする（実サービスの鍵は使わない）

1. 司令塔が検証用の架空アカウント・送信先・保管領域を確認し、実送信とcronが無効であることを確認する。
2. 最初はローカルの `key-rotation-drill.test.ts` を実行する。毎回メモリ内で新旧の架空鍵を作り、秘密は出力しない。
3. 取得URLについて、新鍵の署名が成功・旧鍵/別の目的/期限切れが失敗することを記録する。
4. AES-GCMについて、旧鍵で暗号化した架空の文字を新鍵へ移し、全文を表示せず一致だけ確認。旧鍵だけの暗号文を新鍵で読めないことも確認する。
5. 検証Workerでの実地練習は司令塔が別途実施する。専用の試験鍵のみをsecret入力欄から登録し、架空データを使う。通知は模擬。終了時に試験secret・試験データを正規手順で片付ける。
6. 記録は日時・担当2人・対象環境・版・成功/失敗・旧鍵拒否だけ。実地をしていない段階は「未実施」と書く。
