# LINE Webhook の顧客間分離（2026-10-19）

依頼者: Masato。「第三者へ広く提供するものです、ちゃんと混ざらないように修正」。この依頼により、既存の共通URLを維持するだけの運用から、新規接続はチャネル別URLへ変更する。旧要件の「アカウントごとに変えない」に対する変更記録。画面の形・手順・Pencilの変更は含めない。

## 受入条件

- 新規自動接続の登録URLは `/webhook/<Messaging APIチャネルID>`。URLは公開識別子であり認証情報ではない。
- URLで特定したアカウントの秘密値により、未加工の本文のLINE署名を検証する。他アカウントの鍵・環境変数の既定鍵へフォールバックしない。
- 旧 `/webhook` は移行期間中維持する。署名が複数登録に一致したら先頭を選ばず処理しない。
- 受信履歴・取消のキーは署名から解決したDBアカウントID。送信者が自分の秘密値で任意の `destination` を署名しても他顧客の取消・受信履歴に影響しない。
- 旧形式の受信済み履歴も、所属アカウントとメッセージIDで取消・重複抑止する。
- 別顧客が既存イベントIDを再利用しても、先行顧客の受信記録を上書きしない。
- 手動登録・鍵更新では、IDとシークレットで発行したトークンと指定トークンの公式アカウントが一致することをLINEで確認してから保存する。
- 登録済みチャネルへの新規自動接続は、LINE側の設定変更前に拒否する。
- 秘密値・通知本文をログに追加しない。DB構造変更・本番配備は行わない。

## 移行と範囲

既存接続先を一括で書き換えない。旧URLと新URLは同じ認証後の処理を通す。既存アカウントの接続診断は旧URLも正常として扱い、新しい期待URLを返す。新規追加画面の初期コピー欄は既存デザインの共通URLを維持し、その後の自動接続でチャネル別URLを登録する。

旧形式の「取消が先着し、元メッセージが未到着」の記録には所属アカウントがない。旧キー・メッセージID・署名で解決した友だちのLINEユーザーIDが一致したときだけ、今回の受信本文を表示しないための読み取りに使用する。他顧客の履歴変更や、旧記録の所有権移動には使わない。既存の取消済み受信履歴と、新版で先着した取消も維持する。

また `friends.line_user_id` に全体一意制約が残っている。同一プロバイダーの同じLINE利用者を複数アカウントに登録するケースは、他店へ混ぜず処理を止める現行仕様を維持する。広範なSaaS公開の前に、友だち識別の複合一意化と全関連APIの確認・DB移行の承認が必要。本修正だけでサービス全体の第三者提供準備が完了したとはしない。

## 検証

実際のHMAC署名とSQLiteを使った顧客A/BのURL取り違え、宛先偽装による取消、同じメッセージID、取消の先着、旧履歴の再送、重複秘密値、停止・廃止・未知アカウント、他顧客のイベントIDの試験を追加する。通常受信・友だち追加・取消・接続・公開境界の既存試験も実行する。

### 実行結果

- 取り込み済み開発基点: `0a285867256a6ab605aa3c4908dcab695e2dff2b`。
- Worker関連32ファイル566件、DB関連4ファイル16件、追加の登録拒否試験を含むアカウントAPI84件に合格。型検査・Workerビルドに合格。
- 旧Webhook実装を一時的な試験用ファイルへ取り出し、Bの正しい署名＋Aのdestination＋取消イベントの試験を実行すると、Aの本文が消えることで失敗することを確認。修正版では同じ試験に合格。これはローカル再現であり、本番での被害発生を確認したものではない。
- 実際のLINEアカウントを使った検証環境のA/B端末試験は未実施。自動試験の合格と区別する。
