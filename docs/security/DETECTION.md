# 漏れたかもしれない、と気づくために

2026-10-16 / B-343。目的は「絶対に漏れない」と思うことではなく、変化に気づいて被害を止めること。警告は事故の確定ではない。警告がないことも安全の証明ではない。

## 誰が、いつ見るか

ケンタが一次確認、マサトが停止・復旧の判断、司令塔が調査と修正を担当する。休みの交代担当と電話は非公開の連絡帳へ置く。以下の時間は社内の対応目標で、法律の期限ではない。

- 自動集計は既存の5分ごとの定期確認から実行し、直近15分を数える。基準以上で運用状態の「要対応」用APIとSlackの `#line-harness-エラー報告` へ知らせる。画面への接続はClaude担当。
- 通知を見た人は15分以内にケンタ・マサトへ連絡し、担当者が受領する。漏れの疑い・知らない管理者・知らない鍵の更新は夜間でも即時連絡。15分返事がなければ非公開の電話連絡へ切り替える。
- 毎営業日の始めに、運用状態とSlackを両方確認する。監視の最終完了が15分以上古い／未取得／失敗なら「異常なし」と読まず、監視の故障としてマサトへ連絡する。
- 不審な操作は1時間以内に一次判断し、停止が必要なら[事故対応](INCIDENT-RUNBOOK.md)へ。調査中は1時間ごとに状況と次の連絡時刻を共有する。

**現状はコードを準備した段階。691の適用・配備・通知先の確認・画面接続はまだ行っていない。通知が実運用で動いているとは扱わない。**

## 見張ることと見る場所

初期基準は少人数の運用向けのおすすめ。平常時の件数を見てオーナーが調整する。基準の変更で過去の事故記録を消さない。以下の「機械」は今回作ったもの、「人」は外部設定・人の確認が必要なもの。

| 見張ること | 方法・初期基準（直近15分） | どこで見るか・注意 |
| --- | --- | --- |
| ログイン失敗の急増 | 機械：20回以上 | 認証監査の失敗。本人不明は店を推測せず運営だけへ表示 |
| 知らない場所からのログイン | 人：本人に覚えがなければ即連絡 | ログイン履歴・Cloudflareのログ。今回の機械には位置情報の比較がない。VPNや移動でも変わる |
| 代理ログイン・個人情報の開示 | 機械：1回以上 | 運営の監査記録。閲覧だけの代理ログインも運営側だけで確認。店には隠れた記録を見せない |
| APIの回数の急増 | 機械：監査に残る変更操作1,000回以上。人：全HTTP要求の増加 | 運用状態・Slack・Cloudflareの要求数。GET全体や記録しない操作は機械の分母に入らない |
| CSV・一括の書き出し | 機械：成功10操作以上、または既知の出力件数合計10,000件以上 | 出力監査。件数不明の出力を0件の証明にしない。生成と取得など別操作の重複はあり得る |
| 権限・所属の変更 | 機械：成功1操作以上 | スタッフ更新の監査。氏名変更など同じ入口の変更も保守的に知らせる |
| 鍵・二段階認証の作り直し | 機械：記録対象1操作以上 | API鍵の作り直し・失効、MFA再登録等。Cloudflare・Google等の鍵の変更は各サービスで人が確認 |
| 管理者の追加・招待 | 機械：スタッフ追加1操作以上 | 役割が記録から判別できない追加も通知し、人が管理者かを確認。運営メンバーの追加は運営監査も毎日確認 |
| 夜中の大量操作 | 機械：日本時間0〜6時の業務監査100件以上 | UTC・時差付き時刻・従来の日本時間の記録をそろえて計算。夜間の正当な仕事も確認対象 |
| Webhookの署名の失敗 | 人：急増、または継続した失敗を確認 | Cloudflareのログ。LINEは署名不正にもHTTP 200を返すため、HTTPの失敗率だけで判断しない。今回の集計には入っていない |
| 公開リポジトリへの秘密の混入 | 人：GitHubのSecret scanningと変更時のGitleaks | GitHub Security・検査結果。GitHub側の監視有効化はオーナー。検出したら値を貼らず鍵の種類と場所だけ連絡 |
| 内部の人の持ち出し | 機械の出力・夜間・権限変更＋人の確認 | 少量ずつの取得、画面撮影、共有端末は件数だけで見つからない。退職・権限変更時も点検 |

通知には固定の種類、件数、検知時刻、事故IDだけを載せる。氏名・メール・友だちID・店名・本文・IP・URL・クエリ・鍵は載せない。詳細の証拠は権限を限った事故記録へ置く。

## 設定と故障の見つけ方

`SECURITY_MONITOR_THRESHOLDS` は固定の項目名に対する正の整数のJSON。項目と初期値、APIは[画面との契約](SECURITY-MONITOR-CONTRACT.md)。通常変数でよく、秘密は入れない。未指定は初期値、不正・0・未知の項目は初期値へ戻し設定不正をAPIへ出す。オーナーが変更し、変更理由と時刻を非公開の運用記録へ残す。本作業では環境設定を変更しない。

Slack失敗は成功にせず5分後以降に再送。同じ未解決の異常はまとめ、件数が落ち着いても人が確認して解消するまで残す。再送では重複防止IDを使うが、通信切断後の成否不明時に完全な一度限りを保証するものではない。Slack未設定はAPIで「未設定」、集計の失敗・未取得・15分以上の停止も別に示す。監視そのものが止まるとSlackも止まり得るため、Cloudflare側の実行失敗・最終実行時刻も別に見張る。

既存Cronの配備設定は変更しない。[Cloudflare公式の定期実行](https://developers.cloudflare.com/workers/configuration/cron-triggers/)と対象Workerの設定をオーナーが照合し、架空データだけの検証で、しきい値超え→要対応→Slack→受領→解消→再発を練習する。

## 「わな」の値の案（検証だけ）

本物の権限を持たない見本の鍵、実在の友だちと接続しない見本の記録を、使い捨ての検証環境だけへ置く案。使われるはずのない値へのアクセスを見つけたら、固定の「見本への接触」として必ず通知する。値自体は通知しない。実顧客・LINE送信・本物の資格情報を使わない。

今回は実運用へわなや有効な鍵を追加しない。採用前に、オーナーが配置場所と観測経路を決め、架空の接触1回で通知が出ること、ログやSlackへ見本の値も出ないこと、productionでは登録・有効化できないことを検証する。通常の失敗通知に紛れる案、実際にログインできる鍵を作る案は採用しない。現実の見本値が使われたことを検知できた、とはまだ報告しない。
