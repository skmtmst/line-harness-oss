# V6 2 受信箱 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「2 受信箱」

## 0. 結論と採点

V6の3カラム構成を採用する。会話、顧客情報、次に行うことを同時に見られ、LINEとメール、担当者別未読、テンプレート、内部メモ、保存した検索まで同じ作業面で扱える。運用者が「探す→判断する→返信する→引き継ぐ」を短い移動で完了でき、UI設計はLステップ・Liny相当以上である。

現行にもLINE・メールの受信、個人別未読、担当変更、返信、テンプレート、顧客情報、予約・EC情報、送信冪等性がある。一方、保存した検索はV6と接続されておらず、保留状態、追記型メモ、Webhook重複排除、送信競合、送信失敗台帳、LINE取消への追従、会話単位の閲覧権限が不足する。見た目を載せ替えるだけでは100点にならない。

| 評価軸 | 現在 | 実装後 |
|---|---:|---:|
| V6 UI・UX | 96 | 99 |
| Lステップ・Liny競争力 | 91 | 100 |
| 現行実装 | 78 | 98 |
| データ安全性 | 62 | 98 |
| 実現可能性 | 94 | 98 |
| 要件確定度 | 97 | 99 |

実現不能として除外するのは、LINE利用者が送信済みメッセージを読んだかの取得である。運用者が会話を開いたこと、LINE上で既読にしたこと、送信成功は別々に記録し、利用者既読とは表示しない。

## 2. 達成すること

> 運用者が、担当する顧客の新着を見落とさず、過去の文脈と顧客情報を確認し、安全に1対1返信して、次の担当者へ履歴付きで引き継げる。

- LINEとメールを1つの受信箱で扱う
- 自分の未読と組織全体の未対応を区別する
- 検索・絞り込み・保存した検索から会話を再発見する
- 担当者、対応状況、内部メモを履歴付きで更新する
- テンプレートと変数を使って返信する
- 同時操作、重複Webhook、送信失敗で二重返信を起こさない
- 取消済みメッセージと添付データを適切に消す
- 権限のない会話、個人情報、テンプレートをサーバ側で返さない
- 古い会話を件数上限で失わず、ページ送りで取得する

## 3. 用語を固定する

| 用語 | 意味 |
|---|---|
| チャネル | LINEまたはメール |
| 対応状況 | 未対応、対応中、保留、対応済みの固定4状態 |
| 対応マーク | 友だち属性として自由設定できる印。対応状況とは別物 |
| 自分の未読 | ログイン中の担当者が、その会話の最新メッセージまで見たか |
| 組織の未対応 | 誰も対応済みにしていない会話 |
| 送信成功 | LINEまたはメール事業者が送信要求を受理した状態。相手の既読ではない |
| 内部メモ | 顧客へ送らず、作成者と日時を残す追記型の記録 |

V6画面の「対応マーク」は、実装時に「対応状況」へ変更する。友だち属性の対応マークは右パネル内の別項目として表示する。V6自体はこの要件定義段階では変更しない。

## 4. 画面とルート

| 画面 | ルート |
|---|---|
| 受信箱 | `/chats` |
| 会話を指定して開く | `/chats?channel={line|email}&conversation={id}` |
| 保存した検索を開く | `/chats?savedView={id}` |

V6の2-2〜2-17は別ページにせず、受信箱内のオーバーレイ、プルダウン、右パネル、入力状態として実装する。URLに残すのは選択中の会話と保存した検索だけとし、再読込・共有後も同じ対象へ戻れるようにする。

## 5. 画面要件

### 5-1. 受信箱

上部KPI:

- 要返信
- 最長待ち時間
- 自分担当
- 今日受信
- LINE・メール内訳
- 期限超過

会話一覧:

- 顧客名、アイコン、チャネル
- 最新メッセージの安全な抜粋
- 受信日時、待ち時間
- 自分の未読
- 担当者
- 対応状況
- 重要印

検索・絞り込み:

- 顧客名、本文、電話、メール
- チャネル
- 担当者
- 対応状況
- 未読
- メッセージ種別
- 受信期間
- 待ち時間
- 新しい順、古い順、待ち時間が長い順

検索、件数、ページ送りはサーバ側で同じ条件を使う。読み込んだ先頭100件だけをブラウザで絞り込まない。

### 5-2. 会話

- 送受信方向、担当者、日時、本文、添付、送信元を表示
- 返信、内部メモ、システム履歴を見た目で区別
- 引用返信は引用元を表示し、元メッセージへ移動可能にする
- 取消済みは本文を消し「送信者が取り消しました」と表示
- 送信中、成功、失敗、結果不明、再試行中を区別
- 1,000件で切らず、古い履歴をカーソルで追加取得
- 送信者名と手動・自動・テンプレートを残す

LINE公式アカウント管理画面から直接送った内容はWebhook/APIで取得できないため、完全な履歴を保証しない。運用ではHarnessから送信する。

### 5-3. 返信入力

- テキスト
- 絵文字
- 画像、動画、音声、ファイル
- テンプレート
- 変数差し込み
- 引用返信
- 送信予約
- 内部メモへの切替

送信前:

- 送信先、チャネル、アカウントを固定表示
- 変数の未解決をエラーにする
- 添付形式・容量を検査
- 別担当者が返信中なら警告し、送信直前に版を再確認

送信後:

- 入力欄をすぐ消さず、送信要求を受理してから消す
- 結果不明時に同じ本文を自動再送しない
- 再試行は同じ冪等キーを使う
- 手動の1対1返信は`source=manual`を記録する
- LINE Harness Proxyを通す場合は`X-Line-Harness-Source: manual`を必ず付ける

### 5-4. テンプレート選択

- フォルダ、予約、最近使ったもの、お気に入り
- 名前・本文検索
- 送信前プレビュー
- 変数の解決結果
- 権限のあるフォルダだけ表示
- 削除・非公開・別アカウントの参照を選べない

### 5-5. 顧客情報パネル

- 基本情報
- タグ、友だち情報、対応マーク
- 担当者
- 予約、回答、購入、成果、マイル
- 次に行うこと
- 表示項目の個人設定

パネル非表示でも会話幅を広げ、主要操作を隠さない。表示項目の設定は個人単位で保存する。閲覧権限のない項目は空欄ではなく項目自体を返さない。

### 5-6. 担当者・対応状況

- 担当者なし、自分、ほかの担当者へ変更
- 変更前後、変更者、日時、理由を履歴化
- 対応状況は未対応、対応中、保留、対応済み
- 顧客から新着が来たとき、対応済み・保留は原則未対応へ戻す
- 例外ルールはアカウント設定で明示し、暗黙に戻さない

### 5-7. 内部メモ

- 顧客へ送られないことを入力欄に常設
- 作成者、作成日時、編集履歴を表示
- 原則追記型で、上書きしない
- 誤記訂正は元記録を残して訂正版を追加
- メンション通知は将来拡張とし、初期版では担当者変更とメモ保存だけを行う

### 5-8. 保存した検索

- 現在の全条件、並び順、表示列を保存
- 名前は必須、40文字以内
- 同じ所有者内で同名を禁止
- 個人用と共有を分ける
- 共有の作成・変更は権限が必要
- 保存時の件数ではなく、開いた時点の最新件数を表示
- 未入力、重複名、権限不足、削除済み条件を個別表示
- 条件の一部が使えなくなっても全削除せず、無効項目を示して修正可能にする
- 保存件数の上限は04 §9-1（所有者・範囲・プラン単位で50件）に従う

## 6. データ要件

既存の`chats`、`messages_log`、`support_email_threads`、`support_email_messages`、`inbox_staff_reads`、`saved_searches`、`outbound_send_requests`を移行元として使う。LINEとメールを1テーブルへ破壊的に統合せず、共通の会話読取サービスで同じ形に射影する。

### 6-1. 既存へ追加する項目

`chats`と`support_email_threads`:

- `status`: `unread | in_progress | on_hold | resolved`
- `revision`: 同時更新検査用の連番
- `last_customer_message_at`
- `last_operator_message_at`
- `next_response_due_at`

`messages_log`:

- `line_account_id`の受信時スナップショット
- `line_message_id`
- `webhook_event_id`
- `event_timestamp`
- `quoted_message_id`
- `mark_as_read_token`
- `unsent_at`
- `content_deleted_at`

`outbound_send_requests`:

- `status`: `in_progress | succeeded | failed | unknown`
- `attempt_count`
- `last_attempt_at`
- `next_retry_at`
- `upstream_request_id`
- `error_code`
- `error_summary`

### 6-2. 追加する台帳

`inbox_conversation_events`:

- 会話ID、チャネル
- 種別: assignment/status/note/read/send/conflict/unsend
- 変更前後
- 実行者
- 発生日時
- 相関ID

`inbox_notes`:

- 会話ID、チャネル
- 本文
- 作成者、作成日時
- 訂正対象のメモID
- 削除ではなく無効化の理由

`line_webhook_receipts`:

- LINEアカウントID
- `webhookEventId`
- イベント時刻
- 受付、処理中、成功、恒久失敗
- 再配信フラグ
- 処理相関ID

`inbox_reply_leases`:

- 会話ID、チャネル
- 担当者
- 取得日時、期限
- 取得時の会話revision

`inbox_staff_scopes`:

- 担当者
- LINEアカウント
- 範囲: all / assigned / saved_view
- 保存検索または条件
- 個人情報、履歴、送信、テンプレートフォルダの権限

### 6-3. 保存検索の既存活用

既存`saved_searches.scope='chats'`を使い、条件を次の版付きJSONへ拡張する。

```json
{
  "version": 1,
  "query": "",
  "channels": ["line", "email"],
  "statuses": ["unread", "in_progress", "on_hold"],
  "assignees": ["me"],
  "unread": "mine",
  "messageTypes": ["text", "image", "file"],
  "receivedFrom": null,
  "receivedTo": null,
  "sort": "waiting_desc"
}
```

友だち検索用条件と混同しない。`scope`ごとに検証器と権限を分ける。受信箱の保存検索APIを`/tags`権限へ誤って結び付けない。

## 7. 受信・履歴処理

1. Webhook署名を検証する
2. `(line_account_id, webhookEventId)`を一意キーに受付を確保する
3. 重複なら成功応答し、本文・自動処理を再実行しない
4. LINE event timestampで並び順を決め、受信順だけを信用しない
5. 添付は取得可能な間にR2へ保存し、ハッシュ・MIME・容量を記録する
6. メッセージ、会話更新、イベント台帳を同じ整合単位で保存する
7. 自動応答は受付成功後に別ジョブで冪等実行する
8. 取消イベントでは管理画面の本文を非表示にし、保存済み添付を削除する
9. 監査用にメッセージID、取消日時、処理結果だけを残す
10. 一時失敗と恒久失敗を分け、無限再試行しない

## 8. 既読の扱い

3つを別々に持つ。

1. `inbox_staff_reads`: その担当者が管理画面でどこまで見たか
2. LINEのmark-as-read: 公式アカウント側で会話を既読にしたか
3. 利用者既読: 取得不能のため持たない

会話を開いたら個人別カーソルを更新する。受信イベントに`markAsReadToken`がある場合は、LINEの既読APIを冪等実行する。LINE API失敗時も個人別カーソルを巻き戻さず、「LINE側の既読反映に失敗」と運用状態へ残す。

## 9. 返信処理と同時操作

1. 会話閲覧・送信権限をサーバ側で再確認
2. 短時間の返信リースを取得
3. 会話revisionと画面読込時revisionを比較
4. 競合時は最新メッセージと他担当者の状態を表示し、再確認を要求
5. 送信要求を冪等キー付きで保存
6. 手動送信元を記録
7. LINE送信時は対応APIで`X-Line-Retry-Key`を使用
8. 事業者の応答とリクエストIDを保存
9. 成功時だけ会話、担当、対応状況を更新
10. 結果不明時は自動的に新しいキーで再送せず、照合・同じキーでの再試行へ回す

送信予約は実行時にアカウント、友だち状態、ブロック、権限、テンプレート版を再確認する。予約作成者が退職しても、予約を自動で別担当者名義にしない。

## 10. API要件

| 方法 | API | 用途 |
|---|---|---|
| GET | `/api/inbox/conversations` | LINE・メール共通の検索、絞り込み、カーソル取得 |
| GET | `/api/inbox/conversations/{channel}/{id}` | 会話、顧客情報、履歴 |
| GET | `/api/inbox/conversations/{channel}/{id}/messages` | 古い履歴のカーソル取得 |
| POST | `/api/inbox/conversations/{channel}/{id}/read` | 個人別既読、LINE既読要求 |
| POST | `/api/inbox/conversations/{channel}/{id}/reply-lease` | 返信中の取得・延長 |
| POST | `/api/inbox/conversations/{channel}/{id}/reply` | 手動返信、予約返信 |
| PATCH | `/api/inbox/conversations/{channel}/{id}/assignee` | 担当変更 |
| PATCH | `/api/inbox/conversations/{channel}/{id}/status` | 対応状況変更 |
| POST | `/api/inbox/conversations/{channel}/{id}/notes` | 内部メモ追加 |
| GET | `/api/inbox/conversations/{channel}/{id}/events` | 操作履歴 |
| GET/POST | `/api/inbox/saved-views` | 保存した検索一覧・作成 |
| PATCH/DELETE | `/api/inbox/saved-views/{id}` | 保存した検索変更・削除 |

共通レスポンス:

- `conversationId`と`channel`の複合識別子
- `revision`
- `permissions`
- `nextCursor`
- 集計と一覧に適用した正規化済み条件
- エラーコード、再試行可否、相関ID

## 11. 権限

| 操作 | 必要な判定 |
|---|---|
| 一覧を見る | 組織、LINEアカウント、会話範囲 |
| 会話履歴を見る | 会話範囲、履歴閲覧権限 |
| 個人情報を見る | 個人情報項目権限 |
| 返信する | 会話範囲、送信権限、チャネル権限 |
| 担当を変える | 担当変更権限、変更先の在籍・範囲 |
| 対応状況を変える | 更新権限 |
| 内部メモを見る・書く | メモ権限 |
| テンプレートを使う | フォルダ権限、送信権限 |
| 保存検索を共有する | 共有検索管理権限 |

全判定をAPIで行う。画面でボタンを隠すだけにしない。範囲外IDをURLへ直接指定した場合も404相当とし、存在の有無を漏らさない。

Linyとの差を埋めるため、担当者の範囲を「すべて」「自分担当」「許可された保存検索」に分ける。テンプレートフォルダ、個人情報、会話履歴も別権限にする。

## 12. 状態要件

必須状態:

- 初回読込
- 追加読込
- 会話なし
- 検索結果0件
- 通信エラー
- 部分エラー（LINEだけ、メールだけ）
- 権限不足
- 会話が範囲外へ変更
- 友だちブロック・削除
- 送信中
- 送信失敗
- 送信結果不明
- 他担当者が返信中
- revision競合
- 添付取得期限切れ
- 取消済み
- 保存検索の未入力、重複、削除済み条件
- LINE側既読反映失敗

エラーは理由、影響範囲、直し方、再試行可否を表示する。画面全体を白くせず、送信失敗でも入力内容を保持する。

## 13. Lステップ・Linyとの差

### V6が上回る点

- LINEとメールを同じ作業面で扱う
- 顧客情報、予約、EC、マイル、次の行動を右パネルで接続
- 個人別未読と組織の対応状況を分離
- 保存した検索の作成・入力エラー・重複名まで設計済み
- 次に行うことを会話から直接実行できる

### 追加して同等以上にする点

- 個別返信の送信予約
- 引用返信
- 重要メッセージ
- 担当者ごとの会話範囲
- 個人情報・履歴・機能・テンプレートフォルダの細かい権限
- 送信者アイコン・表示名の運用設定
- 対応状況の自由追加ではなく、固定状態＋必要なら別の対応マーク

### 独自に強化する点

- Webhook重複・順序逆転への耐性
- LINE取消時の保存内容削除
- 二重返信防止のリースとrevision
- 送信結果不明を成功・失敗から分離
- 担当・状態・メモ・送信の追記型監査履歴

## 14. 除外

- LINE利用者の個人単位の既読取得
- LINE公式アカウント管理画面から送った全メッセージの自動取り込み
- 送信済みLINEメッセージの運用者側からの取消
- グループ・複数人トーク対応

AIの要約・返信案は将来追加できるが、受信箱の安全性と履歴が完成する前には入れない。

## 15. 既存データ移行

1. LINE会話、メール会話、メッセージ、既読、担当、メモ、保存検索を件数照合
2. 既存`notes`を作成者不明の「移行前メモ」として`inbox_notes`へ1件ずつ追加
3. `status`を未対応、対応中、対応済みに変換し、保留を追加
4. `saved_searches.scope='chats'`の既存内容を版付き条件へ変換。変換不能は削除せず要修正にする
5. 過去メッセージへ分かる範囲でLINEアカウントと送信元を補完
6. 共通読取APIを旧画面と並行検証
7. 組織、アカウント、担当者ごとの件数・未読・最新日時を照合
8. 新画面を一部組織へ段階公開
9. 戻し手順を確認後に旧読取経路を停止

既存のLINE・メールテーブルを削除しない。新しい受信箱の邪魔になるのはデータではなく、意味の違う状態と権限を同じものとして扱うことである。互換層で読み、段階移行する。

## 18. 公式仕様の根拠

- LINE Messaging APIはWebhook再配信で同じイベントが複数回来る可能性があり、`webhookEventId`による重複排除とtimestampによる順序判断を案内している
- 取消イベント受信時は、自社管理画面と保存先から対象内容を削除することが案内されている
- 受信添付はLINE側で保存期間が保証されないため、Webhook後に速やかに取得する
- `markAsReadToken`を使った既読APIはあるが、これは公式アカウント側のチャットを既読にする機能であり、利用者が送信済みメッセージを読んだ証拠ではない
- `X-Line-Retry-Key`は対応APIの重複実行防止に使うが、配信成功そのものは保証しない
- Linyは担当者ごとに友だち範囲、個人情報、トーク履歴、機能、テンプレートフォルダを制限できる
- Lステップは個別トークで予約送信、対応マーク、重要メッセージ、送信者表示を提供している
