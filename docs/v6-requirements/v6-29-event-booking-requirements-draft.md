# V6 29 イベント予約 要件定義（実装照合版・下書き）

更新日: 2026-08-26
対象: V6 29-x、現行 `/events`・`/events/bookings`、イベントDB/API、Lステップのイベント予約

## 0. 結論と採点

V6は、イベント作成、申込者、満席、キャンセル待ち、運用アクションを1つの流れにしており、Lステップと同等以上を狙える。特に申込者一覧で友だち情報、初回参加、リマインダ、個別トークを並べる設計は、受付後の運用まで一画面で進められる。

現行にもイベント、複数日時枠、承認制、公開範囲、締切、取消、リマインダ、キャンセル待ち、冪等キーがある。新規構築ではない。ただしキャンセル待ちの自動繰上げ、複数人申込の定員消費、申込者向け配信、CSV、公開版、開催変更時の影響管理が不足する。V6の「空きが出たら順番に案内し、24時間返答がなければ次へ」は、単なる通知ではなく期限付き座席保留として実装する。

| 評価軸 | 現在 | 要件反映後 | 判断 |
|---|---:|---:|---|
| V6 UI/UX | 98 | 100 | 作成、申込、待ち、LINE運用が一続き |
| Lステップ対抗力 | 98 | 100 | Lステップ相当の申込管理に期限付き繰上げを加える |
| 現行実装完成度 | 82 | 98 | 中核はあるが待ち繰上げと申込者運用が未配線 |
| データ安全性 | 77 | 99 | 冪等は良い。定員確保、版、履歴、組織境界を強化 |
| 実現可能性 | 98 | 99 | 既存DB/APIを拡張できる |
| 要件確定度 | 97 | 99 | 決済を外し、席・待ち・通知を固定すれば実装可能 |

完全に不可能な画面はない。除外するのは、申込者の同意なしの自動予約確定、満席時の無制限な過剰受付、公開済み内容の破壊的上書き、開催日時の無通知変更、送信済みLINEの取消、オンライン会場URLの一般公開、外部決済契約なしの有料決済である。

## 1. 監査範囲と証拠制限

### 1-1. V6実Node

| Node ID | 画面 |
|---|---|
| `ugP5y` | ★ V6 29-1 イベント予約 |
| `MKrPY` | ★ V6 29-1-A イベントをつくる |
| `i5SN2j` | ★ V6 29-1-B 申込者の一覧 |
| `k5m5Bc` | ★ V6 29-1-C イベント予約・一覧の状態 |

一覧、申込者、状態画面は1920×1080、作成画面は1920×1136。Pencilからテキスト、構造、clip検査を取得した。

画像出力はノイズ化しており、ピクセル一致の証拠には使えない。clip検査では、閉じた共通メニュー、一覧の非表示行、入力値の一部が検出された。意図的なclipかは画像出力復旧後、同じ状態・同じ横幅の実装画像と比較して確定する。対象V6は同日のV5修正を含めて複製された正本で、本監査中の追加編集はしていない。

### 1-2. 現行資産

- `events`: 名称、会場、説明、画像、1人の申込上限、承認制、取消期限、リマインダ、公開、公開対象タグ、キャンセル待ち、申込締切
- `event_slots`: 開始、終了、定員、公開状態
- `event_bookings`: 枠、友だち、状態、判断、取消、出席・無断
- `event_waitlist`: 枠別の待ち順、案内、予約化、取消
- `event_booking_idempotency_keys`: 多重申込防止
- 申込作成時の事前定員確認と、競合後の再確認
- LINEからの申込履歴、本人取消
- 管理者の承認、拒否、取消、出席、無断
- 申込時のマイル、リマインダ、通知、トリガー登録

イベント基盤は新規構築ではない。現行の `events + event_slots` を、イベント本体と開催回として明文化して拡張する。

## 2. Lステップとの差

Lステップは、特定日時のイベント受付、詳細説明、承認、申込上限、本人の変更・取消、CSVを案内している。V6はこれを満たし、キャンセル待ちの順位・期限付き案内、申込者の友だち情報、初回参加、個別トーク、共通アクションまで一体にする。根拠はLステップ公式の[イベント予約](https://linestep.jp/lp/01/features30.html)と[機能一覧](https://linestep.jp/lp/01/features_top.html)。

| 項目 | Lステップ基準 | V6要件 |
|---|---|---|
| 開催日時 | 特定日時、複数日程 | イベント本体＋開催回 |
| 定員 | 日程別定員 | 参加人数を含む原子的定員確保 |
| 承認 | 承認制 | 自動確定・承認制・期限切れ |
| 変更・取消 | 本人操作 | 締切、変更履歴、再通知 |
| CSV | 申込情報出力 | 権限・監査つき出力 |
| 待ち | 任意 | 順位、席保留、回答期限、次候補 |
| 受付後運用 | 配信と連携 | 友だち文脈、個別・一斉送信、出席、成果 |

## 3. この機能で達成すること

運用者が、開催内容と日時、定員、申込条件、通知を設定して公開し、申込・待ち・出席まで安全に管理する。

1. イベント内容を下書きする
2. 1つ以上の開催回を設定する
3. 定員、申込期間、取消期限、承認、待ちを決める
4. 受付・リマインダ・タグ・成果などのアクションを選ぶ
5. お客様表示とLINE文面を確認する
6. 公開する
7. 申込者、待ち、取消、出席を管理する
8. 変更時は影響を確認し、対象者へ新旧内容を通知する

## 4. 情報モデル

### 4-1. イベント本体

複数開催で共通する内容を持つ。

- `event_id`
- アカウント・組織
- 名称、説明、画像
- 開催形式: 店舗、オンライン、併用
- 会場表示、公開前案内
- 公開対象タグ・除外条件
- 1人あたり申込上限
- 自動確定または承認制
- アクション設定
- 下書き・公開・終了・中止
- 公開版

### 4-2. 開催回

日時ごとに持つ。

- `occurrence_id`。現行 `event_slots.id` を移行元にする
- 開始、終了、タイムゾーン
- 会場・担当の上書き
- 定員
- 申込開始・締切
- 取消・変更締切
- キャンセル待ち可否
- 中止状態と理由

V6一覧の1行は原則として開催回を表す。同じイベントに複数回がある場合は「イベント名 / 開催日時」を行内で識別し、詳細で全開催回を見られるようにする。

### 4-3. 申込

- 開催回、友だち、LINEアカウント
- 申込者識別子
- `party_size`。本人を含む参加人数
- 同伴者・ペット等の回答スナップショット
- 状態: 申請中、確定、拒否、取消、期限切れ、参加、無断
- 申込時のイベント名、日時、会場、条件の版
- 受付経路、流入、成果
- 作成、承認、取消、出席の操作者と日時

定員は申込行数ではなく、定員を消費する状態の `party_size` 合計で計算する。

### 4-4. キャンセル待ち

状態を固定する。

```text
waiting → offered → accepted → converted
              └→ expired → 次のwaitingへ
waiting/offered → cancelled
```

- 待ち順
- 希望人数
- 案内日時
- 席保留期限
- 回答token
- 予約化した申込ID
- 取消・失効理由

現行 `waiting / invited / converted / cancelled` は互換変換し、`offered` と期限を追加する。

## 5. 画面とURL

| 画面 | URL | 主な役割 |
|---|---|---|
| イベント一覧 | `/events` | 開催回、申込、定員、待ち、状態 |
| 新規作成 | `/events/new` | 内容、開催回、受付条件、アクション |
| 詳細・編集 | `/events/:id` | 版、開催回、利用先、変更影響 |
| 申込者 | `/events/:id/occurrences/:occurrenceId/applicants` | 確定、待ち、取消、参加 |
| お客様表示確認 | `/events/:id/preview` | 公開条件で申込画面を確認 |
| 変更確認 | `/events/:id/change-review` | 影響者、通知、再承認 |

既存 `/events/edit?id=` と `/events/bookings?id=` は新URLへ転送する。IDなしのエラー画面を通常導線にしない。

## 6. 作成画面

### 6-1. 基本情報

- イベント名、説明、画像
- 開催形式、会場、担当者
- オンラインURLは確定者にだけ公開する
- お客様向け案内
- タイムゾーンは必須、初期値Asia/Tokyo

### 6-2. 開催回

- 日付、開始、終了または所要時間
- 複数開催回を追加できる
- 定員は1以上または無制限
- 1申込の最大参加人数
- 申込開始、締切
- 取消、変更締切
- 自動確定または承認制

同じ会場・担当で重複する場合は警告する。イベント予約だけでは担当者の予定を強制的に塞がず、予約設定28の担当・資源と接続した場合だけ予約空きへ反映する。

### 6-3. キャンセル待ち

- 受ける・受けない
- 案内後の回答期限。既定24時間
- 1回に案内する人数。既定1組
- 席を保留するか。既定は保留する
- 案内文、期限切れ文、次候補への案内
- 手動で順番変更すると監査履歴を残す

空きが出ても勝手に確定しない。期限付き申込URLを送り、本人の承諾後に予約へ変換する。

### 6-4. アクション

共通アクション25を参照する。

- 申込受付LINE
- 承認・拒否LINE
- 前日・当日リマインダ
- タグ追加・削除
- 友だち情報更新
- マイル・スコア
- 成果記録
- シナリオ開始・停止
- Webhook

イベントの公開版はアクション版も固定する。後編集で既存申込の処理を変えない。

### 6-5. 公開前検査

- 開催回が1件以上ある
- 開始＜終了
- 申込開始＜締切＜開催
- 取消期限が開催より前
- 定員と最大参加人数が矛盾しない
- 待ち案内文と回答期限がある
- 受付・承認・中止時のLINE文面を確認できる
- 公開対象が0人でも警告するが、下書き保存は許可する

## 7. 申込と定員

### 7-1. 申込

1. 公開、対象、期間、締切を確認
2. 友だち・本人識別を確認
3. 多重送信を冪等キーで除外
4. 申込上限を確認
5. 原子的に必要人数分の席を確保
6. 自動確定または申請中を作成
7. 受付通知とアクションを実行

事前SELECT後のINSERTだけにしない。DBの1トランザクションまたは条件付き更新で、残席が `party_size` 以上のときだけ確保する。

現行の「挿入後に超過を見て競合負けを削除」は安全弁としては有効だが、正式要件では席台帳・条件付き確保へ置き換える。失敗した試行は監査履歴に残し、申込行を物理削除して痕跡を消さない。

### 7-2. 承認制

- 申請中の席を定員に含めるか設定する。既定は含める
- 承認期限を設定できる
- 期限切れで席を戻す
- 拒否理由は内部用と顧客通知用を分ける
- 承認と同時に定員を再検査する

### 7-3. 取消・変更

- 本人は締切前に取消・開催回変更
- 運用者は期限後も権限付きで取消可能
- 変更は旧申込を取消し、新開催回へ原子的に確保する
- 新枠の確保に失敗したら旧予約を維持する
- 取消後に待ち繰上げjobを1回だけ起動する
- 返金は決済連携がある場合だけ別処理にする

## 8. キャンセル待ちの繰上げ

1. 席が空いたことをイベントとして記録
2. 待ち順と必要人数を確認
3. 入る最初の1組へ席を期限付き保留
4. LINEで申込URLと期限を送る
5. 承諾なら原子的に申込へ変換
6. 期限切れ、取消、送信不能なら保留を解除
7. 次の候補へ進む

要件:

- 同じ空席に複数案内しないlock/idempotency
- 1人が複数端末で押しても1件
- blocked/unfollowedはLINE送信不能として運用者に表示
- LINE未達でも待ちを成功扱いにしない
- 手動案内、順番変更、飛ばす操作は理由必須
- 開催開始後は自動案内しない
- 通知jobが落ちても再開可能

## 9. 申込者一覧

### 9-1. 表示

- 友だち名、画像、申込順
- 開催回、参加人数
- 確定、申請、待ち、取消、参加、無断
- 初回参加か
- 回答フォームの必要項目
- タグ、マイル、流入
- リマインダ送信予定・結果
- 直近の個別トーク

「初回」は現時点の表示名やタグではなく、その人の過去の参加済みイベント件数から算出する。判定時点を記録する。

### 9-2. 操作

- 承認、拒否、取消
- 待ちへ案内、案内取消
- 出席、無断
- 個別トークを開く
- 選択者へ一斉送信
- CSVで書き出す
- タグ、成果、マイルなど共通アクション

V6に表示するボタンは実装する。現行の「準備中」CSVと一斉送信は残さない。

### 9-3. 一斉送信

- 対象状態と人数を確認してから配信6へ渡す
- 対象は送信確認時点の申込者スナップショットを固定
- 重複友だちを1人にまとめるか選ぶ。既定は1人1通
- blocked、unfollowed、送信不可を除外し、理由別件数を表示
- 送信結果をイベントと配信双方から参照可能
- 誤送信防止の権限と確認画面を持つ

### 9-4. CSV

- UTF-8/BOMの選択
- イベント、開催回、申込状態、日時、回答、出席
- 必要権限がある人だけ個人情報列を出力
- 出力者、対象条件、件数、日時を監査
- 数式注入を防止してセル先頭文字を処理
- 秘密値、オンライン会場のtokenを含めない

## 10. 開催変更・中止

公開後の名前、会場、日時、定員、条件変更は新版にする。

- 影響する申込、待ち、リマインダを事前表示
- 日時・会場変更は新旧をLINE通知
- 大きな日時変更は「そのまま参加 / 取消」を本人に確認できる
- 定員を確定人数未満に下げない
- 中止は状態変更で、申込履歴を削除しない
- 中止通知、アクション停止、リマインダ取消を冪等に実行
- 開催終了後の内容は監査訂正以外変更しない

## 11. 状態

### 11-1. 画面状態

- 読込: 骨組みを保ったskeleton
- 空: 「イベントを作る」導線
- 条件0件: 条件解除、検索変更
- エラー: 再読込、失敗理由、追跡ID
- 権限不足: 必要権限と管理者連絡
- 競合: 最新残席と再選択
- 送信失敗: 再試行、送信不能、恒久失敗

### 11-2. イベント状態

```text
draft → published → ended
              └→ cancelled
published → paused → published
```

「満席」「低申込」は保存状態ではなく、開催回・定員・日時から算出する。

## 12. データ要件

追加・拡張:

- `event_versions`: 公開版と内容スナップショット
- `event_occurrences`: 現行slotsを互換拡張
- `event_bookings.party_size`
- `event_booking_snapshots`: 名称、日時、会場、条件、回答
- `event_waitlist.offer_expires_at / offer_token_hash / party_size`
- `event_capacity_ledger`: 確保、解放、保留、失効の追記台帳
- `event_change_logs`: 変更前後、影響人数、操作者
- `event_attendance_events`: 出席訂正を含む追記台帳

すべてアカウント・組織境界を持つ。時刻はUTC保存、表示はイベントのタイムゾーン。削除は履歴がない下書きだけ物理削除を許可する。

## 14. 権限と監査

- 閲覧
- イベント作成・編集
- 公開・停止・中止
- 申込承認・取消
- 出席管理
- 申込者へ送信
- 個人情報CSV出力
- 待ち順の手動変更

画面で押せないだけでなく、APIでアカウント・組織・権限を再検証する。全操作にactor、対象、変更前後、理由、結果、追跡IDを残す。

## 15. 既存データ移行

1. eventsをイベント本体として維持
2. event_slotsを開催回としてIDを維持
3. 既存申込の `party_size=1`
4. 既存待ちの `waiting/invited/converted/cancelled` を新状態へ対応
5. 現行イベント内容から初版を生成
6. 申込時点の版が不明な過去行は「移行版」として明示
7. 件数、状態別人数、定員、待ち順、通知予定を照合
8. 新旧APIの二重受付を防止

既存の冪等キー、承認、本人取消、マイル、リマインダは残す。待ちUIは既存APIへ配線し、コメント上の「待ちがない」という古い認識を修正する。

## 16. 実現しない・除外するもの

- 同意なしの自動予約確定
- 定員を超える仮予約の大量発行
- LINE既読を使った待ち回答判定
- 送信済みLINEの取消
- オンライン会場URLの公開一覧表示
- 公開済みイベント・申込・待ち・出席の物理削除
