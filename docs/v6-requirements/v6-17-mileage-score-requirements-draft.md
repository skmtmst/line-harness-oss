# V6 17 マイレージ・行動スコア 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「17 マイル」「17-2 行動スコア」
位置づけ: Pencil、現行画面、DB、API、実行処理、Lステップ・Liny調査を照合した実装前要件

## 0. 結論と採点

V6の設計は採用する。顧客が使える「マイル」と、運用者だけが見る「行動スコア」を同じ機能群の中で明確に分けた点は正しい。

- マイル: 顧客に見せる。貯める、使う、失効する、履歴を説明できる
- 行動スコア: 顧客には見せない。反応の強さを配信・対応優先度へ使う

現行DBでも、マイルとスコアは既に別テーブルで管理されている。そのため、データ概念を一から作り直す必要はない。一方、現在は次が不足している。

- `/scoring` というURLと「マイル」という画面名が混在している
- マイルの使い道、交換、在庫、受け渡し、失効処理がない
- マイル付与ルールとスコアルールに公開版がなく、変更後の条件を履歴から再現できない
- マイルの確定待ちを利用可能へ移す処理がない
- マイルルール、スコアルール、処理待ち件数の一部がLINEアカウント範囲に分かれていない
- スコア加減点に元イベントの一意キーがなく、同じイベントの再実行で重複加点し得る
- スコアを一斉配信・シナリオなどの共通絞り込み条件に使えない
- `score_threshold` は一度しきい値を超えた後も、イベントごとに再発火し得る
- V6の「30日反応なし」「ブロック時0点」は、現在の単純加減点ルールだけでは実行できない

| 評価軸 | 現在 | この要件を実装後 | 判断 |
|---|---:|---:|---|
| UI・UX | 97 | 98 | 11画面と5タブを採用する |
| Lステップとの競争力 | 96 | 99 | スコア連携に加え、使えるマイルが独自優位 |
| 現行基盤からの実装可能性 | 86 | 97 | 台帳・ルール・処理待ちは既にある |
| データの安全性・正確性 | 58 | 96 | 版、範囲、重複防止、交換の原子性がP0 |
| 要件の確定度 | 90 | 97 | 本書の範囲で実装設計へ進められる |

総合判断: **V6を採用する。マイルは既存台帳を拡張し、行動スコアは既存スコア履歴を重複防止・版・配信条件へ接続する。**

### 0-1. 最重要原則

> マイルは顧客の資産、行動スコアは運用上の目安である。同じ点数として扱わず、保存・表示・権限・利用先を分ける。

- マイル残高は追記型台帳から説明できるようにする
- スコアの高低を顧客の価値や人格として表現しない
- ルール変更は原則として将来のイベントだけに適用する
- 既存履歴を削除・再計算して見かけ上合わせない
- 同じ元イベントを再受信しても、マイルもスコアも二重に付けない
- 所属・本人確認ができない友だちを推測で同一人物にまとめない

## 1. この機能で利用者が達成すること

### 1-1. マイル

> 友だちの行動に応じてマイルを安全に付け、残高・失効・交換まで一続きで管理する。

補助タスク:

- 友だちごとの利用可能、確定待ち、もうすぐ失効するマイルを確認する
- 何をすると何マイル付くかを決める
- 付けすぎを防ぐ回数・対象・期間を設定する
- クーポン、先行案内などの使い道を設定する
- 交換時に残高不足、在庫不足、二重交換を防ぐ
- 手動で増減するとき、理由・実行者・承認を残す
- 友だちへ残高と履歴を説明する

### 1-2. 行動スコア

> 反応の強さを内部スコアとして把握し、その層を確認・配信・自動化へ安全につなげる。

補助タスク:

- 高い・ふつう・低いの人数と変化を確認する
- 加点、減点、0点へ戻すルールを設定する
- しきい値と上限を設定する
- スコア層から友だち一覧と配信条件へ進む
- どの行動で点数が変わったかを確認する
- しきい値を初めて越えたときだけ自動化を動かす

## 2. マイルと行動スコアの境界

| 項目 | マイル | 行動スコア |
|---|---|---|
| 見る人 | 顧客・運用者 | 運用者だけ |
| 目的 | 特典・継続利用 | 反応の強さ・対応優先度 |
| 単位 | mile | 点 |
| 使えるか | 使える | 使えない |
| 失効 | あり得る | 原則なし。無反応ルールで減点できる |
| 手動変更 | 理由・承認つき | 理由つき |
| 主な利用先 | クーポン、先行案内、ランク | 配信条件、友だち検索、自動化 |
| 顧客表示 | 残高・履歴・使い道 | 表示禁止 |
| 正本 | マイル台帳 | スコア履歴＋現在値 |

画面、API、テーブル、CSV、権限で両者を区別する。`point` のような共通語にまとめない。

## 4. 画面ごとの要件

### 4-1. 17-1 友だちの残高

KPI:

- 残高がある人
- 利用可能マイル合計
- 確定待ちマイル合計
- 30日以内に失効するマイル

一覧:

- 友だち
- 利用可能
- 確定待ち
- 30日以内に失効
- 生涯付与
- 使用済み
- 最終変動日時
- 接続中LINEアカウント

操作:

- `友だちのマイル明細を見る`
- `残高をCSVで書き出す`
- `マイルを手で増やす・減らす`

残高の範囲:

- V6初期版は1組織1マイルプログラムを既定とする
- 同一人物として確認済みの `users.id` がある場合だけ、複数LINEアカウントの残高を共通化する
- 選択中アカウントの一覧には、そのアカウントの友だちだけを出す
- 表示する残高が組織共通なら、`共通残高` とアカウント印を表示する
- 未確認の友だちは、その友だち行だけの残高とする
- 他組織のアカウントを同じ財布へ入れない

失効日が設定されていない既存マイルは `失効なし` と表示する。0日・0mileとして扱わない。

### 4-2. 17-1-A たまる決めごと

表示:

- ルール名
- きっかけ
- 出どころ
- 付与数
- 利用可能・確定待ち
- 回数上限
- 対象の一意条件
- 有効期間
- 現在の公開版
- 直近30日の対象・付与・除外数
- 状態（下書き、公開中、停止、設定不備）

操作:

- `決めごとを作る`
- `たまる決めごとを編集`
- `たまる決めごとを停止`
- `前の版から新版を作る`

履歴が1件でもあるルールは物理削除せず、停止・アーカイブする。

### 4-3. 17-1-B マイルの使い道

表示:

- 使い道名
- 種類
- 必要マイル
- 公開状態
- 在庫または発行可能数
- 1人あたり回数
- 有効期間
- 直近30日の交換数
- 受け渡し失敗数
- 現在の公開版

初期版で実装可能な種類:

- 事前発行したクーポンコードの受け渡し
- タグ付与
- シナリオ開始
- テンプレート送信
- 先行案内対象への登録
- ランク付与

クーポンは、EC側で利用できるコードをあらかじめ取り込む方式とする。接続先にクーポン発行APIがない状態で、使えないコードを自動生成しない。

交換時に確認すること:

- 利用可能残高
- 在庫・コード在庫
- 公開期間
- 1人あたり回数
- 友だち状態
- 受け渡しアクションの公開版
- 同じ交換要求の一意キー

マイルを減らせたが特典を渡せなかった場合は、失敗を隠さず、再実行またはマイル返却へ進める。

### 4-4. 17-1-C マイルの履歴

一覧:

- 友だち
- 種類（付与、確定、取消、使用、失効、手動調整）
- 増減数
- 利用可能・確定待ち
- 理由
- 発生元
- 元イベント
- 使用したルール版・使い道版
- 発生日時
- 実行者

絞り込み:

- 種類
- 状態
- ルール・使い道
- 自動・手動
- 期間
- LINEアカウント
- 失敗・要確認

元イベントが削除されても、履歴の理由、数、版、発生時刻は残す。元データの生JSONは画面に出さない。

### 4-5. 17-1-D たまる決めごとをつくる

入力:

- ルール名
- きっかけ
- 出どころ
- 付与マイル
- すぐ使える・確定待ち
- 確定条件・取消条件
- 1日あたり回数
- 同じ対象は1回だけ
- 紹介者へ付けるか
- 倍率対象外にするか
- 開始・終了日時
- 失効期間

きっかけの選択肢には、実際に共通イベントへ接続済みのものだけを出す。未実装イベントを `準備中` で表示しない。

公開前プレビュー:

- 過去30日を使った場合の対象人数と付与見込
- 1人あたり最大付与
- 既存ルールとの重複
- 使われるLINEアカウント
- 確定待ちから利用可能になる条件
- 失効日の例

操作:

- `下書きを保存`
- `決めごとをテスト`
- `たまる決めごとを公開`

公開済み版を直接更新しない。変更は新版として公開し、過去イベントへ遡って適用しない。

### 4-6. 17-1-E 友だちのマイル明細

表示:

- 利用可能、確定待ち、30日以内失効、生涯付与、使用済み
- 本人確認済みの接続LINEアカウント
- 付与・使用・失効・調整履歴
- 使用したルール・特典
- 元イベントへの安全な導線
- 手動調整の理由・実行者

操作:

- `マイルを手で増やす・減らす`
- `友だちの詳細を見る`
- `履歴をCSVで書き出す`

本人統合をこの画面から自動実行しない。別の本人確認・統合機能を使う。

### 4-7. 17-1-F マイルを手で増やす・減らす

入力:

- 増やす・減らす
- マイル数
- 理由区分
- 詳しい理由
- 問い合わせ・注文・調整元ID

確認画面に変更前、変更量、変更後を表示する。

制約:

- 理由を必須にする
- ownerまたは許可されたadminだけが実行できる
- 減算で利用可能残高を下回らない
- 既存台帳を更新・削除せず、調整行を追加する
- 同じ調整を再送しても二重反映しない
- 一定値以上の調整は別のowner承認を必要とする

### 4-8. 17-1-G マイルの使い道をつくる

入力:

- 使い道名・説明・画像
- 種類
- 必要マイル
- 在庫・コード在庫
- 1人あたり回数
- 公開期間
- 特典の有効期間
- 交換後に行う共通アクション版
- 受け渡し失敗時の扱い
- 顧客へ送る案内

操作:

- `下書きを保存`
- `自分で交換をテスト`
- `マイルの使い道を公開`

交換済みの特典を後編集しない。新版を作り、交換履歴は交換時の版を参照する。

### 4-9. 17-2 行動スコア

Pencilの画面構成を採用する。

KPI:

- 点数が付いている人
- 高い層
- ふつうの層
- 低い層
- 30日で上がった・下がった人数

一覧:

- 友だち
- 現在の点数
- 層
- 30日間の変化
- 最後の反応
- 最後に点数が変わった理由

操作:

- `この層の友だちを見る`
- `この層に配信する`
- `点数の内訳を見る`
- `友だちの詳細を見る`
- `行動スコアをCSVで書き出す`

`この層に配信する` は一斉配信の作成画面へ移動し、現在のスコア範囲を共通絞り込み条件として引き継ぐ。対象人数は配信確定時に再評価する。

表示上の注意:

- `スコアはマイルではありません`
- `顧客には表示されません`
- `反応の目安であり、顧客の価値を表すものではありません`

スコアは選択中LINEアカウントの友だち行ごとに計算する。複数アカウントの点数を自動合算しない。

### 4-10. 17-2-A スコアのルール

V6で示した次の種類を実装する。

- 加点
- 減点
- 0点へ戻す
- 1日・対象ごとの回数制限
- 上限・下限
- 高い・ふつう・低い層の境界

入力:

- ルール名
- きっかけ
- 出どころ
- 効果（加点・減点・指定値へ変更）
- 点数
- 回数制限
- 同じ元イベントは1回だけ
- 有効期間
- 対象LINEアカウント

V6の例:

- メッセージ返信 `+2`
- 配信URLクリック `+5`
- こちらに返信 `+8`
- 回答フォーム回答 `+15`
- 予約 `+20`
- 購入 `+25`
- 30日間反応なし `-10`
- ブロック `0点へ変更`

`30日間反応なし` は毎日繰り返し減点しない。30日到達時に1回だけ発生し、再反応後に新しい無反応期間へ入った場合だけ再度対象にする。

層の検証:

- 下限は0、上限は100を既定とする
- 高い層の境界は、ふつうの層より大きくする
- 低い層は0からふつう未満
- 境界を変えても過去点数は書き換えず、所属する層だけ再評価する

公開操作:

- `下書きを保存`
- `スコア変化をテスト`
- `スコアのルールを公開`

Pencilの `出す` は `スコアのルールを公開` へ変更する。公開済みルールを直接編集せず、新版を作る。

### 6-2. マイルに追加するもの

`mileage_programs`:

- 組織またはLINEアカウントの範囲
- 失効方針
- タイムゾーン
- 状態

複数アカウントで同じ財布を使う場合は `mileage_program_accounts` で明示的に関連づける。現在ある全アカウントを無条件に将来のプログラムへ含めない。

`mileage_rule_versions`:

- ルールID、版番号
- きっかけ、出どころ、付与数
- 確定待ち・利用可能
- 回数・対象・期間・失効条件
- 公開者、公開日時

`mileage_ledger` の追加情報:

- 発生元LINEアカウント
- ルール版・使い道版
- 利用可能になる日時
- 取消日時
- 顧客に表示する安全な理由
- 手動調整者・承認者

`mileage_lots`:

- 付与台帳行
- 元の付与数
- 残っている数
- 利用可能日時
- 失効日時

`mileage_spend_allocations`:

- 使用・失効行が、どの付与ロットを何マイル消費したか
- 先に失効するロットから使う

これにより、既に使ったマイルを後から重複失効させない。

`mileage_rewards` / `mileage_reward_versions`:

- 使い道本体、公開版
- 種類、必要マイル、在庫、期間、回数
- 共通アクション版
- 顧客向け案内

`mileage_reward_codes`:

- 事前発行コード
- 未使用、予約中、発行済み、無効
- コード値は画面一覧・ログへ平文表示しない

`mileage_redemptions`:

- 交換要求ID・一意キー
- プログラム、本人、友だち
- 使い道版
- 使用台帳行
- 受け渡し状態
- 試行回数、次回試行、失敗理由
- 発行コードまたは共通アクション実行ID

`mileage_wallets`:

- プログラムと本人識別子
- 利用可能、確定待ち
- 更新番号

台帳が正本で、walletは交換時の残高不足・同時交換を防ぐ投影とする。定期照合で台帳合計と一致させる。

### 6-3. 行動スコアに追加するもの

`scoring_rules`:

- `line_account_id`
- 下書き、公開中、停止
- 現在公開版

`scoring_rule_versions`:

- イベント、出どころ
- 効果（delta / set）
- 値
- 回数・対象・期間
- 下限・上限
- 公開者、公開日時

`friend_scores` は追記型履歴として残し、次を追加する。

- `line_account_id`
- `event_type`
- `source_event_id`
- `rule_version_id`
- `idempotency_key`
- `operation`（delta / set / manual_adjustment）
- `score_before`, `score_after`
- `occurred_at`
- 手動実行者・理由

`UNIQUE(line_account_id, idempotency_key)` を持つ。同じ元イベントを再処理しても1回だけ反映する。

`score_bands`:

- LINEアカウント
- 低い・ふつう・高いの境界
- 下限・上限
- 公開版

`friends.score` は現在値のスナップショットとして残す。履歴合計またはset操作の結果と毎日照合し、不一致を運用状態へ出す。

## 8. 実行要件

### 8-1. マイル付与

1. 元イベントを一意な受付IDで受ける
2. プログラム・LINEアカウント・友だちを確認する
3. 公開中のルール版を固定する
4. 回数・対象・期間を評価する
5. 一意キーで処理待ちを作る
6. 付与台帳とロットを追加する
7. walletを更新する
8. 成功・除外・失敗を記録する

現在の最大5回再試行を維持し、5回を超えたものは `failed` のまま埋もれさせず `要確認` とする。処理待ち件数はプログラム・LINEアカウント範囲で集計する。

### 8-2. 確定待ち

- 何をもって利用可能にするかをルール版に保存する
- 指定日時、注文確定、成果承認などのイベントで確定する
- 取消イベントでは元の確定待ち付与をvoidにする
- 既に利用可能になった行を直接更新して消さず、取消行を追加する
- 確定・取消も元イベントIDで重複防止する

### 8-3. 失効

- 付与ロット単位に失効日を持つ
- 毎日、期限到達した未使用分だけ失効する
- 失効前に設定日数で顧客通知へ渡せる
- 失効処理を再実行しても二重に減らさない
- 過去マイルへ失効日を後付けするときは、対象数・最短日・通知方法を確認して別の移行として実行する

### 8-4. 交換

1. 同じ交換要求を一意キーで確保する
2. 公開版、期間、回数、在庫を確認する
3. walletの利用可能残高を条件付きで確保する
4. 先に失効するロットから使用割当を作る
5. 使用台帳を追加する
6. コードまたは共通アクションを受け渡す
7. 失敗時は安全に再試行する
8. 最終失敗時はowner判断で返却行を追加する

残高確保と使用台帳は原子的に行う。同時交換で残高をマイナスにしない。

### 8-5. 行動スコア

1. 元イベントとLINEアカウントを確認する
2. 公開ルール版を固定する
3. 回数・対象・期間を評価する
4. 現在値を取得する
5. deltaまたはsetを適用し、下限・上限に収める
6. 履歴と `friends.score` を同じ処理で更新する
7. 変更前後の層を比較する
8. 層・しきい値を初めてまたいだ場合だけイベントを出す

自動化へ渡すイベント:

- `score_threshold_crossed`
- `score_band_changed`

現在のように、しきい値を超えた後の全イベントで同じ自動化を動かさない。

## 9. 配信・検索との連携

共通絞り込みに `score_range` を追加する。

- 最小点
- 最大点
- 層
- 評価するLINEアカウント
- 評価時点は原則として配信確定時の現在値

同じ条件を次で使う。

- 友だち検索
- 一斉配信
- シナリオ全体・各通
- 自動応答
- リッチメニュー出し分け
- 共通アクションの条件
- 分析の対象者

保存前に対象人数をプレビューし、実行直前に再評価する。予定人数との差を記録する。

## 10. 権限と安全性

| 操作 | owner | admin | staff |
|---|---|---|---|
| マイル一覧・履歴 | ○ | ○ | 権限範囲のみ |
| 付与ルール・使い道の編集公開 | ○ | 許可時のみ | × |
| マイル手動調整 | ○ | 許可時のみ | × |
| 高額調整の承認 | 別owner | × | × |
| スコア一覧・履歴 | ○ | ○ | 権限範囲のみ |
| スコアルール公開 | ○ | ○ | × |
| スコア手動調整 | ○ | 許可時のみ | × |
| CSV出力 | ○ | 明示権限時のみ | × |

安全ルール:

- スコアへ住所、病歴、障害、人種、宗教などの機微情報を使わない
- スコアだけで契約拒否、価格変更、信用判断などの重大判断を自動実行しない
- 顧客へ行動スコアを送信・表示しない
- マイルコード、内部ID、生イベントJSONを一覧・Slack・ログへ出さない
- 手動調整、版公開、交換失敗時返却を監査ログへ残す

## 11. 既存データの移行

### 11-1. マイル

1. 既存 `default` プログラムと関連LINEアカウントを確認する
2. owner確認後に組織共通プログラムとして関連づける
3. `mileage_rules` を版1として移行する
4. `mileage_ledger` は数・理由・状態を変えずに新項目を補う
5. 既存付与は失効日なしのまま保持する
6. 既存 `pending` は自動確定せず、要確認一覧へ出す
7. 台帳合計と現在の管理画面集計をdry-runで比較する
8. 新送信元だけを新版へ切り替え、二重付与がないことを確認する
9. 使い道は新規で作り、存在しない交換履歴を生成しない

### 11-2. 行動スコア

1. `friend_scores` の累計と `friends.score` を全友だちで比較する
2. 不一致を自動上書きせず、差分表を出す
3. 既存 `scoring_rules` の利用中イベントと所属アカウントを調べる
4. 所属を確定できたものだけ版1へ移行する
5. 所属不明ルールは停止状態の `過去ルール` として隔離する
6. 既存 `friend_scores` を履歴として保持し、移行時に再加点しない
7. 新しい元イベントIDがある処理から重複防止を開始する
8. 旧 `score_threshold` 自動化を、越境イベント方式へ変換・テストする

### 11-3. 切替

- `/scoring` を `/mileage` へリダイレクトする
- 旧マイルAPIは新APIの読取アダプターとして一時的に残す
- 新旧の付与処理を同時に動かさない
- 移行ログに、対象、変換、隔離、差分、未決定を残す
- 元テーブルは監査期間中は削除しない

## 12. Lステップ・Linyとの差

| 観点 | Lステップ・Liny相当 | V6で上回る条件 |
|---|---|---|
| スコア | 行動による加減点・対象抽出 | 層、30日変化、越境イベント、共通絞り込みを同じ値で使う |
| スコアの根拠 | ルールと友だち情報 | 元イベント、使用版、変更前後を履歴から説明できる |
| 配信連携 | スコア条件で配信 | 一斉配信、シナリオ、自動応答、メニュー、分析で共通条件を使う |
| マイル | 同等の中核機能ではない | 貯めるだけでなく、交換、失効、受け渡し、返却まで完結する |
| 複数機能連携 | LINE内の行動中心 | EC、予約、ウェビナー、紹介、Instagram、フォームを共通イベント化 |
| 安全性 | 設定と履歴 | 版固定、重複防止、原子的な交換、監査、照合を持つ |

Lステップを超える中心は、機能数ではなく、`行動 → マイルまたはスコア → 条件・特典 → 履歴` が同じイベントIDで追えることである。

## 13. 除外するもの

実現しない:

- LINEの既読だけを根拠にした加点
- 本人確認なしの複数アカウント残高統合
- 他組織をまたぐ共通財布
- 顧客への行動スコア表示
- スコアを顧客の価値・信用として扱うこと
- 過去イベントへの自動遡及加点
- 移行時の履歴再実行

初期版から除外:

- マイルの現金、暗号資産、送金、換金
- 友だち間のマイル譲渡
- EC接続なしの自動クーポン生成
- ルール変更による過去スコアの一括再計算
- AIが自動でスコアルールを公開すること
- スコアだけで価格、契約、審査結果を変えること
- 複数マイルプログラムを顧客が自由に切り替えること

将来候補:

- ECクーポンAPIとの直接発行
- 家族・店舗単位の共有財布
- 複数プログラム
- ランクごとの継続特典
- スコア変化の説明レポート
