# V6 3 友だち 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「3 友だち」

## 0. 結論と採点

V6を採用する。友だち一覧、14軸の詳細検索、一括操作、個人詳細、重複候補、統合ユーザー、UID移行を1つの機能としてつないだ設計は、通常のLINE拡張ツールを超えてCRMの中心になれる。

ただし、画面どおりに実装する前に「友だちレコード」と「同一人物」を分ける必要がある。現行には`friends.user_id`と`users`があり土台はあるが、プロフィール画像URLの一部を同一人物の主キーに使っている。この値は本人確認済み識別子ではないため、自動統合や重複配信除外の確定根拠から外す。

現行の一覧・基本検索・一部詳細検索・1人への操作・統合表示・重複集計は動く。一方、14軸のうち8軸、一括操作、サーバ保存検索、全件CSV、候補ごとの確認・解除、属性の採用元、UID移行は未実装である。

| 評価軸 | 現在 | 実装後 |
|---|---:|---:|
| V6 UI・UX | 97 | 99 |
| Lステップ・Liny競争力 | 96 | 100 |
| 現行実装 | 70 | 98 |
| データ安全性 | 48 | 98 |
| 実現可能性 | 92 | 98 |
| 要件確定度 | 97 | 99 |

実現不能として除外するのは、異なるLINEプロバイダー間のUIDをLINE APIだけで自動変換すること、名前・プロフィール画像だけで同一人物と確定すること、管理画面からLINE利用者をブロックすることである。

## 2. 達成すること

> 運用者が、対象となる友だちを正確に見つけ、現在の情報と履歴を確認し、誤配信や誤統合を起こさずに個別・一括操作できる。

- 友だちを検索・絞り込み・保存検索から再発見する
- 一覧の表示項目を業務に合わせて変更する
- 個人の属性、対応、予約、購入、配信、履歴を見る
- 選択した複数人へ安全に一括操作する
- LINEアカウントをまたぐ同一人物候補を確認する
- 元の友だちを消さずに統合ユーザーへ関連付ける
- 統合を解除し、判断理由と変更履歴を残す
- UID移行をdry-run、競合確認、本移行、照合、切り戻しで実施する
- CSVを現在ページだけでなく対象全件で安全に出力・取込する
- スタッフのアカウント範囲と項目権限をAPIで守る

## 3. 用語を固定する

| 用語 | 意味 |
|---|---|
| 友だち | 1つのLINEアカウント上の1つのLINE user IDに対応するレコード |
| 統合ユーザー | 複数の友だちや外部顧客IDを同じ顧客として束ねる親レコード |
| 重複候補 | 同一人物の可能性があるが、人または検証済み証拠で未確定の組 |
| UID | LINE user IDまたは自社の検証済み外部顧客ID。種類を必ず併記する |
| LINE関係状態 | 友だち状態、ブロック状態。Webhookのfollow/unfollowを根拠にする |
| 管理画面の表示状態 | 表示中、非表示。LINE上のブロックとは別物 |
| 対応状況 | 未対応、対応中、保留、対応済みの固定業務状態 |
| 対応マーク | 自由に作る業務分類。対応状況とは別物 |
| 担当者 | その顧客対応を受け持つスタッフ |

V6の「相手から／自分から」の表現は、実装時に「LINEでブロック／管理画面で非表示」へ分ける。管理画面からLINE利用者をブロックできるようには見せない。

## 5. 友だち一覧

### 5-1. KPI

- 有効友だち
- LINEでブロック中
- 管理画面で非表示
- 未対応・要確認
- 今月の追加

母数、更新日時、アカウント範囲を表示する。LINE公式の友だち数とDB件数は一致しない場合があるため、KPI名に「Harnessで確認できる」を補足する。

### 5-2. 一覧項目

- 注目
- LINEアイコン、LINE表示名、システム表示名、本名
- LINEアカウント
- 対応状況
- 対応マーク
- 担当者
- 進行中シナリオ
- 最新メッセージと日時
- タグ・主要属性
- 流入元
- 登録日
- LINE関係状態、管理表示状態

名前、コード、タグなどの短い値は途中改行せず、1行省略と`title`で全文を確認できるようにする。個人情報権限がない項目は値を伏せるだけでなく、APIから返さない。

### 5-3. 選択

- 現在ページの全選択
- 個別選択
- 現在の検索結果全件を選択
- 選択解除

「現在ページ20人」と「検索結果231人」を明確に分ける。検索結果全件を選ぶ場合、実行直前に件数・条件・除外理由を再表示する。

### 5-4. 並び順・ページ送り

- 追加が新しい順・古い順
- 最終反応が新しい順・古い順
- 待ち時間が長い順
- 名前順
- 10、20、30、40、50件表示

offset方式は小規模互換として残せるが、実装後は安定したカーソルを使う。同一日時では`friend_id`を第2キーにし、ページ移動中の重複・欠落を防ぐ。

## 6. 詳細検索・保存した検索

### 6-1. 14軸

1. 名前
2. タグ
3. 友だち情報
4. 対応マーク・対応状況・担当者
5. シナリオ
6. イベント予約
7. カレンダー予約
8. 回答フォーム
9. 最終反応日
10. リマインダ
11. 個別メモ
12. ステータスメッセージ
13. 友だち登録日
14. その他の共通イベント・成果・購入

追加で、LINEアカウント、LINE関係状態、管理表示状態、注目、統合済み・未統合を全体条件として持つ。

### 6-2. 条件の意味

- ANDとORを入れ子にできる
- 含む、含まない、等しい、等しくない、以上、以下、範囲、未登録、登録済み
- 日時はJSTで入力し、保存はUTCまたはISO時刻に統一
- 数値、日付、真偽、単一選択、複数選択、文字列で演算子を変える
- 「値がない」と「空文字」を分ける
- 条件変更後400ms程度で該当人数を再計算
- 0人でも条件を保存できる
- 条件に使った項目が削除・権限外になったら、黙って無視せず要修正にする

### 6-3. 保存検索

既存`saved_searches.scope='friends'`を使う。現行localStorage保存は移行用読取だけにし、正本はサーバへ移す。

版付き条件:

```json
{
  "version": 1,
  "root": {
    "op": "and",
    "children": [
      { "kind": "tag", "operator": "includes", "values": ["tag-vip"] },
      { "kind": "last_activity", "operator": "before_days", "value": 30 }
    ]
  },
  "accounts": ["account-a"],
  "relationship": ["following"],
  "visibility": ["visible"],
  "sort": "waiting_desc",
  "columns": ["name", "assignee", "status", "tags"]
}
```

- 個人用と共有を分ける
- 共有の作成・更新・削除は管理権限を要求
- 名前は必須、40文字以内、同じ所有者内で一意
- 件数は開いた時点の最新値
- 条件、並び順、表示項目を一緒に保存
- API権限を`/tags`ではなく`/friends`へ結び付ける

## 7. 一括操作

対象操作:

- タグを付ける・外す
- シナリオを開始・停止
- 担当者を変更
- 対応状況・対応マークを変更
- リマインダを設定・解除
- メッセージを送信・予約
- 共通アクションを実行
- 友だち情報を変更
- 表示・非表示を変更
- コンバージョンを追加・解除

実行手順:

1. 明示IDまたは保存検索・検索条件を選ぶ
2. サーバで対象を再計算
3. 対象数、除外数、アカウント別内訳、サンプルを表示
4. 操作内容と取り消し可否を確認
5. 対象IDスナップショットを固定
6. 一括実行台帳を作る
7. 対象ごとに冪等実行
8. 成功、スキップ、一時失敗、恒久失敗を表示
9. 失敗分だけ再実行
10. 可逆操作は元の値から取り消し実行を作る

ブラウザから1人用APIを人数分呼ばない。途中失敗してもどこまで終わったか分かるサーバ側ジョブにする。メッセージ送信、シナリオ開始など外部・時間依存操作は同じ冪等キーで再試行する。

## 9. 同一人物候補の判定

### 9-1. 根拠の強さ

確定に使える強い根拠:

- 同じLINEプロバイダー配下で同じLINE user ID
- サーバで検証したLINE Login ID tokenから得たuser ID
- 署名付き外部システムの一意顧客ID
- 本人確認済みメール・電話と、運用者の確認

候補に使う中程度の根拠:

- 未確認フォームのメール・電話一致
- 複数の独立した属性一致
- 予約・購入側の検証済み顧客ID

弱い根拠:

- 名前の近さ
- プロフィール画像
- ステータスメッセージ
- 同じ流入元や行動

弱い根拠だけで自動統合しない。現在`IDENTITY_KEY_SQL`が使うプロフィール画像URLのトークンは、確定キーと重複配信除外から外し、候補の参考情報にだけ使う。

### 9-2. 候補状態

- pending: 未確認
- linked: 同一人物として統合
- different: 別人として除外
- deferred: 保留
- invalidated: 根拠が変わり再確認

同じ組を検出のたびに作り直さず、候補IDと判定履歴を維持する。別人判定をした組は、根拠が増えた場合だけ再提示する。

### 9-3. 自動処理

完全一致でも自動統合は初期版で行わない。自動でできるのは候補作成、確信度表示、配信前の警告までとする。自動統合を将来有効にする場合は、本人確認済み識別子、利用目的、同意、解除手段を別途審査する。

## 10. 統合ユーザー

### 10-1. 非破壊統合

- 元の`friends`を削除・上書きしない
- `users`を親として使う
- 友だちとの関連を履歴付きで持つ
- 統合を解除できる
- 解除しても過去の操作履歴を消さない
- どの値をどの友だちから採用したか記録
- 配信優先順位はアカウント・用途ごとに設定

### 10-2. プロフィール競合

表示名、メール、電話、タグ、各属性について次を持つ。

- 候補値
- 出所の友だち・回答・外部システム
- 確認状態
- 採用値
- 採用者・日時
- 自動更新するか固定するか

タグは原則和集合だが、相互排他グループは競合として確認する。数値は合算せず、意味に応じて最新、最大、合計、個別保持を項目定義で決める。

### 10-3. 配信重複除外

統合しただけで常に1通へ減らさない。配信ごとに次を確認する。

- 同じ利用目的か
- 同じブランド・アカウント群か
- 各LINEアカウントで配信許可があるか
- 優先アカウントが送信可能か
- ブロック・停止・権限状態

優先先が送れない場合の代替先を明示する。誰にどのアカウントから送ったかを宛先台帳に固定する。

## 12. UID移行

### 12-1. LINE仕様上の境界

- 同じLINEプロバイダー配下では、チャネル種別が違っても同じ利用者に同じuser IDが発行される
- 異なるプロバイダーでは同じ利用者でも異なるuser IDになる
- 異なるプロバイダーのold UIDからnew UIDを変換するAPIはない
- プロバイダー間でLINE利用者情報を共通利用する場合は、利用目的・規約・同意を確認する

### 12-2. 許可する対応表

- サーバ検証済みLINE Login
- 署名付き外部顧客ID
- 本人確認済みメール・電話
- 運用者確認済みのCSV対応表

名前、画像、未検証フォーム値だけで本移行へ進めない。

### 12-3. 移行手順

1. 移行元・先・利用目的を登録
2. CSVまたは認証済みAPIから対応表を取込
3. 形式、重複、存在、アカウント範囲を検査
4. dry-runで自動一致、要確認、未一致、別人候補を分類
5. 要確認をすべて判断
6. 対象件数と影響する配信・シナリオ・タグ・属性・履歴を表示
7. バックアップと切り戻し点を作成
8. old友だちを上書きせず、新friendまたは統合ユーザー関連を作る
9. 属性の移行元と競合を記録
10. 送信停止・同意状態を厳しい方へ引き継ぐ
11. 新旧の件数、履歴、配信対象を照合
12. 段階公開後に旧IDを送信対象から停止

## 13. CSV出力・取込

### 13-1. 出力

- 現在ページではなく検索対象全件を出力
- 出力項目を選択
- 個人情報項目は権限で制限
- 大量出力は非同期ジョブ
- 完了通知、期限付きダウンロード
- UTF-8 BOMを既定とし、必要な場合だけShift_JIS
- `=`, `+`, `-`, `@`で始まるセルをCSV数式として実行されない形へ無害化
- 作成者、条件、列、件数、ダウンロードを監査

### 13-2. 取込

- Harnessから出力した署名・版付きCSVを既定
- dry-runで追加、更新、変更なし、競合、エラーを表示
- 本名、システム表示名、メモ、対応マーク、表示状態、タグ、友だち情報を対象
- LINE user ID、アカウントIDは勝手に変更しない
- 反映ジョブと項目ごとの変更履歴を残す
- 再アップロードで二重反映しない

## 15. 権限

| 操作 | 必要な判定 |
|---|---|
| 一覧・詳細を見る | `/friends`、担当LINEアカウント、友だち範囲 |
| 個人情報を見る | 項目ごとの個人情報権限 |
| CSVを出力する | 出力権限、列権限、アカウント範囲 |
| CSVを取り込む | 管理者、変更対象項目権限 |
| 一括操作する | 操作別権限、対象全件の範囲 |
| 重複候補を見る | 統合ユーザー閲覧権限 |
| 統合・解除する | owner/admin、本人識別管理権限 |
| UID本移行・切り戻し | owner、不可逆確認、二者確認 |

`assignedLineAccountId`と配下アカウント権限を、一覧、件数、詳細、CSV、一括操作、重複、統合のすべてでサーバ側検査する。現行はアカウントIDをクエリで渡すだけの経路があり、権限境界として不足する。

## 16. 状態・アクセシビリティ

必須状態:

- 初回・追加読込
- データなし
- 検索結果0件
- 部分エラー
- 権限不足
- 対象が別アカウントへ変更
- 同時更新競合
- 一括操作待ち・実行中・部分失敗・完了
- 保存検索の削除済み条件
- 重複候補なし・再検出中・根拠変化
- 統合プロフィール競合
- UID dry-run・要確認・本移行・照合失敗・切り戻し
- CSV検査・部分エラー・期限切れ

アクセシビリティ:

- 一覧を意味のあるtableとして実装
- 行クリックだけにせず、名前をリンクにする
- チェックボックスへ顧客名を含むラベルを付ける
- モーダルはタイトル関連付け、フォーカストラップ、Esc、閉じた後のフォーカス復元
- プルダウンと状態変更をキーボード操作可能にする
- 色だけで確信度・対応状況を区別しない
- 非同期件数、実行進捗、エラーをライブ領域で通知
- 200%ズームと1440pxで横スクロールを出さない

静止画ではフォーカス順、読み上げ、コントラスト値を確定できないため、実装時に実機検査する。

## 17. Lステップ・Linyとの差

### V6が同等以上の点

- タグ、友だち情報、対応、シナリオ、予約、回答を組み合わせる検索
- 該当人数を見ながら条件を作る
- 友だち一括操作
- CSV出力・取込
- 個人詳細と履歴
- 対応マークと担当者運用

### V6が上回る点

- 複数LINEアカウントをまたぐ重複候補
- 元友だちを残す非破壊統合
- 候補ごとの根拠・確信度・保留・別人判定
- 属性ごとの採用元
- 統合ユーザー単位の配信重複除外
- dry-runと切り戻しを持つUID移行
- 予約、EC、マイル、成果、配信を同じ顧客詳細へ接続

### 100点にするため追加する点

- Liny相当の日付経過・残り日数検索
- Lステップ相当のCSV項目選択と安全なインポート
- 保存した検索のサーバ共有
- 一括操作の対象固定・結果台帳・再試行
- アカウント・個人情報・統合操作の細かい権限
- 注目・重要履歴

## 18. 除外

- 異なるLINEプロバイダー間のUID自動変換
- 名前・画像・ステータスメッセージだけの自動統合
- プロフィール画像URLを確定identity keyとして使うこと
- 未検証フォームのメール・電話だけの自動統合
- LINE利用者を管理画面からブロックすること
- LINE公式アカウント管理画面の友だち総数との完全一致保証
- 元の友だち・履歴を削除する統合
- 統合解除時に過去の配信結果を書き換えること
- 全用途で無条件に配信を1通へ減らすこと
- ブラウザから1人用APIを大量ループする一括操作
- 名前だけによるメール・EC顧客との自動名寄せ

## 19. 既存データ移行

1. `friends`、`users`、`user_id`、LINEアカウント、タグ、属性、保存検索を棚卸し
2. 同じ`user_id`の友だちを`friend_identity_links`へ移す
3. `users`に存在しない`friends.user_id`を要修正として隔離
4. プロフィール画像URL由来の自動グループを確定統合から外す
5. 画像一致グループは未確認候補へ戻す
6. 既存保存検索localStorageは、利用者の同意後にサーバへ1回だけ移す
7. 管理画面の非表示とLINEブロックを別状態へ変換
8. 現行チャット状態と対応マークを別列へ分ける
9. 現行CSV出力は「現在ページ」と明記し、新ジョブ完成後に全件出力へ切替
10. 新旧一覧の件数、検索、タグ、担当、状態、最新日時をアカウント別に照合
11. 重複配信除外を旧identity keyと新confirmed linkで二重計算し差分確認
12. 一部アカウントへ段階公開し、戻し手順確認後に旧経路を停止

## 22. 公式仕様の根拠

- LINE user IDは同じプロバイダー内では同一、異なるプロバイダーでは別値になる: https://developers.line.biz/en/docs/messaging-api/getting-user-ids/
- LINE利用者情報をサービス間で共通利用する場合は、プロバイダー設計・規約・利用目的の確認が必要: https://developers.line.biz/en/docs/line-developers-console/best-practices-for-provider-and-channel-management/
- unfollowイベントは利用者が公式アカウントをブロックしたときに発生し、管理側から利用者をブロックするAPIはない: https://developers.line.biz/en/faq/tags/messaging-api/
- Linyはタグ、友だち情報、対応マーク、スタッフ権限を顧客管理として提供している: https://line-sm.com/function/
- Linyは複数友だちへの一括操作と日付の残り期間による絞り込みを提供している: https://line-sm.com/blog/liny-update-summary-2505-06/
- Lステップは友だち情報のCSV出力・取込と反映前確認を提供している: https://linestep.jp/2023/03/26/lstep-csv/
