## 一体型の右パネル

常に店舗選択・同期時刻を表示し、内部タブ「概要 / 口コミ / 投稿 / パフォーマンス /
プロフィール」で切り替える。内部の編集画面には戻るボタンを置く。
Googleへの保存・公開など主要操作は下部に固定し、緑色の主要ボタンは1つにする。

- 概要：店舗写真、店名、評価、口コミ総数、営業時間、新着・未返信・AI下書き・予約投稿。
- 口コミ：新着と未返信は別指標。全件取得、評価・状態・並び替え、返信下書き。
- 投稿：最新情報・特典・イベント。下書き・予約・処理中・公開済み・不承認を区別。
- パフォーマンス：表示、ルート、電話ボタンクリック、サイトクリックを中心にする。
- プロフィール：通常・特別営業時間を最優先。店舗情報・写真等へ同じ箱から進む。

## Google APIとの対応（2026-09-23に公式資料を確認）

Google管理画面の全機能とAPIは同じではない。未確認の機能を利用可能と表示しない。

| 項目 | 確認した契約 / 設計上の扱い |
|---|---|
| 口コミ・評価 | 認可された確認済み店舗で reviews.list。最大50件ずつ nextPageToken を最後まで辿る。averageRating / totalReviewCount を使用し、読み込み済み一部だけで総合評価を再計算しない。 |
| 投稿者 | APIが返す表示名・プロフィール画像を必要に応じて表示。匿名・画像なしの代替表示を用意。店舗写真とは別管理。 |
| 新着通知 | Notifications API + Cloud Pub/Sub。通知後に最新データ取得。重複排除と取りこぼしの再同期を設計する。 |
| 返信 | AIの下書きを人が確認して公開。無断自動返信はしない。送信前に既存返信と口コミの変更・削除を再確認する。 |
| 最新情報 | STANDARD。本文・メディア・CTA。本文1,500文字上限は今回のUI要件として実装時にサーバー側でも検証。 |
| イベント | EVENT。タイトルと開始・終了日時を入力。開催期間と投稿公開日時を分離する。 |
| 特典 | OFFER。タイトル・期間、任意のクーポンコード、利用URL、利用条件。通常CTAはAPIで無視されるため表示しない。利用条件リンクは専用API項目がないため実接続時に表現を確定する。 |
| CTA | BOOK / ORDER / SHOP / LEARN_MORE / SIGN_UP / CALL。CALLはURLを送らない。予約ボタンはリンクであり、予約システム自体を作る機能ではない。 |
| 予約投稿 | 現行LocalPost仕様に scheduledTime と SCHEDULED がある。APIネイティブ予約を優先し、利用可能性を対象接続で検証。未対応なら別途設計し、無断でCron等を増やさない。 |
| 繰り返し | 現行仕様に recurrenceInfo。詳細設定候補として記録し、初期版の主導線には置かない。 |
| メディア | 登録メディアを再利用。LocalPost media は sourceUrl のみサポート。公開取得可能なURL、権利、形式・容量・寸法を確認。原本を変更しない。4:3 / 1200×900 は提案上の推奨サイズで必須サイズと混同しない。 |
| 動画 | Mediaの列挙にVIDEOはあるが、現行説明は写真のみ対応と記載。投稿APIで動画が確実に使えるとは判断できないため、画面では無効・対応確認待ち。Googleで直接管理する代替導線を検討する。 |
| 商品投稿 | 公式ガイド上API作成対象外。Google管理画面の全機能対応とは約束しない。 |
| 営業時間 | Business InformationのregularHoursとspecialHoursを区別。特別営業時間は通常営業時間を上書きし、通常営業時間が前提。 |
| 実績 | Performance API。電話はクリック数で、成立通話数ではない。予約・注文・メニュー指標は対象店舗・連携の対応状況に応じて表示。欠損・未対応は「—」。 |
| Google側変更 | getGoogleUpdated等を活用する候補。自動でGoogle側変更を元に戻さず、差分を確認する。 |

## 営業時間を短い操作で変える

1. 「今日を休みにする」「今日は早く閉める」「祝日を確認」を入口にする。
2. 文章または音声を入力。音声は文字にし、利用許可・送信先・保存有無を説明する。
3. 店舗タイムゾーンと基準日を固定して、具体的な日付・時間の変更案に変換。
4. 変更前後・対象店舗・対象日・通常/特別を見せ、本人が確認して送信。
5. 再取得してGoogle側の状態を表示。受理・公開反映・審査中を混同しない。

例：基準日2026/09/23の「今週金曜9時〜17時」は、2026/09/25だけの特別営業時間。
既存の昼・夜2枠を1枠に置き換えることも明示する。通常の金曜は変更しない。

「あす」「来週の祝日」は店舗のタイムゾーンと祝日カレンダーで検証し、
該当日なし・複数候補・午前午後不明・過去日なら質問して止める。
深夜営業、日跨ぎ、中休み、終日休業、複数日、毎週の繰り返しは別の明示的入力で扱う。
送信は最新値を再取得して必要項目だけ更新し、他の日の特別営業時間を消さない。
Google側に原子的な競合検出がない場合の残る競合リスクは実装前に調査する。

## 実装前に必要な確認

- 利用承認だけでは接続完了ではない。Google Cloud側の必要API、OAuth同意・スコープ、
  店舗の確認状態、対象アカウント、割当量を読み取り確認する。
- 承認メールの300 QPMを前提に過負荷を避け、API別の割当・429・再試行を調べる。
- 新しい外部設定の変更は別途対象・影響・切戻しを説明して承認を得る。
- 同意なしの自動返信・プロフィール編集をしない。第三者への提供方法とGoogleプロジェクトの
  利用形態をポリシーに照合する。ユーザーがログインして使う管理画面を基本とし、
  顧客向けのAPI転貸や無制限の無人操作を提供しない。
- Googleコンテンツの保存・加工条件（限定的、一時的、30日以内等）を確認する。
  全件取得は恒久保存の意味ではない。原文を改変せず、保持期限・削除・暗号化・利用範囲を設計する。
  口コミ本文の外部AI処理も同意、送信先、保存条件を確認してから有効化する。
- 送信後にタイムアウトした場合は先に結果照合。重複投稿・重複返信を避ける。
- 投稿審査、低評価、エラーでも管理者が原因・再試行先を見つけられること。
- Googleとの提携や推奨と誤認させる表記は使わない。
