# V6 4 友だち属性 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「4 友だち属性」
対象範囲: タグ、友だち情報欄、対応マーク、保存した検索、タグ定義CSV

## 0. 結論と採点

V6を採用する。タグの用途・付与元・連動・使用先を一覧で読めること、友だち情報欄の種類を後変更せず安全な移行へ分けたこと、削除前に影響を見せることは、Lステップ・Linyと同等以上を狙える設計である。

ただし、そのまま実装すると危険な点が4つある。

1. タグに埋め込んだ連動アクションは、V6 25の共通アクション・オートメーションへ保存する。タグ画面は設定の入口として残すが、別形式の実行エンジンを作らない。
2. 「対応状況」と「対応マーク」を分ける。未対応・対応中・保留・対応済みは固定の業務状態、対応マークは自由分類とする。
3. 保存した検索に、所有者・アカウント範囲・版・参照方法を持たせる。現行APIは自分専用検索を他スタッフへ返し、所有者以外でも更新・削除できるため、実装前に閉じる。
4. タグ、項目、マーク、検索のすべてにアカウント範囲を持たせる。現行は複数LINEアカウントを持てる一方、これらの定義が全体共通で、担当範囲の境界をDB/APIで保証できない。

| 評価軸 | 現在 | 要件どおり実装後 |
|---|---:|---:|
| V6 UI・UX | 96 | 99 |
| Lステップ・Liny競争力 | 97 | 100 |
| 現行実装 | 64 | 98 |
| データ安全性 | 53 | 98 |
| 実現可能性 | 96 | 99 |
| 要件確定度 | 98 | 99 |

完全に不可能な画面はない。画像・PDF項目、項目移行、CSV取込、複数の自動変更条件も実装可能である。除外するのは、LINEプロフィールから本名・電話・住所・生年月日などを自動取得すること、型の違う既存値を100%正しく自動変換すること、削除済み定義を履歴なしで完全復元すること、曖昧な条件をAIだけで自動修復することである。

## 2. 達成すること

> 運用者が、友だちを分類する定義を安全に作り、どこで使われ、誰に付き、何が自動で動くかを理解してから変更できる。

- タグを分類し、手動・フォーム・流入・外部連携・自動処理から付ける
- タグ付与をきっかけに、版を固定したアクションを安全に実行する
- 友だちごとの値を型付き項目として保存し、フォーム・配信・ECと共有する
- 項目の種類や差し込み名を壊さず、新しい項目へ移行する
- 固定の対応状況と、自由な対応マークを使い分ける
- 条件、並び順、表示列を保存し、権限範囲内で再利用する
- 定義の使用先と変更影響を事前に確認する
- CSVは選択、解析、dry-run、確認、実行、結果の順で処理する
- すべての操作をLINEアカウント範囲とスタッフ権限で守る

## 3. 用語を固定する

| 用語 | 意味 |
|---|---|
| タグ | 同じ属性・分類・一時状態を持つ友だちへ複数付けられる定義 |
| タグフォルダ | タグを整理する1段の入れ物。削除してもタグは未分類へ残る |
| 友だち情報欄 | 友だちごとに異なる型付きの値を1項目1値として持つ定義 |
| 差し込み名 | テンプレート等から値を参照する不変キー |
| 対応状況 | 未対応・対応中・保留・対応済みの固定業務状態 |
| 対応マーク | 自由に作れる友だちの業務分類。対応状況とは別物 |
| 保存した検索 | 条件、対象アカウント、並び順、表示項目を再利用する定義 |
| ライブ参照 | 保存検索の最新版を次回実行時に使う参照方法 |
| 固定参照 | 選択時点の検索版または対象者スナップショットを使う参照方法 |
| 連動アクション | タグ付与などをきっかけに、オートメーション実行基盤で動く処理 |
| アーカイブ | 新規利用を止め、既存の履歴・参照・値を残す状態 |

## 5. すべての定義に共通する要件

### 5-1. アカウント範囲

すべての定義に次を持つ。

- `organization_id`
- `scope_type`: `organization | account_group | line_account`
- `scope_id`
- `created_by`
- `updated_by`
- `status`: `active | archived`
- `version`
- `created_at`、`updated_at`

一覧の上部に現在の範囲を表示する。複数アカウントへ共通利用する場合は、明示的に「全アカウント共通」を選ぶ。担当アカウント外の定義・人数・検索結果をAPIから返さない。

### 5-2. 競合と履歴

- 更新は`version`またはETagで楽観ロックする
- 別スタッフが先に更新した場合は409を返し、差分を見せる
- 作成、変更、アーカイブ、復元、付与、解除、利用、CSV出力を監査へ残す
- 監査には担当者、対象範囲、実行元、変更前後、理由、実行IDを持つ
- 公開済み定義を物理削除しない
- 物理削除は未使用・履歴なし・作成直後の定義だけに限定する

### 5-3. 使用先

一覧と削除確認に固定文言・固定件数を置かない。依存関係APIから次を返す。

- 一斉配信、シナリオ、リマインダ、自動応答、回答フォーム
- リッチメニュー、流入リンク、オートメーション、予約、イベント
- テンプレート差し込み、保存検索、分析、外部連携、EC、アフィリエイト
- 下書き、公開版、停止版、過去実行の区別

使用中の定義をアーカイブするときは、新規選択を止めるだけか、代替へ置換するかを選ぶ。公開版は、過去の意味を維持するため参照ID・版を残す。

## 6. タグ

### 6-1. タグ定義

必須項目:

- 名前、フォルダ、説明、★表示
- アカウント範囲、状態、表示順
- 手動付与を許可するか
- 付け直し方針: `初回のみ | 付け直しごと`
- 連動設定の有効・無効
- マイル設定
- 連動オートメーションIDと公開版

名前は範囲内で一意、1〜80文字。大文字小文字、前後空白、全角・半角の正規化規則を固定する。表示名は変更できるが、内部IDは変えない。

### 6-2. 付与と解除

タグ付与イベントに次を持つ。

```json
{
  "eventId": "uuid",
  "friendId": "friend-id",
  "tagId": "tag-id",
  "action": "added",
  "sourceType": "manual|form|inflow|ec|automation|csv|api",
  "sourceId": "source-id",
  "actorId": "staff-id-or-null",
  "idempotencyKey": "source:event:friend:tag",
  "occurredAt": "ISO-8601"
}
```

- 現在値の`friend_tags`と、追記型の付与履歴を分ける
- 同一冪等キーの再送で二重付与・二重マイルを起こさない
- 解除後も付与元と過去実行を残す
- 自動付与の起点が削除・停止された場合は一覧で「要確認」と出す
- 一括付与は機能3の一括実行台帳を使う

### 6-3. 連動アクション

タグ画面に連動アクションの編集UIを残す。ただし保存先はV6 25の共通アクション・オートメーション定義とする。

- トリガーは`tag.added`
- テキスト、テンプレート、タグ、友だち情報、対応状況、対応マーク、シナリオ、リマインダ、リッチメニュー、運用者通知、マイルを共通アクションで表す
- 実行順、待機、失敗時方針、再試行、停止条件を持つ
- 公開時に版を固定する
- 待機中にタグが外れた場合の`中止 | 続行`をアクションごとに持つ
- 実行中の定義を編集しても、すでに開始した実行は開始時の版を使う
- 循環参照を公開前に検出する

タグ専用の第2実行エンジンは作らない。

### 6-4. マイルと遡及反映

- 本人マイル、紹介者マイル、倍率、優先度、付け直し方針を保存する
- 遡及前に対象人数、既付与除外、紹介者あり、合計マイル、対象アカウントをサーバで計算する
- プレビュー結果に期限付き`previewToken`を発行する
- 実行時に条件を再確認し、差があれば再確認を要求する
- 実行台帳で成功、既処理、除外、失敗を表示する
- 再試行しても同じ台帳行・冪等キーを使う
- 倍率は過去へ適用せず、次回発生イベントから効かせる
- メッセージ等の連動アクションは明示選択なしに遡及実行しない

### 6-5. タグの削除・アーカイブ

既定操作はアーカイブとする。

- 付与中の友だち数
- 現在の参照先と公開版
- 待機中の実行数
- マイル・アクションへの影響
- 代替タグへの置換件数
- 過去履歴が残ること

を表示する。アフィリエイトだけでなく、1件でも有効な公開参照がある場合は物理削除を止める。タグ名入力は最終確認として残すが、依存関係検査の代わりにしない。

### 6-6. タグCSV

V6のCSVは「タグ定義の一括作成」と固定する。友だちへのタグ付与CSVは機能3の友だちCSVへ分ける。

手順:

1. 版付きテンプレートを取得
2. UTF-8のCSVを選ぶ
3. MIME、容量、列、500行上限を検査
4. 正規化後の重複、既存タグ、存在しないフォルダ、権限外範囲を表示
5. 行ごとに`作成 | 更新しない | 要修正`を出す
6. dry-run結果を確認する
7. 冪等キー付きジョブを実行する
8. 成功・スキップ・失敗CSVを取得する

同名タグを黙って更新しない。存在しないフォルダを黙って未分類へ確定せず、確認画面で「未分類として登録」を明示する。CSV出力では先頭が`= + - @`のセルを式として実行されない形へ無害化する。

## 7. 友だち情報欄

### 7-1. 型

採用する型:

- 1行、複数行、数値、日付、日時
- 電話、メール、URL
- 単一選択、複数選択、真偽
- 画像、PDF

現行の`text`、`textarea`、`number`、`date`、`select`、`multi_select`、`checkbox`、`url`、`tel`、`email`は維持する。`datetime`、`image`、`pdf`を追加する。

画像・PDFはURL文字列を値にせず、登録メディアまたは専用添付の`media_id`を保存する。R2上のキー、MIME、サイズ、ハッシュ、ウイルス検査、所有範囲を検証する。画像・PDFはテキスト差し込み不可とし、参照用URLを自動生成して本文へ漏らさない。

### 7-2. 型付き値

現行`friend_field_values.value TEXT`は互換読取を残し、次を追加する。

- `value_text`
- `value_number`
- `value_date`
- `value_datetime`
- `value_json`
- `media_id`
- `source_type`、`source_id`
- `updated_by`、`updated_at`
- `version`

APIは項目定義に応じて型、文字数、選択肢、日付、メール、電話、URLを検証する。現行のようにすべて`String(raw)`で保存しない。

### 7-3. 選択肢

- 選択肢は表示名でなく不変IDを持つ
- 並び順、色、状態を持つ
- 表示名変更で既存値を壊さない
- 使用中選択肢は削除せずアーカイブする
- 複数選択はID配列として保存し、区切り文字列にしない

### 7-4. 差し込み名と既定値

- 差し込み名は作成後不変
- 既存の予約語、形式検証、範囲内一意を維持する
- 既定値は型検証し、最大200文字というV6ルールを型ごとに調整する
- 空欄、未登録、既定値適用を区別する
- 送信プレビューで「実値」「既定値」「空欄」を表示する
- 画像・PDFには既定値を置かない

### 7-5. 個人情報

- `is_personal`は手動指定を正とし、自動推定は提案までにする
- 値の閲覧、編集、CSV出力、API利用を別権限にする
- 権限がない値はマスクでなくAPIから返さない
- 閲覧、変更、出力、削除、移行を監査する
- EC側を正とする項目は管理画面から更新できない理由を返す
- 保持期間、削除要求、法的保持、バックアップからの消去方針を定義する

### 7-6. 項目移行

V6 4-2-Bを採用する。

1. 新しい項目定義を作る
2. 元項目の値と使用先を棚卸しする
3. 変換ルールを選ぶ
4. dry-runで変換可能・要確認・変換不可を出す
5. テンプレート、フォーム、予約、EC等の切替対象を表示する
6. 実行時点の対象を固定する
7. 値を冪等に移す
8. 参照先を版単位で切り替える
9. 件数・サンプル・ハッシュを照合する
10. 元項目を30日間読み取り専用で保持する
11. 問題があれば参照先を切り戻す
12. 30日後にアーカイブする

型変換できない2人などを黙って捨てず、個別修正キューへ残す。

### 7-7. 削除

値が1件でもある、または公開版から参照される項目は物理削除しない。アーカイブ、代替項目への移行、参照先切替を案内する。値の件数だけでなく、フォーム・テンプレート・予約・自動処理・ECマッピング・保存検索の使用先を表示する。

## 8. 対応状況と対応マーク

### 8-1. 分離

固定の対応状況:

- `unhandled` 未対応
- `in_progress` 対応中
- `on_hold` 保留
- `resolved` 対応済み

自由な対応マーク例:

- 要折り返し
- VIP対応
- 返金確認
- 担当者確認

V6のマーク一覧に未対応・対応中等を例として置くことはできるが、固定の対応状況KPIや返信完了判定は対応状況を正として計算する。受信箱のトーク状態、友だちの対応状況、自由な対応マークを同じ列・同じAPIへ潰さない。

### 8-2. 自動変更

受信、返信、担当割当、期限超過、条件一致をトリガーとして選べる。保存先はV6 25のオートメーション定義とし、対応マーク表には参照ルールを要約表示する。

- ルール優先度を明示する
- 同時一致時は1つだけ採用するか、複数マークを許すかを定義する
- 現行は友だち1人につき1マークなので、V6では単一選択を維持する
- 同一時刻の複数ルールは優先度の最上位1件だけを実行する
- 手動変更は自動ルールより優先する保護時間を設定できる
- 変更元、担当者、前後値、理由を履歴へ残す

### 8-3. 初期値・削除

- 初期値は範囲ごとに必ず1つ
- 初期値を0件または複数にできないDB制約を置く
- 使用中マークを削除するときは置換先を必須にする
- 初期値へ置換する場合も対象人数を確認する
- 置換とアーカイブを1トランザクションで行う
- 現行の`ON DELETE SET NULL`を最終動作にしない
- 一括変更も1人ずつ監査イベントを残し、実行台帳から追跡できるようにする

## 9. 保存した検索

### 9-1. 所有権と表示

- 個人用は作成者本人と管理者だけが閲覧・更新・削除できる
- 共有は対象アカウント範囲の利用者へ返す
- 他人の個人用検索を一覧APIで返さない
- 更新・削除は所有者または管理権限をサーバで検査する
- 上限50件は組織全体でなく、所有者・範囲・プラン単位で数える

### 9-2. 条件DSL

機能3の友だち検索と同じ版付きDSLを使う。

```json
{
  "version": 1,
  "root": {
    "op": "and",
    "children": [
      { "kind": "tag", "operator": "includes", "values": ["tag-vip"] },
      { "kind": "field", "fieldId": "contract", "operator": "is_empty" }
    ]
  },
  "accountIds": ["account-a"],
  "sort": "last_activity_desc",
  "columns": ["name", "tags", "assignee"]
}
```

- 条件種類ごとに許可演算子と値の型を検証する
- 存在しないタグ・項目・マーク・フォームを保存時に弾く
- 参照先が後でアーカイブされたら「要修正」と表示する
- 権限外の条件を黙って無視しない
- 該当人数はサーバで同じ条件評価器を使って計算する
- 一覧、配信、オートメーションで別実装の条件判定を持たない

### 9-3. 版と参照方法

保存した検索の更新履歴を持つ。

- 保存時に`revision`を増やす
- 一斉配信・オートメーションから使うときは`ライブ参照`と`固定参照`を選ぶ
- ライブ参照は「次回実行から対象が変わる」と明示する
- 固定参照は検索revisionまたは対象者スナップショットを保持する
- 予約済み配信は原則として実行直前に対象を固定し、その後の検索編集で変えない
- 利用先、利用版、最終利用日時、実行回数を記録する
- 編集前に影響する利用先を表示する

V6 4-4-Aの「条件を変えると次回実行から対象が変わります」は、ライブ参照のときだけ表示する。

## 11. API

### 11-1. 読取

- `GET /api/tags?scope=&status=&withCounts=1`
- `GET /api/tags/{id}/dependencies`
- `GET /api/tags/{id}/history`
- `POST /api/tags/{id}/retroactive-preview`
- `GET /api/tag-imports/{runId}`
- `GET /api/friend-fields?scope=&status=&withUsage=1`
- `GET /api/friend-fields/{id}/dependencies`

- `GET /api/support-marks?scope=`
- `GET /api/saved-searches?scope=&owner=me`
- `POST /api/saved-searches/preview`
- `GET /api/saved-searches/{id}/dependencies`

### 11-2. 更新

- タグ、フォルダ、項目、マーク、検索のPOST/PATCHは`version`必須
- DELETEは原則`POST /archive`へ置換
- 遡及、CSV、移行、置換は`Idempotency-Key`必須
- 実行系は202と`runId`を返す
- dry-run結果と実行条件が変わったら409を返す
- 部分失敗を200成功へ潰さず、行別結果を返す
- エラーは`code`、人向け説明、修正方法、対象行・項目を返す

### 11-3. サーバ側の必須検査

- スタッフの担当アカウント範囲
- 読取、設定変更、付与、個人情報閲覧、CSV出力、アーカイブ権限
- 参照IDの存在と範囲一致
- 型、長さ、選択肢、日付、ファイル、式、件数
- 同時更新、重複、循環参照
- 公開版・待機実行・予約配信への影響
- 冪等キーと再試行状態

## 13. 状態とUI

## 14. Lステップ・Linyとの差

### 14-1. 同等以上にする必須項目

- タグ、情報欄、対応マークで友だちを分類・検索・配信へ利用する
- フォーム回答や友だちの操作からタグ・情報欄を自動更新する
- 情報欄に長文、画像、PDF、選択肢、日付を持つ
- 情報欄をメッセージへ差し込む
- 友だち一覧へ★付き項目を出す
- CSVでテキスト・選択肢・日付を取込できる
- 対応マークで人的対応の対象を絞る
- 機能単位・項目単位のスタッフ権限を守る

### 14-2. V6が超える点

- タグの付与元、マイル、アクション、使用先を1一覧で読める
- 遡及反映の人数・合計を保存前に確認できる

- ライブ条件と固定条件を選べる

## 15. 除外する項目

### 15-1. API・事実上不可能

- LINEプロフィールから本名、電話、メール、住所、生年月日を自動取得する
- ブロック中または同意前の利用者プロフィールを常に取得できるとする
- LINE表示名やプロフィール画像だけで本人情報を確定する
- 異なる型の自由入力を100%正しく自動変換する

### 15-2. 危険なので採用しない

- タグ専用の別アクション実行エンジン
- 使用中定義の物理削除
- 条件項目が消えたときの黙った無視

- 個人用検索を他スタッフへ返すこと
- アカウント範囲を持たないタグ・項目・マーク・検索
- CSV選択直後の即時確定
- 同名タグの黙った上書き
- 項目の種類・差し込み名の直接変更
- 個人情報をマスクだけしてAPIへ返すこと
- 対応状況と対応マークの同一データ化
- 保存検索の編集を、利用先へ常に無条件即時反映すること
- 画面上の固定件数を実データとして扱うこと

## 16. 既存データ移行

1. `tags`、`friend_tags`、`folders`、`friend_fields`、`friend_field_values`、`support_marks`、`saved_searches`を件数・重複・孤児・範囲別に棚卸しする
