# V6 31 機能設定 要件定義（実装照合版・下書き）

更新日: 2026-08-26
対象: V6 31-x、現行 `/settings`、`/api/settings/features`、サイドメニュー・認可基盤

## 0. 結論と採点

V6は、必須機能、任意機能、まとめて切り替える機能、メニュー順、利用頻度、保存後の見え方を一つに整理している。単なる機能一覧ではなく、各社が必要な機能だけを見せる運用画面としてLステップより分かりやすく、要件定義へ進める。

ただし現行実装のオン・オフはサイドメニューを隠すだけで、URL直打ち、API、予約・配信などの自動処理は止めない。保存は複数キーを順番に書くため途中失敗で半分だけ反映され得る。指定したLINEアカウントが本人の管理範囲内かもこのroute内では確認していない。V6の言葉を「機能停止」と解釈して実装すると、表示だけ消えて処理が動く危険がある。

| 評価軸 | 現在 | 要件反映後 | 判断 |
|---|---:|---:|---|
| V6 UI/UX | 99 | 100 | 必須・任意・利用頻度・並び・見え方が明確 |
| Lステップ対抗力 | 100 | 100 | 契約別機能に加え、会社ごとのメニュー整理で上回る |
| 現行実装完成度 | 80 | 99 | 保存とメニュー反映はあるが、サーバ側強制がない |
| データ安全性 | 52 | 100 | 非原子的保存、範囲確認、依存中処理がP0 |
| 実現可能性 | 99 | 100 | 既存設定とメニュー定義を拡張できる |
| 要件確定度 | 98 | 100 | オフの意味を固定すれば実装可能 |

不可能な画面はない。除外するのは、コードやDBテーブル自体を管理画面から削除すること、契約プランを機能設定で上書きすること、緊急停止の代用、稼働中の配信・予約・公開ページを警告なく止めること、データ削除、ユーザーごとに別の全体順を持つこと、利用回数だけで自動的にオフにすることである。

### 1-2. 現行資産

## 2. Lステップとの差

Lステップは公式の[全機能一覧](https://linestep.jp/lp/01/features_top.html)でプランごとの利用可能機能を示し、[スタッフ管理機能](https://linestep.jp/lp/01/features34.html)で4段階と機能別権限を提供している。公開情報では、会社ごとに機能を隠し、利用頻度を見ながらサイドメニュー順まで整理する一体画面は確認できない。

V6は次で上回る。

- 契約上使える機能の中から、会社で使うものだけを表示
- 必須、任意、専用、試験機能を同じカタログで説明
- 利用頻度と依存中データを見て安全にオフ
- 実際のサイドメニューを保存前に確認
- 新機能追加時も既存の並びを壊さない
- ログインユーザー権限と組み合わせ、見える人だけに表示

機能設定はLステップの「プラン」と「スタッフ権限」の代替ではない。契約、会社設定、個人権限を分けたまま合成する。

## 3. 四つの状態を分離する

| 概念 | 決める人 | 意味 |
|---|---|---|
| 契約・entitlement | 運営側 | その会社が購入・利用できるか |
| 機能設定 | 会社の管理者 | 会社として管理画面で使うか |
| ログインユーザー権限 | 会社の管理者 | その人が見られる・変えられるか |
| 運用状態 | 緊急停止権限者 | 障害時に副作用を止めるか |

有効判定は次の積とする。

```text
契約で許可
かつ 会社の機能設定が有効
かつ ユーザー権限が view/edit
かつ 対象LINEアカウントの範囲内
かつ 操作時は運用停止されていない
```

サイドメニューは判定結果の表示であり、認可の正本ではない。

## 4. この機能で達成すること

会社の管理者が、不要な機能を安全に隠し、必要な機能だけを分かりやすい順に並べ、全利用者の管理画面を整理する。

1. 必須・利用可能・契約外・試験中を理解する
2. 機能単体または意味のあるbundleでオン・オフする
3. オフ前に稼働中データと影響を確認する
4. 同一区分内でメニュー順を決める
5. 保存前に実際の見え方を確認する
6. 一回の保存で全変更を同時反映する
7. 変更履歴から誰が何を変えたか確認する

## 5. 機能カタログ

クライアントとworkerへ別々の配列を手書きしない。サーバ側の共有カタログを正本にする。

必須項目:

- `feature_id`: 変更しないID
- 表示名、説明、区分、既定順
- `entitlement_key`
- `bundle_id`: 同じスイッチで切り替える単位
- required、specialized、experimental、retired
- dependencies、dependents
- `disable_policy`
- 関連route、API capability、dispatcher
- 導入version、廃止version

V6で同じスイッチと書かれた組は偶然同じkeyを使わず、bundleとして宣言する。

- 共通情報＋登録メディア
- 成果・アフィリエイト＋コンバージョン
- 予約管理＋予約設定
- 飲食店向け試験機能一式

`common_vars`のようにカタログ上だけ存在して画面から使われないkeyは、移行時にbundleへ統合するか廃止を明示する。

## 6. オフにする時の正式仕様

### 6-1. 共通

- データは削除しない
- 新規作成・編集APIは拒否する
- 閲覧URLは原則拒否し、設定画面へ戻る案内を出す
- 契約外と会社オフを別のerror codeにする
- 再度オンにすると元のデータと並びを復元する
- 変更は全利用者へ1分以内に反映し、次のAPI呼び出しから強制する

### 6-2. 稼働中の処理

機能オフで処理を黙って継続させず、黙って破壊もしない。まず影響確認APIを実行する。

| 状況 | 扱い |
|---|---|
| 稼働中なし | そのままオフ可能 |
| 下書き・履歴だけ | データ保持を示してオフ可能 |
| 公開ページ・稼働中配信・予約受付あり | オフを拒否し、停止先リンクと件数を表示 |
| 外部連携の配送待ち | 配送を完了・取消してからオフ |
| ほかの機能が参照 | 参照元を外すまでオフ不可 |

機能設定は正常運用中の構成変更であり、障害時の緊急停止ではない。公開中の回答フォーム、予約ページ、リッチメニュー、シナリオなどは、それぞれの機能で停止してからオフにする。

## 7. メニュー順

- 基本のダッシュボード、受信箱、友だち、友だち属性は固定
- 設定は末尾固定
- 区分をまたぐ移動は不可
- 非表示項目の順も保持し、再オン時に元の場所へ戻す
- 新規機能はカタログの意味上の隣へ挿入し、保存済み順を壊さない
- 不明ID、重複ID、別区分ID、必須項目欠落を400で拒否
- 並びはLINEアカウント単位または会社単位を明示する。V6は選択中LINEアカウント単位を正本とする
- 全ログインユーザーに同じ基本順を適用し、その上で個人権限による非表示を行う

V6の「34項目表示」は固定文言にせず、現在のカタログと有効機能から算出する。

## 8. 利用頻度

利用頻度は監査イベントから集計する。

- 直近90日の画面訪問人数、編集回数、実行回数、最終利用日
- 自動処理だけ動く機能は「自動実行中」と区別
- 0件でも計測開始前なら「未計測」とする
- 会社内の個人名は表示せず、管理者向け集計のみ
- 利用頻度だけで自動オフしない

「90日使われていない」は画面訪問だけで判定しない。稼働中定義、API利用、公開ページ利用、外部連携を含める。

## 9. データ

### 9-1. 追加・再構成

- `feature_catalog`
- `feature_bundles`
- `account_feature_settings`
- `account_feature_setting_versions`
- `feature_dependencies`
- `feature_usage_daily`
- `feature_setting_audit`

既存`account_settings`は移行元として残せるが、複数keyの一括保存とversion管理には専用テーブルを推奨する。

### 9-2. version

- アカウントごとに`settings_version`
- GETでversionを返す
- PUTは`expected_version`必須
- 競合は409とし、新旧差分を返す
- feature設定とitem orderを同一transactionで保存
- 失敗時は全ロールバック

## 10. API

### 10-1. 読み取り

- `GET /api/settings/features?account_id=`
  - catalog、entitlement、effective state、理由、依存数、usage、order、version
- `POST /api/settings/features/impact`
  - 変更案を保存せず検証し、稼働中、参照元、公開先、影響人数を返す

### 10-2. 保存

- `PUT /api/settings/features?account_id=`
  - `expected_version`
  - bundleごとのenabled
  - section内item order
  - impact確認token
  - 変更理由

サーバは、本人がそのaccountを管理できるか、owner/adminか、契約範囲、required、依存、orderを再検証する。順番に複数upsertせずtransactionを使う。

### 10-3. 利用時の強制

全管理APIはroute metadataの`feature_id`を持つ。機能オフなら、UIに関係なく403と`FEATURE_DISABLED`を返す。公開APIやdispatcherには機能別policyを適用する。未分類routeは30ログインユーザー要件と同様にCI失敗・runtime拒否とする。

## 11. 権限と監査

- 閲覧: owner/admin
- 変更: owner/adminのうち`feature_settings.edit`
- 契約変更: この画面では不可
- 試験機能: 運営側entitlementも必要
- 緊急停止: 運用状態の専用権限

監査に、操作者、対象account、前version、後version、変更前後、影響確認結果、理由、IP/UA、request IDを追記する。一般利用者は削除できない。

## 12. 状態

- 読込中: skeleton、操作不可
- 空: カタログ障害として扱い、初期化ボタンを出さない
- 読込失敗: 再読込。既定値を保存値と誤認させない
- 未保存: 下部追従バーで変更数と保存/破棄
- 保存中: 二重送信不可
- 成功: version更新、全画面へinvalidate通知
- 競合: 409で他者変更を表示し、再読込か差分再適用
- 依存中: オフ不可、停止先へ移動
- 契約外: 鍵表示、管理者でもオン不可
- 権限不足: 閲覧・変更ともサーバ側で拒否
- 一部失敗: 起こさず全ロールバック

## 13. 現行データ移行

1. `feature.*`、`sidebar.order`、`sidebar.item_order`をread-only棚卸し
2. 不明key、重複item、欠落item、既定値との差をCSV化
3. bundleへ正規化し、共有スイッチの矛盾を検出
4. 稼働中定義とオフ値の矛盾を抽出
5. dry-runで新しいeffective stateと現行サイドバーを比較
6. 専用テーブルへtransaction移行
7. 一定期間dual-readし、新を優先、差分監視
8. rollbackは旧値snapshotから行う

現行データを壊さないことはV6の邪魔にならない。旧keyを画面へ露出し続けず、migration adapterで新しいcatalogへ変換する。

## 14. 除外

- 管理画面からのコード削除、テーブル削除、データ削除
- 契約・課金プラン変更
- 緊急停止の代用
- 稼働中成果物を黙って停止
- 機能オフ中もURL直打ちやAPI利用を許すこと
- 利用頻度だけによる自動オフ
- 個人ごとの全体メニュー順
- 本番で試験機能をentitlementなしに表示
- 保存途中の部分反映
