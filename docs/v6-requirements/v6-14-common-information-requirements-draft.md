# V6 14 共通情報 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「14 共通情報」
対象範囲: 一覧、作成・編集、変更影響、変更履歴、期限、削除・差し替え、差し込み、数値操作、条件、移行

## 0. 結論と採点

V6を採用する。特に「変更前に全使用先を確認する」「変更前後の文を並べる」「文字数超過を検知する」「別の共通情報へ差し替えて削除する」は、Lステップ・Linyの一括反映を、事故を起こしにくい形へ進めた設計である。

ただし、そのまま実装へ渡してはいけない点が6つある。

1. V6は短い文字列だけに見える。Lステップ・Liny相当の長文、数値、年月日と、現行で持つURL・画像を型として残す。
2. `{会社名}`は画面表示用の分かりやすいキーとし、保存・参照は不変IDを使う。現行の`{{var.shop_hours}}`は移行中も動かす。
3. 使用中の値を変える場合は、直接保存させず、必ず影響確認を通す。予約中配信・公開中フォーム・文字数超過はサーバで再検査する。
4. 期限切れで自動的に空文字へするのを既定にしない。既定は「送信・公開を止めて運用者へ通知」。明示した代替値がある場合だけ自動切替する。
5. 数値の加算・減算を原子的にする。現行の読取後更新では同時実行時に在庫・残席を失う。
6. 共通情報をLINEアカウント範囲へ分ける。現行DBは複数LINEアカウントを持てる一方、`common_vars`にはアカウント範囲がない。

| 評価軸 | 現在 | 要件どおり実装後 |
|---|---:|---:|
| V6 UI・UX | 97 | 99 |
| Lステップ・Liny競争力 | 96 | 100 |
| 現行実装 | 67 | 98 |
| データ安全性 | 47 | 98 |
| 実現可能性 | 97 | 99 |
| 要件確定度 | 97 | 99 |

完全に不可能な画面はない。除外するのは、送信済みLINEメッセージの遡及変更、秘密値の共通情報保存、使用先を無視した物理削除、曖昧な文字列だけによる自動差し替え、同時更新を失う非原子的な数値操作、無期限の循環参照である。

2026-08-28の実装状況:

| 項目 | 状態 | 根拠 |
|---|---|---|
| 一覧の次回予約 | 実装済み | 一覧APIが次回予約と残り件数をまとめて返し、1行ごとのAPI呼出を廃止 |
| 使用中の物理削除防止 | 実装済み | 7種類の現行利用先を厳密な従来トークン単位で再走査し、APIを直接呼んでも409で停止 |
| 影響確認に失敗した削除 | 実装済み | 0件扱いにせず503で安全側に停止 |
| LINEアカウント境界 | 一部実装 | 一覧・作成・編集・予約・削除と、配信・自動応答・フォーム・シナリオ実行を選択／送信先アカウントで分離。所属不明の旧データは推測せず対象外 |
| V6一覧の骨格と状態 | 一部実装 | `WuKzU`へ移行し、本文タイトル重複、準備中操作、初回空と検索0件の混同を解消 |
| 版・範囲・履歴・原子的数値・差し替え | 未実装 | PR 14-1〜14-5の残り。機能14全体は完了扱いにしない |
| V6画像比較 | 未確認 | `WuKzU`・`yPkWe`を1440px/1920pxでClaudeへ引き渡す |

現在の削除防止は、危険な物理削除を先に塞ぐための互換層である。V6正本のアーカイブ・代替への差し替え・追記型使用先台帳は引き続き必要である。

既存の共通情報は、どのLINEアカウントに属するかを証明できる列が無かった。本文中の差し込みだけから所属を推測すると別店舗へ値を誤送信するため、自動共有・自動割当は行わない。既存行は保持し、管理者が対象アカウントを確認して明示割当する移行画面を別工程で用意する。現行の差し込み名はDB全体で一意のため、同じ差し込み名を複数アカウントで個別に持つための制約移行も残る。

- 変更前後の文章、予約中配信、公開中フォーム、文字数上限超過を確認できる
- 送信済み文は変わらないと明記する
- 削除時は代替キーへ一括差し替えを推奨する

## 2. 達成すること

> 運用者が、複数の配信・フォーム・画面で共通利用する情報を1か所で管理し、影響を確認してから安全に更新できる。

- 会社名、営業時間、住所、署名、注意事項、URL、日付、数値、画像を型付きで管理する
- メッセージ作成時に検索・選択し、入力ミスなく差し込む
- 値を変える前に、現在の使用先と変更後の表示を確認する
- 予約中、公開中、文字数超過、空値、期限切れを公開・送信前に止める
- 数値を予約、イベント、リッチメニュー、オートメーションから安全に増減する
- 数値・日付・文字列を条件に、配信・表示・処理を分ける
- 変更者、変更理由、変更前後、利用先、実際に送った値を追跡する
- 使用中の共通情報は、代替へ置換してからアーカイブする
- 複数LINEアカウントでは、範囲を明示し、別アカウントの値を誤配信しない

## 3. 用語を固定する

| 用語 | 意味 |
|---|---|
| 共通情報 | 同じ範囲の友だち・配信先に共通して使う型付きの値 |
| 表示名 | 運用者が一覧で読む名前。後から変更できる |
| 差し込み名 | 画面で見せる`{会社名}`のような短い名前。範囲内で重複不可 |
| 内部ID | 参照を壊さない不変ID。本文・設定の正本はこのIDを参照する |
| 従来キー | 現行の`{{var.shop_hours}}`。移行完了まで互換参照として残す |
| 現在値 | いま差し込まれる公開済みの値 |
| 下書き | 編集中で、まだ利用先へ反映されない値 |
| 変更版 | 変更前後、理由、担当者、公開日時を持つ追記型の履歴 |
| ライブ参照 | 送信・表示の実行時に、その時点の現在値を解決する参照 |
| 固定参照 | 公開時・予約時に指定版を固定し、後の変更を受けない参照 |
| 使用先 | テンプレート、配信、フォーム等、共通情報を参照している定義・版 |
| 解決結果 | 実際の送信・表示時に差し込まれた値と版 |
| アーカイブ | 新規選択を止め、履歴・過去参照を残す状態 |

## 4. 画面とルート

| 画面 | ルート・状態 |
|---|---|
| 一覧 | `/contents/vars` |
| 作成 | `/contents/vars/new` |
| 編集 | `/contents/vars/{varId}/edit` |
| 変更影響 | `/contents/vars/{varId}/impact?draftVersion={version}` |
| 変更履歴 | 編集画面内。全件は`/contents/vars/{varId}/history` |
| 使用先 | 編集または影響確認から`/contents/vars/{varId}/usages` |
| 削除・差し替え | 一覧上の全面オーバーレイ |

現行の`/contents/vars/edit?id=...`は旧URLとして受け、正規URLへリダイレクトする。V6の削除確認は全面オーバーレイ1枚とし、別ページを複製しない。

## 5. 共通情報の定義

### 5-1. 必須項目

- 表示名: 1〜200文字
- 差し込み名: 1〜64文字、範囲内で重複不可
- 内部ID: UUID、変更不可
- 種類
- 現在値または公開済み版
- フォルダ
- アカウント範囲
- 社内メモ
- 状態: `draft | active | expired | blocked | archived`
- 空値の扱い
- 有効開始・有効終了
- 作成者、更新者、作成日時、更新日時
- 楽観ロック用version

### 5-2. 種類

| 種類 | 入力 | 主な用途 | 検査 |
|---|---|---|---|
| 標準 | 200文字まで | 会社名、電話、営業時間 | 改行不可 |
| 長文 | 9500文字まで | 署名、規約、注意事項 | 改行可、媒体別上限を別途検査 |
| 数値 | 整数・小数 | 在庫、残席、料金 | 精度、最小・最大、丸め方 |
| 年月日 | 日付 | 開始日、記念日 | タイムゾーンを持たない日付 |
| 日時 | 日時 | 締切、公開時刻 | タイムゾーン必須 |
| URL | URL | 予約、地図、資料 | `https`を既定、危険なscheme禁止 |
| 画像 | メディアID | ロゴ、バナー | V6 15の登録メディアを参照 |
| 真偽 | ON/OFF | 営業中、受付可 | 表示文言を別に定義可能 |

現行の`text | url | image | number`は失わない。Lステップ・Liny相当の長文・年月日を追加する。画像はURL文字列を直接持たず、登録メディアIDを参照する。

種類は作成後に直接変更しない。別種類へ変える場合は、新しい共通情報を作成し、変換プレビュー、使用先差し替え、検証、旧定義アーカイブの順で移行する。

### 5-3. 差し込み名と内部参照

- 画面では`{会社名}`のように日本語で表示できる
- 保存する本文・構造化コンテンツは`commonVarId`を持つトークンを正本とする
- テキストのみの既存保存形式では`{{var.shop_hours}}`を互換キーとして解決する
- 表示名を変えても参照は壊れない
- 差し込み名を変える場合は、旧名をaliasとして保持し、使用先差し替え完了後に無効化する
- 共通情報の値に別の差し込みを入れる入れ子は、初期版では禁止する
- 将来許可する場合も循環検出、最大深度、解決順を必須にする

### 5-4. アカウント範囲

各定義に次を持つ。

- `organization_id`
- `scope_type`: `organization | account_group | line_account`
- `scope_id`
- `created_by`、`updated_by`

一覧、検索、挿入候補、API、実行時解決のすべてで範囲を検査する。複数アカウント配信では、送信先アカウントごとに値を解決する。全体共通値を使う場合も、画面で「全アカウント共通」と明示する。

## 6. 作成・編集・公開

### 6-1. 作成

1. 名前、差し込み名、種類、範囲、値、フォルダ、メモを入力する
2. 種類別バリデーションを行う
3. 同じ範囲の重複名・重複キーを確認する
4. 空値の場合は用途と空値動作を明示する
5. 保存して下書きまたは公開する

未使用の新規項目は作成画面から直接公開できる。最初から使用先へ差し込む場合は、利用先側の公開確認で検査する。

### 6-2. 編集

- 名前、フォルダ、メモの変更は値変更と分ける
- 値を変えると下書き版を作る
- 使用先が0件なら、検査後に直接公開できる
- 使用先が1件以上なら、「共通情報を保存」ではなく「影響を確認」へ進む
- 変更理由を必須にする
- 別スタッフが先に更新した場合は409を返し、差分を表示する
- 編集中に使用先が増減した場合は、公開直前に影響を再計算する

V6編集画面の直接保存ボタンは、未使用時だけ有効にする。使用中は影響確認を飛ばせない。

### 6-3. 変更履歴

変更履歴は追記型とし、次を残す。

- 版番号
- 変更前・変更後
- 名前、種類、範囲、期限、空値動作の差分
- 変更理由
- 作成者、承認者、公開者
- 作成、公開、失効日時
- 影響確認時の件数と警告数
- 戻し元の版

「前の版へ戻す」は過去行を上書きせず、過去値を元に新しい版を作る。

### 6-4. 固定参照とライブ参照

既定は用途別に分ける。

| 用途 | 既定 |
|---|---|
| 下書きテンプレート、未公開フォーム | ライブ参照 |
| 公開中フォーム、リッチメニュー | ライブ参照。ただし影響確認必須 |
| 予約前の一斉配信 | 選択可能 |
| 予約済み一斉配信 | 固定参照を既定。ライブへ変更する場合は警告 |
| シナリオ・リマインダの新規開始 | 公開版を開始時に固定 |
| 進行中シナリオ・リマインダ | 開始時の版を維持 |
| 法務文言、規約、価格 | 固定参照を既定 |
| 在庫、残席、営業時間 | ライブ参照を選択可能 |

V6の「予約中の配信にも効きます」は、すべてへ暗黙適用しない。予約済み配信をライブ参照にしている場合だけ効くと明示する。

この機能の利用先は**スナップショット型**である（`v6-32-feature-cross-review.md` §2）。配信job・ステップ・挿入先は取り込んだ版を固定し、新版への切替は利用先ごとに件数と差分を確認してmigration eventを記録する。上表のライブ参照は、利用先が明示的に選び影響確認を通した場合だけの例外とする。

## 7. 変更影響の確認

### 7-1. 使用先台帳

共通情報の使用先を追跡する。

- テンプレート、一斉配信、シナリオ、リマインダ、自動応答、友だち追加時配信
- 回答フォーム、リッチメニュー、予約、イベント、ウェビナー
- LINE通知、オートメーション、NEN配信、EC連携、外部連携
- 下書き、公開中、予約中、停止中、アーカイブ済みの区別
- 参照方法: `live | pinned`
- 参照している版
- 最終検査日時

本文スキャンだけを正本にしない。保存時に構造化参照を更新し、移行中の従来キーだけ定期スキャンで補う。

### 7-2. 影響プレビュー

影響APIは次を返す。

- 全使用先数と種類別件数
- すぐ変わる使用先、固定され変わらない使用先
- 予約中、公開中、進行中
- 現在文と変更後の文
- 媒体別の文字数・バイト数・JSON構造・URL・altText検査
- 空になる箇所
- 文字数超過、必須値欠落、無効URL、画像未公開
- 対象アカウントと権限外件数
- 送信済み・完了済みは変わらないこと

プレビューには短時間有効の`previewToken`、対象版、使用先集合のハッシュを持たせる。公開時に再計算し、件数・警告・版が変わっていれば再確認を求める。

### 7-3. 公開を止める条件

- 文字数・構造・必須値のエラー
- 公開中または予約中の使用先が空になる
- 権限外の利用先へ影響する
- 競合更新がある
- 有効なプレビューがない
- 使用先の公開版を読み取れない
- URL・画像・日時が型検査に通らない

警告だけで続行できるものと、エラーで止めるものをAPIで分ける。「おすすめします」だけで危険な変更を通さない。

## 8. 期限とスケジュール

### 8-1. 有効期間

- `valid_from`と`valid_until`を持つ
- 時刻を使う場合はアカウントのタイムゾーンを表示する
- 期限前通知を1日前・3日前・7日前から選べる
- 期限切れ時動作を明示する

期限切れ時動作:

1. 代替版へ切り替える
2. 固定の代替文へ切り替える
3. 影響する送信・公開を止め、運用者へ通知する（既定）
4. 空文字へする（使用先0件、または影響確認で明示承認した場合のみ）

### 8-2. 更新予約

現行の1回だけの値切替を引き継ぐ。数値はさらに次を持つ。

- 代入、加算、減算
- 日次、週次、月次の繰り返し
- 開始、終了、タイムゾーン
- 最小、最大、負数許可
- 冪等キー
- 実行履歴と次回実行

乱数代入は業務上の再現性・監査性が低いため、初期版では除外する。必要になった場合は用途、seed、範囲、監査を別要件にする。

## 9. 数値操作と条件

### 9-1. 数値操作

- 数値を文字列列の読取後に更新しない
- DB上で型付き数値を原子的に更新する
- `operation_id`と冪等キーを持つ
- 同じイベントの再送で二重加算しない
- 最小値・最大値をDBで検査する
- 在庫・残席が0未満になる更新は409で止める
- 操作前後、起点、実行IDを履歴へ残す

現行`applyCommonVar`のread-modify-writeは置き換える。

### 9-2. 条件

共通条件部品から次を指定できる。

- 数値: 等しい、以上、以下、範囲内
- 年月日・日時: 前、後、期間内、期限までの日数
- 標準・長文: 一致、含む、空、空でない
- 真偽: ON、OFF

条件はオートメーションの公開版へ保存し、共通情報画面には使用先として表示する。共通情報専用の別条件エンジンは作らない。

## 10. 差し込みと実際の送信

### 10-1. 挿入UI

- テンプレート、一斉配信、シナリオ、リマインダ、自動応答、フォーム等で同じ挿入部品を使う
- 名前、種類、範囲、現在値、期限、空状態を検索できる
- 選択後はチップ表示し、内部IDを保存する
- 値そのものをコピーしたのか、ライブ参照を入れたのかを区別する
- プレビューは現在値、指定日時の予定値、テスト対象アカウントで切り替える

### 10-2. 解決

- 実際の送信アカウント、送信日時、固定版、範囲から値を解決する
- 値を解決できない場合は、空で黙って送らず、事前検査または送信失敗へ分ける
- Flex等のJSONは、文字列値だけを安全に置換し再serializeする
- 共通情報の値を新たなテンプレート構文として再解釈しない
- 一斉配信、複数アカウント重複排除配信、テスト配信で同じ解決器を使う

現行の複数アカウント重複排除配信は`{{var.*}}`を解決する値を渡していない。V6実装前に単一の解決器へ統合する。

### 10-3. 送信履歴

送信・表示ログには次を残す。

- 共通情報ID、版、解決値
- 送信アカウント、宛先、送信時刻
- 解決後の実送信本文または検証可能なスナップショット
- 配信・シナリオ・フォーム等の起点ID
- エラー時は未解決キーと理由

送信済みの文は変更しない。履歴画面も現在値で再描画せず、送信時の解決結果を表示する。

## 11. 削除・差し替え

### 11-1. 既定はアーカイブ

- 使用先0件でも、変更履歴または送信履歴があればアーカイブする
- 物理削除は未公開・未使用・履歴なしの作成直後データだけ
- アーカイブ後は新規差し込み候補から外す
- 過去版、送信履歴、使用先履歴からは読める

### 11-2. 代替へ差し替え

1. 使用先と版を取得する
2. 同じ範囲・互換種類の代替だけ候補にする
3. 全使用先で変更前後をプレビューする
4. 構造・文字数・空値を検査する
5. トランザクションまたは再開可能ジョブで参照を置換する
6. 件数を照合する
7. 旧定義をアーカイブする
8. 変更履歴と実行結果を残す

名前だけの文字列置換は行わない。参照IDまたは厳密な従来キー単位で置換する。

### 11-3. このまま削除

V6の確認入力は残すが、使用先がある定義の物理削除には使わない。「このまま削除」は「このままアーカイブ」に変更する。使用先を空にする操作は、代替なしで全利用先を明示編集した場合だけ許可する。

## 13. API

| 操作 | API | 要点 |
|---|---|---|
| 一覧 | `GET /api/common-vars` | 範囲、検索、状態、期限、未使用、並び、カーソル |
| 詳細 | `GET /api/common-vars/{id}` | 現在版、下書き、使用数、履歴要約 |
| 作成 | `POST /api/common-vars` | 型・範囲・重複検査 |
| 下書き更新 | `PATCH /api/common-vars/{id}/draft` | `If-Match`必須 |
| 影響確認 | `POST /api/common-vars/{id}/impact-preview` | draft版、使用先ハッシュ、警告、エラー |
| 公開 | `POST /api/common-vars/{id}/publish` | previewToken、理由、再検査 |
| 使用先 | `GET /api/common-vars/{id}/usages` | 種類・状態・版・参照方法 |
| 履歴 | `GET /api/common-vars/{id}/versions` | 追記型履歴 |
| 戻す | `POST /api/common-vars/{id}/versions/{version}/restore` | 新しい下書きを作る |
| 数値操作 | `POST /api/common-vars/{id}/operations` | 原子的、冪等 |
| 予約 | `POST /api/common-vars/{id}/schedules` | 1回・繰返し、次回実行 |
| 差し替え | `POST /api/common-vars/{id}/replace` | previewToken、代替ID、非同期ジョブ |
| アーカイブ | `POST /api/common-vars/{id}/archive` | 使用先・履歴保持 |
| CSV出力 | `POST /api/common-vars/exports` | 監査、期限付きダウンロード |

一覧APIは、現行の1項目ごとのスケジュール取得をやめ、次回予定と使用数をまとめて返す。100件で100回APIを呼ぶN+1を残さない。

## 14. 権限と安全性

権限を分ける。

- `common_var.definition.read`
- `common_var.definition.create`
- `common_var.draft.edit`
- `common_var.impact.preview`
- `common_var.version.publish`
- `common_var.number.operate`
- `common_var.usage.replace`
- `common_var.definition.archive`
- `common_var.definition.export`
- `common_var.audit.read`

命名は共通基盤（`v6-shared-platform-requirements.md` §3）の`domain.resource.action`に従う。

APIで範囲と権限を検査する。画面の非表示だけにしない。権限外の使用先名・本文・件数も返さない。

共通情報へ保存してはいけないもの:

- LINEチャネルアクセストークン
- APIキー、Webhook署名秘密、パスワード
- クレジットカード情報
- 個人ごとに異なる個人情報
- HTML、JavaScript、SQLなどの実行コード

秘密値は外部連携の秘密情報保管へ、友だちごとの値は友だち情報欄へ保存する。

## 15. 状態、エラー、アクセシビリティ

各画面に次を定義する。

- 読込中: スケルトンまたは進捗、二重操作不可
- 空: 「共通情報を作る」導線
- 検索0件: 条件解除だけ。作成導線と混同しない
- エラー: 再試行、入力保持、原因別文言
- 権限不足: 何ができず、誰へ依頼するか
- 競合: 自分と最新の差分、再読込、下書き保存
- 影響計算中: 件数と警告が確定するまで公開不可
- 期限切れ: 対象使用先と復旧導線
- 一部失敗: 差し替えジョブの成功・失敗・再試行

要件:

- 全操作をキーボードで行える
- ダイアログはフォーカストラップ、Esc、閉じた後のフォーカス復帰を持つ
- 色だけで警告・エラー・状態を示さない
- 長い値は単語途中で折らず、省略表示と全文確認を用意する
- 1440px・1920pxで主要画面に横スクロールを出さない
- 200%拡大でも主要操作を失わない

## 16. Lステップ・Linyとの差

| 項目 | Lステップ・Liny | V6要件 |
|---|---|---|
| 一元管理・差し込み | あり | あり |
| 種類 | 標準・長文・数値・年月日 | それらにURL・画像・日時・真偽を追加 |
| 数値操作 | 代入・加算・減算、スケジュール | 原子的更新、冪等、履歴、上限下限を追加 |
| 条件分岐 | 数値等を条件に利用 | 共通条件部品と公開版へ統合 |
| 変更影響 | 一括反映が中心 | 使用先、変更前後、予約中、公開中、上限超過を事前表示 |
| 変更履歴 | 公開情報だけでは詳細不明 | 版、理由、担当者、戻しを必須化 |
| 削除 | 公開情報だけでは詳細不明 | 代替へ安全に差し替え、既定はアーカイブ |
| 送信履歴 | 公開情報だけでは詳細不明 | 実送信時の版と解決値を保存 |
| 複数アカウント | 製品内の単位に依存 | 組織・グループ・LINEアカウント範囲を明示 |
| URLクリック計測 | Lステップは共通情報URLへURL設定不可 | URL型でも追跡リンク生成を明示選択できる |

競争力の中心は「一括反映」そのものではない。変更事故を、使用先・変更後文・予約状態・上限検査まで見せて止められることでLステップ・Liny越えを狙う。

## 17. 除外するもの

- 送信済みLINEメッセージを後から変更・取消すること
- 共通情報に秘密値・パスワード・個人別情報を保存すること
- 使用中定義を確認なしで物理削除すること
- 期限切れを暗黙に空文字へし、そのまま送ること
- 名前の部分一致だけで全本文を自動置換すること
- 共通情報の値に任意コード・任意式を入れて実行すること
- 初期版で共通情報を無制限に入れ子参照すること
- 非原子的な数値更新、冪等キーなしの増減
- 乱数の自動代入
- 外部システムを正本にするリアルタイム同期。必要時はV6 26外部連携で別途定義する
- 正常画像なしでV6との視覚一致を完了扱いにすること

### 18-2. 移行手順

## 22. 公式比較根拠

- Lステップ公式: 共通情報は全友だちへ同じ値を配信文へ挿入し、標準・長文・数値・年月日の4種類を持つ
- Lステップ公式: テンプレート等で置換タグから挿入し、プレビュー確認、データ移行ができる
- Lステップ公式: 数値はスケジュール更新、代入・加算・減算、条件指定に使える
- Lステップ公式: 共通情報のURLはURL設定を利用できないという制約がある
- Liny公式: 営業時間、連絡先、署名、規約を一元管理し、一か所の変更を全体へ反映する
- Liny公式: 在庫・予約可能人数を管理し、値に応じた案内分岐に使える

## 23. 最終判断

V6の画面方向は正しい。特に影響確認と差し替え削除は残す。100点に近づけるために削るのは画面ではなく、危険な挙動である。

実装前に必ず直す要件は次の4点。

1. 使用中の直接保存を禁止し、影響確認を必須にする
2. 期限切れの暗黙空文字送信を禁止する
3. 複数アカウント範囲と共通解決器を作る
4. 数値更新を原子的・冪等にする

この4点を満たせば、V6はLステップ・Linyの共通情報機能を機能面で満たし、変更事故の予防、監査、削除安全性で上回れる。
