# V6 34 はじめの設定と案内 要件定義（実装照合版・下書き）

作成日: 2026-09-03
対象: 初回セットアップの順路、レシピ、マニュアル導線、エラー文面の対応表、空状態の文言規則。現行 `packages/create-line-harness`、Worker `/setup` 導入ガイド、共通トップバー `shared/top-bar.tsx`、`lib/manual-links.ts`、`shared/not-connected.tsx`、`shared/list-state.tsx`、各 route のエラー応答

## 0. 結論と採点

Lステップ最大の弱点は、初期設定が LINE Developers、LINE公式アカウントマネージャー、Lステップの複数画面にまたがり、公式自身が初期設定手順と導入後に最初に行う設定を別記事で説明していることにある（`docs/lstep-liny-screen-behavior-research-2026-08.md` §3-1）。同じ調査は「レシピから開始」「エラーを直せる文章にする」を P1 に挙げている（同 §5）。V6 の 32 本にはこの要件がゼロだった。本書はそれを 1 本にまとめる。

現行には、セットアップ CLI（Cloudflare 認証、D1、Worker、管理画面、LINE 資格情報の登録、Owner 作成を 1 コマンドで行う）、Worker の `/setup` 導入ガイド、トップバーの `マニュアル`（URL 未確定で全部非活性）、未取得を `—` で表す `not-connected.tsx`、4 状態の `ListState`、BAN 検知の運用者通知がある。一方で、管理画面に入った後の「最初の 1 通が届く」までの順路が無く、レシピが無く、マニュアル URL の正本表が無く、エラー文面は route ごとにばらばらで、英語のまま画面に出るものが多い。

| 評価軸 | 現在 | 要件反映後 | 判断 |
|---|---:|---:|---|
| V6 UI/UX | — | 98 | 専用画面が無い。§5 の新規画面をPencilへ追加して確定 |
| Lステップ対抗力 | 70 | 100 | 順路 1 本、レシピ 1 操作、マニュアル 1 箇所で最大の弱点を突く |
| 現行実装完成度 | 45 | 97 | CLI と部品はある。順路・レシピ・対応表が無い |
| データ安全性 | 80 | 100 | レシピ複製の冪等と権限、エラー文面からの内部情報漏れ防止 |
| 実現可能性 | 97 | 99 | 既存定義 API の複製で作れる。新しい実行基盤は要らない |
| 要件確定度 | 92 | 98 | マニュアル URL の確定と 3 レシピの本文だけが残る |

除外するのは、レシピを「特別な定義」として実行時に別扱いすること、ウィザードが完了するまで他の画面を閉じ込めること、マニュアルを画面ごとに埋め込むこと、エラーの原文（英語・内部語・SQL）を画面へそのまま出すこと、AI が無承認で設定を生成することである。

## 2. Lステップとの差

### 2-1. 超える点

- 初回セットアップを「最初の 1 通が届く」までの 1 本の進捗として、管理画面の中で完了させる。Lステップは公式記事を読みながら複数画面を行き来する
- レシピを 1 操作で複製し、作られた定義とつながりを一覧で見せる。Lステップは機能ごとに作りに行く
- マニュアルをトップバー 1 箇所に固定し、画面 ID から公式記事へ飛ぶ。リンク切れを定期確認する
- エラーコードごとに運用者向け文面と次の行動を持ち、`action execution failed` のような原文を出さない
- 空状態を 2 種類に固定し、作れる一覧にはボタン名に対象を含めた作成導線を必ず出す

### 2-2. 同等の点

- LINE Developers での作業（チャネル作成、Webhook URL、LIFF）は手順案内にとどめる。どちらも代行できない
- 公式記事は外部リンク。管理画面に本文を埋め込まない
- 初期設定の段階数（アカウント → 属性 → 友だち追加時 → シナリオ）は Lステップの「導入後に最初に行う設定」と同じ範囲

### 2-3. 除外

- ウィザード完了前の画面閉じ込め
- レシピの実行時の特別扱い（複製後は通常の定義）
- AI による無承認の設定生成
- マニュアルの画面内埋め込みとツールチップ多重化

## 3. この機能で達成すること

> 初めて管理画面に入った運用者が、迷わず「最初の 1 通が届く」まで進み、目的に合う設定一式を 1 操作で用意し、困ったときに 1 箇所からマニュアルへ行け、失敗したときに次の行動が分かる。

1. 初回セットアップの順路を 1 本の進捗として表示し、各段の完了をサーバで判定する
2. レシピを複製し、作られた定義を通常の定義として扱う
3. マニュアル導線をトップバー 1 箇所に固定し、URL の正本表を持つ
4. エラーコード → 運用者向け文面 → 次の行動の対応表を持つ
5. 空状態の文言を 2 種類に固定する

## 4. 用語を固定する

| 用語 | 意味 |
|---|---|
| 順路 | 初回セットアップの 4 段（33 → 04 → 09 → 05）と最終確認 |
| 段の完了 | 画面を開いたことではなく、サーバ側の条件が満たされたこと |
| 最初の 1 通 | 友だち追加時配信またはシナリオの 1 通目が、実友だちまたはテスト受信者に `succeeded` で届いたこと |
| レシピ | 機能横断の見本。複製すると複数の定義が作られる |
| 複製 | レシピから定義を作ること。複製後は通常の定義で、レシピとの結び付きは出どころの記録だけ |
| マニュアル | トップバーの 1 リンク。画面 ID に対応する公式記事 URL |
| 正本表 | 画面 ID → 公式記事 URL の表。リンク切れ確認の対象 |
| 対応表 | エラーコード → 運用者向け文面 → 次の行動の表 |
| 空状態 | まだ作れる一覧が空（`fRgeK`）と、結果 0 件・履歴が空（`BDOJu`）の 2 種類 |

## 6. 初回セットアップの順路

### 6-1. 段

| 段 | 機能 | 完了条件（サーバ判定） | 飛び先 |
|---|---|---|---|
| 1 | 33 LINEアカウント | 稼働中アカウントが 1 件以上あり、Webhook 突合が `matched`、チャネルシークレットが検証済み | `/accounts/{id}?tab=connection` |
| 2 | 04 友だち属性 | タグまたは友だち情報欄が 1 件以上ある。組織の既定タグ（`新規`）が作られていれば可 | `/tags?tab=tags` |
| 3 | 09 友だち追加時配信 | 公開版のルールが 1 件以上あり、受け皿ルールがある | `/friend-add-settings` |
| 4 | 05 シナリオ | 公開版のシナリオが 1 件以上あり、段 3 のルールから開始される | `/scenarios` |
| 最終確認 | 最初の 1 通 | 友だち追加時配信またはシナリオの 1 通目が `succeeded` で 1 件以上。テスト受信者への送信も可 | `JN6mQ` |

- 段は順序を推奨するが、飛ばして進んでよい。前の段が未完了でも後の段の画面は開ける
- 完了判定は画面訪問ではなく上の条件。判定は `GET /api/getting-started` で毎回計算し、キャッシュしない
- 段 4 は「レシピから作る」を第一の導線にする（§7）
- 最終確認は「QR を読んで友だち追加する」と「テスト受信者へ送る」の 2 経路。どちらも `messages_log` または配信台帳の `succeeded` で判定する
- 全段完了で進捗帯を消す。再表示は新規画面 A からだけ

### 6-2. 進捗帯（ダッシュボード）

- 文言: 「はじめの設定 2 / 5 が完了。次は友だち追加時の配信を作る」。数字には単位を付ける
- 右端に `はじめの設定を開く`（新規画面 A へ）
- 権限不足の段がある人には、その段を「管理者に依頼」と表示し、ボタンを描かない
- 1 アカウントも無い組織では段 1 だけを出し、他の段は灰色

### 6-3. CLI との関係

- CLI は段 1 の登録までを行う。CLI が入れた `LINE Harness` という表示名は段 1 の画面で変更を促す
- CLI で LIFF ID を入れなかった場合、段 1 に「LIFF 未登録」を出す。友だち追加 URL に必要
- Worker の `/setup` 導入ガイドは CLI 実行前の案内として残す。管理画面の順路とは役割を分ける

## 7. レシピ

### 7-1. 定義

- レシピは「作られる定義の一覧」と「定義間のつながり」を持つ静的な見本。実行基盤を持たない
- 複製すると、対象アカウントに通常の定義が下書きで作られる。公開は運用者が各定義の画面で行う
- 複製後の定義はレシピと結び付かない。出どころ `created_from_recipe_id` と複製 run ID を記録するだけ
- レシピ本文（メッセージ文面）は見本。差し込み変数は 11 テンプレートの変数を使い、会社名などは 14 共通情報から引く

### 7-2. 初期同梱 3 本

| レシピ | 目的 | 作られる定義 |
|---|---|---|
| 新規登録 7 日間フォロー | 友だち追加後 7 日間で関係を作る | タグ `新規`（04）、友だち追加時ルール「はじめて」→ タグ付与＋シナリオ開始（09）、シナリオ 7 通（0 日目挨拶、1 日目、3 日目、5 日目、7 日目、質問 1 通、完了時タグ `フォロー完了`）（05）、テンプレート 7 本（11） |
| 予約前日リマインド | 予約の前日と当日に知らせる | リマインダ「予約前日 18:00」「当日 9:00」（07。起点は予約日時）、テンプレート 2 本（11）、予約確定時の共通アクション「リマインダ登録」（27 → 25 第 1 期の接続契約） |
| 問い合わせ自動応答 | 営業時間外と定型質問に自動で返す | 自動応答ルール 3 本（営業時間、アクセス、キーワード不一致の受け皿）（08）、テンプレート 3 本（11）、対応状況を「未対応」にするアクション（02） |

- 予約前日リマインドは 31 で予約機能がオンのときだけ複製できる。オフなら 31 へ誘導する
- 作られる定義の名前は「{レシピ名} - {定義名}」を既定にし、複製画面で接頭辞を変えられる
- 同名の定義が既にあるときは「(2)」を付けず、複製前に警告して名前の変更を求める

### 7-3. 複製の手順

1. 必要な機能（31）と権限（各機能の `edit`）を検査する。足りなければ複製できない理由を項目ごとに出す
2. 作られる定義の一覧、名前、状態（下書き）、つながり（09 → 05、27 → 07）を表示する
3. 冪等キー付きで `POST /api/recipes/{id}/clone`。1 job で作り、途中失敗は全部戻す（部分的に作らない）
4. 複製 run に作られた定義 ID を残し、画面に一覧とリンクを出す
5. 「公開する」は各定義の画面で行う。複製画面から一括公開しない

### 7-4. 版

レシピは版を持つ。複製後の定義はスナップショット型利用先（cross-review §2）で、レシピの新版を出しても既に複製した定義は変わらない。

### 7-5. 組織のレシピ

- owner/admin は既存の定義一式からレシピを作れる（「この一式をレシピにする」）。初版では初期同梱 3 本と組織レシピの複製だけを実装し、レシピの共有・書き出しは除外
- 組織レシピは `line_account_id` の範囲を持つ。別アカウントへ複製するときは 33 の設定コピーと同じ検査を通す

## 8. マニュアル導線

### 8-1. 置き場所

- トップバー `cBSCb` の画面名の横 1 箇所だけ。画面内、案内帯、ツールチップに置かない
- 現行 `top-bar.tsx` の `manualHref` をそのまま使う。空なら非活性表示（現行動作を維持）
- 外部リンクは新しいタブで開き、`rel="noopener"`

### 8-2. 正本表

- キーは画面 ID（`scripts/visual-qa/screens.mjs` の対象画面一覧と同じ ID）
- 列: 画面 ID、画面名、公式記事 URL、最終確認日時、状態（`ok | broken | unset`）
- 現行 `manual-links.ts` の 4 キー（`createOfficialAccount`、`enableMessagingApi`、`findChannelCredentials`、`createLiffApp`）は画面 ID ではなく作業 ID。正本表に「作業 ID」の列を足して吸収し、新規画面 A の各段から参照する
- 正本表は運営側が編集し、組織ごとに変えない。組織独自のマニュアルは初版で扱わない
- 画面側は `GET /api/manual-links?screen=` で URL を引く。無ければ非活性

### 8-3. リンク切れの定期確認

- 週 1 回の cron で全 URL に HEAD を送り、2xx 以外または 10 秒超過を `broken` にする
- `broken` になった URL のリンクは非活性にし、運営側へ 24 の運用者通知を 1 回だけ送る
- 確認の再試行は共通基盤 §6-2 の外部 API の既定に従う
- 確認結果は正本表の最終確認日時と状態に残す。履歴は 90 日

## 9. エラー文面の対応表

### 9-1. 規則

- 画面に出す文面は対応表から引く。route の `error` 原文（英語・内部語）をそのまま出さない
- 対応表の行は「エラーコード → 運用者向け文面 → 次の行動」。次の行動は押せるもの（画面へ移動、再試行、管理者へ依頼）にする
- 対応表に無いコードは「処理できませんでした（追跡番号 {requestId}）」と「管理者へ連絡」に落とす。原文を出さない
- 秘密値、SQL、スタックトレース、内部 ID を文面に含めない
- 応答形式は共通基盤 §10。`code` が無い現行 route は移行期間に `error` 文字列をキーにして引く

### 9-2. 対応表（初版）

コードは `apps/worker/src` に実在するものを使う。出典列は現行の route または service。

| # | エラーコード / 現行文字列 | HTTP | 運用者向け文面 | 次の行動 | 出典 |

自動処理（25、08、09）の失敗は「何番目の何が、なぜ失敗し、どこまで完了したか」を出す。例: 「3 番目「会員用メニューへ変更」が失敗しました。対象メニューは停止中です。メニューを公開するか、この動作を外してください。1〜2 番目は完了しています。」（screen-behavior-research §5 の良い例）。共通アクション台帳の `skipped` 理由と `permanent error code` を対応表で文面にする。

## 10. 空状態の文言規則

`docs/v6-common-rules.md` §2-4 の 2 種類と、読み込み中・失敗を合わせた 4 つ以外を作らない。

| 状況 | 部品 | 文言の規則 |
|---|---|---|
| 新しく作れる一覧が、まだ空 | `fRgeK` | 「まだありません」＋作成導線。ボタン名は `{対象}を作る`。対象名を必ず含める（`シナリオを作る`、`LINEアカウントを登録`）。レシピがある機能は `レシピから作る` を副次ボタンで並べる |
| 絞り込み・検索の結果が 0 件、履歴が空 | `BDOJu` | 「データがありません」。作成導線を付けない。絞り込み中は `絞り込みを解除` を出す |
| 読み込み中 | `sZE9Q` | 表の骨組みを保つ。文言は出さない |
| 失敗 | `OLMp0` | §9 の対応表から文面と次の行動を引く。追跡番号を添える |

- 「まだありません」と「データがありません」を入れ替えない。作れる一覧かどうかで決める
- 権限不足は空状態ではない。`ListState` の権限不足で描き、必要な権限と管理者への依頼を出す
- 未取得の値は D8 のとおり `—` と「未取得」。理由が分かれば「取得失敗」「権限不足」「未接続」。「取得できません」「unavailable」を画面に出さない
- 空状態に説明文を 2 つ以上置かない。説明が要るなら案内帯 1 本

## 11. データ要件

### 11-1. 追加する台帳

`recipes`:

- ID、名前、目的、版
- 所属: `system`（初期同梱）または組織・アカウント
- 必要な機能 key（31 のカタログ key）
- 定義の見本（種類、名前、本文、つながり）を版付き JSON で保持
- 作成者、作成日時

`recipe_clone_runs`:

- レシピ ID と版、対象アカウント
- 冪等キー
- 状態: `queued | succeeded | failed | rolled_back`
- 作られた定義（種類と ID の一覧）
- 実行者、開始・完了日時、失敗理由コード

`manual_links`:

- 画面 ID または作業 ID、画面名
- URL
- 状態: `ok | broken | unset`
- 最終確認日時、確認結果の HTTP status
- 更新者、更新日時

`error_messages`:

- エラーコード（または現行文字列のキー）
- 運用者向け文面（差し込み `{requestId}`、`{n}` 等）
- 次の行動の種類: `navigate | retry | contact_admin | none` と行き先
- 出典、版

### 11-2. 既存へ追加する項目

- 各定義テーブル（`scenarios`、`auto_replies`、`reminders`、`friend_add_rules`、`templates`、`tags`）: `created_from_recipe_id`、`recipe_clone_run_id`

順路の完了は台帳を持たず、`GET /api/getting-started` が 33・04・09・05・配信台帳を読んで毎回計算する。判定条件は §6-1。

## 14. 状態

- 順路: 各段 `done | todo | blocked（権限不足）| failed（判定の取得失敗）`。全段完了、進捗帯を閉じた
- レシピ一覧: 空（初期同梱があるため通常は発生しない。カタログ障害として `OLMp0`）、読み込み中、失敗、必要な機能オフ、権限不足
- 複製: 確認中、複製中（二重送信不可）、成功（作られた定義の一覧）、失敗（全部戻した）、同名警告
- マニュアル: `ok`（活性）、`unset`（非活性、「マニュアルは準備中です」）、`broken`（非活性、「リンクを確認中です」）
- エラー文面: 対応表にあり、対応表になし（汎用文面＋追跡番号）
- 空状態: §10 の 4 つ
