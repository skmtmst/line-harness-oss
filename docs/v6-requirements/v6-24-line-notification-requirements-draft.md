# V6 24 LINE通知 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「24 LINE通知」
位置づけ: Pencil、現行画面、DB、API、LINE Messaging APIの制約を照合した実装前要件

## 0. 結論と採点

V6の「顧客へのお知らせ」と「運用者へのお知らせ」を分ける設計は採用する。両方を残すことで、顧客への取引通知と、スタッフの見落とし防止を1つの機能群で扱える。Lステップの外部通知に追いつくだけでなく、EC・予約・配信失敗まで業務イベントにつなげられるため、正しく実装できれば上回れる。

ただし、現在の実装には重大な不足がある。

- 顧客通知の設定と履歴がLINEアカウント単位に分かれていない
- 現在の顧客通知はECの固定イベント専用で、汎用的な通知定義・版・送信台帳がない
- 運用者通知用の古いテーブルはあるが、APIが実行経路に接続されておらず、送信処理も動いていない
- 送信の再試行、宛先解決、重複防止、LINE月間枠の保護が共通化されていない
- Pencilにある個人ごとの「届きました」「開いた時刻」はLINE公式APIでは取得できない
- 「もう一度送る」が、再試行と新規再送を区別していない

| 評価軸 | 現在 | この要件を実装後 | 判断 |
|---|---:|---:|---|
| UI・UX | 96 | 98 | 6画面の構成を採用し、表示語だけ正確にする |
| Lステップとの競争力 | 96 | 99 | 双方向と業務イベント連携で上回る |
| 現行基盤からの実装可能性 | 72 | 95 | EC通知・スタッフ・LINE送信基盤を再利用できる |
| データの安全性・正確性 | 42 | 96 | アカウント分離と送信台帳がP0 |
| 要件の確定度 | 88 | 96 | 本書の範囲で実装設計へ進められる |

総合判断: **V6を採用する。ただし、個人別の開封・到達表示は除外し、顧客通知と運用者通知を別定義・共通送信台帳で実装する。**

### 0-1. 最重要原則

> 現行データを壊さないことは、古い画面や危険な保存形式を残すことではない。既存データを移行元・履歴として保持し、新しい正本へ安全に読み替える。

- 既存のECイベント、顧客通知設定、送信ログ、スタッフ設定は削除しない
- 画面と新APIは、LINEアカウントが明確な新しい正本だけを使う
- 所属が不明な過去データを推測で顧客へ割り当てない
- 移行時に通知を再送しない
- 元テーブルは移行後も監査期間中は読取専用で保持する

## 1. この機能で利用者が達成すること

主タスクは2つ。

1. **顧客へのお知らせ**: 注文、入金、発送、返金など、顧客が必要とする取引上のお知らせを、重複なく安全に届ける。
2. **運用者へのお知らせ**: 予約、受信箱、配信、連携、審査などで対応が必要になったとき、担当スタッフへ見落とさず知らせる。

共通の補助タスク:

- 何を、いつ、誰に、どの手段で送るかを設定する
- 公開前に自分またはテスト受信者へ送る
- 送れなかった理由を確認し、安全に再試行する
- 誰が設定を変え、どの版が送信に使われたかを確認する
- LINEの月間送信枠を確認し、重要な顧客通知を守る

## 2. 顧客通知と運用者通知の境界

| 項目 | 顧客へのお知らせ | 運用者へのお知らせ |
|---|---|---|
| 宛先 | LINE友だちである顧客 | 管理画面のスタッフ |
| 目的 | 取引・予約・契約に必要な案内 | 対応漏れ・異常・業務判断の通知 |
| 主な元データ | EC、予約、回答、決済 | 受信箱、予約、配信、連携、審査、在庫 |
| LINE宛先 | 顧客のLINE user ID | スタッフ本人が連携したLINE user ID |
| 代替手段 | 取引メール | スタッフメール・管理画面内通知 |
| 個人設定 | 顧客の配信同意・友だち状態 | スタッフの通知設定・勤務状態 |
| 管理権限 | owner/admin | owner/admin。staffは受信設定のみ |
| 共通化するもの | 送信台帳、再試行、監査、LINE枠 | 送信台帳、再試行、監査、LINE枠 |

顧客通知を運用者通知へ変更したり、運用者通知を顧客通知へ変更したりできない。新しく作り直す。

## 4. 画面ごとの要件

### 4-1. 24-1 顧客へのお知らせ

一覧に表示するもの:

- お知らせ名
- 種類（注文、入金、発送、返金、定期便、予約など）
- 状態（下書き、公開中、停止、設定不備）
- きっかけ
- 送る時刻
- 直近30日の対象数
- LINE API受付数
- 送信対象外・送信失敗数
- 自社計測リンクのクリック数
- 最終実行日時

KPI:

- 公開中の定義数
- 停止中の定義数
- 本日のLINE API受付数
- 本日の送信失敗数
- 当月LINE送信枠の残り

Pencilの `開封率` は、そのまま個人別の事実として表示しない。LINEの集計条件を満たす場合だけ、テンプレート・日単位の `LINE上で表示された人数` を集計KPIとして表示する。20人未満など取得条件を満たさない場合は値を `—`、ラベルを「未取得」（共通基盤 §9）、取得待ちは「集計待ち」と表示する。

操作:

- `お知らせの中身を見る`
- `顧客へのお知らせを停止`
- `顧客へのお知らせを再開`
- 新規作成は、接続済みの業務イベントが追加された場合だけ `顧客へのお知らせを作る`

初期版では現在の11種類のECイベントを移行する。販売促進配信はこの画面で作らない。

状態:

- 読込中
- 顧客通知がまだない（作成導線つき）
- 検索結果0件
- 取得失敗
- 権限不足
- LINEアカウント未接続
- 月間送信枠の取得失敗

### 4-2. 24-1-A 顧客通知の編集

表示・入力:

- お知らせ名
- きっかけとなるイベント
- 送るタイミング
- 送信対象外条件
- 見出し、本文、利用できる差込項目
- ボタン名、遷移先
- 画像
- LINEで送れない場合の取引メール
- 現在の公開版、下書き版、最終更新者
- 右側のLINEプレビュー

差込項目はイベント種別ごとの許可リストから選ぶ。元データのJSONキーを直接入力させない。秘密値、内部ID、カード情報、管理用メモを差し込めないようにする。

保存と公開:

- `下書きを保存` は公開中の版に影響しない
- `顧客へのお知らせをテスト` は指定済みテスト受信者だけへ送る
- `顧客へのお知らせを公開` で新しい不変版を作る
- 公開済み版を直接編集しない
- 公開後も、既に送信待ちになった通知は確定済み版を参照する
- 停止は新規受付を止める。送信中のものを無断で取り消さない

公開前検証:

- LINEアカウント
- きっかけとなるイベント
- 必須差込項目
- HTTPSの遷移先・画像URL
- 許可した遷移先ドメイン
- 取引メールの法的根拠と送信元
- 同じイベントに対する重複定義
- 月間送信枠への影響

メール代替をONにする場合は、メールアドレスが確認済みで、取引上必要な通知に限る。販売促進へ流用しない。

### 4-3. 24-1-B 送れなかったもの

一覧に表示するもの:

- 宛先種別（顧客・運用者）
- お知らせ名
- 発生元
- 対象者
- チャネル（LINE・メール・管理画面）
- 状態
- 理由
- 試行回数
- 次回試行予定
- 最終試行日時
- 対応者

絞り込み:

- 宛先種別
- チャネル
- 失敗理由
- 自動再試行あり・なし
- 期間
- 対応済み・未対応

状態名:

- `LINEでつながっていないため対象外`
- `受け取るスタッフがいないため停止`
- `LINE APIが一時的に受け付けなかったため再試行`
- `設定が正しくないため停止`
- `月間送信枠が足りないため代替手段へ切替`
- `メールアドレスがないため送信対象外`

`ブロックされたため失敗` は、follow/unfollowなど自社が保持する状態から確認できる場合だけ表示する。LINE送信APIの成功・失敗だけからブロックと断定しない。

操作を分ける。

- `送信を再試行`: 同じ通知を、安全に未完了の試行として続ける
- `新しくもう一度送る`: 既にLINE APIが受け付けた可能性がある場合の明示的な新規送信
- `受信箱で連絡`
- `メールで連絡`
- `対応済みにする`

新規再送には確認画面、理由、実行者の記録を必須にする。到達が不明な通知を無確認で再送しない。

### 4-4. 24-1-C お知らせの記録

一覧に表示するもの:

- 宛先種別
- 通知定義と使用版
- 発生元イベント
- 対象者
- チャネル
- 受付状態
- LINE API受付日時またはメール送信結果
- 自社計測リンクのクリック日時
- 試行回数
- 実行元（自動・手動・テスト）

LINEについて個人単位で表示してよい状態:

- 送信待ち
- 送信中
- LINE API受付済み
- 送信対象外
- 再試行予定
- 送信失敗

個人単位で表示してはいけない状態:

- 届きました
- 開きました
- 読みました
- LINE上でリンクを押しました

自社のリダイレクトURLを使った場合だけ、`リンクを押しました` を自社計測として記録できる。これはLINEの既読・開封ではないことを画面上でも区別する。

集計:

- 定義・日・集計単位ごとのLINE API受付数
- 送信対象外、失敗、再試行数
- 自社計測リンクのユニーククリック数
- LINE公式の集計条件を満たす場合だけ表示人数・クリック人数
- 条件未達は0ではなく、値 `—`・ラベル「未取得」（共通基盤 §9）

CSVには表示権限、出力権限、出力理由を必要とし、メールアドレス、電話番号、注文番号を必要以上に出さない。

### 4-5. 24-2 運用者へのお知らせ

一覧に表示するもの:

- ルール名
- きっかけ
- 重要度
- 受け取るチーム・スタッフ
- チャネル
- まとめる時間または重複防止時間
- 本日の発生数
- 本日の送信数
- 受け取る人がいない件数
- 最終発生日時
- 状態（下書き、公開中、停止、設定不備）

初期イベント候補:

- 受信箱の未返信が設定時間を超えた
- 回答フォームを受け付けた
- 予約が入った、変更・キャンセルされた、予約枠が競合した
- 顧客への配信が失敗した
- 外部連携・広告送信・自動化が失敗した
- 写真審査が未対応のまま設定時間を超えた
- 在庫または業務指標がしきい値を超えた

イベントが実装されていない項目は選択肢へ出さない。`準備中` を表示しない。

受け取る人が0人で、利用できる代替チャネルもないルールは公開できない。警告だけで公開を許可しない。

### 4-6. 24-2-A 運用者通知の作成・編集

入力:

- ルール名
- きっかけ
- 条件、しきい値、集計範囲
- 重要度
- 受け取るチーム・スタッフ
- LINE、メール、管理画面内通知
- すぐ送る、まとめて送る、指定時間に送る
- 重複をまとめる時間
- 通知しない時間
- 緊急時に通知しない時間を無視するか
- 勤務中のスタッフだけへ送るか
- 宛先がない場合の代替手段
- 通知文面と業務画面への遷移先

宛先プレビュー:

- 現時点で受け取るスタッフ
- LINE未連携
- メール未確認
- 権限不足
- 休み・勤務時間外
- 個人設定で停止中
- 代替チャネルへ切り替わる人数

個人設定との優先順位:

1. アカウントと権限の範囲
2. ルールで指定したチーム・スタッフ
3. スタッフの通知設定
4. 勤務中のみの条件
5. 利用可能なチャネル

安全・障害に関する重大通知で個人停止を許さない場合は、ルール作成時に明示し、ownerだけが設定できる。通常通知では個人設定を尊重する。

操作:

- `下書きを保存`
- `自分へテスト送信`
- `運用者へのお知らせを公開`
- `運用者へのお知らせを停止`

Pencilの `出す` は、実装時に `運用者へのお知らせを公開` へ変える。何が起きるかをボタン名だけで分かるようにする。

公開済みルールは版を固定する。変更時は新版を作り、過去の通知は当時の版を参照する。

## 5. データ要件

### 5-1. 顧客通知の定義

`customer_notification_definitions`

- `id`
- `line_account_id`
- `key`
- `name`
- `category`
- `source_event_type`
- `status`（draft / published / stopped）
- `current_version_id`
- `transactional_only = 1`
- `created_by`, `created_at`, `updated_at`
- `UNIQUE(line_account_id, key)`

`customer_notification_versions`

- `definition_id`
- `version_number`
- きっかけ、送信時刻、除外条件
- LINEテンプレート
- 許可済み差込項目
- ボタン・画像
- メール代替方針
- 集計単位の規則
- `published_by`, `published_at`

公開版は更新しない。前版から新版を作る。

この機能の利用先（送信待ち通知、運用者ルールの宛先解決）は**スナップショット型**である（`v6-32-feature-cross-review.md` §2）。送信待ちは確定済み版を参照し、新版へ自動で切り替えない。

### 5-2. 運用者通知の定義

`operator_notification_rules`

- `line_account_id`
- `name`
- `source_event_type`
- `importance`
- `status`
- `current_version_id`
- `created_by`, `created_at`, `updated_at`

`operator_notification_rule_versions`

- 条件、しきい値
- 通知時刻・通知しない時間
- 重複防止時間
- チャネル方針
- 宛先方針
- 代替手段
- 文面・遷移先
- 公開者・公開日時

`operator_notification_recipients`

- 版ID
- 宛先種別（team / staff / role）
- 宛先ID

既存の `staff_members.notification_preferences`、`line_user_id`、`assigned_line_account_id` は再利用する。ルールの宛先と個人設定を混ぜて1つのJSONにしない。

### 5-3. 共通の発生・送信台帳

`notification_instances`

- 1回の業務イベントから生まれた通知
- 宛先種別
- 定義・版
- 発生元種別・ID
- 重複判定キー
- 発生回数・まとめた件数
- 状態

`notification_deliveries`

- `line_account_id`
- `instance_id`
- `audience_type`（customer / operator）
- `recipient_type`, `recipient_id`
- `channel`（line / email / in_app）
- `idempotency_key`
- `status`
- `attempts`
- `next_retry_at`
- `provider_request_id`
- `provider_status`
- `error_code`, `error_message_safe`
- `queued_at`, `accepted_at`, `failed_at`
- `UNIQUE(line_account_id, idempotency_key)`

LINEの状態は `provider_accepted` とし、`delivered` と名づけない。メールも、利用するメール事業者が配達・不達Webhookを返す場合だけ配達状態を記録する。

`notification_interactions`

- 自社計測リンクのクリックだけを記録
- `delivery_id`, `link_key`, `clicked_at`
- 保存期間と削除処理を持つ

`notification_aggregate_metrics`

- LINE集計単位・日・通知定義
- 送信数、表示人数、クリック人数
- `waiting / ready / unavailable_privacy / failed`

LINEの集計単位は通知定義と日など、種類数を抑えた固定規則にする。注文・顧客ごとに無制限に作らない。

## 6. API要件

すべてのAPIは認証、選択中LINEアカウント、閲覧可能範囲、役割をサーバー側で検証する。`lineAccountId` を省略した全件取得は提供しない。

顧客通知:

- `GET /api/line-notifications/customer-definitions`
- `GET /api/line-notifications/customer-definitions/:id`
- `POST /api/line-notifications/customer-definitions`
- `PATCH /api/line-notifications/customer-definitions/:id/draft`
- `POST /api/line-notifications/customer-definitions/:id/test`
- `POST /api/line-notifications/customer-definitions/:id/publish`
- `POST /api/line-notifications/customer-definitions/:id/stop`

運用者通知:

- `GET /api/line-notifications/operator-rules`
- `GET /api/line-notifications/operator-rules/:id`
- `POST /api/line-notifications/operator-rules`
- `PATCH /api/line-notifications/operator-rules/:id/draft`
- `POST /api/line-notifications/operator-rules/:id/recipients-preview`
- `POST /api/line-notifications/operator-rules/:id/test`
- `POST /api/line-notifications/operator-rules/:id/publish`
- `POST /api/line-notifications/operator-rules/:id/stop`

記録:

- `GET /api/line-notifications/deliveries`
- `GET /api/line-notifications/deliveries/:id`
- `POST /api/line-notifications/deliveries/:id/retry`
- `POST /api/line-notifications/deliveries/:id/resend`
- `GET /api/line-notifications/metrics`
- `GET /api/line-notifications/quota`

`retry` は未完了の試行を続ける操作、`resend` は新規通知として送る操作に分ける。どちらも権限、状態、監査理由を検証する。

## 7. 送信処理と失敗時の戻り

### 7-1. 発生から送信まで

1. 元の業務処理と同じトランザクションで、イベントまたは送信待ちを確保する
2. 通知定義の公開版を固定する
3. アカウント、対象者、除外条件、宛先を解決する
4. `notification_deliveries` を一意キーで作る
5. 送信前に1件を確保し、二重実行を防ぐ
6. LINE、メール、管理画面内通知へ送る
7. 受付結果と安全なエラーを保存する
8. 再試行または代替チャネルへ進める

一意キーの基本形:

`sourceEventId + definitionVersionId + recipientId + channel`

### 7-2. 再試行

自動再試行するもの:

- 通信切断
- タイムアウト
- LINE・メール事業者の429
- 一時的な5xx

自動再試行しないもの:

- 認証・接続設定の不備
- 不正な本文・URL
- 宛先なし
- LINEでつながっていない
- 権限不足
- 月間枠不足で代替手段もない

試行回数・間隔は共通基盤（`v6-shared-platform-requirements.md`）§6-2の既定に従い、事業者の `Retry-After` を尊重する。同じLINE送信の再試行にはLINE SDKが既に対応している `X-Line-Retry-Key` を使う。

### 7-3. 通知の集中を防ぐ

- 運用者通知はルールごとの重複防止時間でまとめる
- 同じ障害をスタッフ人数×発生回数だけ送らない
- ルール単位・アカウント単位の時間上限を設ける
- 緊急以外は通知しない時間を尊重する
- 低重要度の運用者LINE通知より、顧客の取引通知に月間枠を優先する
- LINE枠が少ない場合は運用者通知をメール・管理画面内通知へ切り替える

| 操作 | owner | admin | staff |
|---|---|---|---|
| 顧客通知の閲覧 | ○ | ○ | 権限範囲のみ |
| 顧客通知の編集・公開 | ○ | ○ | × |
| 運用者ルールの作成・公開 | ○ | ○ | × |
| 自分の通知設定 | ○ | ○ | ○ |
| 失敗・記録の閲覧 | ○ | ○ | 権限範囲のみ |
| 手動再送 | ○ | 許可時のみ | × |
| CSV出力 | ○ | 明示権限時のみ | × |

失敗・記録画面には氏名、注文番号、メール、電話番号が出る可能性があるため、次を必須にする。

- アカウント範囲と役割で制限する
- 一覧では必要最小限に省略する
- 詳細表示とCSV出力を別権限にする
- 出力者、理由、対象期間を監査ログへ残す
- 秘密値、アクセストークン、元イベントの生JSONを画面へ出さない
- 保存期間終了後に個人識別情報を削除または匿名化する

## 9. 既存資産の再利用と移行

### 9-1. 再利用するもの

- `ec_events`: 現在のECイベントと外部イベントの重複防止
- `ec_notification_settings`: 顧客通知の初期テンプレート移行元
- `messages_log`: 過去の送信履歴
- `staff_members`: スタッフ、LINE連携、担当アカウント
- `notification_preferences`: スタッフ個人のLINE・メール設定
- `LineClient.pushMessage`: retry keyと集計単位を渡せるLINE送信
- `line-monthly-plan`: LINE月間上限取得
- 既存のメール送信経路: 運用者メールの受け皿

### 9-2. そのまま正本にしないもの

- `notification_rules` / `notifications`: アカウント、宛先、版、再試行が不足し、現在のworkerで実行されていない
- アカウント未分離の `ec_notification_settings`
- アカウント未分離の `ec_events`
- `processed` を顧客への到達とみなす現行ECイベント表示
- 現在の固定JSONをそのまま公開版として更新する方式

### 9-3. 移行手順

1. 新テーブルとアカウント別APIを追加する
2. `ec_events` と `ec_notification_settings` に所属アカウントを確定できる仕組みを足す
3. 所属が確定したEC設定を顧客通知定義・版へ変換する
4. 所属が不明な設定・履歴は `過去データ・所属未確定` として隔離する
5. 既存の11種類のECイベントを新しい送信台帳へ接続する
6. 新旧で同じ通知を二重送信しない切替フラグを設ける
7. 検証環境でイベントを流し、1イベント1通知を確認する
8. 旧設定APIを読取専用にする
9. 運用者通知は新しいイベントから開始し、古い `notification_rules` を自動で公開しない

移行時に過去イベントを送信待ちへ戻さない。

## 10. Lステップとの差と上回る条件

| 観点 | Lステップ相当 | V6で上回る条件 |
|---|---|---|
| 運用者通知 | 受信・フォーム等を外部通知 | 受信、予約、配信失敗、連携失敗、自動化まで共通イベントで通知 |
| 顧客通知 | LINE配信の設定が中心 | EC・予約の取引通知を独立台帳、版、代替手段つきで管理 |

Lステップの画面をそのまま複製することを目標にしない。LINE Harnessがすでに持つEC、予約、受信箱、スタッフ、外部連携を安全につなぐことを優位性とする。

## 16. 実装照合の進捗（2026-08-29）

今回、顧客通知と運用者通知の両方を残す方針を変えず、先に既存の運用者通知APIからアカウント混在の危険を除いた。

- ルール一覧、詳細、作成、変更、削除はLINEアカウント選択を必須にする
- 管理者が閲覧・変更できるLINEアカウントかをサーバー側で確認する
- IDを直接指定しても、別LINEアカウントのルールは取得・変更・削除しない
- 通知履歴も選択中LINEアカウントだけを返し、全件取得へ戻らない
- DBの読書き関数もLINEアカウントを必須引数にし、後続の実行処理が無所属検索を使えないようにする
- 所属不明の既存データを推測で新しいアカウントへ割り当てない

まだ完了ではない。顧客通知の定義と不変版、運用者通知の不変版と宛先解決、共通送信台帳、再試行、LINE枠保護、V6 6画面、画像比較は後続実装とする。本変更では本番DB更新・配備を行わない。

### 16-1. 運用者通知の安全な下書き段階

V6 `DpxOK` と `N2gAza` の受け皿は、既存の `notification_rules` とアカウント別APIを再利用して実装する。ただし、受け取るスタッフの解決と送信処理はまだ接続しないため、次を固定する。

- 新しいルールはDBで明示的に停止状態として保存する
- 画面には「下書き」と表示し、公開やテスト送信の操作を出さない
- APIへ直接 `isActive: true` を送っても公開を拒否する
- チーム名など、まだ実体へ接続していない値を人数や送信済み件数に見せない
- 取得できない件数は `—`、取得できて0件は `0件` と書き分ける
- 顧客向け通知と運用者向け通知を同じ一覧へ混ぜない
- 共通通知台帳（`notification_instances` / `notification_deliveries`）の書き込み責任は24が持つ。01ダッシュボードはそれを読むだけで、書き込まない

この段階の完了は「下書きを安全に保存・再表示できる」までとし、「通知が動く」「スタッフへ届く」とは判定しない。公開には、スタッフID単位の宛先解決、通知設定、冪等キー付き送信台帳、再試行、配信結果の表示を別工程で接続する。
