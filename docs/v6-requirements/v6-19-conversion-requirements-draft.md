# V6 19 コンバージョン 要件定義（実装照合版・下書き）

更新日: 2026-08-26
対象: V6 19-x、現行 `/conversions`、`conversion_points`、`conversion_events`、Lステップのコンバージョン管理

## 0. 結論と採点

V6の設計方向は良い。成果地点を単なるURL計測ではなく、EC・回答フォーム・予約・ウェビナー・友だち属性まで同じ「成果」として定義し、利用先、金額、重複、取消、レポートを一続きにした点はLステップを超えられる。

ただし、現行実装はV6の見た目を支えるデータになっていない。特に、成果地点の削除で過去イベントが連鎖削除されること、金額を成果地点の現在値から再計算して過去金額まで変わること、Web到達計測が実際の実行経路につながっていないこと、冪等性と組織境界がないことは実装前に直す。

| 評価軸 | 現在 | 要件反映後 | 判断 |
|---|---:|---:|---|
| V6 UI/UX | 96 | 99 | 主タスク、意味、影響、停止が分かりやすい |
| Lステップ対抗力 | 94 | 100 | 内部イベントと外部Web成果を同じ台帳で扱えば上回る |
| 現行実装完成度 | 61 | 98 | CRUDと簡易集計はあるが、V6表示の大半は未実装 |
| データ安全性 | 35 | 99 | 現在は削除・金額変更・重複・境界に重大な不足 |
| 実現可能性 | 96 | 99 | 既存台帳を移行し、共通イベント・アクションへ接続できる |
| 要件確定度 | 97 | 99 | Web個人特定の限界以外は実装へ渡せる |

完全に不可能な画面はない。除外するのは、Cookieや端末制限を越えた100%のWeb個人特定、LINE上の個人単位既読を成果条件にすること、過去データの根拠を失う定義上書き、使用中の成果地点と過去実績の物理削除、同じ外部イベントの重複計上、根拠のないファーストタッチ推測である。

### 1-2. 現行資産

- `conversion_points`: 名前、種別、固定額、計測方法、対象URL、繰返し、帰属日数、LINEアカウント
- `conversion_events`: 成果地点、友だち、紹介コード、アフィリエイター、承認状態、metadata、発生日時
- `/api/conversions/points`: 一覧、作成、更新、削除

新規に全部作るのではない。既存データを安全な版・イベント台帳へ移行する。

## 2. この機能で達成すること

運用者が「何を成果として数えるか」を一度定義し、どの機能から起きた成果でも同じ基準で、重複なく、取り消し可能な記録として残し、期間・経路・金額を再現できるようにする。

主タスクは次の1本。

1. 既存の似た成果地点を確認する
2. 起点となる出来事を選ぶ
3. 数え方、金額、取消、帰属を決める
4. 利用先と試算を確認する
5. 公開して計測を開始する
6. 一覧とレポートで実績・失敗・利用先を確認する
7. 変更時は新版、停止時は過去を残す

## 3. 用語

| 用語 | 意味 |
|---|---|
| 成果地点 | 何を1件の成果とするかを定める版付き定義 |
| 成果イベント | 実際に起きた1件。発生時点の金額・定義版・根拠を固定する |
| 起点イベント | 注文確定、フォーム送信、予約確定、ページ到達など元の出来事 |
| 取消イベント | 返品、予約取消など、元成果を打ち消す追記イベント |
| 利用先 | 案件、分析、自動応答、NEN配信、マイル、オートメーションなど |
| 帰属 | どの流入・配信・紹介を成果の起点として採用するか |
| 計測停止 | 新規成果を作らず、過去記録と利用先を保持する状態 |

UIでは `CV` を補足以外の主語にしない。「成果地点」「成果」「数える」を使う。

## 4. 画面とURL

| 画面 | URL | 主な役割 |
|---|---|---|
| 成果地点一覧 | `/conversions?tab=points` | 状態、件数、金額、利用先、未使用を確認 |
| レポート | `/conversions?tab=report` | 期間比較、日別、地点別、経路別を確認 |
| 新規作成 | `/conversions/new` | 起点・重複・金額・取消・利用先を定義 |
| 詳細・編集 | `/conversions/:id` | 現行版、履歴、利用先、テスト、停止、新版作成 |
| 停止・差替え確認 | `/conversions/:id/stop` またはモーダル | 影響を確認して安全に停止 |
| 成果イベント一覧 | `/conversions/:id/events` | 1件単位の根拠・取消・帰属を確認 |

V6の「中身を見る」は `/conversions/:id`、「使う場所を足す」は利用先選択パネルへ進む。タブは `?tab=` を正本とする。

## 5. 成果地点の種類

### 5-1. 内部イベント

| 運用者表示 | source_type | 必須の一意キー |
|---|---|---|
| ECの注文が確定 | `ec.order.confirmed` | 店舗＋注文ID＋状態版 |
| ECの定期便が確定 | `ec.subscription.started` | 店舗＋契約ID |
| 回答フォームが送信 | `form.submitted` | フォーム＋回答ID |
| 予約が確定 | `booking.confirmed` | 予約ID＋状態版 |
| イベント申込が確定 | `event.registration.confirmed` | イベント＋申込ID |
| ウェビナーを見終えた | `webinar.completed` | 動画＋視聴者＋完了版 |
| タグが付いた | `friend.tag.added` | 友だち＋タグ＋付与履歴ID |
| 手動で記録 | `conversion.manual` | 画面発行の冪等キー |

### 5-2. Webイベント

- 許可済みドメインに計測タグを設置する
- LINE内の計測リンクから短命の匿名セッションを引き継ぐ
- `page_view`、任意のタグ発火、サーバWebhookを受け付ける
- Cookie拒否・Safari制限・別端末の場合は個人特定できないことがある
- 個人不明でも匿名成果として総数へ含めるかは成果地点ごとに明示する
- 生URLの前方一致だけで本人と断定しない

### 5-3. 外部Webhook

- 接続先ごとの署名鍵、時刻、nonceを検証する
- `source_event_id` を必須にして再送を重複計上しない
- 受信、検証失敗、処理待ち、成功、恒久失敗を台帳へ残す
- 管理者セッション用APIを外部Webhookに流用しない

## 6. 作成・編集

### 6-1. 入力

- 成果地点名
- 起点イベントと対象（フォーム、予約メニュー、商品など）
- 対象条件・除外条件
- 数える回数: 毎回、1人1回、期間内1回、対象1件につき1回
- 期間内1回の日数とタイムゾーン
- 金額: 起点の実額、固定額、金額なし
- 取消: 元イベント取消で自動取消、手動のみ、取消なし
- 帰属モデル: 最終接点、最初の接点、指定接点、帰属なし
- 帰属期間
- 対象LINEアカウント・組織
- 利用先

### 6-2. 試算

V6の「過去30日にあてはめる」は保存前の試算であり、過去イベントを本番成果として追加しない。試算は別APIで実行し、件数、金額、重複除外数、取消数、対象外理由を返す。

本番で過去を取り込む必要がある場合は、通常作成と分けた管理者向けバックフィル処理とし、dry-run、対象期間、実行者、冪等キー、件数照合を必須にする。

### 6-3. 版

- 下書きは上書き可能
- 公開時に不変の `conversion_definition_version` を発行
- 名前・説明だけは表示用情報として更新可能
- 起点、重複、金額、取消、帰属を変える場合は新版を作る
- 既存の成果イベントは発生時の版を参照し続ける
- 利用先は明示的に新版へ切り替えるまで旧版を使う

## 7. 成果イベント

### 7-1. 不変記録

1件ごとに次を固定する。

- 組織、LINEアカウント
- 成果地点ID、定義版ID
- 起点イベントIDと種類
- 友だちIDまたは匿名セッションID
- 発生時刻、受信時刻、タイムゾーン
- 発生時の金額、通貨、税・送料を含むか
- 帰属した経路、配信、紹介者と採用理由
- `idempotency_key`
- `recorded`、`skipped_duplicate`、`reversed`、`failed` の状態
- 個人情報を除いた根拠metadata

金額は現在の `conversion_points.value × 件数` で再計算しない。

### 7-2. 重複

- 同一 `organization_id + source_type + source_event_id + conversion_definition_version_id` に一意制約
- 1人1回はDB一意制約または直列化されたトランザクションで保証
- 重複受信は200系で既存結果を返し、`skipped_duplicate` を記録
- 現行のSELECT後INSERTだけの重複防止は競合に弱いため廃止

### 7-3. 取消

- 元イベントを削除・負数上書きしない
- `reversal_of_event_id` を持つ取消イベントを追記
- レポートは総成果、取消、純成果を区別
- 取消後に再確定した場合も別イベントとして履歴を残す

## 8. 利用先とアクション

### 8-1. 利用先台帳

案件、分析、自動応答、シナリオ、NEN配信、マイル、オートメーション、広告連携を構造化参照として保存する。名前・JSON・URL文字列の全文検索を正本にしない。

### 8-2. 成果発生後の動作

Lステップの強みである「成果検知後のタグ付与・メッセージ・シナリオ開始・メニュー変更」を欠かさない。V6では25の共通アクションを利用先として接続する。

- 公開済みアクション版を参照
- 成果イベントIDを冪等キーに含める
- 成功、スキップ、再試行、恒久失敗を実行台帳へ残す
- 取消時アクションは別に定義する
- 1つ失敗しても成果イベント自体は消さない

## 9. 一覧

### 9-1. 表示

- 名前、起点、数え方、対象期間の件数・純金額、状態、利用先
- `計測中`、`下書き`、`停止`、`入力不良`、`起点停止` を区別
- 0件の地点と未使用の地点を警告
- 利用先と直近失敗へ直接進める
- 短い名称は途中改行せず、長文は省略＋title

### 9-2. 検索・絞り込み

- 名前
- 期間
- 状態
- 起点イベント
- 利用先あり・なし
- 0件
- エラーあり
- LINEアカウント
- 件数、金額、更新が新しい順

CSVは現在の絞り込み、期間、タイムゾーン、純額定義をヘッダーへ含める。

## 10. レポート

### 10-1. KPI

- 総成果件数
- 取消件数
- 純成果件数
- 純金額
- 1件あたり純金額
- 前期間比
- いちばん伸びた成果地点

### 10-2. 日別

- 成果地点別の積み上げ
- 総数と純数の切替
- 配信・キャンペーンの注記は、実イベント接続がある場合だけ表示
- 30日固定ではなく期間選択に追従

### 10-3. 地点別・経路別

- 現期間、比較期間、増減
- 流入経路、配信、広告、紹介者別
- 件数だけでなく対象母数がある場合はCVRを表示
- 「いちばん多い経路」は帰属根拠が保存された成果だけで計算
- 未帰属を隠さず独立表示

### 10-4. 再現性

レポートは成果イベントのスナップショット、取消、帰属根拠から再計算可能にする。成果地点の現在設定を変えて過去数値を変えない。

## 11. 停止・差替え・削除

### 11-1. 既定操作

V6の「数えるのをやめる」を既定とする。

- 新規計測を停止
- 過去記録・分析・利用先を保持
- 停止日時、理由、実行者を記録
- 利用先には停止状態を表示

### 11-2. 差替え

- 利用先ごとに別成果地点・版へ切り替える
- 更新対象一覧を事前表示
- 競合検査後に一括更新
- 途中失敗はロールバックまたは再開可能なジョブにする
- 過去イベント同士を無理に合算しない

### 11-3. 物理削除

イベント、利用先、監査履歴が1件でもある成果地点は物理削除不可。未公開・未使用・イベント0件だけを管理者が削除できる。

現行の `ON DELETE CASCADE` と即時DELETEは移行後の通常APIから使用しない。

## 15. 状態・エラー・アクセシビリティ

- 空: 成果地点をつくる導線あり
- 検索0件: 条件変更だけを案内
- 読込: 表の列幅を保ったskeleton
- 部分失敗: KPI、一覧、利用先を別々に表示
- 権限不足: 見えない・押せない・実行できないを区別
- 起点停止: どの接続が止まったかと修正先を表示
- 重複: エラーではなく「既に記録済み」
- Web個人不明: 匿名成果・除外を設定どおり表示
- CSV生成中: job状態と再取得
- キーボードでタブ、絞り込み、確認モーダルを操作可能
- グラフは表形式の代替と色以外の凡例を持つ

表示するボタンに `準備中` を残さない。実装できない操作は出さない。

## 16. Lステップ・Linyとの差

### 16-1. Lステップが満たす要件

- 外部サイトへコンバージョンタグを設置
- ページ到達した友だちを特定
- 初回だけ・毎回の通過アクション
- タグ、メッセージ、シナリオ、リッチメニューなどを自動実行
- ファネル分析と広告連携に利用
- 計測対象ドメインの事前登録

### 16-2. V6が上回る条件

| 項目 | Lステップ | V6要件 |
|---|---|---|
| 成果の起点 | 主にLINE/Web行動 | EC、予約、フォーム、ウェビナー、タグ、Webを共通化 |
| 金額 | 行動・分析中心 | 発生時実額、固定額、取消、純額を再現 |
| 定義変更 | 詳細不明 | 公開版不変、過去数値を固定 |
| 利用先 | アクション・分析 | 利用先台帳と影響確認、差替え |
| 重複 | 初回/毎回を選択 | 元イベント一意キー＋期間ルール |
| 削除 | — | 停止優先、過去実績を物理削除しない |
| 監査 | — | 根拠、版、帰属、取消、操作履歴 |

Lステップ越えは、画面数ではなく「どの機能で起きた成果でも同じ台帳に入り、後から数字の根拠を再現できること」で判断する。

## 17. 除外するもの

- Cookie拒否、Safari制限、別端末を越えた100%のWeb個人特定
- LINEの個人単位既読・未読を成果条件にすること
- LINE送信済みメッセージの取消
- 利用先・過去イベントがある成果地点の物理削除
- 公開済み定義の直接上書き
- 現在の固定額で過去金額を再計算すること
- URL前方一致だけによる本人・成果確定

## 22. 最終判断

V6は要件定義へ進める状態で、削除する画面はない。実装可能性も高い。

ただし、現在の `conversion_points` と `conversion_events` をそのままV6へ当てるのは不可。最優先は、過去実績を消さない停止、発生時金額の固定、公開版不変、冪等、取消、組織境界である。その土台の上へ内部イベント、Web成果、共通アクション、レポートを載せれば、Lステップと同等ではなく、業務成果の再現性で上回れる。

## 23. 実装進捗（2026-08-28）

- 停止したURL到達地点は新しい成果を作らないようにした
