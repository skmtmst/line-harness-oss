# V6 25 オートメーション 要件定義（実装照合版・下書き）

作成日: 2026-08-25
更新日: 2026-09-03
対象: V6「25 オートメーション」
位置づけ: Pencil と現行リポジトリを照合した、実装に渡す前の要件定義。共通アクションのカタログは `v6-25-automation-action-contract.md`（正本）、きっかけは `v6-25-automation-trigger-contract.md` が持つ

## 0. 結論と採点

V6の画面設計は、そのまま要件定義へ進める品質にある。Lステップ相当の「きっかけ→条件→処理」に加え、共通アクション、版固定、利用先の把握があり、設計上は競合より一段上を狙える。

ただし、現行実装はオートメーション1件の中に条件と処理をJSONで保存し、その場で順番に実行する方式である。このまま画面だけV6へ替えると、公開済み定義の後編集、待機中の処理の変化、二重送信、記録の欠落が起きる。そのため、画面実装より先に版と実行台帳を足す。

| 評価軸 | 現在 | この要件を実装後 | 判断 |
|---|---:|---:|---|
| UI・UX | 94 | 97 | 画面構造は採用する |
| Lステップとの競争力 | 94 | 98 | 共通アクションと版管理が強み |
| 現行基盤からの実装可能性 | 62 | 94 | 既存実行部品を再利用すれば可能 |
| 安全性・運用性 | 48 | 96 | 版固定、冪等性、再試行が必須 |
| 要件の確定度 | 76 | 95 | 本書の前提で実装へ進められる |

総合判断: **採用する。V6を正本として新しい実行基盤を作り、現行データだけを段階移行する。**

### 0-1. 最重要原則

守る対象を混同しない。

| 守るもの | 守らないもの |
|---|---|
| 友だち、タグ、シナリオなどの業務データ | 現行画面の構造 |
| 既存オートメーションの意味 | `conditions` / `actions` を1行に入れる旧JSON形式 |
| 過去の実行履歴 | 現行APIの入力形式 |
| 誰がいつ何を実行したか | 公開済み定義を直接更新する動き |

> **V6を古い形式へ合わせない。古いデータをV6の新形式へ変換する。**

新しい画面とAPIは、最初から版、処理、実行、履歴が分かれた新形式だけを扱う。旧形式の読み取りと変換は移行専用層に閉じ込め、通常機能から参照させない。

## 1. この機能で利用者が達成すること

主タスクは1つ。

> 友だちの行動をきっかけに、対象条件を判定し、複数の処理を安全に順番どおり実行し、その結果と使われた版を後から確認できる。

補助タスク:

- 見本から短時間で作る
- 1人だけでテストしてから有効にする
- 同じ処理のまとまりを共通アクションとして再利用する
- 新しい版を公開しても、既存の利用先を勝手に変えない
- 失敗、条件外、待機中、完了を実行台帳で確認する
- 友だち一覧から選んだ友だちへ、公開済み共通アクションを手で実行する（03の一括操作経由）

## 2. この版で変えないもの

- V6の画面構造、タブ順、ボタン名、共通ルール
- 既存の友だち、タグ、シナリオ、テンプレート、リッチメニューのデータ
- 既存のシナリオアクションが持つ、条件、順序、再実行防止の考え方
- 過去の `automation_logs`。移行後も読み取り可能な履歴として残す
- LINEアカウント単位のデータ分離

## 4. 画面ごとの要件

各画面に「表示」「操作」「状態」「文言」を定める。状態の描画は共通部品 `ListState` を使い、空・読み込み中・失敗・権限不足の4状態を最低限持つ。未取得の数値は §4-9 の規則で `—` にする。

### 4-1. 25-1 オートメーション（`gief7`）

表示:

- 帯4つ: 動いているもの（本数）、この30日に動いた回数、失敗した回数、減らせた手作業（時間）
- 減らせた手作業は「1回30秒の試算」と明記する。分析20の `QQ1SR`（使われ方）と同じ集計口を読み、独自計算を作らない
- 列: 名称、きっかけ、対象条件の要約、処理の要約、公開版、この30日の実行、失敗、最終実行、状態
- 「いつ、だれに、何をするか」を人が読める1文で行ごとに表示する
- 同じきっかけのオートメーションが複数ある場合は、行に「同じきっかけのルールが他にあります。両方動きます」を出す
- 全アカウント共通の定義は「すべてのアカウントに効きます」の札を出す

操作:

- 主操作は `見本から作る`。ゼロから作る `オートメーションをつくる` も一覧内に置く
- 行操作: `設定を編集`、`動いた記録を見る`、`前の版から新しい下書きを作る`、`複製`、`止める` / `動かす`、`保管`
- 検索対象は名称、きっかけ、処理
- 絞り込みは、すべて、動いている、止めている、失敗あり、30日動いていない
- 期間の初期値は直近30日。並び順の初期値は実行回数が多い順
- `止める` / `動かす` は確認ダイアログを経て反映し、すでに始まった実行には影響しない
- 削除はしない。利用中または履歴ありは `保管` にする。現行実装の「削除する」は `保管` へ置き換える

状態:

| 状態 | 条件 | 見せ方 |
|---|---|---|
| 空・作れる | オートメーション0件 | 作成導線つき空状態。帯は0件を0のまま出す |
| 検索結果0件 | 検索・絞り込みで0件 | 条件変更だけを案内し、作成を主操作にしない |
| 読み込み中 | 初期・再取得中 | 一覧骨格を保つ。帯は `—` |
| 失敗 | 一覧APIの取得失敗 | 再読み込み導線と事故番号。帯は全部 `—` |
| 権限不足 `view` | 閲覧のみ | 行操作を出さない。帯と一覧は見える |
| 権限不足 `none` | 機能自体が不可 | メニュー非表示、URL直打ちは403画面 |
| 未取得 | 集計口が未接続 | 帯の数値は `—`、ラベルは「未取得」 |
| 上限 | 同時実行数などの契約上限 | 上限、現在数、解消方法を表示する |

文言:

- 空: 「動いているオートメーションはありません。」
- 失敗: 「オートメーションを表示できませんでした。登録したルールは消えていません。再読み込みしても直らない場合はエラー報告へ。」の一文は維持する
- 動かす確認: 「これから起きるきっかけで動き始めます。止めているあいだに起きたぶんは、さかのぼって動きません。あとから止められます。」
- 止める確認: 「止めているあいだ、このきっかけでは何も動きません。ルールの設定は残るので、あとから動かし直せます。」
- 切替失敗: 「稼働を切り替えられませんでした。状態を読み直してから、もう一度お試しください。」

### 4-2. 25-1-A オートメーションをつくる（`Rv8Jv`）

3段階で作る。節番号を画面に出す。

1. どのルールか（名称、説明、LINEアカウント）
2. 何が起きたら動かすか（きっかけ、対象となる友だち）
3. 何をするか（処理）

表示:

- きっかけごとの補足を1行で出す。例: 「空欄なら、どんな内容でも動きます。」「友だち追加のとき。ブロック解除では動きません。」
- 対象条件は共通条件部品。条件に一致する見込み人数を「当てはまりそうな人数」として表示し、取得できないときは `—` と「未取得」
- 処理は上から順。各行に順序、条件、失敗時の動き（止める・次へ進む）、再試行の有無（接続契約 §6 の分類を表示するだけで、回数は編集させない）
- 人が読める文章で「いつ、だれに、何をするか」を右側に常時表示する
- 同一イベントが再度発生した場合の再実行可否を設定する
- 選べる処理はカタログのうち接続済みの段だけ。段の正本は接続契約 §1
- 同じきっかけの他オートメーションがある場合、保存前に「同じきっかけのルールは両方動きます」と警告する

操作:

- `下書きを保存` と `作成して有効にする` を分ける。下書きのまま置ける
- `1人でテスト`（実送信を伴う。§9 の permission が必要）
- `見本から始める` は 25-1-C へ戻る導線
- 公開前検査: 未接続処理、循環、無効参照、宛先なし、過去時刻、到達不能分岐を一覧で返し、1件でもあれば有効化できない

きっかけの実装可否:

| V6のきっかけ | 現状 | 要件 |
|---|---|---|
| 友だち追加 | 既存 | `friend_add` に統一する |
| タグ追加・解除 | 既存 | `tag_change` と actionで判定する。「付いたときだけ」の絞り込みを追加する |
| メッセージ受信 | 既存 | `message_received` を使う |
| フォーム回答 | イベント記録はあるが未接続 | `form_submitted` を共通イベントへ接続する |
| 注文確定 | EC側の既存イベントあり | 既存ECイベント名を正規化して使う |
| 日時指定・毎日・毎週 | 未実装 | アカウントのタイムゾーンを必須にし、5分単位で起動する |
| リンククリック | 計測はあるが未接続 | `link_clicked` を共通イベントへ接続する |
| 予約確定 | 型だけあり、発火未確認 | `calendar_booked` の発火元を追加してから表示する |
| ブロック・フォロー解除 | 未実装 | LINE Webhookで確実に取れる範囲だけ別イベントとして追加する |

画面に出すきっかけは、保存と実行まで接続済みのものだけにする。「準備中」の選択肢は出さない。

状態:

| 状態 | 条件 | 見せ方 |
|---|---|---|
| 読み込み中 | 選択肢（タグ、シナリオ、テンプレート）の取得中 | 「選択肢を読み込んでいます」。保存ボタンは押せない |
| 失敗 | 選択肢の取得失敗 | 「選択肢を読み込めませんでした」と再読み込み。入力済みの値は消さない |
| 入力不備 | 必須未入力、JSON不正など | 欄ごとのエラー。`fieldErrors` を欄の直下に出す |
| 参照先不明 | 選んだタグ・シナリオが保管済み | 該当行に「参照先が見つかりません」を出し、公開不可 |
| 権限不足 `view` | 閲覧のみ | 全欄を読み取り専用にし「操作する権限がありません」 |
| 同時編集競合 | `409 VERSION_CONFLICT` | 「別の人が先に変更しました」と再読み込み。入力内容を保持する |
| 未保存 | 編集中で保存前 | 「まだ保存していません」。離脱時に確認する |

文言:

- 「作る前に起きたことにはさかのぼりません」
- 「上から順に実行します。」
- 「同じ処理を使い回せます」（共通アクションの説明）
- 現行実装の「下書きのまま止めておく口がまだありません」は、下書き保存の接続後に削除する

### 4-3. 25-1-B オートメーションが動いた記録（`DkPY0`）

表示:

- 列: 実行日時、友だち、オートメーション名と版、きっかけ、結果、処理の成功数／失敗数、テスト実行の札
- 結果は `succeeded`、`skipped`（理由付き）、`waiting`、一部成功、`permanent_failed`、`cancelled` を区別して表示する
- 行を開くと、使用したオートメーション版、共通アクション版、各処理の結果（状態、試行回数、エラーコード、外部参照ID、開始・終了）を見られる
- 条件外も記録する。明細保持期間は90日、それ以前は日別件数だけ残す
- テスト実行は本番実行と区別して表示する。既定の一覧では本番だけを出し、切替で含める
- 過去の記録は、定義を編集しても書き換えない
- 旧 `automation_logs` は「移行前の記録」として別タブで閲覧専用に出す

操作:

- 検索: 友だち、オートメーション名、期間、状態、テストを含む
- 新しい順を初期値にする
- `CSVで書き出す`（非同期生成、`automation.run.export`）
- `もう一度やる`（失敗した処理だけの手動再試行、`automation.run.retry`）。成功済みの処理を再実行しない安全な口が入るまで表示しない。現行実装が意図して出していない状態を、要件としても正とする
- `実行を取り消す`（`waiting` の実行だけ。開始済みの処理は戻さない）

状態:

| 状態 | 条件 | 見せ方 |
|---|---|---|
| 空 | 記録0件 | 「実行の記録がありません」。作成導線は出さない |
| 検索結果0件 | 絞り込みで0件 | 条件変更を案内 |
| 読み込み中 | 取得中 | 一覧骨格を保つ |
| 失敗 | `GET /api/automation-runs` 失敗 | 再読み込みと事故番号 |
| 権限不足 `view` | 閲覧のみ | 再試行・取り消し・CSVを出さない |
| 権限不足 `none` | 不可 | 403 |
| 一部未取得 | 旧ログ側だけ取得失敗 | 新記録は出し、旧記録のタブに「取得失敗」 |
| 本文マスク | 顧客本文の閲覧権限なし | 受信本文は伏せ字。理由「権限不足」 |

文言:

- 空: 「実行の記録がありません」
- 条件外の理由: 「対象条件に当てはまりませんでした」
- gate 拒否の理由: 「運用停止中のため動かしませんでした」など、gate の名前を人の言葉にする

### 4-4. 25-1-C 見本から作る（`WjYAC`）

表示:

- 見本カード: 名前、説明、きっかけ、すること、`これで作る`
- 画面先頭に「見本を選ぶと、公開されていない下書きを作ります。タグやシナリオは、次の画面でこのアカウントのものを選び直してください。」
- 見本はアカウントの実データIDを持たず、タグ・シナリオ・テンプレートを利用者が選び直す
- 使えない処理を含む見本は、その処理の実装完了まで非表示にする
- 設計は12件。実装3件との差はきっかけ別の絞り込みと合わせて埋める

操作:

- `これで作る` は `POST /api/automation-templates/:key/drafts` で下書きを作り、25-1-A へ遷移する。公開状態で作らない
- きっかけ別の絞り込み
- 見本の更新で、既に作ったオートメーションは変わらない

状態:

- 「取得できません」「unavailable」は画面文言に使わない。APIの状態名 `unavailable` / `partial` / `stale` はそのまま

- 内部識別子（`undefined`、`NaN`、`Invalid Date`、内部ID）を画面に出さない

## 5. データ要件

### 5-0. V6の新形式を正本にする

新形式は旧テーブルの都合から決めない。V6で必要な動作から先に決める。

| V6で必要なこと | 新形式の正本 |
|---|---|
| 公開済み内容を変えない | オートメーション版 |
| 待機中も同じ内容で最後まで動く | 実行開始時に固定した版 |
| どの処理が失敗したかを見る | 処理ごとの実行結果 |
| 同じ送信を重ねない | 実行・処理ごとの冪等キー |
| 共通処理を使い回す | 共通アクション本体・版・利用先 |
| 新版を利用先ごとに切り替える | 固定版を持つ利用先 |

新規作成、編集、公開、実行はすべて新形式へ直接保存する。新しい操作を旧JSONへ書き戻す処理は作らない。

### 5-1. 既存で使うもの

| 既存 | 使い方 |
|---|---|
| `automations` | 既存定義の移行元。移行中は互換読み取りを残す |
| `automation_logs` | 過去履歴。削除・上書きしない |
| `scenario_actions` と発火記録 | 共通アクションの処理形式と一度だけ実行の先例 |
| 友だち・タグ・シナリオ・テンプレート | 各処理の参照先 |
| 既存イベント発火処理 | 友だち追加、タグ、受信、成果、ECのきっかけ |
| 既存Cron・送信待ち・冪等性の仕組み | 待機、再開、重複防止の実装パターン |

### 5-2. 新しく必要なもの

名前は実装時に既存命名へ合わせるが、責務は分ける。

| データ | 主な項目 | 必要な理由 |
|---|---|---|
| オートメーション本体 | account、名称、状態、現在版、優先順 | 定義の同一性と版を分けるため |
| オートメーション版 | 版番号、きっかけ、対象条件、処理定義、公開日時、作成者 | 公開済み定義を不変にするため |
| 実行 | 対象友だち、使用版、状態、現在位置、再開日時、冪等キー、テスト区分 | 待機・再開・二重防止のため |
| 処理の実行結果 | 処理ID、試行回数、結果、skip reason、エラーコード、外部参照ID、開始・終了 | どこで失敗したかを見るため |
| 共通アクション本体 | account、名称、状態、現在公開版 | 利用先と版を分けるため |
| 共通アクション版 | 版番号、処理、公開日時、作成者 | 利用先を固定するため |
| 利用先 | 種類（機能）、利用先ID、使用箇所、固定版 | 影響範囲と手動更新のため |
| migration event | 利用先ID、旧版、新版、実行者、日時、影響件数 | 版切替を監査するため |

必須制約:

- すべての新規定義に `line_account_id` を必須とする
- 1つの発生イベントと処理に対して冪等キーを一意にする
- 公開済み版を更新できないDB制約またはサーバー制約を置く
- 履歴がある本体は物理削除しない
- 版・利用先・実行・処理結果に検索用インデックスを置く

## 6. 保存形式と移行

現行の `conditions` と `actions` のJSONを、そのまま新版の公開定義として使い続けない。旧形式は移行元であり、新機能の互換仕様ではない。

### 6-1. 変換対応表

| 現行データ | V6の変換先 | 判定 |
|---|---|---|
| `automations.id/name/description` | オートメーション本体 | 自動変換 |
| `event_type` | 第1版のきっかけ | 対応表にある値だけ自動変換 |
| `conditions` JSON | 第1版の対象条件 | 認識できる条件だけ自動変換 |
| `actions` JSON | 第1版の処理 | 接続契約 §1 のカタログにある処理だけ自動変換 |
| `is_active` | 本体の動作状態 | 自動変換。ただし要確認行は強制停止 |
| `priority` | 本体の優先順 | 自動変換 |
| `line_account_id` | 本体の所属アカウント | 値ありは自動、空は隔離 |
| `automation_logs` | 旧実行履歴 | 変換せず閲覧専用で保持 |

### 6-2. 3種類の移行判定

| 判定 | 条件 | 移行後の扱い |
|---|---|---|
| 自動変換 | きっかけ・条件・処理をすべて認識できる | 第1版を作成。元が有効なら有効状態を引き継ぐ |
| 要確認 | 一部の条件・処理が不明、参照先がない | 下書きとして変換し、停止状態で表示する |
| 除外 | 所属アカウント不明、JSON破損、安全に意味を再現できない | 通常一覧へ出さず、移行レポートへ隔離する |

「要確認」と「除外」を、空の処理や成功扱いへ変換してはいけない。

### 6-3. 一時的な移行層

移行層が行うのは次の3つだけ。

1. 旧形式を読み取る
2. 新形式へ変換できるか判定する
3. 変換結果と理由をレポートする

移行層から新しい画面へ旧形式を返さない。新しい実行エンジンから旧形式を読まない。新APIから旧形式へ書き込まない。

移行手順:

1. V6の新形式と入力検証を先に確定する
2. 新テーブルを既存と並行して追加する
3. 本番データを変更しないdry-runで、自動変換・要確認・除外の件数と理由を出す
4. 自動変換できる各 `automations` を、本体＋第1版へ変換する
5. 認識できない処理は「要確認の下書き」として停止する
6. `line_account_id` が空の既存行は「旧全体設定」として隔離し、通常画面から編集させない
7. 新規作成と編集を新API・新形式へ切り替える
8. 実行エンジンをアカウント単位で新版へ切り替える
9. 過去の `automation_logs` は旧履歴として残し、新規実行は新しい実行台帳へ記録する
10. 全対象の照合後、旧JSONへの書き込みと旧実行エンジンを停止する

一括移行はしない。シナリオ、自動応答、回答フォームは、利用先ごとに変換・検証してから共通アクションへ接続する。

### 6-4. 旧形式を終了する条件

次が全部そろった時点で、旧形式を終了する。

- dry-runの自動変換件数と実移行件数が一致する
- 要確認・除外の全件に理由と対応者が付いている
- 有効だったオートメーションの動作比較テストが完了している
- 新旧で対象者、処理順、送信内容が一致する
- 二重実行を防ぐ切替手順が検証されている
- 新しい実行台帳がV6画面から確認できる
- ロールバック時も旧データを上書きしない

終了後も旧テーブルと過去ログは一定期間読み取り専用で保持するが、V6のAPI・画面・実行処理からは切り離す。

## 7. API要件

| 操作 | メソッド・パスの案 | 失敗時 |
|---|---|---|
| 一覧・集計 | `GET /api/automations` | 再試行可能な取得エラーを返す。集計未接続は `freshness: unavailable` |
| 下書き作成 | `POST /api/automations` | 入力欄ごとのエラーを返す。公開状態で作らない |
| 見本から下書き | `POST /api/automation-templates/:key/drafts` | 見本なしは404。二重作成しない |
| 新版作成 | `POST /api/automations/:id/versions` | 競合時は再読み込みを促す |

| 有効・停止 | `POST /api/automations/:id/status` | 変更前状態を維持 |
| 1人テスト | `POST /api/automations/:id/test` | 失敗した処理と理由を返す |
| 実行一覧 | `GET /api/automation-runs` | cursorで再取得可能にする |
| 実行詳細 | `GET /api/automation-runs/:id` | 権限外は存在も明かさない |
| 失敗処理の再試行 | `POST /api/automation-runs/:id/retry` | 成功済み処理は再実行しない。新しい attempt を返す |
| 実行の取り消し | `POST /api/automation-runs/:id/cancel` | `waiting` 以外は409 |
| 実行CSV | `POST /api/automation-runs/export` | 202＋job ID。件数・条件・actorを監査 |
| 共通アクション一覧 | `GET /api/common-actions` | 同上 |
| 共通アクション作成 | `POST /api/common-actions` | 入力欄ごとのエラーを返す |
| 複製 | `POST /api/common-actions/:id/duplicate` | 下書きを返す。元は変えない |
| 新版公開 | `POST /api/common-actions/:id/versions/:version/publish` | 循環・無効参照を返す |
| 利用先の版更新 | `POST /api/common-actions/:id/bindings/:bindingId/version` | 実行中は旧版固定のまま更新。migration event を記録 |
| 手動実行 | 03 の `POST /api/friend-bulk-runs`（`run_common_action`） | 25 側に別の口を作らない |

API側の必須ルール:

- `lineAccountId` はセッションから決め、画面の任意値を信用しない
- 任意JSONをそのまま保存せず、処理種別ごとのスキーマで検証する。処理種別は接続契約 §1 の識別子だけを受け付ける
- 旧 `conditions` / `actions` 形式を新APIの入力として受け付けない
- 新APIは新形式だけを読み書きし、互換変換は移行専用処理だけで行う
- 更新競合を版番号または `If-Match` で検知する
- 未知の処理種別は成功扱いにせず、公開を拒否する
- LINE送信・Webhookなど外部処理は冪等キー、タイムアウト、再試行可否を記録する
- WebhookはHTTP 2xx以外を失敗として扱う
- 宛先なし、トークンなし、対象友だちなしを成功扱いにしない
- 一覧APIは状態、期間、友だち、名称、cursorを受け取る
- 応答形式と失敗コードは共通基盤 §10 に従う

## 8. 実行要件

実行は「イベント受付→対象判定→実行作成→各処理→完了」の順にする。

1. イベントに一意な受付IDを付ける
2. LINEアカウント内の有効なオートメーションだけを候補にする
3. 公開版を固定する
4. 共通基盤 §6-3 のruntime gateを通し、拒否は `skipped` と拒否理由を記録して終了する
5. 条件外なら `skipped`（skip reason `condition`）を記録して終了する
6. 条件一致なら実行行を1件だけ作る
7. 各処理を順番に実行し、結果を1件ずつ残す
8. 待機は実行を `waiting` にし、`resume_at` 後にCronで再開する
9. 共通アクションを呼ぶときは、利用先に固定された版を実行へ記録する
10. 外部処理は同じ処理実行IDを冪等キーとして使う
11. 一時失敗は `retry_wait` にし、共通基盤 §6-2 の既定でCronが再試行する。恒久失敗は `permanent_failed`
12. 全処理の終了後に成功・一部成功・失敗を確定する

状態名は横断レビュー §4 を正本にする。現行実装の識別子は移行時に次へ寄せる。

| 現行実装 | 正式な状態名 |
|---|---|
| `queued` | `queued` |
| `running` | `claimed` |
| `waiting`（待つ） | `waiting`（機能固有として追加） |
| `waiting`（再試行待ち、`retry_at` あり） | `retry_wait` |
| `success` | `succeeded` |
| `partial` | 実行全体の「一部成功」。処理ごとは `succeeded` / `permanent_failed` の組で表す |
| `failed` | `permanent_failed` |
| `skipped_condition` | `skipped` ＋ skip reason `condition` |
| `cancelled` | `cancelled` |

待機・日時指定の精度は既存Cronに合わせて **5分単位、最大遅延5分を目標** とする。秒単位の正確な実行はこの版の対象外。

## 9. 権限

この表は役割 bundle の既定値であり、正本は `v6-30-login-users-requirements-draft.md` §7 の三段階（`edit` / `view` / `none`）と重要操作 permission である。表中の「個別権限」「指定者のみ」「二者承認」は、次の permission key を staff へ個別付与することを指す。

| 操作 | owner | admin | staff |
|---|---:|---:|---:|
| 一覧・実行台帳・版・利用先の閲覧 | ○ | ○ | 許可されたアカウントのみ |
| 下書きの作成・編集・複製 | ○ | ○ | 個別権限 |
| 公開・新版公開 | ○ | ○ | × |
| 有効化・停止・保管 | ○ | ○ | × |
| 1人テスト（実送信あり） | ○ | ○ | 個別権限 |
| 失敗処理の再試行・実行の取り消し | ○ | ○ | 指定者のみ |
| 利用先の版更新 | ○ | ○ | × |
| 友だち一覧からの手動実行 | ○ | ○ | 個別権限 |
| 実行台帳のCSV書き出し | ○ | ○ | 個別権限 |
| 受信本文の閲覧 | ○ | ○ | 個別権限 |

| permission key | 対象操作 |
|---|---|
| `automation.definition.edit` | オートメーション・共通アクションの下書き作成、編集、複製 |
| `automation.definition.publish` | 版の公開、新版公開、有効化 |
| `automation.definition.stop` | 停止、再開、保管 |
| `automation.definition.test` | 1人テスト（実送信を伴う） |
| `automation.run.retry` | 失敗処理の手動再試行、`waiting` の取り消し |
| `automation.run.export` | 実行台帳のCSV書き出し |
| `automation.action.execute_manual` | 友だち一覧から選んだ友だちへの共通アクション手動実行 |
| `automation.binding.migrate` | 利用先の版更新 |

- 全アカウント共通の定義は owner だけが作成・変更する
- テスト実行も実送信を伴うため、実行前に対象友だちと発生する外部処理を確認する
- 権限はUIの非表示とは独立してサーバ側で再検証する（v6-30 §8）

## 10. 版と履歴

この機能の利用先は **スナップショット型**（cross-review §2）。配信job、シナリオの通、回答フォームの回答後動作、通知定義などが共通アクションの版を取り込んで動く。

- 公開済み版は不変
- 編集は新しい下書きで行う
- 新版公開で既存利用先を自動更新しない
- 利用先ごとに件数と差分を確認してから新版へ切り替え、migration event を記録する
- 実行開始時にオートメーション版と共通アクション版を固定する
- 待機中も固定版を変えない
- 旧版を使う場合も、その版から新しい版を作って公開する
- 過去の実行結果、入力イベント、処理結果、使用版は書き換えない
- 保管した定義も過去の実行台帳から参照できる

## 11. Lステップとの差

比較対象はLステップの「アクション設定」（各画面に置く共通のアクション設定）、「アクション管理（手動実行）」（登録したアクションを友だちリストで選んだ友だちに手で実行）、「スケジュール実行」（アクションの定期実行）。根拠は `docs/lstep-gap-analysis.md` の X-1、X-2、R-3 と `docs/lstep-liny-screen-behavior-research-2026-08.md` §4-3、§4-5、§5-16。

超える点:

- 版固定とスナップショット型利用先。新版を公開しても利用先は固定版を使い続け、利用先ごとに差分を見て切り替える。実行中・待機中は開始時の版で完走する
- 実行台帳。処理ごとの結果、試行回数、使用版、条件外・gate拒否の理由まで残し、友だち詳細のタイムラインから追える。Lステップ公開資料には実行記録の粒度の記載が無い（研究 §5-16 `B`）
- 副作用なしの1人テストと公開前検査。循環呼び出し、参照切れ、同じきっかけの重複、未接続処理を公開前に止める（研究 §6 P0「安全な公開フロー」）
- Webhook再送・画面再試行に対する冪等実行。`(event_id, action_position)` 相当の一意制約で二重実行しない（研究 §4-3、§4-5 `B`）
- 未取得を `—` と理由で区別し、失敗を0件と表示しない

同等:

- アクション設定: 05、08、09、13 など各機能の画面から同じ共通アクションを参照する（研究 §4-3「同じアクション列を呼び出す」）
- アクション管理（手動実行）: 友だち一覧で選んだ友だちへ公開済み共通アクションを手で実行する（X-1）。V6では03の一括操作runが `automation.action.execute_manual` で実行し、実行台帳に手動実行者を残す
- スケジュール実行: 1回の日時指定、毎日、毎週をきっかけとして画面から設定する（X-2。きっかけ接続契約）
- 複数アクションの連鎖: 1ルールで複数の処理を上から順に実行し、失敗時に止める・続けるを処理ごとに持つ（R-3）
- 待つ、条件で分ける、別のアクションを呼ぶ

除外:

- 100人を超える日時一括配信（06 一斉配信の責務。きっかけ接続契約「今回の除外」）
- 秒単位の起動と、Worker停止中に過ぎた日時の自動遡及
- 任意のcode、SQL、JSON式を処理として実行すること
- 公開済み版の直接編集と、新版公開時の全利用先の自動更新
- Lステップ側の版の扱いと実行記録の粒度は公開資料で未確認のため、「Lステップに無い」とは断定しない（研究 §9）

## 12. 除外するもの

以下は不可能または事故につながるため、この版から除外する。

- 公開済み版の直接編集
- 実行中・待機中の処理を後編集で変えること
- 新版公開時に全利用先を自動更新すること
- 過去イベントへの自動遡及実行
- 共通アクションが自分自身または循環経路を呼ぶこと
- 未知の処理を無視して成功にすること
- 外部サービスまで含めた完全な「必ず1回だけ」の保証
- 秒単位の日時指定
- 実装されていない選択肢や「準備中」ボタンの表示
- 取得できない件数を0として表示すること
- 履歴の物理削除や公開済み版の上書き
- 処理ごとに独自の再試行回数を持つこと

外部送信は「少なくとも1回＋冪等キー」で重複を防ぐ。相手側が冪等キーを扱えない場合は、自動再試行の可否を処理ごとに明示する。

## 13. 完了条件

### 画面

- V6 8画面すべてで、空・読み込み中・失敗・権限不足の 4 状態が共通部品 `ListState` で描画され、契約テストが通る
- 主操作ごとに、成功・失敗・権限不足（`view` と `none`）の 3 経路を自動テストで確認する
- 画面遷移は `scripts/visual-qa/screens.mjs` の対象画面一覧と過不足なく一致する
- 設計との画像比較は共通工程ゲート（`v6-shared-platform-requirements.md` §10「工程ゲート」）に従う。要件の完了条件には含めない
- 1440px・1920pxで8画面に横スクロールが0件
- タブ順とボタン名が §3 の固定値と一致し、`準備中` の文字列が0件
- 空・読み込み中・失敗の全てに `data-list-state` が付き、撮影側から状態名で取得できる
- 帯・セルの未取得が `—` と「未取得」「取得失敗」「権限不足」「未接続」のいずれかで表示され、「取得できません」「unavailable」が画面文言に0件

### 機能

- きっかけ→条件→処理→テスト→有効化→停止→実行台帳の一周を自動テストで確認する
- `skipped`（条件外・gate拒否）、`waiting`、一部成功、`permanent_failed`、`cancelled` を再現する自動テストが通る
- 公開後に定義を編集しても、開始済み実行の使用版が変わらないことをテストで確認する
- 新版公開後、利用先の固定版が変わらず、`automation.binding.migrate` 後だけ新版になり migration event が1件記録される
- 同じイベントを2回投入しても処理の実行結果が1件のまま増えない
- 自分自身・再帰深さ3超の共通アクションを公開しようとすると422で拒否される
- 接続契約 §1 に無い処理種別は公開・実行ともに拒否される
- 一時失敗の再試行が共通基盤 §6-2 の既定と一致し、成功済み処理が手動再試行で再実行されない
- 他アカウントの定義・実行・利用先へURL直打ち・API直叩きで到達できない

### 品質

- 型検査、契約テスト、機能テスト、ビルドが通る
- きっかけごとの発火テストがある
- 版固定、冪等性、再試行、待機再開、権限、アカウント分離のテストがある
- 旧データ移行のdry-run結果と、変換できない行の一覧がある
- 自動変換・要確認・除外の全件に、判定理由がある
- 新API・新画面・新実行エンジンが旧JSONを参照していないことをgrepで確認する
- 移行前後で `automation_logs` の件数が一致する

## 14. 実装を分ける単位

1PRで全部を変えない。依存順に分ける。

1. **基盤**: 新しい版、実行、処理結果、共通アクション、利用先のテーブルと移行dry-run
2. **実行エンジン**: 版固定、冪等性、失敗処理、待機再開、状態名の正式化
3. **第1期処理の統合**: 接続契約 §3 の処理
4. **きっかけの接続**: フォーム、リンク、予約、日時指定
5. **共通アクションAPI・画面**: 25-2、25-2-A、25-2-B
6. **オートメーションAPI・画面**: 25-1、25-1-A、見本、状態
7. **実行台帳・移行切替**: 25-1-B、旧ログ併読、最終切替
8. **第2期処理の接続**: 接続契約 §4（17、24 の台帳API接続を含む）
9. **第3期処理の接続**: 接続契約 §5（19、27 の基盤完成後）

各PRは `codex/development` の最新化、テスト、反映履歴、PRゲートを個別に通す。
