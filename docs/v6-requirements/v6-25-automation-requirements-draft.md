# V6 25 オートメーション 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「25 オートメーション」
位置づけ: Pencil と現行リポジトリを照合した、実装に渡す前の要件定義

## 0. 結論と採点

V6の画面設計は、そのまま要件定義へ進める品質にある。Lステップ相当の「きっかけ→条件→処理」に加え、共通アクション、版固定、利用先の把握があり、設計上は競合より一段上を狙える。

ただし、現行実装はオートメーション1件の中に条件と処理をJSONで保存し、その場で順番に実行する方式である。このまま画面だけV6へ替えると、公開済み定義の後編集、待機中の処理の変化、二重送信、記録の欠落が起きる。そのため、画面実装より先に版と実行台帳を足す。

| 評価軸 | 現在 | この要件を実装後 | 判断 |
|---|---:|---:|---|
| UI・UX | 94 | 97 | 画面構造は採用する |
| Lステップとの競争力 | 94 | 98 | 共通アクションと版管理が強み |
| 現行基盤からの実装可能性 | 62 | 94 | 既存実行部品を再利用すれば可能 |
| 安全性・運用性 | 48 | 96 | 版固定、冪等性、再試行が必須 |
| 要件の確定度 | 76 | 95 | 本書の前提で実装へ進められる |

総合判断: **採用する。V6を正本として新しい実行基盤を作り、現行データだけを段階移行する。**

### 0-1. 最重要原則

守る対象を混同しない。

| 守るもの | 守らないもの |
|---|---|
| 友だち、タグ、シナリオなどの業務データ | 現行画面の構造 |
| 既存オートメーションの意味 | `conditions` / `actions` を1行に入れる旧JSON形式 |
| 過去の実行履歴 | 現行APIの入力形式 |
| 誰がいつ何を実行したか | 公開済み定義を直接更新する動き |

> **V6を古い形式へ合わせない。古いデータをV6の新形式へ変換する。**

新しい画面とAPIは、最初から版、処理、実行、履歴が分かれた新形式だけを扱う。旧形式の読み取りと変換は移行専用層に閉じ込め、通常機能から参照させない。

## 1. この機能で利用者が達成すること

主タスクは1つ。

> 友だちの行動をきっかけに、対象条件を判定し、複数の処理を安全に順番どおり実行し、その結果と使われた版を後から確認できる。

補助タスク:

- 見本から短時間で作る
- 1人だけでテストしてから有効にする
- 同じ処理のまとまりを共通アクションとして再利用する
- 新しい版を公開しても、既存の利用先を勝手に変えない
- 失敗、条件外、待機中、完了を実行記録で確認する

## 2. この版で変えないもの

- V6の画面構造、タブ順、ボタン名、共通ルール
- 既存の友だち、タグ、シナリオ、テンプレート、リッチメニューのデータ
- 既存のシナリオアクションが持つ、条件、順序、再実行防止の考え方
- 過去の `automation_logs`。移行後も読み取り可能な履歴として残す
- LINEアカウント単位のデータ分離

## 4. 画面ごとの要件

### 4-1. 25-1 一覧

- 主操作は「見本から作る」。ゼロから作る導線も一覧内に置く
- 検索対象は名称、きっかけ、処理
- 絞り込みは、すべて、動いている、止めている、失敗あり、30日動いていない
- 期間の初期値は直近30日
- 並び順の初期値は実行回数が多い順
- 同じきっかけのオートメーションが複数ある場合は、両方が動くことを案内する
- 一覧の数値は、選択期間内の実行台帳から集計する。取れない数を0で埋めない
- 有効化・停止は確認後に反映し、すでに始まった実行には影響しない
- 削除はしない。利用中または履歴ありは「保管」にする

### 4-2. 25-1-A つくる

3段階で作る。

1. きっかけ
2. 対象となる友だち
3. 実行する処理

必須動作:

- 条件に一致する見込み人数を確認できる
- 人が読める文章で「いつ、だれに、何をするか」を表示する
- 1人だけでテストできる
- 下書き保存と「作成して有効にする」を分ける
- 同一イベントが再度発生した場合の再実行可否を設定する
- 同じきっかけの他オートメーションとの重複を公開前に警告する
- 公開後の過去イベントは遡って実行しない

きっかけの実装可否:

| V6のきっかけ | 現状 | 要件 |
|---|---|---|
| 友だち追加 | 既存 | `friend_add` に統一する |
| タグ追加・解除 | 既存 | `tag_change` と actionで判定する |
| メッセージ受信 | 既存 | `message_received` を使う |
| フォーム回答 | イベント記録はあるが未接続 | `form_submitted` を共通イベントへ接続する |
| 注文確定 | EC側の既存イベントあり | 既存ECイベント名を正規化して使う |
| 日時指定・毎日・毎週 | 未実装 | アカウントのタイムゾーンを必須にし、5分単位で起動する |
| リンククリック | 計測はあるが未接続 | `link_clicked` を共通イベントへ接続する |
| 予約確定 | 型だけあり、発火未確認 | `calendar_booked` の発火元を追加してから表示する |
| ブロック・フォロー解除 | 未実装 | LINE Webhookで確実に取れる範囲だけ別イベントとして追加する |

画面に出すきっかけは、保存と実行まで接続済みのものだけにする。「準備中」の選択肢は出さない。

### 4-3. 25-1-B 動いた記録

- 実行、条件外、待機中、一部成功、失敗、取り消しを区別する
- 友だち、オートメーション名、期間、状態で検索できる
- 新しい順を初期値にする
- CSVで書き出せる
- 行を開くと、使用したオートメーション版、共通アクション版、各処理の結果を見られる
- 条件外も記録する。ただし保存量を抑えるため90日を明細保持期間とし、それ以前は日別件数だけ残す
- テスト実行は本番実行と区別して表示する
- 過去の記録は、定義を編集しても書き換えない

### 4-4. 25-1-C 見本

- 見本を選ぶと、公開ではなく下書きを作る
- 現在のV6の見本は残す。ただし使えない処理を含む見本は、その処理の実装完了まで非表示にする
- 見本はアカウントの実データIDを持たず、タグ・シナリオ・テンプレートを利用者が選び直す
- 見本の更新で、既に作ったオートメーションは変わらない

### 4-5. 25-1-D 状態

| 状態 | 条件 | 見せ方 |
|---|---|---|
| 空・作れる | オートメーション0件 | 作成導線つき空状態＋「見本から作る」 |
| 検索結果0件 | 検索・条件で0件 | 結果0件の共通空状態 |
| 読み込み中 | 初期・再取得中 | 読み込み共通部品 |
| 失敗 | API取得失敗 | 再試行導線と事故番号 |
| 権限不足 | 閲覧または編集権限なし | 見えない操作と灰色表示を役割別に分ける |
| 上限 | 同時実行数などの契約上限 | 上限、現在数、解消方法を表示する |

### 4-6. 25-2 共通アクション

- 名称、説明、公開版、使われている場所、最終更新、状態を表示する
- 絞り込みは、すべて、公開中、下書き、旧版利用あり、未使用
- 「共通アクションをつくる」を主操作にする
- 複製は下書きを作る。元とのリンクは持たない
- 公開済みの内容は編集できない
- 新版公開後も、既存の利用先は現在の版を使い続ける
- 旧版を使う場所がある場合は、件数と利用先を表示する

### 4-7. 25-2-A 共通アクションをつくる

各処理は順序、条件、失敗時の動き、再試行方針を持つ。

初期対応する処理:

- タグを付ける・外す
- 友だち情報を設定・加減・消去する
- 対応マークを付ける
- シナリオを開始・停止・再開する
- LINEメッセージまたはテンプレートを送る
- リッチメニューを切り替える・外す
- 担当者を割り当てる
- マイルを増減する
- 運用者または顧客へ通知する
- 外部Webhookへ送る
- 待つ
- 条件で分ける
- 別の共通アクションを呼ぶ

既存の `scenario_actions` とシナリオ用編集部品を、タグ、友だち情報、対応マーク、シナリオ、共通情報の正本として再利用する。回答フォーム・自動応答が持つ別形式は、共通形式へ変換するアダプターを用意する。

処理ごとの失敗時設定:

- 止める
- 次へ進む

再試行可能な外部処理は、1分、5分、30分の最大3回を既定とする。入力不備、権限不足、宛先なしは再試行せず失敗にする。

### 4-8. 25-2-B 版と使われている場所

- 利用先ごとに、固定中の版、新しい版の有無、実行中件数、待機中件数を表示する
- 利用先ごとに「新しい版へ更新」を実行する
- 更新前に差分と影響を表示する
- 公開済み版へ直接戻さない。「この版をもとに新しい版を作る」にする
- 実行中または待機中の処理は、開始時の版のまま完了する
- 過去の実行記録は使用版を保持する

## 5. データ要件

### 5-0. V6の新形式を正本にする

新形式は旧テーブルの都合から決めない。V6で必要な動作から先に決める。

| V6で必要なこと | 新形式の正本 |
|---|---|
| 公開済み内容を変えない | オートメーション版 |
| 待機中も同じ内容で最後まで動く | 実行開始時に固定した版 |
| どの処理が失敗したかを見る | 処理ごとの実行結果 |
| 同じ送信を重ねない | 実行・処理ごとの冪等キー |
| 共通処理を使い回す | 共通アクション本体・版・利用先 |
| 新版を利用先ごとに切り替える | 固定版を持つ利用先 |

新規作成、編集、公開、実行はすべて新形式へ直接保存する。新しい操作を旧JSONへ書き戻す処理は作らない。

### 5-1. 既存で使うもの

| 既存 | 使い方 |
|---|---|
| `automations` | 既存定義の移行元。移行中は互換読み取りを残す |
| `automation_logs` | 過去履歴。削除・上書きしない |
| `scenario_actions` と発火記録 | 共通アクションの処理形式と一度だけ実行の先例 |
| 友だち・タグ・シナリオ・テンプレート | 各処理の参照先 |
| 既存イベント発火処理 | 友だち追加、タグ、受信、成果、ECのきっかけ |
| 既存Cron・送信待ち・冪等性の仕組み | 待機、再開、重複防止の実装パターン |

### 5-2. 新しく必要なもの

名前は実装時に既存命名へ合わせるが、責務は分ける。

| データ | 主な項目 | 必要な理由 |
|---|---|---|
| オートメーション本体 | account、名称、状態、現在版、優先順 | 定義の同一性と版を分けるため |
| オートメーション版 | 版番号、きっかけ、対象条件、処理定義、公開日時、作成者 | 公開済み定義を不変にするため |
| 実行 | 対象友だち、使用版、状態、現在位置、再開日時、冪等キー | 待機・再開・二重防止のため |
| 処理の実行結果 | 処理ID、試行回数、結果、エラー、開始・終了 | どこで失敗したかを見るため |
| 共通アクション本体 | account、名称、状態、現在公開版 | 利用先と版を分けるため |
| 共通アクション版 | 版番号、処理、公開日時、作成者 | 利用先を固定するため |
| 利用先 | 種類、利用先ID、使用箇所、固定版 | 影響範囲と手動更新のため |

必須制約:

- すべての新規定義に `line_account_id` を必須とする
- 1つの発生イベントと処理に対して冪等キーを一意にする
- 公開済み版を更新できないDB制約またはサーバー制約を置く
- 履歴がある本体は物理削除しない
- 版・利用先・実行・処理結果に検索用インデックスを置く

## 6. 保存形式と移行

現行の `conditions` と `actions` のJSONを、そのまま新版の公開定義として使い続けない。旧形式は移行元であり、新機能の互換仕様ではない。

### 6-1. 変換対応表

| 現行データ | V6の変換先 | 判定 |
|---|---|---|
| `automations.id/name/description` | オートメーション本体 | 自動変換 |
| `event_type` | 第1版のきっかけ | 対応表にある値だけ自動変換 |
| `conditions` JSON | 第1版の対象条件 | 認識できる条件だけ自動変換 |
| `actions` JSON | 第1版の処理 | 認識できる処理だけ自動変換 |
| `is_active` | 本体の動作状態 | 自動変換。ただし要確認行は強制停止 |
| `priority` | 本体の優先順 | 自動変換 |
| `line_account_id` | 本体の所属アカウント | 値ありは自動、空は隔離 |
| `automation_logs` | 旧実行履歴 | 変換せず閲覧専用で保持 |

### 6-2. 3種類の移行判定

| 判定 | 条件 | 移行後の扱い |
|---|---|---|
| 自動変換 | きっかけ・条件・処理をすべて認識できる | 第1版を作成。元が有効なら有効状態を引き継ぐ |
| 要確認 | 一部の条件・処理が不明、参照先がない | 下書きとして変換し、停止状態で表示する |
| 除外 | 所属アカウント不明、JSON破損、安全に意味を再現できない | 通常一覧へ出さず、移行レポートへ隔離する |

「要確認」と「除外」を、空の処理や成功扱いへ変換してはいけない。

### 6-3. 一時的な移行層

移行層が行うのは次の3つだけ。

1. 旧形式を読み取る
2. 新形式へ変換できるか判定する
3. 変換結果と理由をレポートする

移行層から新しい画面へ旧形式を返さない。新しい実行エンジンから旧形式を読まない。新APIから旧形式へ書き込まない。

移行手順:

1. V6の新形式と入力検証を先に確定する
2. 新テーブルを既存と並行して追加する
3. 本番データを変更しないdry-runで、自動変換・要確認・除外の件数と理由を出す
4. 自動変換できる各 `automations` を、本体＋第1版へ変換する
5. 認識できない処理は「要確認の下書き」として停止する
6. `line_account_id` が空の既存行は「旧全体設定」として隔離し、通常画面から編集させない
7. 新規作成と編集を新API・新形式へ切り替える
8. 実行エンジンをアカウント単位で新版へ切り替える
9. 過去の `automation_logs` は旧履歴として残し、新規実行は新しい実行台帳へ記録する
10. 全対象の照合後、旧JSONへの書き込みと旧実行エンジンを停止する

一括移行はしない。シナリオ、自動応答、回答フォームは、利用先ごとに変換・検証してから共通アクションへ接続する。

### 6-4. 旧形式を終了する条件

次が全部そろった時点で、旧形式を終了する。

- dry-runの自動変換件数と実移行件数が一致する
- 要確認・除外の全件に理由と対応者が付いている
- 有効だったオートメーションの動作比較テストが完了している
- 新旧で対象者、処理順、送信内容が一致する
- 二重実行を防ぐ切替手順が検証されている
- 新しい実行記録がV6画面から確認できる
- ロールバック時も旧データを上書きしない

終了後も旧テーブルと過去ログは一定期間読み取り専用で保持するが、V6のAPI・画面・実行処理からは切り離す。

## 7. API要件

| 操作 | メソッド・パスの案 | 失敗時 |
|---|---|---|
| 一覧・集計 | `GET /api/automations` | 再試行可能な取得エラーを返す |
| 下書き作成 | `POST /api/automations` | 入力欄ごとのエラーを返す |
| 新版作成 | `POST /api/automations/:id/versions` | 競合時は再読み込みを促す |
| 公開 | `POST /api/automations/:id/versions/:version/publish` | 未接続処理、循環、無効参照を一覧返却 |
| 有効・停止 | `POST /api/automations/:id/status` | 変更前状態を維持 |
| 1人テスト | `POST /api/automations/:id/test` | 失敗した処理と理由を返す |
| 実行一覧 | `GET /api/automation-runs` | cursorで再取得可能にする |
| 実行詳細 | `GET /api/automation-runs/:id` | 権限外は存在も明かさない |
| 共通アクション一覧 | `GET /api/common-actions` | 同上 |
| 共通アクション作成 | `POST /api/common-actions` | 入力欄ごとのエラーを返す |
| 新版公開 | `POST /api/common-actions/:id/versions/:version/publish` | 循環・無効参照を返す |
| 利用先の版更新 | `POST /api/common-actions/:id/bindings/:bindingId/version` | 実行中は旧版固定のまま更新 |

API側の必須ルール:

- `lineAccountId` はセッションから決め、画面の任意値を信用しない
- 任意JSONをそのまま保存せず、処理種別ごとのスキーマで検証する
- 旧 `conditions` / `actions` 形式を新APIの入力として受け付けない
- 新APIは新形式だけを読み書きし、互換変換は移行専用処理だけで行う
- 更新競合を版番号または `If-Match` で検知する
- 未知の処理種別は成功扱いにせず、公開を拒否する
- LINE送信・Webhookなど外部処理は冪等キー、タイムアウト、再試行可否を記録する
- WebhookはHTTP 2xx以外を失敗として扱う
- 宛先なし、トークンなし、対象友だちなしを成功扱いにしない
- 一覧APIは状態、期間、友だち、名称、cursorを受け取る

## 8. 実行要件

実行は「イベント受付→対象判定→実行作成→各処理→完了」の順にする。

1. イベントに一意な受付IDを付ける
2. LINEアカウント内の有効なオートメーションだけを候補にする
3. 公開版を固定する
4. 条件外なら `skipped_condition` を記録して終了する
5. 条件一致なら実行行を1件だけ作る
6. 各処理を順番に実行し、結果を1件ずつ残す
7. 待機は実行を `waiting` にし、`resume_at` 後にCronで再開する
8. 共通アクションを呼ぶときは、利用先に固定された版を実行へ記録する
9. 外部処理は同じ処理実行IDを冪等キーとして使う
10. 全処理の終了後に成功・一部成功・失敗を確定する

待機・日時指定の精度は既存Cronに合わせて **5分単位、最大遅延5分を目標** とする。秒単位の正確な実行はこの版の対象外。

## 9. 権限

| 役割 | 見える | 触れる |
|---|---|---|
| 統括 | 全アカウントの一覧・履歴・版・利用先 | 作成、公開、停止、保管、版更新、テスト |
| 管理者 | 自分のLINEアカウント内の全情報 | 作成、公開、停止、保管、版更新、テスト |
| 担当者 | 許可されたアカウントの一覧・実行記録 | 閲覧のみ。編集操作は表示しない |

テスト実行も実送信を伴うため、統括・管理者だけにする。実行前に対象友だちと発生する外部処理を確認する。

## 10. 版と履歴

- 公開済み版は不変
- 編集は新しい下書きで行う
- 新版公開で既存利用先を自動更新しない
- 利用先ごとに明示的に新版へ更新する
- 実行開始時にオートメーション版と共通アクション版を固定する
- 待機中も固定版を変えない
- 旧版を使う場合も、その版から新しい版を作って公開する
- 過去の実行結果、入力イベント、処理結果、使用版は書き換えない

## 11. 除外するもの

以下は不可能または事故につながるため、この版から除外する。

- 公開済み版の直接編集
- 実行中・待機中の処理を後編集で変えること
- 新版公開時に全利用先を自動更新すること
- 過去イベントへの自動遡及実行
- 共通アクションが自分自身または循環経路を呼ぶこと
- 未知の処理を無視して成功にすること
- 外部サービスまで含めた完全な「必ず1回だけ」の保証
- 秒単位の日時指定
- 実装されていない選択肢や「準備中」ボタンの表示
- 取得できない件数を0として表示すること
- 履歴の物理削除や公開済み版の上書き

外部送信は「少なくとも1回＋冪等キー」で重複を防ぐ。相手側が冪等キーを扱えない場合は、自動再試行の可否を処理ごとに明示する。

## 12. 完了条件

### 機能

- V6の8画面・全状態が動く
- きっかけ、条件、処理、テスト、有効化、停止、実行記録が一周する
- 条件外、待機中、一部成功、失敗を再現できる
- 公開後に定義を編集しても、開始済み実行が変わらない
- 新版公開後も、利用先が手動更新されるまで旧版を使う
- 同じイベントを再投入しても同じ処理が二重実行されない
- 循環する共通アクションを公開できない
- 不明な処理種別を公開・実行できない

### 画面

- PencilのV6実Node IDと実装URLをPRに固定する
- 1440px・1920pxで主要一覧に横スクロールがない
- 空、結果0件、読み込み、失敗、権限不足、上限の各状態が出る
- ボタン名とタブ順がV6に一致する
- `準備中` のボタンがない
- 設計画像と同じ状態・同じ幅の実装画像を並べて目視確認する

### 品質

- 型検査、契約テスト、機能テスト、ビルドが通る
- イベントごとの発火テストがある
- 版固定、冪等性、再試行、待機再開、権限、アカウント分離のテストがある
- 旧データ移行のdry-run結果と、変換できない行の一覧がある
- 自動変換・要確認・除外の全件に、判定理由がある
- 新API・新画面・新実行エンジンが旧JSONを参照していない
- 過去ログが欠けていない

## 13. 実装を分ける単位

1PRで全部を変えない。依存順に分ける。

1. **基盤**: 新しい版、実行、処理結果、共通アクション、利用先のテーブルと移行dry-run
2. **実行エンジン**: 版固定、冪等性、失敗処理、待機再開
3. **既存処理の統合**: タグ、友だち情報、シナリオ、LINE、Webhook、リッチメニュー
4. **きっかけの接続**: フォーム、リンク、予約、日時指定
5. **共通アクションAPI・画面**: 25-2、25-2-A、25-2-B
6. **オートメーションAPI・画面**: 25-1、25-1-A、見本、状態
7. **実行記録・移行切替**: 25-1-B、旧ログ併読、最終切替

各PRは `codex/development` の最新化、テスト、設計画像比較、反映履歴、PRゲートを個別に通す。
