# V6 20 分析 要件定義（実装照合版・下書き）

作成日: 2026-08-25
対象: V6「20 分析」
位置づけ: Pencil、現行画面、DB、API、集計処理を照合した実装前要件

## 0. 結論と採点

V6の設計は採用する。前半4タブで全体を把握し、後半4タブで詳しく調べる構成は、Lステップ相当のクロス・ファネル・URL計測を残しながら、「使われ方」「保存結果」「経路別の差し引き」まで扱える。

現行実装から消してはいけないものも明確になった。

- 送信数と配信実績
- クロス集計
- ファネルの作成と表示
- URLクリック
- Search Console

ただし、現行ファネルは時系列を判定しておらず、分析APIにはLINEアカウントの絞り込みがない。V6へ載せ替える前に、データ分離とイベント時系列を直す必要がある。

| 評価軸 | 現在 | この要件を実装後 | 判断 |
|---|---:|---:|---|
| UI・UX | 96 | 98 | 9画面を採用する |
| Lステップとの競争力 | 96 | 99 | 「使われ方」と結果保存が強み |
| 現行基盤からの実装可能性 | 74 | 95 | 既存集計を残して読取基盤を追加する |
| データの正確性 | 52 | 96 | アカウント分離と時系列判定が必須 |
| 要件の確定度 | 87 | 96 | 本書の前提で実装へ進められる |

総合判断: **採用する。既存の分析を落とさず、V6を正本にして分析用の読取基盤を追加する。**

### 0-1. 最重要原則

分析専用のデータは、業務データの正本を置き換えない。

> 既存テーブルは業務の正本として残し、分析では必要な事実だけを、アカウント・人・時刻がそろった追記型の読取データへ束ねる。

- 友だち、配信、フォーム、成果、予約などの元データは上書きしない
- 分析用イベントは元データを参照する読取モデルであり、業務処理の正本にしない
- 保存した分析結果は生成時点のスナップショットとして不変にする
- 取れない数字を0にしない
- 相関を原因として説明しない

## 1. この機能で利用者が達成すること

主タスクは1つ。

> 友だちがどこから来て、何に反応し、どこで止まり、どの施策が成果につながったかを、同じ数字で比較して次の行動へつなげる。

補助タスク:

- 友だちの増減と配信日の関係を見る
- 配信ごとの到達・開封・クリックを見る
- 流入経路ごとの成果と費用を比べる
- 作ったのに使われていない設定を見つける
- 条件を掛け合わせて対象者を見る
- 時系列のファネルで離脱場所を見る
- URLごとのクリックを確認する
- 分析条件とその時点の結果を保存する
- 定期レポートと大きな変化の通知を設定する

## 2. この版で変えないもの

- V6の8タブと、前半4つ・後半4つの区切り
- V6の9画面、ボタン名、右390pxカラム、共通状態
- 既存の配信実績、URLクリック、ファネル定義、サイト計測データ
- `/search-console` のGoogle検索分析
- 過去の元ログと履歴
- 既存の第一接触を基準にした流入経路の考え方

Search Consoleを「Google Analytics」と呼ばない。現行画面は実際にはGoogle検索のデータであり、GA4ではない。V6の8タブからは外すが、正しい名前の「Search Console」として経路と成果から移動できるように残す。

## 4. 画面ごとの要件

### 4-1. 20-1 友だちの増減

表示する数値:

- 期間内に増えた人数
- 期間内に減った人数
- 差し引き
- 現在つながっている人数
- 初回追加と再追加の内訳

グラフ:

- 日ごとに、増えた人数を基準線より上、減った人数を下に表示する
- 同じ日に行った一斉配信・主なシナリオ配信を印で重ねる
- 配信後に減った人数が増えても「配信が原因」と断定しない
- 日を選ぶと、増減の内訳と当日の主な施策を表示する

現行データの制限:

- 初回追加、直近の解除、解除回数は既存データから取れる
- 過去のすべての解除・再追加時刻は残っていないため、読取イベント導入前の完全な日別履歴は復元できない
- 復元できない期間は「一部」（as_of併記）と表示し、推測で埋めない

### 4-2. 20-1-A 配信の反応

表示する数値:

- 送信数
- 到達数
- 開封人数・開封率
- クリック人数・クリック率
- 反応が取得できなかった配信数

一覧:

- 配信名、送信日時、対象人数、到達、開封、クリック、成果
- 一斉配信とシナリオ配信を区別する
- LINEの配信実績と、自社の計測URLクリックを混ぜずに表示する
- 20人未満などLINE側の制約で取得できない場合は `—` と理由を表示する
- 取得待ち、取得失敗、取得対象外を区別する

時間帯グラフ:

- 自社計測URLの `clicked_at` から、クリックが発生した時間帯を表示する
- 「最もクリックされた時間」と表現し、「最適な配信時間」と断定しない
- 率を出す場合は、送信時にそのURLが届いた人数を分母にする

### 4-3. 20-1-B 経路と成果

経路ごとに表示する。

- クリック
- 友だち追加
- 現在つながっている人数
- 反応した人数
- 成果件数
- 成果金額
- 広告費
- 1人追加あたりの費用
- 成果1件あたりの費用
- 成果金額から広告費を引いた差し引き

集計ルール:

- 既定の経路帰属は第一接触とする
- 中継リンクを通らないLINE追加は、経路不明として扱う
- 成果は承認済みを既定とし、保留・却下を別表示する
- 成果金額は成果地点または注文に保存された実値を使う
- 広告費は「18 流入と計測」の広告側取込データを使う
- 広告費が未接続なら、費用・差し引き・CPAを0にせず、値は `—`、ラベルは「未接続」とする（共通基盤 §9）
- 帰属方式と集計期間を画面に表示する

Search Consoleは、この画面の「つながる先」に正しい名称で置く。GA4連携は別要件であり、この版には含めない。

### 4-4. 20-1-C 使われ方

目的は、作った数を競うことではなく、未使用・重複・参照切れを見つけること。

対象:

- テンプレート
- シナリオ
- 回答フォーム
- リッチメニュー
- タグ・友だち情報
- 流入リンク・成果地点
- オートメーション・共通アクション
- 登録メディア・共通情報

表示:

- 作成数、利用中、未使用、参照切れ
- 最終利用日時
- 使われている場所の件数
- 利用先一覧への移動
- 参照情報を最後に確認した時刻

未使用だから自動削除してはいけない。削除は各機能の確認フローへ移動する。

### 4-5. 20-1-D 定期レポートをつくる

設定項目:

- レポート名
- 対象の保存した分析
- 毎週・毎月
- 曜日または日付、時刻、タイムゾーン
- 受信する担当者
- 画面内、メール、運用者LINE通知
- 通常レポートとは別に知らせる変化の条件

変化通知:

- 同じ長さの直前期間と比較する
- 最低母数を満たす場合だけ判定する
- 増減率または実数差で設定する
- 取得待ち・部分データの期間は異常判定しない
- 通知には顧客本文、秘密値、URLクエリを含めない

送信結果と、そのとき使った分析結果を保存する。通知先は「24 運用者へのお知らせ」と連携する。

### 4-6. 20-2 クロス分析

V6の基本操作:

- 縦軸を選ぶ
- 横軸を選ぶ
- 数えるものを選ぶ
- 期間を選ぶ
- 追加条件を最大15軸で指定する
- ますを選んで、人数、全体比、前期間との差を見る
- 選んだ人を友だち一覧で見る、または配信作成へ渡す

対応する軸:

- 流入経路
- タグの有無
- 友だち情報の選択値
- 行動スコア帯
- シナリオの状態
- フォーム回答の選択値
- 成果地点
- 購入・予約の状態
- 期間内の行動有無

自由入力文、個人名、URL全文など、高種類・個人情報になる値は軸にしない。表示上限は縦50×横20とし、超える場合は上位と「その他」にまとめる。

選択したますの人数は重複しない友だち数。延べ件数を使う場合は、画面に「件」と明記する。

### 4-7. 20-2-A ファネル

V6のファネルは、単なる条件の交差ではなく時系列で判定する。

例:

1. 友だちになった
2. 初めて反応した
3. フォームに答えた
4. 予約した
5. 購入した

判定ルール:

- 1段目を起点に、その人の判定期間を開始する
- 2段目以降は、前の段の後に発生したイベントだけを数える
- 最後の段まで、起点から設定日数以内であること
- 1つの結果内では同じ友だちを1回だけ数える
- 判定期間が終わっていない人を「途中」と「離脱」に分けない
- 離脱は、判定期間が終わって次段へ進まなかった人だけ
- 段ごとに平均到達時間と中央値を計算する
- 比較条件を最大3群まで並べる
- 各段の「止まった人を見る」「この人たちに配信する」を使えるようにする

現行実装の修正必須点:

- 現在は同一期間内の集合を順に絞るだけで、発生順を見ていない
- `window_days` を実際の判定に使っていない
- `segment_json` を結果に使っていない
- `purchase` は選択肢にあるが集計処理がない
- 未知の段を0人として隠している
- ファネルにLINEアカウントの所属がない

未知の段、参照切れ、時刻不明がある場合は公開・集計を拒否し、0人として表示しない。

### 4-8. 20-2-B URLクリック

既存の `tracked_links` と `link_clicks` を正本として使う。

表示:

- URL名、飛び先、状態、使用場所
- クリック回数
- 分かった友だちの人数
- 届いた人数
- クリック率
- 最初・最後のクリック日時
- クリック後に実行するタグ・シナリオ
- 0回のURL

注意:

- 友だち不明のクリックもクリック回数へ含める
- 人数は友だちを特定できた分だけにする
- クリック率の分母は、そのURLを実際に含むメッセージが届いた友だち数
- 現行にはURL単位の送信対象記録がないため、過去のクリック率は復元できない
- 新規送信からURL露出記録を追加し、過去は `—` と理由を表示する
- CSV操作は画面内に1つだけ置く

### 4-9. 20-2-C 保存した分析

保存するものを2つに分ける。

1. **分析の定義**: 軸、条件、期間の決め方、数えるもの
2. **分析結果**: 基準日時、対象期間、母数、結果、データ更新時刻

表示:

- 名前、種類、作成者、更新日時
- 固定期間または直近90日などの期間方式
- 最後に計算した結果
- 過去結果の一覧
- 定期レポートの有無
- 失敗・部分データ・取得待ち

定義を編集しても過去結果を変えない。編集は新しい定義版にし、以後の実行だけに使う。

## 5. 状態

| 状態 | 条件 | 見せ方 |
|---|---|---|
| ふつう | 必要データが揃う | 値、母数、期間、更新時刻を表示 |
| 空・作れる | ファネル・保存分析・定期レポート0件 | 作成導線つき空状態 |
| 結果0件 | 条件に合う人がいない | 条件を変える案内。作成ボタンは出さない |
| 読み込み中 | 初期取得・再集計 | 読み込み共通部品 |
| 取得待ち | LINE・広告側の反映待ち | 0ではなく待ちと反映目安を表示 |
| 取得対象外 | 少人数など外部制約 | `—` と理由を表示 |
| 部分データ | 過去履歴やアカウント帰属が一部不明 | 対象期間と欠けた範囲を表示 |
| 判定中 | ファネルの判定期間内 | 離脱へ含めず別人数で表示 |
| 失敗 | 集計・外部取得失敗 | 再試行と事故番号を表示 |
| 権限不足 | 閲覧・書出し・作成権限なし | 操作を隠し、理由を表示 |
| 上限 | 軸・期間・保存数の上限 | 現在値と解消方法を表示 |

各指標は `available / pending / unavailable / insufficient / partial / failed` の状態を持つ。APIが数値だけを返さない。

未取得の画面表記は共通基盤（`v6-shared-platform-requirements.md` §9）の表に揃える。値は `—`、ラベルは「未取得」。理由が分かる場合は「取得失敗」「権限不足」「未接続」にする。APIの状態名はそのまま使う。

## 6. データ要件

### 6-1. 既存で使うもの

| 既存 | 用途 |
|---|---|
| `friends` | 現在状態、初回・直近の追加解除、所属アカウント |
| `messages_log` | 送受信、配信・シナリオ、送信時刻 |
| `broadcast_insights` | 到達、LINE開封、LINEクリック |
| `tracked_links` / `link_clicks` | 自社URLクリック |
| `funnels` / `funnel_steps` | 現行ファネル定義の移行元 |
| `friend_tags` / `friend_field_values` | 現在属性と一部の付与時刻 |
| `form_submissions` | フォーム回答イベント |
| `conversion_events` / `conversion_points` | 成果件数・金額 |
| `entry_routes` / `ref_tracking` | 第一接触の流入経路 |
| `site_events` | サイト行動 |
| `engagement_events` | 既に追記型で残る行動 |
| 各機能の利用先API・参照表 | 「使われ方」の元データ |
| `/search-console` | Google検索分析。別画面として維持 |

### 6-2. 新しく必要な読取データ

| データ | 主な項目 | 必要な理由 |
|---|---|---|
| 分析イベント | account、friend/visitor、種類、元種類・元ID、発生時刻、許可済み属性、値、冪等キー | 時系列ファネルと複数機能の統一集計 |
| 日別集計 | account、日、指標、区分、分子、分母、値、状態、更新時刻 | 概要4画面を高速に表示 |
| 分析本体・定義版 | account、種類、名前、条件、期間方式、版、作成者 | 定義変更と過去結果を分ける |
| 分析結果 | 定義版、基準日時、期間、母数、結果、締切時刻、状態 | 保存結果を不変にする |
| 一時対象者 | 結果、ます・段、friend、期限 | 友だち一覧・配信へ同じ人を渡す |
| URL露出 | account、message、friend、tracked_link、配信元、送信時刻 | 正しいURLクリック率の分母 |
| 利用関係 | account、利用元、使用箇所、利用先、最終確認 | 「使われ方」を横断表示 |
| レポート設定・実行 | account、定義、予定、受信者、しきい値、実行結果 | 定期レポートと通知履歴 |

分析イベントは業務の正本ではなく、追記型の読取モデルとする。元行を削除しても保存済み結果を書き換えない。

### 6-3. 分析イベントに入れる範囲

- 友だち追加・再追加・解除
- メッセージ送受信
- タグ追加・解除
- シナリオ開始・完了
- フォーム回答
- URLクリック
- サイト行動
- 予約確定・取消
- 注文・発送・定期購入状態
- 成果発生・承認・却下
- オートメーション実行

メッセージ本文、URLクエリ、秘密値、広告の生レスポンスは入れない。分析に使う属性は許可一覧方式にする。

### 6-4. LINEアカウント分離

すべての分析定義、イベント、集計、結果、ファネル、レポートに `line_account_id` を必須とする。

- 選択中アカウントの権限をAPIで検証する
- クエリ値だけを信用しない
- アカウント不明の旧行は通常集計へ混ぜない
- 全社横断は統括権限の明示操作だけにし、通常画面では1アカウントを表示する
- account Aの友だち・配信・成果がaccount Bへ出ない自動テストを必須にする

現行の分析APIはアカウント条件がなく、現状のままV6へ使わない。

### 6-5. 保持期間

| データ | 既定 |
|---|---|
| 人を特定できる分析イベント | 13か月 |
| 日別集計 | 25か月 |
| 一時対象者 | 24時間 |
| 保存した分析結果 | 13か月 |
| 定期レポート実行結果 | 13か月 |
| 元の業務ログ | 各機能の既存保持ルール |

保持期間を過ぎた個人イベントは削除し、日別集計だけを残す。保存結果の期間変更は管理設定と料金設計を伴うため、この画面から変えない。

## 7. 保存形式と移行

### 7-1. 既存データを壊さない移行

1. 新しい分析イベントと日別集計を追加する
2. 元データを変更しないdry-runで、アカウント帰属・時刻・重複を検査する
3. 元ID＋イベント種類の一意キーで、変換可能な履歴を追記する
4. アカウント不明、時刻不明、破損参照を部分データとして報告する
5. 新しいイベントは業務処理と同じ受付IDで二重記録を防ぐ
6. 概要画面を日別集計へ切り替える
7. ファネルとクロス分析を新読取モデルへ切り替える
8. 旧APIは互換期間だけ残し、V6画面からは呼ばない

### 7-2. 現行ファネルの移行

- `funnels` をアカウント所属の分析本体へ変換する
- `funnel_steps` を第1定義版へ変換する
- 参照先と段種類がすべて有効なら「要再計算」とする
- `purchase`、未知の種類、参照切れは「要確認」として停止する
- 現行結果は時系列ではないため、過去結果スナップショットとして移行しない
- 新エンジンで再計算した日から正式結果にする

### 7-3. 過去に復元できないもの

- すべての解除・再追加の履歴
- 解除済みタグの過去付与期間
- URLが誰に届いたかという過去の分母
- LINE Insightsから取得できない個人別開封者
- 広告費未取込期間の費用・差し引き

これらを推測値で埋めない。画面に開始日・欠けた範囲・理由を表示する。

## 8. API要件

| 操作 | メソッド・パス案 | 主な出力 |
|---|---|---|
| 友だち増減 | `GET /api/analytics/friends` | 日別増減、内訳、データ状態 |
| 配信反応 | `GET /api/analytics/reactions` | 配信別実績、時間帯、状態 |
| 経路と成果 | `GET /api/analytics/routes` | 経路別成果、費用、帰属方式 |
| 使われ方 | `GET /api/analytics/usage` | 利用・未使用・参照切れ |
| クロス実行 | `POST /api/analytics/cross/query` | 行列、母数、前期間差、結果ID |
| ファネル一覧・作成 | `GET/POST /api/analytics/funnels` | アカウント内の定義 |
| ファネル新版 | `POST /api/analytics/funnels/:id/versions` | 不変の定義版 |
| ファネル結果 | `POST /api/analytics/funnels/:id/run` | 通過、途中、離脱、時間、結果ID |
| URLクリック | `GET /api/analytics/url-clicks` | URL別クリック・分母・状態 |
| 保存分析 | `GET/POST /api/analytics/saved` | 定義、版、最終結果 |
| 結果履歴 | `GET /api/analytics/saved/:id/snapshots` | 不変の過去結果 |
| 対象者作成 | `POST /api/analytics/results/:id/audiences` | 24時間の対象者ID |
| レポート設定 | `GET/POST /api/analytics/report-schedules` | 予定、受信者、しきい値 |
| CSV | `POST /api/analytics/exports` | 非同期書出しID |

API共通ルール:

- account、期間、タイムゾーン、データ締切時刻を必ず返す
- 指標は値と状態をセットで返す
- 期間上限は人単位の詳細13か月、日別集計25か月
- 任意SQL、任意列名、未検証JSONを受け付けない
- 軸・条件・段は許可されたスキーマで検証する
- 重い集計は非同期にし、進捗と再試行を返す
- cursorを使い、巨大な友だちID一覧をレスポンスやURLへ出さない
- 未知のイベント・段は0件にせずエラーにする

## 9. 集計要件

### 9-1. 日別集計

- 5分Cronまたはイベント追記後のキューで更新する
- 当日と遅着があり得る直近7日を再集計する
- 最終更新時刻を画面に表示する
- 元データとの日次照合を行い、ずれは運用状態へ通知する
- 同じ元IDを二重計上しない

### 9-2. 保存結果

結果には次を固定する。

- 分析定義版
- 基準日時
- 対象期間
- タイムゾーン
- 対象母数
- 指標と分母・分子
- 結果行列または段ごとの結果
- データ締切時刻
- 取得待ち・部分データの範囲
- 実行者または定期実行ID

### 9-3. 対象者連携

- クロスのます、ファネルの段、URLのクリック者から一時対象者を作る
- `/friends` と `/broadcasts/new` へ一時対象者IDだけを渡す
- 友だちIDをURLへ並べない
- 24時間後に対象者明細を削除する
- 配信作成時に人数と基準日時を再確認する

## 10. 権限

| 役割 | 見える | 触れる |
|---|---|---|
| 統括 | 許可された全アカウント、保存結果、レポート | 定義、版、書出し、レポート、横断分析 |
| 管理者 | 自分のLINEアカウント内の全分析 | 定義、版、書出し、レポート |
| 担当者 | 許可されたアカウントの集計 | 閲覧。個人一覧、書出し、配信連携は権限キーで制御 |

個人を特定できる一覧とCSVは、集計閲覧とは別権限にする。権限外のアカウント・結果IDは存在も明かさない。

## 11. 除外するもの

この版から除外する。

- 取得できないLINE開封・クリックを0で表示すること
- LINE Insightsの集計値から個人の開封者を推測すること
- Search ConsoleをGoogle Analyticsと表示すること
- GA4の新規連携
- 中継リンクなしの友だち追加へ、推測した流入元を付けること
- 広告費未取得期間の費用・差し引きを0にすること
- 配信後の解除増加を、その配信が原因だと断定すること
- 過去の解除履歴、タグ解除、URL露出を推測で復元すること
- 同じ期間に条件を満たしただけの人を、順番に進んだと扱うこと
- 判定期間中の人を離脱へ含めること
- 未知の段・参照切れを0人として隠すこと
- 複数アカウントの数字を通常画面で混ぜること
- メッセージ本文、秘密値、URLクエリを分析イベントへ保存すること
- 高種類の自由文をクロス分析の軸にすること

- 保存済みの過去結果を書き換えること

## 15. Lステップとの差

根拠は `docs/lstep-feature-parity-matrix.md`（#19 URLクリック測定、#20 サイトスクリプト、#21 ファネル分析、#24 クロス分析、#25 流入経路分析）と `docs/lstep-gap-analysis.md`（D-1 ブロック率の内訳、G-8 送信数、SD-1 シナリオのステップ別到達人数）。

超える点:

- ファネルを同一期間の集合の絞り込みではなく、発生順と判定期間で数え、判定中と離脱を分け、最大3群を比較する（parity #21）
- クロス分析のますとファネルの段から、同じ対象者を友だち一覧・配信作成へそのまま渡す（parity #24）
- 「使われ方」で未使用・重複・参照切れの設定を横断して見つける
- 保存した分析を定義版と結果スナップショットに分け、定義を編集しても過去結果を変えない
- 経路と成果に広告費、1人追加あたり費用、差し引きを並べ、未取得を0にしない

同等の点:

- URL別のクリック回数・人数・率と、押した人への配信（parity #19）
- サイト行動を友だちへ紐づける計測（parity #20）
- 流入経路ごとのクリック→追加→成果の比較（parity #25）
- 送信数・配信実績の日次集計（gap G-8）

除外:

- GA4の新規連携と、Search ConsoleをGoogle Analyticsと呼ぶこと
- LINE Insightsの集計値から個人の開封者を推測すること
- 取得できない開封・クリック・広告費を0で表示すること
- 自由入力文・個人名・URL全文をクロス分析の軸にすること
