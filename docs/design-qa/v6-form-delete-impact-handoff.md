# `gBp2J` 回答フォーム削除確認：画面実装への引き継ぎ

## 正本と範囲

- Node: `gBp2J`
- ルート: `/form-submissions`
- 固定base: PR #581 の画面実装
- この契約PRは、削除前の影響確認・保管・版競合だけを提供する。
- 画面は `apps/web` だけで実装し、Worker・DB・migrationを複製しない。

## 読む口

`GET /api/forms/:id/delete-impact?account_id=:accountId`

返るものは、フォーム名、公開中か、回答数、開かれた記録、利用先、回答URL、`revision`、
`delete` / `archive` の推奨です。**取得失敗を0件として描かないでください。**
読み込み中・取得成功0件・取得失敗を別の状態にします。

利用先の名前を引けない参照も `state: unavailable` で残ります。行を落とさず、
「名前を確認できない利用先」として削除を止めてください。内部IDは出しません。

## 実行する口

- 物理削除: `DELETE /api/forms/:id?account_id=:accountId&expected_revision=:revision`
- 保管: `POST /api/forms/:id/archive?account_id=:accountId`
  - body: `{ "expectedRevision": revision }`

物理削除できるのは、非公開・回答0・開かれた記録0・利用先0・確認時と同じ版だけです。
それ以外は回答と利用先を残し、公開を止めて通常一覧から外す「保管」です。

## 409の扱い

409の `data` には最新の削除影響が入ります。窓を閉じずにその値へ差し替え、
「別の変更がありました。最新の影響を確認してください。」と出してください。
古い「削除できます」を残してはいけません。

非同期の返事は `accountId + formId + requestGeneration` の3つで照合します。
アカウント切替時は、対象・影響・エラー・busyをすべて消します。遅れて返った
別フォームの影響や、前のアカウントの削除窓を出してはいけません。

## 画面の受入条件

1. 押し口に `data-qa-open="gBp2J"`、窓に `data-design-node="gBp2J"` を付ける。
2. 取得前は実行ボタンを出さない。失敗時もボタンを出さず再読込だけを出す。
3. 本文に「何が消える・何が残る・元に戻せない」を明記する。
4. 回答数、開かれた記録、利用先名と導線、回答URLが使えなくなることを読み合わせる。
5. 影響がすべて0件なら物理削除、1件以上または公開中なら保管を出し分ける。
6. 実行中は二重押しと窓を閉じる操作を止める。
7. 409は最新の影響へ更新する。403/404/409/503を内部語なしで言い分ける。
8. 1440px・1920pxでページと窓の横スクロールを0にする。

## 撮影用の固定データ

`scripts/visual-qa/fixtures.mjs` の `FORM_DELETE_IMPACT_FIXTURES` を使います。

- `archive`: 回答128件・開かれた記録214件・利用先2件・公開中
- `delete`: 回答0件・開かれた記録0件・利用先0件・非公開
- `failure`: 503。ブラウザ側の `route.fulfill` へ status/bodyをそのまま渡す

通常・取得成功0件・取得失敗・409更新・実行中を両幅で撮ってください。

## 必須の契約テスト

- 影響取得前・失敗時に削除/保管ボタンが無い
- 未取得を0件と表示しない
- `expectedRevision` を必ず送る
- 409で最新影響へ置き換わる
- アカウント/対象切替と遅延応答で古い窓が残らない
- API失敗でも窓を閉じず、成功表示へ進まない
