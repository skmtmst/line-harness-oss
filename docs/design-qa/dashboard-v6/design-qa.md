# ダッシュボードV6 画像比較（機能1）

**結論：5枚とも構造一致。うち4枚はデータ未接続。**

## 判定の言葉

| 判定 | 意味 |
|---|---|
| **構造一致** | 配置・部品・文言が設計と合う |
| **データ未接続** | 出どころが無く値が `—`。**これを最終的な「一致」にはしない** |
| **一致** | 実データまで繋いで設計と比べ、差が無い |

`—` のまま「一致」にすると、実装漏れが台帳から消えます。

## 撮り方

| | 出どころ |
|---|---|
| 設計 | Pencil の実ノードを `html-css` で書き出し、Chromium で実寸描画（幅1920） |
| 実装 | 実ルート `/` を操作して 1440・1920 で撮影 |

**撮り方は `scripts/visual-qa/screens.mjs` にデータで書いてあります。**
機能ごとに使い捨てのスクリプトを書くと、262枚ぶんで必ず撮り方がずれ、
**ずれた絵どうしを比べて「差がある」と言ってしまいます。**

```
node scripts/visual-qa/capture-screens.mjs --check
node scripts/visual-qa/capture-screens.mjs --feature 1 --impl
node scripts/visual-qa/capture-screens.mjs --feature 1 --design --from <書き出したhtmlの置き場>
```

この5枚は、使い捨てスクリプトで撮ったものと**画素がまったく同じ**に
なることを確かめてから、仕組み側の絵に置き換えてあります。

**時計を止めて撮っています。** 「6日前」は `Date.now()` から出るので
（`pending-inbox-card.tsx` の `elapsed()`）、止めないと**日をまたぐたびに
絵が変わり**、基準画像として使えません。`2026-08-19T12:00:00Z` に固定し、
固定データの受信日時をその6日前・4日前に置いてあります。

## 直したもの

設計に合わせて画面を組み直しました。**裏の接続は追っていません。**
出どころの無い数字は `—` のままにしてあります。決め打ちで数を書くと、
本物らしく見えるぶん、無い数より悪いためです。

### `NjK9q` 表示件数の切り替えを足した

`PAGE_SIZE = 5` が固定で、選ぶ場所がありませんでした。総数5件でも2行を
出して終わりで、**残り3件へ行く手段がありませんでした。**

- 表の右上に「表示件数」（5 / 10 / 15 / 20件表示）
- 下に「1〜2 / 5件」と番号のページ送り
- ページ送りは**共通部品**（`components/shared/pagination.tsx`、Pencil `Blot6` が正本）へ寄せた。自前の「前へ／次へ」は消した

### `Alekb` 通知ベルをダッシュボードへ繋いだ

部品（`components/shared/notification-panel.tsx`）は前からあったのに、
呼んでいるのは検証用ルートとテストだけでした。期間の右にベルを置き、
押すとパネルが開きます。

**中身を出す口はまだありません。** バッジに数を作って出さず、件数は0、
一覧は「通知はありません」のままです。→ **データ未接続**

### `vUXKb` 右カラムを設計の構成にした

| したこと | 中身 |
|---|---|
| 「現在の対応マーク」を足した | 未対応・対応済みは `inbox` から出る。**自動変更は口が無いので `—`** |
| 「友だちの状態」を設計の形にした | 友だち総数／有効／ブロック・非表示（率）の3行＋内訳。総数と内訳が無いと、223人が誰に止められたのか読めない |
| 送信枠の帯の重複を外した | 「今月の配信」にも同じ帯が出ていた。**同じ数を2回**描いていた |
| 運用アラートを設計の2行にした | 「最も古い未対応：9,110分前」と「二段階認証：`—`」 |
| 文言 | 月初リセット→**毎月1日リセット**、予定されている予約→**配信・予約** |

`/api/accounts/:id/health` が `riskLevel: 'ok'` を返していたのも直しました。
画面の型は `'normal' | 'warning' | 'danger'` で、`'ok'` はどれにも当たらず
「状態確認中」のままでした。**実装の差に見えていましたが、こちらの返事が
違っただけです。**

## `ZN0ov` ダッシュボード編集の差

### パネルが全高でない

設計は画面の上端から下端までの縦長パネルで、**カード20枚が1画面に並びます**。
実装は高さが1010pxほどで途中で切れ、「接続状態」から下が見えません。
設計にある 友だちの状態／今後の予定／今月の配信／最近の成果／予約状況／
流入経路TOP3／ファネル要注意／オートメーション失敗 に、そのままでは届きません。

### 「4枠まで」の注意が一行に縮んでいる

設計は黄色い箱で書いてあります。

> 「今日やること」は4枠までです
> 5つ目をONにすると、いちばん下のカードが自動でOFFになります。順番を入れ替えて、先に出したい4つを上に置いてください。

実装は見出しの右に「最大4枚まで・ドラッグで順番変更」の一行だけです。
**ONにしたときに何が起きるかが読めません。**

### 行の副文が「位置」から「中身」に変わっている

| | 設計 | 実装 |
|---|---|---|
| 対応が必要な受信 | 上部・小カード | LINE・メールの未対応 |
| 出荷予定 | メイン・横長 | メイン｜横幅いっぱい |
| 友だち追加リンク | メイン・左カラム | 追加URL・QRコード |

設計は**どこに置かれるか**を書いています。並べ替える画面なので、位置が読めないと
動かした結果が予想できません。

### そのほか

| 場所 | 設計 | 実装 |
|---|---|---|
| 見出しの下 | 表示するカードと位置を変更します | （無い） |
| 「初期状態に戻す」 | タブと同じ行の右端 | タブの上に単独で左寄せ |
| タブの形 | 塗りつぶしの札（緑） | 下線タブ |
| 保存ボタン | ダッシュボードに反映 | 変更を適用 |
| パネル幅 | 約540px | 約440px |

## `JN6mQ` 友だち追加QRの差

### QR画像が出ない（取得不能）

実装の絵では、QRの場所に壊れた画像の枠と alt（友だち追加QRコード）が出ます。
**こちらの固定データがQR画像を返していないため**で、実装の差とは言い切れません。
画像を返せるようにしてから撮り直します。

### 形式タブの並びと見出し

| | 設計 | 実装 |
|---|---|---|
| 見出し | ダウンロード形式 | 形式 |
| 並び | PNG / JPG / SVG | PNG / **SVG / JPG** |

### ボタン

| | 設計 | 実装 |
|---|---|---|
| 主ボタン | ⬇ 画像をダウンロード（緑・アイコン付き） | PNGをダウンロード（白・アイコン無し） |
| 印刷 | 🖨 PDFで印刷（アイコン付き） | PDFで印刷（アイコン無し） |

主ボタンが白いので、**この画面でいちばんやりたいことが目立ちません。**

### そのほか

- QRの下：設計は「然-NEN- 公式」＋リンク `https://lin.ee/nen-official`。実装は名前だけで**リンクが無い**
- 「使うときのヒント」：設計は ⓘ 付きの**枠付きの箱**。実装は区切り線の下にベタ書き
- リンク欄：設計は枠の中で2行に折り返し、コピーは文字のリンク。実装は1行で省略され、コピーは緑のボタン

## 決まった方針（2026-08-27）

| | 決めたこと |
|---|---|
| ページ送り | **共通仕様の「前へ・番号・次へ」を維持**。設計 `NjK9q` は `‹ 1 2 ›` の矢印だが、`byqIW` など他の設計は「前へ…次へ」で、設計内に2種類ある。共通部品（Pencil `Blot6`）に寄せる |
| Select の選択印 | **V6 `Gfsb4` に合わせて右端のチェックへ移した**。左の四角い枠は「複数選べる」ように見え、1つだけ選ぶプルダウンと読み違える |

Select は共通部品なので、開いた状態を撮っている画面すべてに効きます。
基準画像を撮り直し、単体テスト650件・画像比較44件が通ることを確かめました。

## 設計そのものの食い違い（2件目）

`NjK9q` は「5件表示」でページ送りが **1・2 の2ページ**出ていますが、
総数は5件です。5件表示なら1ページに収まります。**設計側の直しが要ります。**

## 判定を保留にした3点（こちらの固定データが薄いだけかもしれない）

`/api/accounts/:id/health` を `{ riskLevel: 'ok', logs: [] }` としか返して
いないため、次の3つは実装の差か固定データ不足かを**まだ切り分けられません**。
切り分けてから判定します。**いまは「実装が違う」とは書きません。**

| 場所 | 設計 | いまの実装 |
|---|---|---|
| 状態の札 | 正常稼働 | 状態確認中 |
| LINE Webhook | 3 / 3 正常 | 確認中 |
| 自動処理 | 稼働中 | 要確認 |

## 設計そのものの食い違い（1件）

`vUXKb` の中で数が合いません。

- 「接続状態」の**有効友だち 4人**
- 「友だちの状態」の**有効 398人**

同じ `friends.active` から出る値なので、両方は描けません。ここでは398で
返しています。**設計側の直しが要ります。**

## 固定データについて

全部0で返していたあいだ、ダッシュボードは空の絵しか描けませんでした。
受信の表もページ送りも送信枠の帯も出ないので、**設計と並べても「差が無い」
とは言えません**（そもそも比べる中身がない）。設計の絵に書いてある値を
`mock-api.mjs` に入れてから撮っています。

途中で1つ落とし穴がありました。`/api/support/inbox` を
`{ items, total }` の形で返したところ、画面が読むのは `{ items, summary }`
だったため、**行が1つも描かれないのにページ送りだけ出る**という、実際には
起きない絵になりました。型に照らして直してあります。

final result: **構造一致（データ未接続あり）** — 5枚とも設計の構成にそろえた。`—` の4枚は、口ができたら「一致」へ上げる
