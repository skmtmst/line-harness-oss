**設計は「流入リンクごとに初回案内を並べる一覧」**です。店頭QR・広告・紹介の
それぞれに別の初回案内を置き、優先順位で当てます。

①はじめて追加した人 と ②以前からの友だち・ブロック解除した人 の2つに
分けるだけで、**流入リンクで出し分ける仕組みがそもそもありません。**

画面にもそう書いてあります（`page.tsx:712`）：
「流入元の記録は友だち追加のたびに必ず走るので、ここでは選びません。」

つまり設計の A〜C・F・G・I は「作り込みが足りない」のではなく、
**別の形の機能**です。1枚ずつ突き合わせても意味が薄いので、そう記録します。

## 実装にしか無いもの（設計に描かれていない）

**「どう振り分けられるか」の流れ図**が右側にあります。友だち追加 →
ブロックされたことがある？ → はじめて／以前から、と分岐を絵で見せます。
設計にはありません。**設定の効き方が読める**ので、消すべきものではないと考えます。

**注意の帯**も実装だけです。「この2つを分けないと、以前からのお客さまに
『はじめまして』の挨拶が届きます」。設計は同じ文言を一覧の小さな説明として
持っており、**言いたいことは同じ**です。

## 受け口はあるのに画面が読んでいない（`P2J0Te`）

`/api/friend-add-routing/events` は**友だち追加の履歴を返せます**
（誰が・どの経路から・実行できたか）。型（`FriendAddEventList`）まであります。
ところが画面は一度も呼んでいません（`grep 履歴|events` が0件）。

設計の「最近の友だち追加」は、まさにこの返事で描けます。
**足りていないのは画面だけ**です。

## 気になった書き方2つ

**`friends.unfollow_count を見る`** が流れ図に出ています。データベースの列名です。
運用の人がこれを読んで何をすればいいのかは決められません。
機能8の `line_account_id` `silent rule` と同じ種類の書き方です。

**タグが見つからないと「タグ「?」を付ける」** と出ます（`page.tsx:627`）。
同じ関数のすぐ下では、読めない形に「設定を確認してください」と出しています。
消したタグを指しているときも、そちらの言い方のほうが揃います。

どちらも実装側の決めごとなので、ここでは記録だけにします。

## 固定データで1回しくじりました

タグを足すアクションを `config: { tagId: 'tag-0' }` と書いて、札が
**「タグ「?」を付ける」**になりました。画面は `c.tagIds`（配列）を読みます
（`page.tsx:633`）。

**実装の不具合に見えました。実際はこちらの書き方が違うだけ**です。
`tagIds` と `op: 'add'` に直して、札に「タグ「EC顧客連携済み」を付ける」と
出ることを確かめました。

同じ理由で `configured: true` も返すようにしました。返さないと画面は
「まだ決めていない」の注意帯を出し続け、**設定してあるのに未設定の絵**で
撮れてしまいます。
