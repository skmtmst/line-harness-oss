# 下書きPR 43本の仕分け（撮影側 → Codex）

「20ファイル以下で競合していない30本前後を撮影側が取り込む」という見立てで
始めたが、**実際に取り込めたのは1本だけ**だった。理由を先に書く。

## 見立てが外れた3つの理由

**① 触るファイルだけ見ても、依存は見えない。**
`#640` `#639` `#641` はどれも `apps/web` しか触らないが、
**まだ存在しない API を前提にしている**。

| PR | 前提にしている口 | いまの木 |
|---|---|---|
| `#640` | `InboxStats.assigneeUnread` | 型にも worker にも無い |
| `#639` | `api.supportMarks.automationRules` ほか4口 | 4口とも無い |
| `#641` | `WebinarOverview` 型 | 無い |

API契約の追加は指示書の変更禁止に当たるので、撮影側では入れられない。

**② 束の中の1本は、前の本に依存する。**
`#644`（LINEプレビュー）は7ファイルすべて `apps/web` だが、
`edit-steps.ts` と `webinar-notifications.tsx` を import している。
どちらも束の前2本（`#623` `#641`）が作るファイルで、いまの木には無い。

**③ 「競合なし」は古い base に対する判定。**
`#641` の枝は **8月28日**の `codex/development` から分かれている。
いまは9月3日で6日進んでおり、当てると `webinars/page.tsx` が競合する。
GitHub の `mergeable` は枝の base に対する値なので、そのままでは使えない。

## 束をどう降ろすか

**束は先頭を1本見れば中身が全部見える。** 例えば一斉配信の7本は、
先頭 `kenta-v6-feature6-design-gaps` に7本ぶん（30ファイル・1330行）が載っている。
1本ずつ降ろすより、束ごと見て束ごと降ろすほうが速い。

ただし**どの束も、いまの `codex/development` に対しては競合する**。
枝が古いので、降ろす前に載せ替えが要る。

## 撮影側からの申し送り

第2ラウンドで機能ごとに設計と突き合わせているので、**同じ画面を2人で触ると
ぶつかる**。束を降ろすときは機能名を先に言ってもらえれば、その機能の
判定を後回しにする。
