**他のどれよりも先に入れてほしい。**

いま `required-pr-gate` は base が `codex/development` か `main` の PR にしか
掛かっていない。積み上げPRには一度も掛かっていないので、
**#1 / #46 / #57 はチェックが1件も付いていない**。

先にこれを入れておけば、以降のPRは全部検査された状態で見られる。

**入れたあとに起きること**: 開いている全PRで gate が回り始める。
一時的にCIの実行数が増える。落ちるものがあれば、
そこは元から検査されていなかったところなので、拾えたということ。

**注意**: `pull_request` の workflow は base と head を合わせたもので走る。
つまり #59 が `codex/development` に入っても、
base が作業ブランチのままの積み上げPR（#45〜#58）では
すぐには回らない。それらは下から順にマージされて
`codex/development` に届く時点で検査される。

## マイグレーションについて

v0.24.0 までで **088〜104 の17件**が入る。
**まだどのデータベースにも当てていない。**

適用は、PRのマージとは別の作業として扱う。
実際に当てる直前に、次の4点を改めて共有する。

1. **対象** — どのデータベースに当てるか（本番／検証）
2. **影響** — どのテーブルがどう変わるか、既存データがどうなるか
3. **バックアップ** — 何をどこに退避してから当てるか
4. **切り戻し** — 失敗したときにどう戻すか

追加のみのポリシー（`CONTRIBUTING.md §Migration Policy`）に沿っているので、
列とテーブルが増えるだけで、既存の列は消えない。
`scripts/check-migrations.ts` が毎回それを確かめている。

ただし1件だけデータを書き換えるものがある。

```sql
-- 104_scenario_concurrency_default.sql
UPDATE scenarios SET allow_concurrent = 1 WHERE allow_concurrent = 0;
```

これは新しい列の既定値（0）が、既存のシナリオの挙動を変えてしまうのを
防ぐためのもの。詳しくは `docs/v024-decisions.md §5`。
