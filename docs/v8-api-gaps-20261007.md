# V8で不足していたAPIの契約（2026-10-07）

対象枝：`codex/kenta-v8-api-gaps`。管理画面の見た目は変更していません。
すべて既存の認証・アカウント閲覧範囲を使います。成功は `{ success: true, data: ... }` です。
画面で使う型は `packages/shared/src/types.ts`、呼び出す関数は `apps/web/src/lib/api.ts` にあります。

## 友だちの進行中の配信・処理

`GET /api/friends/:id/upcoming`。追加の入力はありません。最大20行を返します。
`api.friends.upcoming(id)` で呼びます。

既存の `nextBooking`・`nextBookingError`・`nextAutoDelivery`・`nextAutoDeliveryError` はそのまま残し、次を追加しました。

```ts
items: Array<{
  kind: 'scenario' | 'reminder' | 'broadcast' | 'automation'
  id: string
  name: string
  scheduledAt: string | null
  sentCount: number | null
  totalCount: number | null
  href: string
  audienceEvaluatedAt?: string
}>
itemsError: boolean
```

- シナリオの `id` は友だちの登録IDです。全体の数は登録時の公開版を使い、送った数は実際の送信記録にある工程を重複せず数えます。同じ工程から複数メッセージが出ても1工程です。
- リマインダの `id` は友だちの登録IDです。登録ごとに1行にまとめ、成功した配信の数と登録時の版の全体数を返します。再試行待ちでは次の再試行日時を返します。
- シナリオは `active`・`delivering`、リマインダは `active` が対象です。次回日時がまだ確定していない登録も返し、日時は `null` です。
- 一斉配信は `scheduled` で停止されていないものが対象です。現在の全員・タグ・絞り込み・複数アカウントの重複除外を、既存の対象判定で確かめます。無効なLINEアカウントには出しません。送信時には対象が再判定されるので、判定日時 `audienceEvaluatedAt` を付けます。進捗は `0 / 1` です。
- 自動化は友だちの本実行の `queued`・`running`・`waiting` です。`id` は実行ID、日時は `resume_at`（未確定なら `null`）です。送信数と処理の工程数は同じ意味ではないため、数は両方 `null` にします。
- 各行の `href` は既存の詳細画面・実行詳細を開く住所です。日時の早い順で、未確定は最後です。
- 新しい一覧の取得に失敗した場合は `items: []`・`itemsError: true`。従来の最寄り予約・最寄り配信は独立して読みます。

migration はありません。

## 友だちの90日集計

`GET /api/friends/:id/summary`。追加の入力はありません。
`api.friends.summary(id)` で呼びます。

```ts
{
  periodDays: 90
  from: string
  to: string
  deliveryOpenRate90Days: number | null
  deliveryOpenMeasuredCount90Days: number
  purchases90Days: {
    count: number
    totalAmountMinor: number | null
    currency: string | null
    byCurrency: Array<{
      currency: string
      count: number
      totalAmountMinor: number | null
    }>
  } | null
}
```

- 集計期間は実行時刻から90日前までです。両端を含み、未来の購入は入りません。
- **個人ごとの開封記録は現在ありません。** LINEの配信全体の開封集計を個人に割り振らず、`deliveryOpenMeasuredCount90Days: 0`・`deliveryOpenRate90Days: null` を返します。リンクを押した記録も開封とは扱いません。個人計測の新設は今回の範囲に含めていません。
- EC連携の登録がないと購入は `null`。連携済みで購入がなければ件数・金額とも0です。
- 選択中アカウント・本人の注文台帳を使い、取消・全額返金の注文は除きます。返金済みの状態でも、元の金額と返金額から部分返金だと確認できる注文は購入に残して返金額を引きます。返金済みなのに返金額が不明な注文は除きます。
- 金額は通貨の最小単位（JPYなら円）です。複数通貨は合算せず `totalAmountMinor`・`currency` を `null` にし、`byCurrency` を使います。金額が不明な注文があれば、その通貨の金額は `null` です。

既存の友だち詳細の返り値は変更していません。migration はありません。

## ダッシュボードの最近の動き

`GET /api/dashboard/activity?account_id=<アカウントID>&limit=10`。
`account_id` は必須（`accountId` も既存仕様に合わせて受け付けます）。`limit` は省略時10、1〜100の整数です。
`api.dashboard.activity(accountId, limit?)` で呼びます。

```ts
{
  items: Array<{
    id: string
    kind: 'broadcast_sent' | 'booking_created' | 'event_booking_created'
      | 'form_submitted' | 'friend_added'
    summary: string
    occurredAt: string
    href: string
  }>
}
```

通知センターではなく、実際の配信・予約・回答・友だち追加の記録から、起きた日時の新しい順で返します。
予約の時刻ではなく、予約が入った日時を使います。取消済みになった予約も、受付が起きた記録として残ります。
フォームの試し回答は除きます。所属が確定できない匿名の回答は、複数アカウントへ重ねて出しません。
複数アカウント配信は対象アカウントに出します。友だちの名前や回答本文は、ひとことに含めません。
不正な件数・アカウント未指定は400、閲覧できないアカウントは404です。

migration はありません。

## 送り先の版の確認

`PUT /api/webhooks/outgoing/:id?lineAccountId=<アカウントID>`。
既存の変更項目に `expectedVersion?: number`（1以上の整数）を追加しました。
`api.webhooks.outgoing.update(id, lineAccountId, { ...変更項目, expectedVersion })` で呼びます。

一覧・詳細・更新の成功応答には次を含めます。既存の項目も残します。

```ts
version: number
updatedBy: string | null // 担当者のID
updatedAt: string
```

違う版ではDBを書き換えず、409を返します。

```ts
{
  success: false
  code: 'VERSION_CONFLICT'
  error: string
  data: {
    currentVersion: number
    updatedBy: string | null
    updatedAt: string
  }
}
```

`ApiError.code` と `ApiError.data` から読めます。データの型は `OutgoingWebhookVersionConflict` です。
画面で読む版の照合と、DB更新の条件の両方で競合を防ぎます。
省略時はこれまでどおり保存できますが、変更のたびに版は進みます。
自動停止・削除・復元でも版が進みます。担当記録のない旧行・自動変更の担当は `null` です。
通信結果の件数だけを更新した場合は編集の版を進めません。

migration は **586 `586_outgoing_webhook_version.sql`** の草稿です。

## フォーム回答の済んだ工程

既存の `GET /api/forms/:id/submissions?account_id=...` と再実行の応答で、`postActions` に `completed` を追加しました。
既存の `state`・`pending` は残します。

```ts
postActions: {
  state: 'completed' | 'failed' | 'in_progress' | 'untracked'
  pending: string[]
  completed: Array<{ step: string; completedAt: string | null }>
} | null
```

一覧の呼び出しは `api.forms.submissions(formId, accountId, { page?, limit?, query? })`。
成功は `data: { items, total, page, limit, summary }` です。既存のページなしの配列応答も残ります。

回答1件を読み直す口も追加しました。
`GET /api/forms/:id/submissions/:submissionId?account_id=...`。
`api.forms.submission(formId, submissionId, accountId)` で呼びます。
成功は既存の回答行と同じ `data: { id, formId, formVersionId, friendId, friendName, data, destinationWrite, postActions, createdAt }` です。
回答の存在・フォームとの一致・閲覧アカウントを確認します。試し回答は404です。

新しい完了は工程名と日時を同じDB更新で記録し、再実行しても最初の日時を変えません。
記録された工程だけを済みとして返します。過去の工程には日時がないため `completedAt: null` です。工程記録もない回答は `untracked`・`completed: []` です。

migration は **587 `587_form_step_completion_times.sql`** の草稿です。
