## 公開中のSHA確認（deploy-staging.sh の末尾への追記案）

`deploy-cloudflare-staging.yml` はビルド元の完全なSHAをWorkerの公開変数と管理画面のビルドへ渡す。
設定の再配備では本線のSHAに置き換えず、各作業ツリーの元SHAを使う。
Workerは `/admin/version` と `/health`・`/api/health`、管理画面は静的な `/version.json` で返す。
返す情報はSHA・版・日時（Workerの既存の公開ハッシュ等も維持）だけ。秘密値は返さない。
配備workflowの最終確認も公開口を読み、一致を確かめてからロックを解放する。

手元の `~/lh-work/tools/hq/deploy-staging.sh` はこの依頼では変更していない。
司令塔は通常の `target=all` 配備runが成功した後、`.last-staging-deploy` への記録の前に次を入れる。
`qa_repo` はこの変更を統合済みのクリーンな本線の作業ツリーを指定する。
`sha` と `id` はその配備で固定したSHAとrun IDであり、「最新のrun」を推測して使わない。

```sh
run_sha=$(gh run view "$id" -R "$R" --json headSha -q .headSha)
current_sha=$(gh api "repos/$R/commits/codex/development" -q .sha)
if [ "$s" = "completed success" ] && [ "$run_sha" = "$sha" ] && [ "$current_sha" = "$sha" ] &&
  node "$qa_repo/scripts/deploy/verify-public-build.mjs" \
    https://stg-api.musubo.jp "$sha" https://stg-admin.musubo.jp "$sha"; then
  echo "$sha" > "$LAST"
else
  # 成功済みSHAとして記録しない。次の配備を繰り返す前に理由を司令塔へ渡す。
  echo "公開SHA確認失敗、または配備中に本線が更新されました" >&2
  exit 1
fi
```

照合はログイン無しのGETのみ。unknown・短縮SHA・不一致・HTTP失敗・異常なhealthを失敗にする。
CDN反映待ちのため最大15回読み直すが、再配備はしない。
独立配備なら対象外を `- -` にする。設定再配備なら各元SHAを指定する。
元コードに公開口が無い古い版は確認できないため、成功にしない。

## SELECTのみの未適用確認（d1.sh への追記案）

`migrate-d1.yml` の `operation=migrate, mode=dry-run` は、
`scripts/deploy/d1-pending-readonly.mjs` を呼び、台帳の有無と適用済みファイル名をSELECTだけで読む。
台帳が無い場合は全ファイルを未適用と数え、表は作らない。
認証・通信・JSON・台帳応答の失敗は「不明」として終了し、0件にはしない。
出力は `COUNT: N` とサマリーの未適用ファイル一覧。DDLはバックアップ後のapply分岐だけに移した。

`~/lh-work/tools/hq/d1.sh` のdry-run呼び出しは、統合後の本線を明示して次に置き換える。
既存のapply分岐は承認済みの個別ファイルに限る運用を維持する。

```sh
gh workflow run migrate-d1.yml -R "$R" --ref codex/development \
  -f operation=migrate -f environment=staging -f mode=dry-run
```

この `--ref` は必須。省略すると既定枝の旧workflowを実行する可能性がある。
dry-run後は起動したrun IDの成功と `COUNT:` を読む。起動前からある別runや件数不明は通さない。
統合前の旧dry-runは読み取り専用として使わない。この作業ではworkflowを起動していない。
