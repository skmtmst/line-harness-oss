記録日時：2026-10-09 20:19 JST。依頼書は変更していない。

## 原因と直した所

### 予約管理：偽 API の形が違っていた

画面は `/api/booking/admin/availability?menu_ids=...` の一括取得で `by_menu` を読む。Workerも `by_menu` を返す。一方、偽 API はHTTP 200で単件の `by_staff` を返していた。`batch.by_menu` を反復できず、画面が「空き枠を読み込めませんでした」となり、速度検査が `error` で止まった。

同じ要求、同じowner（readOnly=false）で、修正前は `by_staff, closed_dates`、修正後は6メニューの `by_menu` を確認した。修正後の画面では読み込みエラーが消えた。権限不足や本物の予約APIの故障ではなく、偽 API の応答の問題だった。画面は変更していない。

`mock-api.mjs` を一括・単件で器を分けるようにし、9月・10月・店舗ルールの固定データを保った。Workerと同じ空白・重複の整理も行った。実HTTPの回帰試験を追加し、修正前3条件で失敗、修正後合格を確認した。

### 負荷測定：通信差し替えのCORS

予約の修正後、2,000行の差し替え応答が `Access-Control-Allow-Origin: *` を付けており、画面の `credentials: include` に対してブラウザが拒否した。差し替え側では2,000行を作れていても、画面には届かなかった。

`speed-budget.mjs` の差し替え応答を要求元のOriginと `Access-Control-Allow-Credentials: true` に直した。単体試験と実ブラウザで修正前の拒否・修正後の2,000行受信を確認した。通常のscripts試験にChromiumのインストールを要求しないよう、実ブラウザの試験は `speed-cors.browser.mjs` として分けた。

CORSを直した後は、実画面の2,000行条件で標準の20秒＋再読み込み20秒が時間切れになった。WebとAPIはHTTP 200（ともに1ms未満）で応答していた。補助的に90秒まで待っても正常な描画の測定に至らず、その試行を止めた。画面の性能変更は依頼対象外なので行っていない。時間切れを0や合格に置き換えていない。

## v7配信本文の画素差

監査と同じbase `2b0460c94a8220e287ba3d6d9ff66208e0ec6e4e` とhead `f69c833ac76c16e34cb96f67825405a0e83058fe` を別の一時スナップショットでビルドし、同じ偽API・v7・固定時計・1152/1440で配信本文だけを撮った。

| 幅 | CIの差 | 手元の差 | 差の範囲 | CSS順序だけを揃えた診断 |
| --- | ---: | ---: | --- | ---: |
| 1152 | 34,046画素 | 32,313画素 | 149,324〜1002,667 | 0画素 |
| 1440 | 30,442画素 | 29,145画素 | 319,278〜996,621 | 0画素 |

原因はV8で増えた共通部品のCSSの配信順。baseはCard→MessageComposer、headはMessageComposer→Cardになり、同じ優先度のCardの1px枠と影が勝つ。本文が1px、後続の操作が2pxずれる。例えば1440の本文は `(320,332,幅676)` → `(321,333,幅674)`。

診断のためブラウザ内でMessageComposerの既存の `border:0; box-shadow:none` を後から適用すると、両幅とも差が0画素になった。共通部品のCSS順序による差と確認できた。製品のv7/V8画面・部品・CSSは修正していない。
