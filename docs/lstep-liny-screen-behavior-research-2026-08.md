# Lステップ・Liny 画面／裏側挙動の再調査と実装仕様

- 調査基準日: 2026-08-22
- 対象: Lステップ、Liny、LINE Harness 管理画面
- 想定利用者: 中小企業のLINE運用担当者、問い合わせ担当者、管理者
- 目的: 競合の画面を似せるのではなく、各画面で起きる裏側の処理まで再現可能な仕様へ落とす
- この文書は `lstep-gap-analysis.md`、`lstep-behavior-research.md`、`lstep-scenario-research.md`、`lstep-reminder-research.md` を更新する横断版。過去資料を消さず、2026-08-22時点の判断はこちらを優先する

## 1. 結論

LINE Harness は、主要機能の「画面があるか」という段階から、配信・シナリオ・自動応答・リマインダ・フォーム・リッチメニューの主要処理を実装する段階まで進んでいる。一方、LステップやLinyの本当の強さは機能数ではなく、次の一本線にある。

```text
友だちの行動
  → 条件を評価
  → 複数アクションを決めた順に実行
  → 友だち情報と配信状態を更新
  → メッセージを安全に送る
  → 結果を計測
  → 次の配信・接客へ再利用
```

Harnessで優先すべきなのは、個別画面を増やすことではない。全画面で同じ「条件」「アクション」「メッセージ」「スケジュール」「計測」「権限」を使い、設定のつながりを画面上で確認できるようにすることである。

競合から取り込むべき重点は次の3点。

1. **Lステップ型の実行エンジン**: さまざまな画面から同じアクションを呼び出し、上から順に実行する
2. **Liny型の組織運用**: 問い合わせ担当者向けの簡易画面、友だち・機能・フォルダ単位の権限制御
3. **Harness独自の分かりやすさ**: 依存関係、送信前の対象人数、実行順、失敗、結果を同じ流れの中で見せる

## 2. 証拠の読み方

| 記号 | 意味 | この文書での扱い |
|---|---|---|
| `A` | 実アカウントで画面を確認済み | 画面構造の根拠にできる |
| `B` | 公式サイト・公式ブログ・公式マニュアルで確認 | 機能と公開仕様の根拠にできる |
| `C` | Harnessのコード、マイグレーション、テスト、更新履歴で確認 | 現行実装の根拠にできる |
| `I` | 公開情報からの実装上の推定 | 競合仕様として断定しない |
| `U` | 未確認 | 実装前に検証する |

### 証拠の範囲

- Lステップは、過去調査でスタートプランの実アカウント32ページを参照している。ただし状態を変える作成・保存・送信・削除は行っていない。`A`
- Linyは、2026年8月時点の公式機能ページ、公式アップデート、公開されている管理画面画像を参照した。ログイン後の全画面を操作した証拠はない。細かい競合固有動作は `B` または `U` とする。
- LINEプラットフォーム固有の再送、重複、メッセージ種別、リッチメニュー優先順位はLINE Developers公式を根拠とする。`B`
- Harnessは `codex/development` のコードとテスト、`docs/release-log/unreleased.md` を基準にした。画面ルートの存在だけを「完成」とは扱わない。`C`

## 3. 競合の現在地

### 3-1. Lステップ

Lステップは、配信、顧客管理、予約、フォーム、計測を「アクション設定」で横断的につなぐ構造が中心にある。公式説明では、アクション設定はシナリオ、自動応答、テンプレート、予約、フォーム、リマインダ、友だち追加、タグ、URLクリック、コンバージョン、流入経路、リッチメニューなどから呼び出せる。複数アクションは**上から順に実行**される。`B`

確認できる主要機能は、個別トーク、一斉・絞り込み配信、シナリオ、自動応答、テンプレート、リマインダ、リッチメニュー、フォーム、予約、タグ、友だち情報、カスタム検索、クリック・流入・コンバージョン・クロス・ファネル分析、スタッフ、通知、Webhook、APIである。`B`

使いにくさの根は、機能不足ではなく「同じ設定が多くの画面に分散すること」と「初期設定がLINE Developers、LINE公式アカウント、Lステップの複数画面にまたがること」にある。公式自身が初期設定手順と導入後に最初に行う設定を別記事で詳細に説明している。`B`

### 3-2. Liny

Linyも、タグ・友だち情報・フォーム回答・予約・クリック・Web行動を蓄積し、セグメント配信、シナリオ、リッチメニュー、アクション、分析へ再利用する構造を持つ。`B`

Linyで特に強いのは組織利用である。スタッフ権限では友だち情報、個別トーク、配信、統計、コンテンツを制限でき、2026年8月には個別トークの操作権限と、テンプレート・回答フォーム・イベント予約のフォルダ権限が追加された。オペレーター機能は、個別トークと予約を中心に使える簡易画面として説明されている。`B`

2026年の更新では、Webコンバージョン、Meta広告連携、新回答フォーム、前回内容での再予約、実行時点を基準にしたリマインダ開始、配信フォルダ、カルーセルやFlexから予約画面を開く動きが追加・改善されている。`B`

### 3-3. Harness

現行コードには、友だち・トーク、属性、シナリオ、一斉配信、自動応答、テンプレート、リマインダ、友だち追加、フォーム、イベント・カレンダー予約、リッチメニュー、流入経路、分析、スコア、アクション、通知、Webhook、スタッフ、アカウントなどの画面とAPIがある。`C`

2026年8月19日以降の更新履歴とコードでは、次を確認できる。`C`

- シナリオ: 複数トリガー、対象条件、8種のメッセージ、質問、アクション、完了後処理、テスト送信
- 一斉配信: 15項目のAND/OR条件、差し込み、8種のメッセージ、フォルダ、開封計測の選択、配信前確認
- 自動応答: 複数キーワード、曜日・祝日、対象条件、1人1回、複数アクション、一律応答、ヒット数
- リマインダ: 固定日時と経過時間、友だち情報の日付、8種のメッセージ、下書き、編集、テンプレート
- リッチメニュー: 12レイアウト、タップ領域、複数アクション、出し分け、フォルダ、タップ計測
- フォーム: ブロック編集、分岐、入力制限、回答の友だち情報化、回答後アクション、期限・回数・定員、公開回答画面、画像アップロード

したがって、過去の「32機能中32機能をV2でカバー」は**設計上の対応表**としては使えるが、現行の完成判定には使わない。現在は、機能ごとに「画面」「保存」「実行」「失敗処理」「計測」「権限」「視覚確認」の7点を判定する必要がある。

## 4. 全画面に共通する裏側の実装契約

### 4-1. 友だちを中心にしたデータ構造

```text
LINEアカウント
  └─ 友だち
      ├─ タグ
      ├─ 友だち情報欄
      ├─ 対応マーク・担当者・メモ
      ├─ シナリオ／リマインダ購読状態
      ├─ フォーム回答・予約
      ├─ クリック・流入・Webコンバージョン
      ├─ 送受信履歴
      └─ スコア・集計イベント
```

すべてのデータは `account_id` と `friend_id` で分離する。個人情報を含む値は、閲覧権限、変更履歴、エクスポート履歴を残す。

### 4-2. 共通条件エンジン

一斉配信、シナリオ、自動応答、リッチメニュー、保存した検索、分析の条件は同じ形式で保存する。

```json
{
  "all": [
    { "field": "tag", "operator": "contains", "value": "購入済み" },
    { "field": "visible", "operator": "equals", "value": true }
  ],
  "any": [
    { "field": "prefecture", "operator": "equals", "value": "東京都" },
    { "field": "prefecture", "operator": "equals", "value": "神奈川県" }
  ]
}
```

必須仕様:

- `all` はすべて一致、`any` は1つ以上一致。空のグループの意味を固定する
- 保存前に対象人数をプレビューする。確定時に再評価し、予定数との差を表示する
- 条件項目を削除・型変更する前に利用箇所を表示する
- 「現在の値」で評価するのか「イベント発生時の値」で評価するのかを画面に明記する
- 日時はアカウントのタイムゾーンで入力し、内部ではUTCで保存する

### 4-3. 共通アクションエンジン

フォーム回答、ボタンタップ、キーワード、友だち追加、予約、クリック、コンバージョン、手動実行から同じアクション列を呼び出す。

標準アクション:

1. テキスト送信
2. テンプレート送信
3. タグ追加・解除
4. 友だち情報の設定・加算・減算・クリア
5. 対応マーク・表示・担当者の変更
6. シナリオ開始・停止・移動・前のシナリオ再開
7. リマインダ開始・停止
8. リッチメニュー表示・解除
9. 予約操作
10. 内部通知・外部通知
11. スコア加算・減算
12. Webhook・外部API呼び出し

実行契約:

- 画面の並び順どおり上から実行する
- 各行に `continue_on_error` を持たせる。既定は停止
- 1イベントに `event_id`、各実行に `action_run_id` を付ける
- `(event_id, action_position)` を一意にし、Webhook再送や画面再試行で二重実行しない
- 実行前・成功・失敗・スキップを記録し、友だち詳細のタイムラインから追える
- 実行途中で条件を再評価するアクションと、開始時スナップショットを使うアクションを区別する
- 外部送信はトランザクション内で直接行わず、outboxへ積んでからWorkerが処理する

### 4-4. 共通メッセージ作成

テキスト、画像、動画、音声、スタンプ、位置情報、カルーセル、Flex／テンプレートを共通部品で作る。

- 名前、友だち情報、共通情報、配信日、カウントダウンを差し込む
- 保存時と送信直前の両方でLINEの制約を検査する
- 実際の友だちデータを選んだプレビューと、テスト送信を用意する
- URL短縮・クリック計測のON/OFFと、計測名を本文編集と同じ場所で設定する
- 一斉配信、シナリオ、リマインダで同じ本文を再利用しても、元テンプレート更新時に追随するかコピーするかを選ぶ

### 4-5. 配信キュー、重複防止、再試行

LINEはWebhookを再送することがあり、同じイベントが複数回来ること、順番が前後することを公式に明記している。`webhookEventId` で重複を検出し、時系列判断が必要な場合はイベントの `timestamp` を使う。`B`

LINE送信APIの安全な再試行には、最初の送信から同じ `X-Line-Retry-Key` を付ける。5xx・タイムアウトだけ指数バックオフで再試行し、2xx、409、その他4xxは再試行しない。`B`

Harnessの必須状態:

```text
scheduled → queued → sending → accepted
                         ├─ retry_wait → sending
                         ├─ failed_terminal
                         └─ cancelled
```

- `accepted` はLINEが受理した状態であり、友だちへ必ず表示された保証ではない
- ブロック等で届かないケースとAPIエラーを分ける
- キャンセルは未送信分だけに効かせ、すでに受理された送信を戻したように見せない
- 送信対象、本文、差し込み後本文、再試行キー、LINE応答、時刻を監査可能にする。ただし管理画面・Slackへ秘密値や顧客本文を不用意に出さない

### 4-6. 計測イベント

各画面独自の集計ではなく、共通イベントから集計する。

| イベント | 主な発生元 | 最低限の属性 |
|---|---|---|
| `friend_added` / `friend_blocked` | LINE Webhook | friend、流入経路、時刻 |
| `message_received` | LINE Webhook | friend、種別、時刻 |
| `message_accepted` | 送信Worker | 配信、ステップ、友だち、LINE応答 |
| `link_clicked` | 短縮URL | link、friend、message、時刻 |
| `form_submitted` | 公開フォーム | form、friend、回答版、時刻 |
| `booking_created/cancelled` | 予約 | booking、course、staff、時刻 |
| `scenario_started/step_completed/completed` | シナリオ | scenario、step、trigger、時刻 |
| `action_succeeded/failed` | アクション | action、position、source、error |
| `conversion_recorded` | Web・手動・外部API | conversion、source、value、時刻 |

個人単位の既読はMessaging APIから取得できない。LINEの開封・クリック集計は一定人数未満で値が返らない場合があり、push/multicastの独自集計名には月次上限がある。画面では「0」と「取得不能」を分ける。`B`

## 5. 画面別の挙動とHarness実装仕様

### 5-1. ダッシュボード

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 今日の未対応、失敗した配信、予約、送信残枠、友だち推移を確認し、次の操作へ進む |
| 裏側 | 受信、予約、配信キュー、LINE送信枠、接続状態を別々に取得し、取得時刻とエラーを保持する |
| 触りやすくする | 全機能の数字を並べず「今日対応」「止まっている」「結果」の3群に分ける |
| 完了条件 | 数字から対象一覧へ遷移できる。推定値・未取得・0件を区別できる |

### 5-2. 受信箱・個別トーク

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | LINE／メールの会話を探す、担当を割り当てる、返信する、内部メモを残す |
| 裏側 | 会話イベントを時系列化し、担当者別未読、対応状態、返信者、送信状態を保存する |
| 競合から学ぶ点 | Linyのオペレーター機能のように、接客担当へ必要な個別トーク・予約だけを見せる |
| 事故防止 | 手動の1対1 LINE返信には `X-Line-Harness-Source: manual` を付ける。自動配信には付けない |
| 完了条件 | 二重返信防止、送信失敗の再試行、権限外の会話非表示、監査ログが動く |

### 5-3. 友だち一覧・友だち詳細

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 検索、保存済み検索、一括選択、タグ・シナリオ・リマインダ等の一括操作、詳細確認 |
| 裏側 | 一覧条件と一括操作対象をサーバーで再検証する。「表示中の全件選択」は画面表示分だけと混同しない |
| 詳細 | 属性、対応状態、購読、回答、予約、クリック、送受信、アクション実行を同じタイムラインで追う |
| 事故防止 | 一括処理は対象人数、除外人数、実行内容を確認後にジョブ化し、進捗と失敗CSVを出す |
| 完了条件 | 一覧と配信条件の人数が同じ定義で一致する |

### 5-4. タグ・友だち情報・対応マーク・保存した検索

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 顧客分類と入力項目を作り、どこで自動更新されるか設定する |
| 裏側 | タグ付与元、値の更新元、型、権限、最終更新者、利用箇所を記録する |
| Lステップ／Liny | メニュー、フォーム、クリック、配信アクションから自動付与・更新する `A/B` |
| 触りやすくする | 「定義」「自動で変わる条件」「使われている場所」「現在の人数」を1画面で見る |
| 事故防止 | 利用中の項目は即削除せず、参照箇所と影響人数を表示して無効化を先に行う |
| 完了条件 | 作成、手動変更、自動変更、過去分への適用、削除／無効化が別々に試験される |

### 5-5. シナリオ一覧・作成・編集

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 開始条件、対象、配信方式、ステップ、質問、アクション、完了後処理を組む |
| 裏側 | 開始時に購読レコードと次回実行時刻を作り、各ステップ完了後に次回時刻を再計算する |
| Lステップ | 時刻指定と経過時間指定がある。別シナリオへ移動し、終了後に前のシナリオを再開できる `A/B` |
| Harness | 複数トリガー、対象条件、質問、8種メッセージ、完了後の停止・前へ戻る・別へ移動をコードで確認 `C` |
| 触りやすくする | 左に流れ、中央に選択中ステップ、右に対象・日時・届く見た目・次の動きを表示する |
| 事故防止 | 停止中シナリオを開始元から参照した場合、循環移動、同時購読、同時刻の順序を公開前に検査する |
| 完了条件 | 登録時刻が予定時刻後の場合、タイムゾーン、停止・再開、重複開始、完了処理をE2Eで固定する |

### 5-6. 一斉配信

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 宛先、本文、送信日時、計測、配信速度を決める |
| 裏側 | 保存は下書き、予約時に条件を検査、送信直前に対象を再評価し、受信拒否・非表示等を除外してキュー化する |
| 現行 | AND/OR条件、全員配信、差し込み、8種メッセージ、フォルダ、開封計測選択、配信前確認を確認 `C` |
| 触りやすくする | 右側に対象人数、除外理由、送信数見込み、テスト送信、LINE上の見た目を固定表示する |
| 事故防止 | 予約後編集は新しい版を作る。送信開始後は未送信分だけ停止可能にする |
| 完了条件 | 二重送信、途中再開、対象人数変化、月間送信上限、20人未満の計測不可を試験する |

### 5-7. テンプレート・カルーセル・Flex

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | 再利用する本文やカードを作り、ボタンごとの動作を設定する |
| 裏側 | 版を持ち、利用側が参照版を固定するか最新版へ追随するかを保存する |
| Liny | 2026年7月にカルーセル／Flexのアクションからイベント・カレンダー予約を開けるよう更新 `B` |
| 触りやすくする | 編集中のLINEプレビュー、各ボタンの動き、使用箇所、タップ結果を同時表示する |
| 事故防止 | 画像比率、文字数、ボタン数、URL、参照先の停止・削除を保存前に検査する |
| 完了条件 | テンプレート更新が予約済み配信へ与える影響を明示して試験する |

### 5-8. 自動応答

| 項目 | 仕様 |
|---|---|
| 画面で行うこと | キーワードまたは全受信、時間帯、曜日、対象、回数、実行アクションを決める |
| 裏側 | 正規化した受信文を有効ルールへ照合し、優先順位を決め、実行記録を重複なく残す |
| 現行 | 複数キーワード、最低字数、文字種、曜日・祝日、対象、1人1回、複数アクション、一律応答を確認 `C` |
| 未確認 | Lステップで複数ルールが同時一致した場合、最初の1件だけか全件か `U` |
| Harness既定 | 一覧順で評価し、最初の一致1件を実行。変更時は画面上に明記する |

## 6. 触りやすくする具体案

### P0: 設定のつながりを見えるようにする

各設定の上部に、次の共通サマリーを出す。

```text
きっかけ: フォーム「初回アンケート」を送信
対象: 未購入 かつ 関東（現在 1,284人）
実行: 1. タグ付与 → 2. メニュー変更 → 3. シナリオ開始
結果: 成功 1,241 / 失敗 3 / 対象外 40
```

「この設定がどこから呼ばれ、何を呼ぶか」をグラフにして、削除や停止前に影響を示す。

### P0: 作成画面を同じ型にそろえる

一斉配信、シナリオ、自動応答、リマインダ、フォーム、オートメーションは次の順にそろえる。

1. 目的と名前
2. きっかけ
3. 対象
4. 届ける内容／行う動作
5. 送る時刻・順序
6. テスト
7. 公開前確認
8. 結果

### P0: 安全な公開フロー

- `下書き → テスト済み → 予約／公開 → 稼働中 → 停止 → アーカイブ`
- 公開前に、対象人数、除外、送信上限、参照切れ、循環、停止中の参照、権限を検査する
- 稼働中の編集は次版として保存し、いつから切り替わるか表示する

### P1: 役割別ナビゲーション

左メニューに全機能を常時並べない。

| 役割 | 最初に見せるもの |
|---|---|
| 問い合わせ担当 | 受信箱、友だち、予約、自分の未対応 |
| 運用担当 | 配信、シナリオ、フォーム、リッチメニュー、結果 |
| 管理者 | アカウント、権限、接続、監査、送信上限 |

全機能検索と「最近使った」を用意し、メニューを隠して行き止まりを作らない。

### P1: レシピから開始

利用者の目的を先に選ぶ。

- 友だち追加後にアンケートを送る
- 予約の前日と1時間前に知らせる
- キーワードへ営業時間外案内を返す
- 購入済みの人へメニューを切り替える
- クリックした人だけへ後日送る

選ぶと必要なタグ、フォーム、配信、アクションを一式作り、最後に設定間のつながりを見せる。

### P1: エラーを「直せる文章」にする

悪い例: `action execution failed`

良い例: `3番目「会員用メニューへ変更」が失敗しました。対象メニューは停止中です。メニューを公開するか、この動作を外してください。1〜2番目は完了しています。`

### P2: 分析から次の操作へ戻す

分析を眺めて終わらせない。離脱した人、クリックした人、未予約の人を条件として保存し、そのまま配信または担当者タスクへつなぐ。

## 7. 優先順位

| 優先 | 実施内容 | 理由 | 完了の証拠 |
|---|---|---|---|
| P0 | 全機能の現状を7点判定で再棚卸し | 画面の存在と完成を分ける | 画面・保存・実行・失敗・計測・権限・視覚の一覧 |
| P0 | 共通条件／アクション／メッセージ契約を固定 | 画面ごとのずれを止める | 型、API、DB、契約テスト |

| P0 | 配信・Webhookの冪等性と再試行を統一 | 二重送信を防ぐ | 重複イベント、5xx、timeoutの自動試験 |

## 8. 競合と突き合わせる実機テスト

Linyのログイン後挙動と、Lステップの状態変更を伴う挙動は、公開情報だけでは確定できない。次を同じデータで実行し、画面・DB・LINE端末の時刻を記録する。

| # | テスト | 確認すること |
|---|---|---|
| 1 | 同じ文に一致する自動応答を2件作る | 最初の1件／全件、評価順、アクション順 |
| 2 | アクション2番目を意図的に失敗させる | 1番目の確定、3番目の継続、再試行 |
| 3 | 同じWebhookイベントを再送する | 返信・タグ・シナリオが一度だけか |
| 4 | シナリオA中にBを開始し、B完了後に戻す | 停止位置、再開位置、同時購読 |
| 5 | 配信時刻を過ぎてシナリオへ登録する | 当日スキップか翌日か、秒・分の丸め |
| 6 | 友だち情報の基準日を変更する | リマインダ再計算、過去時刻の扱い |
| 7 | 同時に最後の予約枠を取る | 排他、片方のエラー、通知の重複 |
| 8 | 公開フォームを回答途中で編集する | 回答版、途中回答、保存先の整合 |
| 9 | 既定と個別リッチメニューを同時設定する | 優先順位、反映時刻、解除後表示 |
| 10 | フォルダ権限のない担当者がURL/APIを直接呼ぶ | 一覧件数、詳細、実行、CSVの遮断 |

完了時には、競合ごとに次を残す。

- プラン、アカウント、実行日時、タイムゾーン
- 操作前後の画面キャプチャ
- 設定値
- LINE端末で届いた順番と時刻
- 競合の実際の結果
- Harnessの結果
- 一致／意図的な差／不具合
