# Lステップ機能差分の棚卸し（実装判断用）

Lステップ管理画面（実アカウント `meauty渋谷店`）の全ページをキャンバスに取り込み、UIテキストを抽出して
LINE Harness に**無い**機能だけを列挙したもの。実装するかどうかを判断するための材料として使う。

- 調査日: 2026-08-15
- 対象: Lステップ管理画面 内部リンク 26ページ（閲覧のみ。状態が変わる操作は一切していない）
- 突き合わせ先: `apps/web/src/app` 配下の管理画面と `packages/db/schema.sql`
- 詳細・編集画面 6ページを追加取得済み（第2.5節）。未取得は新規作成フォームとリッチメニュー関連

判定の凡例:

| 記号 | 意味 |
|---|---|
| ❌ | Harness に相当機能なし |
| △ | データ構造はあるが管理画面・機能として出ていない |
| ✅ | 実装済み（差分なし。本書では原則省略） |

---

## 1. 横断的な差分（ほぼ全画面に共通）

Lステップは一覧画面のUIパターンが全機能で統一されている。ここが最も差が大きい。

| # | 機能 | Lステップの実装 | Harness 現状 | 実装判断の観点 |
|---|---|---|---|---|
| C-1 | **フォルダ分類** | タグ／シナリオ／テンプレート／自動応答／リマインダ／アクション／回答フォーム／友だち情報欄／共通情報／カスタム検索／イベントの**全一覧**に「新しいフォルダ」。未分類フォルダに件数バッジ | ❌ `tags` `templates` `scenarios` などに親フォルダ列なし | 運用が育つと一覧が破綻する。汎用の `folders(id, kind, name, parent_id, display_order)` + 各テーブルに `folder_id` を1本入れれば全機能に横展開できる。**共通基盤なので先に入れるほど安い** |
| C-2 | **ドラッグ並び替え** | 全一覧に `drag_indicator` ハンドルと「並び替え」ボタン | △ `booking/menus` `booking/staff` `events` のみ `sort_order` あり | C-1と同時に `display_order` を各テーブルへ。単独の価値は中 |
| C-3 | **お気に入り（star）** | タグ・回答フォームなどに星マーク。友だちリストの「★つきタグ・友だち情報」列と連動し、**一覧に出す項目をユーザーが選べる** | ❌ | 星それ自体より「友だち一覧に表示する列をユーザーが選ぶ」仕組みが本体。運用者の画面カスタマイズとして価値が高い |
| C-4 | **保存した検索 / 詳細検索** | 友だちリストとトーク一覧の両方から同じ検索条件を呼び出せる。条件自体は「カスタム検索管理」でマスタ管理 | ❌ | セグメント配信の条件と共通化できるはず。Harness は配信時にAND/OR条件を組めるので、**その条件を名前付きで保存・再利用できるようにする**のが最小実装 |
| C-5 | **下書き** | 友だちリスト／シナリオ配信／テンプレート／回答フォームに「下書きを開く」。作りかけをページを離れても保持 | △ `broadcasts` `webinars` のみ draft あり | 長いフォーム（シナリオ・フォーム作成）ほど効く。localStorage だけでも体験は大きく改善 |
| C-6 | **画面ごとの説明文＋マニュアル導線** | 全画面のタイトル直下に1行説明（例:「友だちを分類するタグを管理できます。」）＋「マニュアル」リンク | ❌ | 実装コストがほぼゼロで、社内スタッフのオンボーディングに直接効く。**最優先で入れてよい** |
| C-7 | **空状態メッセージ** | 「アクションが作成されていません」等を明示 | 一部のみ | 低コスト。C-6と同時にやる |
| C-8 | **CSVアップロード／ダウンロード** | タグ管理にCSV一括登録 | ❌ 全画面で該当なし | 初期移行と大量登録で効く。優先度は移行予定の有無で決まる |

## 4. 実装判断のたたき台

あくまで提案。実際の優先度は運用要件で決めてください。

### 最大の発見：4機能が1本の線で繋がっている

Lステップの強さは個々の機能ではなく、**次の連鎖が1本に繋がっている**こと。ここを分解して入れても効果が出にくいので、
セットで設計することを勧めます。

```
G-1 友だち情報欄（項目をマスタ定義）
  ↓ FB-2 フォームの各項目に「登録先」を指定
G-5/FB-1 回答フォームで回答を集める
  ↓ 回答がそのまま友だち情報欄に入る
FD-1 友だち詳細で情報欄フォルダがタブとして並ぶ（＝顧客カルテ）
  ↓ ME-1 テンプレートの変数挿入UIから差し込む
パーソナライズされた配信
```

Harness には現状この線が1本も無い。**逆に言えば、この5点（G-1 / FB-2 / FB-1 / FD-1 / ME-1）を入れるだけで
Lステップの中核体験にほぼ追いつく**。他の項目は運用の快適さの話で、優先度は一段下がります。

### 先に入れると全体が楽になるもの（基盤）

1. **C-6 画面説明＋マニュアル導線 / C-7 空状態** — ほぼコストゼロ、オンボーディングに即効
2. **C-1 フォルダ ＋ C-2 並び替え** — 汎用テーブル1本で全機能に横展開。後回しにするほど各テーブルへの追加が増える。FD-1（情報欄タブ）の前提でもある
3. **G-1 友だち情報欄** — 上記の連鎖の起点。`friend_fields` + `friend_field_values`
4. **FD-6 本名・システム表示名・個別メモ** — LINE表示名は本名とは限らない。低コストで実務効果が大きい

### 事故・取りこぼしを防ぐもの（運用リスク）

4. **P-1 ログイン履歴** — 顧客データを扱う以上の最低限
5. **D-2 + G-8 送信数と残枠** — 課金と配信停止に直結
6. **N-1 Webhook URL の突き合わせ表示** — 設定ミスの早期発見
7. **G-7 外部通知（Slack）** — 問い合わせの取りこぼし防止
8. **I-1 メッセージ種別フィルタ / T-1 絞り込み** — 対応漏れ防止

### 運用の質が上がるもの

9. **ME-1 テンプレートの変数挿入UI（＋G-4 共通情報）** — 上記連鎖の出口
10. **FB-1/FB-2 フォームビルダーと回答の登録先指定** — 現場にフォーム作成を渡せるか
11. **FD-1/FD-2 友だち詳細のタブ集約（顧客カルテ）**
12. **AR-2/AR-3/R-3 自動応答の一律応答・時間帯条件・複合アクション**
13. **SD-1 シナリオのステップ別到達人数** — 集計だけで離脱地点が見える
14. **T-3 トーク内のシナリオイベント時系列表示**
15. **FB-3 日付項目からのリマインダ起動**
16. **A-1 導入前友だち／ブロック解除者の分岐**
17. **ME-2 文字数カウンタと分割警告 / SD-3 一括テスト** — 配信事故の予防

### 要件次第（先に判断が必要）

- **G-5 登録メディア一覧** — リッチメニューを本格運用するなら必須、しないなら不要
- **G-6 データ移行** — 多店舗展開の予定があるか
- **G-3 対応マーク管理** — 固定3値で足りるか
- **C-8 CSV** — 初期移行の量による
- **E-2 イベント承認制** — 予約運用の方針による

## 5. 調査上の注意

- キャンバスに取り込んだ `L 1-2 友だちリスト` `L 1-4 個別トーク` `L 4-4 トーク一覧` `L 1-2-1 友だち詳細` には**実際の顧客名・電話番号・トーク本文がそのまま含まれる**。デザインファイルを外部共有する場合は必ず除外すること。本書には一切含めていない。
- `/account/newuser`（新規アカウント発行）は実環境でアカウント発行に関わる可能性があるため意図的に開いていない。
- **新規作成フォーム**（「新しいシナリオ」等）は未取得。クリック時点でレコードが作られる可能性があり、実環境で試していない。既存レコードの編集画面で構造は把握できているため、差分の把握には支障なし。
- **リッチメニュー関連の画面が Lステップ側に見当たらなかった**。このアカウント（スタートプラン）ではメニューに現れないため、上位プランまたはオプション機能の可能性が高い。Harness の `2-5 リッチメニュー` に対応する比較対象は未確認のまま。
- 取得できた画面は一覧26＋詳細6の計32ページ。すべて閲覧のみで、保存・送信・配信・削除・公開・テスト送信の類は一切実行していない。
