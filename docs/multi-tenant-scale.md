# 多社運用の容量と処理設計

対象は `e77d145e494d66aee0f5a2427f483ca588753fa8` を基準とする0.24.0と本変更。500統括・5,000 LINEアカウント、平均1,000友だち、大口10万友だちを仮定した。これは受入上限・性能保証ではない。実Cloudflareでの総負荷、外部APIの総量、データ移行は未検証である。

## 結論

単一D1・全社共通Cronの現構成では、この規模の安定運用を保証できない。今回のコード変更で件数打ち切り、SQL増幅、先頭に偏る巡回を改善した。DB分割、監視履歴の保持方式、残る配信・同期処理の分割が完了するまでは「5,000アカウント対応済み」としない。

[D1の公式制限](https://developers.cloudflare.com/d1/platform/limits/)は1DB 10GB、1 Worker実行1,000 SQL、1行/文字列2,000,000バイト。各DBのSQLは直列処理される。Workerの一般subrequest制限とは別に扱う。[Queuesの制限](https://developers.cloudflare.com/queues/platform/limits/)はsendBatch最大100通/256KB、consumer実行最大15分。これらの上限は性能目標ではない。

## コードで改善する範囲

| 経路 | 元の制約 | 本変更の動作・検証 |
| --- | --- | --- |
| 認証時の所属検索 | COALESCE条件でテナント索引が使いにくい | 非defaultはtenant_id等価、defaultはNULL互換を維持。SQLiteで同値と索引を確認 |
| 統括の要対応 | 1店舗10 SQL、100店舗で上限域 | まとめて5 SQL、150/5,000店舗の合成試験 |

| 店舗比較一覧 | 全店を個別集計してから20件へ切る | 期間ごとの集合SQLで比較・中央値・欠測を保持 |
| 友だち日次記録 | 6時間ごと最大1,000件、1日4,000件 | 5分ごと100件、5,001件を51回で巡回 |
| 顧客分類 | 1分1件で日次の全社完了が不足 | 1分5件、未完了優先、失敗隔離・期限付き実行権 |

| 時間分散配信 | Queue継続を1秒間隔にすると分散設定を短縮する | 配信ごとの次回可能時刻を保存。早い再配達では送らず、通常配信は進める。6,000宛先/60分の合成試験 |
| 予約配信の認証情報 | 予約がない他社の復号失敗でも全予約が止まる | 非秘密の状態だけ一覧化し、送信対象ごとに復号・失敗隔離 |
| token・プロフィール更新 | 全社資格情報を毎回読取 | dueだけ25件、試行履歴で失敗群を隔離し、未試行の後続へ進む |
| Sheets日次同期 | 全接続を読取、partialも当日済み扱い | 完了済みをSQLで除外、25接続/50秒、未完了のページを同日再開 |
| Calendar空き控え | 先頭100接続に固定 | 試行時刻で公平化、Queue経路は1接続ずつ継続 |
| アカウント別処理 | 監視は全社を同時開始、分析は全体で1店/5分 | 専用Queueのコードを追加。設定未追加のため未稼働 |

日次の5,000件試験は友だちデータが空の合成SQLiteである。件数・公平性・再開・SQL数を確認しており、大口1社のSQL実行時間や実D1の処理速度を証明するものではない。

## 容量の測定

bootstrap.sqlの索引・triggerを含むSQLiteへ合成友だち10,000人とメッセージを投入した外挿。実D1の実測値ではない。

| 想定 | 友だちとmessages_logだけの概算 |
| --- | --- |
| 500万友だち、100バイト本文を1人1通 | 約9.05GB |
| 500万友だち、100バイト本文を1人5通 | 約30.61GB |
| 500万友だち、1KB本文を1人1通 | 約14.46GB |

予約・注文・監視・監査等の容量は含まない。さらに現監視は5分ごと1社1run・9結果なので、5,000アカウントでは1日約144万run・1,296万結果を作る。Queueだけ導入しても保存量の問題は解消しない。

複数アカウント重複除外配信も、10店舗×1,000宛先の合成データでdedup_progressが初期1,941,997バイト、全送信後2,381,996バイトになった。1行JSON方式のまま大口配信を認めない。小さな部分送信へ分割するだけでは、全宛先のJSON保存という制約が残る。

## 専用Queueの準備と未有効化の理由

`ACCOUNT_WORK_QUEUE` が無いと従来の経路を使う。本PRはWrangler、Cron、実リソースを変更しない。予約Cron `*/2 * * * *` は、設定されるまで実行されない専用producerの入口である。既存deliveryと同じinvocationへ全社producerを載せない。

- 100アカウント単位でhealth / analytics / broadcast / calendarをenqueue。5分窓、永続カーソル、受理後だけcheckpointを更新。途中失敗は古い窓を完了してから次の窓へ進む。
- 1メッセージはアカウントID・処理種別・窓・連番のみ。資格情報・顧客本文は載せない。
- consumerは1アカウント/処理単位。D1で所有者付き20分leaseを取り、完了記録で成功済み再配達を省略する。失敗はretry。DLQは構成側で必須。
- tokenの期限が分かっていて60秒以内に切れる場合、配信台帳を進めず更新後の再試行を待つ。Queueと定期更新の実行順を仮定しない。
- lease競合だけは21分後に再試行し、強制終了で残った20分leaseの満了前にretry回数を使い切らない。通常の失敗は60秒後に再試行する。
- 配信と分析の続きは最大20回、各処理の永続進捗から再開する。停止中の配信を連続enqueueしない。NULL所有の旧配信・複数店舗配信は既存Cronの回収に残す。dedupは候補・宛先送信枠を制限してもアカウント全件走査とJSON保存が残り、処理全体の有界化は未達。
- token更新はリマインド前の既存順序を保ち、対象の選び方を有界化する。非同期Queueへ移して順序を壊さない。
- キューの再配達はat-least-once。LINE受理済み台帳・retry keyが送信の根拠であり、Queueの完了記録だけでexactly-onceを主張しない。

5,000アカウントに4処理を5分ごとに投入すると、継続分を除いて1日576万メッセージになる。初期構成のまま全社へ有効化しない。変更が無い分析・配信の対象除外、監視の共通化、保持方式、実D1での待ち時間を先に測る必要がある。

検証用構成案（まだ作成・適用していない）：

| 項目 | 隔離した合成データ検証の案 |
| --- | --- |
| Worker | 専用検証Worker。通常stgの外部送信停止を解除しない |
| D1 | 空の検証専用DB 2個。実データ・本番秘密をコピーしない |
| Queue | 作業QueueとDLQ各1個、max_batch_size=1、初期max_concurrency=2、max_retries=10 |
| 保持 | 作業QueueとDLQ 14日。容量と最古滞留時間を監視 |
| Cron | 専用producerだけ。最初は手動1窓を確認後、定時化 |
| 外部送信 | LINE・メール・決済等はstubへ固定。実顧客通知なし |
| 失敗条件 | D1 overload、10分以上のhealth遅延、取りこぼし、二重受理、増え続けるqueue lag |

## DB分割の移行設計

`dbFor()` は現在env.DBを返すだけである。Workerの製品TypeScript317ファイルにenv.DB直接参照5,639箇所（文字列検索、テスト除外）があり、認証・全社JOIN・定期処理も含む。関数1個の変更でDB分割が終わる設計ではない。

1. 中央DBは認証・統括/アカウントの配置台帳・全体運営情報を保持する。業務DBは統括単位で固定配置し、同一統括の店舗を原則同じDBに置く。大口は専用DBへ割り当てる。テナントIDからの単純moduloは再配置で変わるため使わない。
2. 検証は2業務DBから開始。配置台帳はtenant_id、shard_key、routing_version、stateを持つ。認証で確定したtenantから配置を引き、URL/ヘッダー指定だけで別DBへ切替えない。
3. DB引数を受け取る境界を整え、HTTP、Webhook、Queue、Cron、バッチ、バックアップ/復元/消去を同じ配置に通す。中央認証と業務をまたぐSQL JOINを、認可済みIDと集計投影へ分離する。
4. DBごとにschema versionとマイグレーション台帳を持つ。全DB一括DDLを避け、1つの検証DB→少数→残りの順で展開する。1DBの失敗で別社を停止しない。
5. 顧客データを含むコピー前にDB/設定のバックアップと復旧手順を確定。コピー、件数・checksum・外部キー照合、差分取り込み、短時間の対象統括書込み停止、再照合、routing_versionの切替を別工程にする。二重書き込みを原子的更新とみなさない。
6. 切替直後の書込みが新DBに入った後は、配置を旧DBへ戻すだけではデータを失う。対象統括を停止し差分を逆適用・照合して戻す。復元・切戻しも承認対象。
7. 容量の警告は5GB、再配置準備7GB、上限到達前に移動を完了する案。顧客数だけで割り当てず、保存量とSQL待ち時間で配置する。値は実負荷検証後に確定する。

上記は設計案であり、配置台帳・移行SQL・全経路ルーティングは未実装。既存DBの移行を自動的に始めない。

## 大容量の進捗と監視履歴

- 重複除外配信：recipient別の進捗表へ正規化。broadcast_id / identity_keyの一意制約、送信account_id、friend_id、状態、retry_key、claim期限を持つ。既存dedup_progressは旧形式として読み、停止確認後にページ単位で移行・一致照合する。新しいマイグレーション番号は共同管理者との採番後に確定する。
- 監視：全アカウント共通のD1/R2疎通は一度計測する。アカウント状態はlatestと変化履歴を分離し、詳細履歴は検索要件と保存期間を決めて退避する。正常履歴を無制限に積まない。
- `operation_alerts.source_run_id` はrun削除でCASCADEする。単純な古いrun削除を入れると未解決アラートまで消えるため、このPRでは削除処理を追加しない。参照構造とアーカイブ復元を試験してから移行する。

## 残る有界化と受入条件

Google Sheetsは今回対象を有界化したが、巨大シートの主キー列を読む量が残る。リマインドには1ページ500登録に対する共有SQL予算の不足があり、シナリオ40通/5分・予約リマインド100通/5分などの全社共通枠も残る。外部カレンダーはQueue未有効では100接続/5分なので5,000接続に250分かかる。Queue経路は1接続/実行、1窓最大21接続まで継続する。スタッフ接続が多い1アカウントは次の窓へ持ち越すため、15分freshの受入試験が別途必要。これらを個別Queue/期限順の処理へ移すまで、全社同時集中時の時間保証は未達である。

frequent Cron先頭と予約配信開始時の全社復号は除去し、分析は非秘密項目だけ読む。配信分析ジョブ内とscenario/reminder等の全社復号は残る。予約配信の開始経路も、期限に達した全予約の列挙と一部の即時送信が残り、キュー側の予算だけでは全体を制限できない。ランク判定も1社500人程度で1,000 SQLに達し得るため、公開設定の原子性を維持した分割処理が必要。単体ジョブの上限だけでなく、同じinvocationへ載るSQL合計で検証する。

配信後動作の回収は全体で700 SQL・15秒の開始前予算を共有する。ただし開始した1動作の内部SQL・副作用は途中で強制停止しないため、任意executorの内部処理量を保証しない。古い形式の「一部doneだけで後続記録がない」履歴の全件復元も含めない。実行中の結果不明行は自動再実行せず、人手の確認対象として残す。

受入試験は、500社/5,000アカウント、平均1,000友だち、大口10万、同時予約通知、外部429、1社の不良設定、worker強制停止、Queue重複・順不同、DB shard停止、再配置中の書込み、バックアップ復元を含める。実通知は送らず合成先で確認する。SQL数<1,000、binding parameter<=100、行サイズ<2MB、永続キューの最古待ち時間と日次完了率を記録する。UI p95、配信期限、保存年数、許容月額は実測と運用要件から確定する。

## 承認の境界

今回のコード修正は通常の検証配備として扱う。新リソース、Cron変更、DBマイグレーション・コピー・削除・復元は、[作業安全規則](../AGENTS.md)と[配備ゲート](DEPLOY-GATE.md)に従い、対象・影響・バックアップ・切戻しを提示して個別承認を得る。本番操作は含めない。
