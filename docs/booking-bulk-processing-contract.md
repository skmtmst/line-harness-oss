# 一括予約の券・支払い・承認・通知

この文書は、繰り返し予約と複数人の予約の共通処理を設計する。動きの正本は [B4](v8-requirements/gap-features/B4-recurring-booking.md)・[B5](v8-requirements/gap-features/B5-party-multi-menu.md)・[B2](v8-requirements/gap-features/B2-tickets-monthly.md) と既存の予約・支払いの要件。設計の記載だけで利用可能と扱わず、LIFF の「準備中」は後続の実装と検証がそろうまで維持する。

## 1. 正本と現行の境界

| 対象 | 決まっている動き | 現行で不足する所 |
|---|---|---|
| 繰り返し | 各回に1予約、組で1回承認、確定時に各回の券を1回利用 | bulkの券登録は最初の回のみ。組の承認は未接続 |
| 複数人 | 人ごとに1予約。券は本人だけ。券以外の合計を1回で支払う | 合計決済と人別の支払内訳が未接続 |
| 繰り返しの先払い | 各回別。前日に店が支払リンクを送る | bulkはオンライン払いを409で止める。将来回のリンク発行・期日が未接続 |
| 確定の知らせ | 組1通を本人へ。リマインドは各回 | bulkはnotificationsAvailable:false。単独予約の確定処理をそのまま全件へ呼ぶと確定LINEが重複する |
| 保存 | 作成直前に空きを再検査し全部か無し。キー再送で組を増やさない | 現行のbatchとキーは維持し、券・承認・支払台帳にも広げる |

調査対象は createBulkBooking、管理者series/groups、LIFF requests、単独予約の承認、券のDB trigger、確定副作用、支払開始・Webhook。管理者series作成は別経路であり、LIFF bulkだけ直して同じ機能を残さない。

## 2. 保持する入口と追加契約

既存の入力名を変更しない。LIFF POST /api/liff/booking/requests は recurrence または members と startMode を受ける。両方の同時指定は不可。管理者 POST /api/booking/admin/series と /api/booking/admin/groups は今の権限を維持する。各入口の入力を内部の共通計画へ変換する。

現在の実装の入口は [bulk作成](../apps/worker/src/features/booking/booking-bulk.ts)、[管理者の繰り返し](../apps/worker/src/routes/booking-series.ts)、[組とLIFFの補助口](../apps/worker/src/routes/booking-gap3.ts)、[単独承認](../apps/worker/src/routes/booking/register-decisions.ts)、[券](../apps/worker/src/features/booking/booking-entitlements.ts)、[確定副作用](../apps/worker/src/features/booking/booking-confirmed-effects.ts)、[支払開始](../apps/worker/src/features/booking/booking-payment-start.ts)で照合する。

作成前の見積もりに、作成対象の各回・各人と支払計画を返す。各項目は index、日時、menuId、staffId、券IDまたは支払方法、保存予定の税込価格（JPY整数）、デポジット、残額、期日を持つ。見積もり識別子・期限・設定版を返し、作成時に同じ計画への同意を受ける。クライアントの価格・残数・承認済み指定を採用しない。

後続へ渡すHTTP設計は次のとおり。既存の入口を拡張し、bulk-preview・別のpayment-link・別のsettlementの入口は新設しない。追加する項目と組のdecisionだけは未実装なので、OpenAPIと共有型を先に足し、接続試験が通るまで画面から呼ばない。既存のGETの応答や単独の見積もりは互換性を維持する。

| 入口 | 入力 | 成功のdata |
|---|---|---|
| 既存 POST /api/booking/admin/series/preview と GET/POST /api/liff/booking/series/preview | 今のseries入力＋各回の券/支払選択。GETの追加値はJSONクエリ | 既存occurrencesを保持し、quoteId、expiresAt、planVersion、items、total、amountDueを追加。店52回・LIFF12回 |
| 既存 GET /api/liff/booking/cost-estimate | 単独入力を保持。複数人はmembers/startMode/starts_at/人別選択をJSONクエリで追加 | 既存cancellation/deposit/paymentを保持。複数人時は上のquoteと人別内訳を追加 |
| 既存 POST /api/booking/admin/groups（previewOnly:true の拡張） | 作成と同じ入力＋previewOnly:true | quoteと人別内訳のみ。組・予約・券利用・決済を作らない。previewOnly省略/falseの既存作成は維持 |
| 既存の作成3入口 | 既存入力＋quoteId/planVersion。券/支払選択を追加する場合は各itemのindexに対応付ける。Idempotency-Key必須 | 既存seriesId/groupId・bookings・total・replayedを保持し、items、amountDue、version、approval、payment、notificationを追加 |
| POST /api/booking/admin/series/:id/decision、および /api/booking/admin/groups/:id/decision | action:approve/reject、expectedVersion、reason（拒否時必須）。Idempotency-Key必須 | version、approval、bookingsの全ID/状態、payment、notification、replayed |
| 既存 POST /api/booking/admin/payments/:id/send-link の拡張 | 今のdryRun:trueを維持。実装後の検証用送信はdryRun:false・expectedVersion・Idempotency-Key。idは対象支払ID | 既存paymentId/checkoutUrl/simulation/sentを維持。status、expiresAt、deliveryStatus、replayedを追加。模擬を実送信成功にしない |
| 既存 GET /api/liff/booking/me と管理者のseries/group詳細 | 本人、または所属する組の予約ID/組ID | 既存履歴/詳細に組のversion、approval、items、total、amountDue、payment、notificationを追加。必要時だけ本人用checkoutUrl。別人/秘密値なし |

itemsは各予約予定のindex・日時・担当・メニュー・価格・券充当・請求額を表す。totalは予約価格の合計、amountDueは券を除いた今回の請求額であり、同じ値と決めつけない。approvalはpending/approved/rejected、paymentはnot_required/scheduled/unpaid/pending/paid/failed/expired/refund_pending/refunded、notificationはnot_queued/queued/succeeded/retry_wait/unknownを返す。個々の予約statusは既存のrequested/confirmed等を維持する。

previewOnlyは真偽値だけを許し、不正値は400。見積もりでは組・予約・券利用・決済・通知・作成キーの台帳を変えず、quoteの保存スナップショットだけを別スコープへ保持する。同じキーで後から作成しても見積もり応答を作成結果として返さない。GETで追加するJSONクエリはUTF-8で8,192バイトを上限とし、超過は400で拒否する。繰り返しで長くなる入力は既存POST series/previewへ送る。上限とエラーはOpenAPIに載せる。

quoteIdは店舗・本人・正規化入力・解決済み価格/ルール/選択・設定版・有効期限を結ぶサーバー保存スナップショット。作成時は現行値を再検査し、差があれば409 quote_staleで何も作らない。同じ作成キーですでに保存済みなら、quote期限切れでも既存結果を返す。作成の再送を期限切れとして失敗させない。

- 本人向け：認証済みLIFFの店舗と友だちで特定する。友だちIDや店舗を本文から信用しない。
- 管理者向け：owner/admin/staffかつ予約権限・店舗所属・書込可。閲覧のみと代理ログインは403。メニュー設定の変更と、既存send-link・payment-eventsのreplayはowner/adminだけ。スタッフへ送信/再処理の権限を広げない。
- 別店舗・別人・無効メニュー・許可外の券は書き込む前に拒否。明細から他人の個人情報や決済先の秘密値を返さない。

## 3. 券利用の計画

繰り返しは作成する回を日時・元のindex順に並べ、本人の券を使える回へ1回ずつ割り当てる。飛ばした回は利用しない。残3回で4回申し込む場合は、先の3回が券、最後が支払いという内訳を確認してもらう。券のみのメニューでは不足回を有料へ切り替えず、再選択を求める。

複数人ではgroup_index=0の本人の予約にだけ券を付ける。お連れさまに本人の券を流用せず、他人の券IDの受信も拒否する。本人の券＋お連れさまの支払いは有効で、現行の「entitlement_idとpayment_methodは併用不可」を予約ごとの条件にする。単独予約の制限は維持する。

booking_entitlement_usesの予約ごと一意と、確定時のtrigger減算を利用する。requestedでは減算せず、確定への遷移と減算を同じbatchに含める。月謝は各回の店舗時間帯の月に分け、イベント予約を含む既存の月上限・有効期限・適用先も同じ検査を通す。

見積もり後に残数や設定が変わったら409で、作成時は組・予約・利用を何も残さない。承認時なら全件をrequestedのまま残し、減算・確定・通知受付を残さない。勝手に支払いへ変えない。requestedは券の残数を予約確保する意味ではない。

## 4. 支払いの単位と失敗時の状態

| 種類 | 支払単位 | 確定との関係 |
|---|---|---|
| 繰り返し | 券でない各回に別の支払予定。組の合計一括課金はしない | 組承認で予約を確定でき、各回の前日に店がリンクを送る。未払いを自動課金や一括取消にしない |
| 複数人 | 券で充当しない人の金額をまとめて1回。明細は人別 | 承認と支払いを別に管理し、必要な両方が済んだら全予約を同時確定 |
| 店頭・支払なし | Checkoutを作らず、人別の方法・額を保存 | 承認だけで確定 |

金額は各担当の上書き料金・指名料・追加メニューを解決したサーバーの税込JPY整数で固定する。券を使う本人分を請求へ含めない。デポジットは適用ルールに従って合計を計算し、その合計と一致する人別配賦を保存する。端数の配賦順は元のindexで固定する。異なるメニューの異なる支払ルールを1つの値へ黙って統一せず、見積もりで各明細のルールを示す。

既存booking_paymentsは1予約を参照する。複数人の1回の決済を人数分のbooking_paymentsへ複製しない。支払単位（組・回、請求額、通貨、状態、provider参照、安定キー）と予約別配賦を持つ追加台帳を後続で設ける。合計と配賦の一致、返金累計が決済額を超えない条件をDBと試験で守る。単独予約の既存台帳と混同しない。

繰り返しの将来回に作成時から30分などの保留期限を付けない。前日の手動送付操作で、その回の支払先を有効期限つきで作り、同じ操作を再送しても同じ支払を返す。現在のpayment-startはrequested予約向けなので、既存send-linkの内部に「繰り返しの確定済みの回・その回の支払予定」を検査する分岐を接続する。支払予定は作成時に安定したpaymentIdを持ち、send-linkは同じ支払ID/送信目的/操作キーの台帳を参照する。通常払いと将来回のどちらから入っても二重にリンクや送信を作らない。従来のdryRun:trueは外部送信なし、実送信は検証環境と承認済み宛先だけに限定する。

D1内で支払予定と外部実行待ちを保存し、commit後にproviderを呼ぶ。外部決済とD1が1つの原子的処理になるとは扱わない。provider失敗は未払いと再試行待ち、応答不明は照合待ち。予約を一部だけ確定せず、請求も再発行しない。署名検証済みWebhookを、登録先・通貨・額・状態・イベントIDで照合し、二重・順不同・DB保存失敗から回復させる。既存POST /api/booking/admin/payment-events/:id/replayを回復の入口として維持し、内部で支払単位に応じて単独/組の共通処理へ分岐する。組の再処理で代表1件だけを確定しない。

支払い完了時に券や予約の競合で全件確定できない場合、providerの入金まで巻き戻せた扱いにしない。支払済み・確定保留を保存し、照合/要対応に残す。再送で再課金せず、初期のbulk対応では既存の要対応台帳と同じくreview_requiredにし、owner/adminが照合結果を確認して全件確定か返金を判断する。自動返金を新しく始めない。単独予約の遅い入金の回復処理へ組の代表1件だけを渡して復元することも禁止する。この状態では確定通知とリマインドを受け付けない。

初期版の人を減らす取消は、B5 §6に従い期限内・先払いでない組だけ。先払いの組は組全体の取消とし、部分返金ができた扱いにしない。手動承認の組では承認済みになるまでCheckoutを開始しない。拒否・期限切れの後に遅れて入金が届いた場合は再確定せず、要対応へ残す。owner/adminの判断後の返金も受付と完了を分け、失敗を未完了の台帳へ残す。

## 5. 組の承認と排他

承認対象は作成時の組の予約全件。組ID、approve/reject、expectedVersion、Idempotency-Keyを受ける。部分承認の入力は受けない。単独予約の承認入口へ組の予約IDを送った場合は409 group_decision_requiredで止め、組IDと組の承認へ案内する。黙って対象を全件へ広げず、一部だけ確定する経路も残さない。

組の承認状態（pending/approved/rejected）と支払状態を分離する。requestedだけから承認待ちか支払待ちかを推測しない。全予約の状態・券・空き/定員・設定版を再確認し、組版の条件付き更新、全予約の遷移、券消化、確定副作用の受付を1つのD1 batchにする。1件でも競合すれば409で全体を戻す。

自動承認でも同じ確定処理を通る。管理者の電話・店頭予約の承認扱いは既存仕様を保ち、支払いの未対応を飛ばす口にしない。拒否では組全体をrejectedにし、未利用の券を減らさず、支払/通知/リマインドの未完了操作を停止・回復可能な状態へ移す。外部送信中や課金中は既存の送信中ガードを使い、停止不能を成功と返さない。

### 組の変更・取消（既存入口も後続3束の対象）

PATCH /api/booking/admin/series/:id、POST /api/booking/admin/series/:id/cancel、POST /api/booking/admin/groups/:id/cancel、POST /api/booking/admin/bookings/:id/group/cancel と本人用の変更・取消を、作成と同じ計画/支払/通知処理へ接続する。現行の「料金を見積もってstatusを変えるだけ」を支払対応済みとしない。

- 券の束：この回/この回から後の対象を確定し、取消時の既存triggerによる返却を1回だけに保つ。月謝の月をまたぐ変更は既存のentitlement_month_changeの409で、組/各予約/利用のどれも変えない。期限や対象外を支払いへ黙って変えない。
- 支払いの束：取消料を各回/各人で計算し、取消時点の見積もり・同意を保存。期限内の支払済み取消は既存の返金条件と同じく全額を返す処理を受け付け、返金失敗を未完了へ。期限後の取消料も台帳へ記録する。外部返金の完了と予約取消を1つの原子的成功にしない。未払いリンクは停止し、遅い入金は要対応へ送る。
- 通知の束：対象回の未送信リマインド/カレンダー/古い確定通知を止め、送信中ガードを通してから変更/取消を保存する。確定した対象の変更/取消を組1通で本人へ知らせ、組版と対象予約一覧を通知の安定キーへ含める。
- 全部か無しの保存・版競合を守る。B4の範囲変更は空きのない回を元のまま残してconflictsに明示するが、券の月変更などDBの整合違反は全体409。部分的に直った結果を全件成功と表示しない。

## 6. 通知と回復

組の確定通知は本人に1通で、全日付または人別内訳を含める。お連れさまへ送らない。予約ごとの確定LINEを止めても、各回のリマインド・カレンダー・成果・自動化まで止めないよう、確定通知とそれ以外の副作用を分ける。

- 組通知のキーは店舗・組種別・組ID・通知種別・確定版を含める。同じキーの再実行は成功済みを送らない。
- 各回のリマインドとカレンダーは既存予約IDの安定キーを保つ。飛ばした回・拒否・取消・支払待ちで未確定の回には作らない。
- 組の通知台帳は組IDと対象予約IDの一覧・版・宛先本人を保存する。予約1件の既存台帳に代表IDだけ入れ、残りの回の変更を追えない形にしない。
- DBの確定と通知受付は同じbatch。送信失敗で確定を戻さず、受付済み・再試行待ち・送信成功・到達不明を別に返す。到達不明は既存の運用どおり自動再送しない。
- 日付や人数が多い場合はLINEメッセージ上限内でまとめ、必要なら安全な本人用の履歴リンクを添える。送信先・本文を試験外の顧客へ送らない。

## 7. 冪等と失敗の契約

初回作成・組承認・手動支払リンク送付・Webhook・通知を別の操作として記録する。店舗と本人/操作者のスコープを越えてキーを共有しない。同じキー・同じ正規化入力は同じ操作結果、同じキー・違う入力は409。JSONのキー順だけで別操作にせず、正規化後の入力を保存する。

| 入力・故障 | 期待結果 | 残る状態 |
|---|---|---|
| 4回、券残3、本人が4回目の支払を確認 | 4予約・利用予定3・支払予定1 | 確定の時に3だけ減算 |
| 2人、本人は券、もう1人はonline | 本人の利用1・合計決済1・人別内訳2 | 他人の券なし・本人分の二重請求なし |
| 見積もり後に空き/券/設定の版が変わる | 409と再確認情報 | 作成なら何も残らない、承認なら元の全予約 |
| 保存の同時二重押し | 1組・予約N・各回/各人の台帳1 | 同じIDを返す |
| 別店舗・別人・閲覧のみ・代理の書込 | 403/404（既存形式） | 変更・外部作用なし |
| 承認の途中1件でDB故障 | 失敗/409 | 全requested、減算0、通知受付0 |
| 複数人の支払保留期限が切れる | 組と全requested予約を同じbatchでexpiredへし、全員の席を解放 | 券減算0、確定通知/リマインド0。支払リンク停止、遅い入金は要対応 |
| 合計課金の成功Webhook再送 | 1回だけ反映し全件を同時確定 | 課金/券/確定通知の重複0 |
| 課金成功後DB保存が失敗 | 成功扱いにせず照合・再処理 | 再課金なし、未完了を残す |
| 組通知が失敗・到達不明 | 予約確定は保持 | 再試行待ち/確認待ち。到達不明の自動再送0 |

既存の未対応409（bulk_online_payment_not_available等）は、その分岐の後続実装と異常系試験が合格するまで維持する。部分対応を全体対応として公開しない。

## 8. 後続の境界と完了証拠

1. 券の束：各回/本人の利用計画、見積もりと再検証、全件承認のbatchと排他。単独承認の抜け道、変更/取消の返却と月境界・イベントとの共用・不足・二重送信の試験。
2. 支払いの束：支払単位と人別配賦・合計決済・繰り返し各回の前日手動リンク、承認との分離、保留期限での全席解放、署名Webhook・既存replayとの接続・変更/取消/返金。Stripe試験モードで金額/重複/失敗回復を確認する。
3. 通知の束：組1通と各回リマインド、永続受付・回復・変更/取消の停止と再登録・送信中ガード・到達不明。送信はモックまたは承認済み検証先のみ。画面の有効化は全ての先行契約がつながった後。

この設計束では製品コード、migration、外部接続を変更しない。見積もりの保存スナップショット、承認状態、支払単位・配賦、組通知/操作履歴には後続でschema拡張が必要になる。既存表を流用できる箇所も後続の独立レビューで照合し、migration番号は司令塔から受け取ってから作る。稼働DBには適用しない。

試験結果と独立レビューの証拠は束の引き渡し記録へ記載する。既存の単位試験の合格は、将来契約の実装完了の証拠にはしない。
