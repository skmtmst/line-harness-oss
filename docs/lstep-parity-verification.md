# Lステップ機能の再現可能性 — 裏側の検証

デザインは描けても、LINEのAPIで取れないデータは実装できない。V2の各画面が本当に動くかを、公式ドキュメントで裏取りした結果。

- 検証日: 2026-08-15
- 出典: LINE Developers 公式ドキュメント（末尾に記載）

---

## 1. 検証結果サマリ

| # | 機能 | 判定 | 根拠・制約 |
|---|---|---|---|
| 1 | 一斉配信の開封数・開封率 | **○ 取れる** | narrowcast / broadcast は `GET /v2/bot/insight/message/event` で直接。push / multicast は送信時に `customAggregationUnit` を付ければ集計できる |
| 2 | URLクリック数 | **○ 取れる** | 同上（`uniqueClick`）。加えて自社の短縮URLでも実測できる |
| 3 | 今月の送信残枠 | **○ 取れる** | `GET /v2/bot/message/quota` と `/quota/consumption` |
| 4 | リプライ数・プッシュ数の日次 | **○ 取れる** | `/v2/bot/message/delivery/reply` `/push` `/multicast` `/broadcast` |
| 5 | 友だち数の日次推移 | **○ 取れる** | `GET /v2/bot/insight/followers?date=` |
| 6 | リッチメニュー（作成・エリア・出し分け） | **○ 取れる** | Rich menu API。エリアは最大20個 |
| 7 | クーポンの作成・送信 | **○ 取れる** | Messaging API で作成可能。ただし**「下書き」状態にはできない**（公式アカウントマネージャーからなら下書き可） |
| 8 | **個人単位の開封（誰が読んだか）** | **✕ 取れない** | インプレッションは集計値のみ。「この人は読んだ」は判定できない |
| 9 | **既読の取得** | **✕ 取れない** | Messaging API に既読の概念がない |
| 10 | **配信対象20人未満の開封数** | **✕ 出ない** | 統計値が20未満、またはイベント発生人数が20人未満のとき `null` が返る |
| 11 | 「自分からブロック」の内訳 | **△ 自社実装** | LINE公式アカウントに「運営側からブロック」の概念はない。Lステップの表示は同社の非表示機能。V2では自社の「非表示」として持つ |
| 12 | ECの本名・電話番号・住所の紐づけ | **○ 実装可能** | 自社実装。`nen_ec_member_snapshots` の `customer_id ↔ friend_id` で突合済み |

## 2. 設計に反映した制約

検証で見つかった制約のうち、**画面設計を変えたもの**。

### 2-1. `customAggregationUnit` の上限（月1,000種類）

push / multicast で開封を取るには、送信時にユニット名を付ける必要がある。

- **当月中に最大1,000種類**まで。1,001種類目以降は集計されない
- **1メッセージに指定できるユニット名は1つだけ**

**影響**: 一斉配信は「1配信＝1ユニット」で月1,000配信まで。実用上は足りる。
一方、**シナリオ配信のステップごとに開封を取ろうとすると、ステップ数 × 配信回数でユニットを消費する**。
定期実行のシナリオで毎回ユニットを切ると、すぐ上限に当たる。

**設計方針**: シナリオはステップ単位で固定のユニット名を使い、期間で切らない。一斉配信は配信ごとに切る。

### 2-2. 20人未満は数字が出ない

配信対象が20人未満だと、開封・クリックが `null` で返る。

**影響**: V2の一斉配信一覧には「誕生日クーポン 24通」のような小規模配信がある。20人を割る配信では開封欄が空になる。

**反映済み**:
- `V2 4-2-1 一斉配信の作成` の配信前チェックに「**開封数を集計できます / 対象252人。20人以上なので集計されます。20人未満だと表示されません。**」を追加
- `V2 4-2-2 配信の詳細` の「数え方」に「**配信対象が20人未満のときは、LINE側の仕様で開封数・クリック数が表示されません**」を追加

### 2-3. 個人単位の開封は取れない

**反映済み**: `V2 4-2-2 配信の詳細` の「数え方」を「**開封は LINE の集計値です。個人単位では取れないため「誰が読んだか」は分かりません**」に修正。

**影響する仕様**: 「友だちが読んだところから再開」（V2 4-6 友だち追加時の配信）は、**既読ではなく「配信済みステップの次から」**という自社定義になる。実装時に定義を固定すること。

## 3. ECの個人情報を友だち情報欄へ紐づける

### 実現方法

`nen_ec_member_snapshots` に `customer_id` があり、`friend_id` と突合済み。購入時にECへ入力された本名・電話番号・住所を、`friend_field_values` へ流し込めばよい。

### 設計に反映したもの

`V2 3-2-1 項目を追加する` に「**値の入り方**」セクションを追加した。

| 選択肢 | 挙動 |
|---|---|
| 手で入力する | スタッフが友だち詳細から入力 |
| 回答フォームから入れる | フォームの登録先として指定 |
| **EC連携から自動で入れる** | EC側の項目とマッピング。突合できている友だちにだけ反映 |

あわせて2つの仕掛けを入れた。

**「EC側の値を正とする」トグル** — 住所や電話番号のようにECが最新を持つ項目は、管理画面から編集できないようにする。手で書き換えても次の同期で戻るため、編集させない方が混乱しない。

**個人情報の警告** — 本名・電話番号・住所・生年月日を扱う項目には、閲覧できる権限を絞る設定（既定：管理者・運用者のみ）と、参照した記録をログに残す旨を表示。

### 実装時に決めるべきこと

1. **突合できない人の扱い** — 現状の設計では8件が未突合。この人たちには反映されない。手動で紐づける導線（EC連携の「会員の突合」タブ）が必要
2. **取得目的の明示** — 個人情報保護法上、利用目的を通知または公表する必要がある。EC側のプライバシーポリシーに「LINE公式アカウントでの連絡・案内に利用する」旨を含めるか確認
3. **削除要求への対応** — 友だちが削除を求めた場合、EC側とLINE側の両方から消す手順を決める
4. **アクセスログ** — `login_audit` に「個人情報項目を参照した」記録を残す

## 4. 「Lステップを完全に再現できるか」への回答

**現時点では保証できない。** 理由は3つ。

### 4-1. 新規作成フォームを見ていない

実環境のため、「新しいシナリオ」「新しい回答フォーム」などの**作成ボタンは押していない**（押した時点でレコードが作られる可能性があるため）。
既存レコードの編集画面から構造は把握したが、**新規作成時にしか出ない設定項目がある可能性**は排除できない。

### 4-2. 上位プランの機能が未確認

参照したアカウントは**スタートプラン**。リッチメニュー関連の画面がメニューに現れなかったことから、上位プランやオプションでしか使えない機能が存在する。それらは未調査。

### 4-3. 見えない仕様が必ずある

10年近く運用されているツールには、画面に出ない挙動（配信の順序制御、リトライ、重複排除、文字数の丸め方など）が蓄積している。画面の観察だけでは再現しきれない。

### 完全再現に近づけるために必要なこと

| # | やること | 目的 |
|---|---|---|
| 1 | **検証用のLステップアカウントを別途契約する** | 実環境を汚さずに作成フォームまで確認できる |
| 2 | 上位プランで1か月だけ契約し、全機能を棚卸しする | プラン差分の把握 |
| 3 | 同じシナリオを両方で組み、配信結果を突き合わせる | 見えない挙動の差分検出 |
