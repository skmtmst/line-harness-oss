# 設計を決めないといけないところ（v0.25.0）

V2設計どおりに作れなかった箇所の一覧。

実装は止めずに進めている。**設計にある数字を出す仕組みが無いとき、
数字を捏造せず、意味の近い別の数を出すか「—」にしている。**
どちらを選んだかと、設計どおりにするなら何が要るかをここに書く。

- 更新: 2026-08-16
- 対象: `docs/design-node-ids.md` の V2 85画面

---

| 列 | 意味 |
|---|---|

| いまの実装 | 設計どおりでない場合に、代わりに出しているもの |

## まとめ：根っこは5つ

個別に見ると19件あるが、原因は5つに集約される。

### A. 送信の出どころを記録していない（6-2 / 7-1 / 8-2）

`messages_log` に「この送信は何由来か」（テンプレート／シナリオ／リマインダ／
一斉配信）を持っていない。1列足せば3件まとめて解ける。

```sql
ALTER TABLE messages_log ADD COLUMN origin_kind TEXT;   -- 'template' | 'scenario' | 'reminder' | 'broadcast'
ALTER TABLE messages_log ADD COLUMN origin_id TEXT;
```

**過去ぶんは埋まらない。** 入れた日から先だけ正しくなる。

### B. 初回返信の時間を記録していない（1-1 / 2-1）

受信してから最初に返すまでの時間。`chats` に `first_replied_at` を足し、
送信時に「まだ入っていなければ入れる」だけでよい。

### C. 短縮URLとテンプレートが紐づいていない（6-1）

`tracked_links` はテンプレート本文から自動生成されるが、どのテンプレート由来かを
持っていない。クリック率をテンプレート単位で出すにはこれが要る。

### D. 友だち情報欄に型が無い（8-1）

`friend_fields` が文字列しか持たない。日付型を入れると、リマインダの起点に
使える項目を数えられるほか、入力欄も日付ピッカーにできる。

### E. 「いつ変わったか」を残していない（9-2 / 10-2 / 10-3）

対応マークも保存した検索も、いまの値しか持っていない。設計は
「過去7日」「今月の呼び出し」のように期間で切って見せる。

個別に履歴表を足すより、汎用の操作記録を1つ持つほうがよい。
`login_audit`（103）と同じ形で、対象・種類・日時を残す。

## 次に決めてほしいこと

1. **A（送信の出どころ）を入れるか。** 1マイグレーションで3件解ける。
   過去ぶんが埋まらないことを許容できるか
2. **4-2（20人未満の配信を開封率の平均から除く）でよいか。** いまそう実装している
3. **3-1（今月の追加の前月比）** を設計どおり増減だけにするか、実装のとおり
   前月の実数も出すか

1 が一番効く。2 と 3 は見た目の話なので、実物を見てから決めても遅くない。
