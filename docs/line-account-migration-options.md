# 約400店舗のLINEアカウント移行：2つの選択肢

飲食店の多店舗案件で「LINEアカウントを移行できるか」を判断するための資料。
結論から言うと、**「移行」という言葉が指す内容が2通りあり、どちらを選ぶかで結果が正反対**になる。

- 作成日: 2026-08-15
- 前提: 既存の各店舗が、それぞれLINE公式アカウントを持っている（約400）

---

## 0. 先に正しておきたい前提

事前の検討メモにあった認識のうち、2点は事実と異なる。

### 「認証済みアカウントであればユーザー識別IDを引き継げる」→ 誤り

userId は**認証状態とは無関係**で、**プロバイダー**に紐づいて発行される。

- 同一プロバイダー配下のチャネルであれば、Messaging API でも LINE Login でも **同じ userId**
- プロバイダーが異なれば、同じ人でも **別の userId**
- **プロバイダーは後から変更できない**

つまり userId を維持できるかどうかは「認証済みか」ではなく「同じプロバイダーのままか」で決まる。

### 「認証済みでないアカウントでもユーザー情報を取得できるか」→ 取得可否は認証状態で変わらない

未認証（グリーンバッジなし）でも Messaging API は使える。認証状態が効くのは、LINEアプリ内検索での表示、プレミアムID、一部の広告メニューなど。友だち情報の取得可否そのものは変わらない。

---

## 1. 2つの選択肢

### (A) 既存アカウントはそのまま、配信システムだけ自社に切り替える

各店舗のLINE公式アカウントには一切触らず、Messaging API の **Webhook URL の向き先を自社システムに変更**し、チャネルアクセストークンを自社側に登録する。

| 項目 | 結果 |
|---|---|
| 既存の友だち | **全員そのまま維持** |
| userId | **維持**（同じチャネル・同じプロバイダーのため） |
| 既存顧客への通知 | **継続できる** |
| ブロック状態 | 維持 |
| 過去のトーク履歴 | LINE公式アカウントマネージャー側には残る。自社DBには切替時点以降のみ蓄積 |
| 店舗側の作業 | LINE Developers でチャネル作成・トークン発行・Webhook設定（1店舗あたり10〜15分程度） |

**注意点**

- 既存で別のツール（Lステップ等）を使っている店舗は、そのツールが設定している Webhook URL を上書きすることになる。**切替の瞬間に旧ツールへの配信が止まる**ため、店舗ごとに切替日時の合意が要る。
- Webhook URL は1チャネルに1つしか設定できない。並行稼働はできない。
- 過去のトーク履歴・タグ・シナリオは引き継がれない。必要なら旧ツールからのエクスポートを別途行う。

### (B) 新しいLINE公式アカウントへ引っ越す

| 項目 | 結果 |
|---|---|
| 既存の友だち | **ゼロから** |
| userId | 変わる（別チャネル・別プロバイダーになるため） |
| 既存顧客への通知 | **できない**。新アカウントを友だち追加してもらう必要がある |

400店舗規模でこれを選ぶ理由は、現実的にはほぼない。既存アカウントが使えない事情（アカウントの所有権が店舗ではなく代理店にある、BANされている等）がある場合の最終手段。

---

## 2. 400店舗規模での作業量

(A) を選んだ場合の試算。

| 作業 | 単位 | 400店舗 |
|---|---|---|
| チャネル作成・トークン発行・Webhook設定 | 10〜15分/店 | 67〜100時間 |
| 店舗への説明・切替日時の調整 | 15分/店 | 100時間 |
| 切替後の疎通確認 | 5分/店 | 33時間 |

**削減できるところ**

- 本部が各店舗のLINE公式アカウントの管理権限を持っているなら、店舗との調整は不要になり、作業は本部側で完結する（**ここが最大の分岐**）
- チャネル設定は LINE Developers のコンソール作業で、API では自動化できない。ただし手順書＋画面録画で店舗側に依頼する形にすれば分散できる
- 疎通確認は自動化できる（テスト送信 → Webhook受信 → 記録 の一連を自社側で回す）

---

## 3. 判断のために先に確認すべきこと

1. **各店舗のLINE公式アカウントの管理権限を、本部が持っているか**
   持っていれば (A) は本部作業だけで完結する。持っていなければ400店舗との個別調整になる。
2. **既存で使っているツールは何か**
   Lステップ等を使っている場合、Webhook を奪う形になるので解約時期との調整が要る。
3. **プロバイダーをどう設計するか**
   400店舗を1プロバイダーにまとめれば、店舗をまたいで同じ人を同じ userId で識別できる。店舗ごとにプロバイダーを分けると、同じ人でも店舗ごとに別人として扱われる。**後から変更できないので、ここは最初に決める必要がある**。
   - 本部で顧客を横断的に見たい → 1プロバイダーに集約
   - 店舗ごとに完全に独立させたい → 店舗ごとにプロバイダー
4. **過去のトーク履歴・タグを引き継ぐ必要があるか**
   必要なら旧ツールのエクスポート仕様を先に確認する。

---

## 4. 推奨

**(A) 既存アカウントのまま配信システムを切り替える、かつ 1プロバイダーに集約。**

理由は3点。

- 400店舗分の友だち資産をそのまま引き継げる。ここを失う選択肢は取りにくい
- userId が維持されるので、既存の顧客データとの突き合わせができる
- 1プロバイダーに集約すれば、本部側で「同じ人が複数店舗を利用している」を検出できる。これは多店舗展開の最大の武器になる

ただし 3-1（管理権限の所在）の答え次第で作業量が桁で変わるため、**そこを確認してから着手するのが安全**。

---

## 5. 予約システム側の制約（あわせて確認済み）

| 項目 | 状況 |
|---|---|
| レストランボードの外部API | **公開されていない**。連携はリクルートのAirシリーズ内に限定 |
| ホットペッパーの公開API | 存在するが**店舗検索API**であり、予約データの取得ではない |
| Googleカレンダー連携で席情報 | **取得できない**。カレンダーは時間枠しか持たず、席・卓の概念がない |
| 現実的な代替 | 各予約サイトから届く**予約確定メールをパース**して取り込む。多くの店舗管理SaaSが採用している方式 |

このため「レストランボードを中心に集約する」構成は現状のままでは成立しにくい。
**自社側に座席在庫を持ち、そこを正とする**設計に寄せたほうが破綻しない。

ダブルブッキングについては、自社側の在庫は完全に守れる。ただし外部サイト側の枠を自動で閉じるにはそのサイトのAPIが必要で、
API非公開のサイトでは「取り込み後に人が閉じる」運用が残る。ここは完全自動にはできない。
