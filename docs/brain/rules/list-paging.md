# 共通一覧契約

## 目的

一覧ごとにページ送り、並び順、絞り込みの意味が変わる事故を防ぐ。新しい一覧 API と、既存 API を改修するときの正本はこの契約とする。

## 1. ページ方式の選択

### offset 方式

- 管理画面の設定一覧など、最大でも数千件程度で、ページ番号へ直接移動する必要がある一覧に使う。
- 要求は `page`（1始まり）と `limit`。サーバー内部の開始位置は `(page - 1) * limit` とする。
- 応答には `total` を含める。画面の総ページ数は `max(1, ceil(total / limit))` とし、0件でも1ページとして扱う。

### cursor 方式

- チャット、写真、配信履歴など、追加が続き、読み込み中にも順序が変わり得る一覧に使う。
- 要求は `cursor` と `limit`。初回は `cursor` を送らない。
- `cursor` はサーバーだけが解釈する URL-safe な不透明文字列とし、画面で分解・生成しない。壊れたカーソルは `400 cursor_invalid` で拒否する。
- 続きがあるときだけ応答に `nextCursor` を含める。末尾は `nextCursor` を省略する。

## 2. 件数

- 新規 API の `limit` は既定 50、上限 200 を基本とする。上限超過は上限へ丸める。
- 空、整数でない値、0以下は既定値へ戻す。
- 既存 route に別の既定値・上限がある場合、この共通化だけを理由に変更しない。route を移行する票で互換性を確認してから変える。

## 3. 並び順と絞り込み

- 並び順はサーバーで固定し、同値時に一意になる列（通常は `id`）まで指定する。
- 応答の `sort` は、適用した順に `{ field, direction: "asc" | "desc" }` を並べる。画面から任意の列名を SQL へ渡さない。
- 絞り込みはサーバーで行い、その後でページを切る。取得した1ページを画面側で再絞り込みして件数やページ数を変えない。
- 絞り込み条件が変わったら、offset は1ページ目、cursor は先頭から読み直す。

## 4. 応答

成功時の一覧データは次の形にそろえる。全体の API envelope（`success` / `data`）を使う route では、この形を `data` に入れる。

```ts
type ListResponse<T> = {
  items: T[]
  total?: number
  nextCursor?: string
  limit: number
  sort: Array<{ field: string; direction: 'asc' | 'desc' }>
}
```

- offset 方式は `total` を必須とし、`nextCursor` を返さない。
- cursor 方式は `nextCursor` を必要なときだけ返し、`total` を数えるための追加クエリは行わない。
- `items` が空でも成功は 200 とし、読み込み失敗と区別する。

## 5. 旧契約の期限

- 既存の `pagination: { ... }` は、既存画面を壊さないため **2026-10-31** まで読み替えを許す。
- 2026-09-08 以降に新設する route は旧形を増やさない。既存 route は個別の移行票で新形へ移し、移行期間中だけ Web 側の境界で読み替える。
- 2026-11-01 以降は旧形を読む互換処理を削除し、この文書の形だけを受け付ける。

## 6. 実装の責任境界

- Worker は入力の正規化、固定並び順、サーバー絞り込み、`items` とページ情報の組み立てを担当する。
- Web は応答済みの `items` を表示し、読み込み中・失敗・0件を共通の `ListState` で言い分ける。
- route 固有の検索条件、認可、カーソルの中身は各 route が担当する。共通ヘルパーは認可や SQL を代行しない。
