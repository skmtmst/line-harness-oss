# Pen.dev V5/V6 画面移行の準備状況と開始チェックリスト

作成日: 2026-08-24

対象: LINE Harness 管理画面

設計の正本: Pen.devを保存している Pencil ファイル `4b332ccf-fe84-4df8-9e23-6554f2bef197/pencil-new.pen`

## 1. 結論

現在は、**画面を選び、その画面で使う部品と機能を先に確認すれば移行を開始できる段階**である。

一方で、**Pen.devのどの画面でも、指示だけで直ちに正確に移せる段階にはまだ達していない**。Pen.devには再利用部品が85件あるが、コード側で設計値・状態・配信まで契約化されているのは4系統である。残り81件をすべて共通化するのではなく、次の3種類に分ける必要がある。

1. 全画面で使う共通部品
2. 複数の機能だけで使う機能群共通部品
3. 1画面・1機能だけで使う専用部品

今後の画面移行は一括で行わない。利用者が「次はダッシュボードのV5」のように対象を指定した後、設計・機能・不足部品・受け入れ条件を1画面ずつ確定し、承認後にその画面だけ実装する。

設計の優先順位は次で固定する。

1. 基本設計はV5
2. 対象画面または対象部品にV6がある場合はV6
3. V6固有の差がない場合はV5の共通部品
4. 見た目が似ていても意味や操作が違う場合は、同じ部品へ無理に統合しない

## 2. 現在の準備状況

### 2-1. 判定

| 段階 | 意味 | 現在 |
|---|---|---|
| レベル0 | 設計の正本や検証方法がなく、画面移行を始められない | 通過済み |
| レベル1 | 対象画面を決め、事前確認を通せば1画面ずつ始められる | **現在地** |
| レベル2 | どの画面を指定されても、共通部品と状態がそろっておりすぐ要件定義へ入れる | 未到達 |

レベル2へ進むには、85件を機械的にコード化するのではなく、全画面共通候補の分類と契約化を終える必要がある。

### 2-2. できていること

| 区分 | 現在の内容 | 証拠 |
|---|---|---|
| 設計トークン | V5/V6で使う変更・追加トークン12件をコードへ反映 | `design-parts.json` で全件 `active` |
| サマリーカード | V5、V6、配信告知の差を名前付きvariantで固定 | `XywGr`、`mNUQ3` ほか |
| 標準ボタン | 主要・副次の寸法、色、型、無効状態を固定 | `nBRKk`、`uzNEC` |
| 表見出し | 見出し行と見出しセルを固定 | `tPTMp` |
| ページ切替 | 前後、ページ番号、現在地、省略規則を固定 | `Blot6` |
| 設計値照合 | ビルド後CSSまで照合 | 12トークン＋69部品宣言＝81件一致 |
| 影響調査 | トークン・部品変更が届くルートと未追跡を報告 | `design:impact` |
| 設計負債ゲート | 直書きが増えた場合や、減少後に基準を締め忘れた場合に失敗 | `design:debt:check` |
| 画像比較ルール | 実ノード、同じ状態、同じ幅で比較する手順がある | `pendev-v4-implementation-runbook.md` |

### 2-3. まだ「視覚一致済み」ではないもの

契約済み4部品は、Pencilの値とビルド後CSSが一致している。ただし、実画面が認証画面へ移動し、同じデータ状態を用意できないため、4部品とも画面全体の `visualVerification` は `unverified` である。

このため、CSS値が一致しただけで「Pen.devどおり」と報告してはいけない。各画面で固定データまたは再現可能な検証状態を用意し、画像比較を行う。

### 2-4. 現在残っている直書き

| 指標 | 現在の基準値 |
|---|---:|
| 任意値記法 | 1,482 |
| 解決できない `className` | 467 |
| 主要ボタン直書き | 154 |
| 副次ボタン直書き | 301 |
| `<th>` 直書き | 303 |

これは「今すぐ全件を置き換える件数」ではない。対象画面の移行時に、Pen.devの部品と意味が一致する箇所だけ減らし、基準値を毎回締め直す。

## 4. 不足している状態の棚卸し

Pen.devの通常画像だけでは、実装に必要な状態が足りない。対象画面で使う状態は、開始前に次から選び、実ノードまたは明文化した仕様を持つ。

### 4-1. 操作状態

- [ ] 通常
- [ ] hover
- [ ] キーボードフォーカス
- [ ] 押下中または選択中
- [ ] 無効
- [ ] 読取専用
- [ ] 処理中・連打防止
- [ ] 成功
- [ ] 入力エラー
- [ ] 処理失敗

### 4-2. データ状態

- [ ] 読込中
- [ ] データ0件
- [ ] 1件
- [ ] 通常件数
- [ ] 最大件数または多数ページ
- [ ] 長い名前・長いURL・大きな数値
- [ ] 一部だけ取得できない
- [ ] 全体を取得できない
- [ ] 権限不足
- [ ] 削除済み・参照先なし

### 4-3. 画面遷移状態

- [ ] 初期表示
- [ ] 検索・絞り込み後
- [ ] 並び替え後
- [ ] ページ切替後
- [ ] モーダル表示
- [ ] ドロワー表示
- [ ] 重要操作の確認
- [ ] 保存後
- [ ] 戻る操作または未保存離脱

### 4-4. 表示幅

- [ ] 1920pxのPen.dev基準画像
- [ ] 1920pxの実装画像
- [ ] 1440pxの実装画像
- [ ] 1440pxと1920pxでページ全体の横スクロールなし
- [ ] 1440pxと1920pxで主要な表の横スクロールなし
- [ ] 短い見出し・名前・ボタンが単語途中で改行されない
- [ ] 省略した値を `title` 等で全文確認できる
- [ ] スマートフォン設計がある場合は、その実ノード・幅・状態も取得

## 5. 未解決ルールと開始への影響

| 未解決 | 影響 | 開始条件 |

未解決事項は、関係しない画面まで止めない。ただし、対象画面で使う場合は「調査中」のまま実装を始めない。

## 6. 画面移行を開始できる条件

以下を**すべて満たした場合だけ**、専用ブランチを作って画面実装を開始する。`未確認`、`たぶん同じ`、`画像は後で撮る` は不合格とする。

### 6-1. 対象の固定

- [ ] 対象ルートとクエリを1画面分に限定した
- [ ] 一覧・作成・編集・詳細のどこまで含むか明記した
- [ ] V6の有無をPencil全体で確認した
- [ ] V6があればV6、なければV5を採用した
- [ ] 画面名ではなく、対象状態ごとの実ノードIDを記録した
- [ ] 対象状態ごとの1920px基準画像を保存した

### 6-2. 機能要件の固定

- [ ] 現在の画面にある表示、操作、API、遷移を列挙した
- [ ] Pen.devにあるが現在のコードにない機能を列挙した
- [ ] 現在のコードにあるがPen.devに見えない機能を列挙した
- [ ] 各差分を「残す・追加する・外す・別画面へ移す・今回は対象外」のどれかに決めた
- [ ] 保存、送信、削除、遡及、外部連携など運用へ影響する操作を分けた
- [ ] 権限、アカウント切替、直接URL、戻る操作の要件を決めた
- [ ] 読込中、空、エラー、長文、最大件数の表示を決めた
- [ ] 足りないAPIや保存先があれば、画面実装と別要件に分けた

### 6-3. 共通部品の固定

- [ ] 対象画面に出る反復要素をすべて一覧にした
- [ ] 各要素を「契約済み共通部品・新しい共通部品・機能群共通部品・画面専用」に分類した
- [ ] 既存部品は、Pen.devと寸法・状態・意味が一致する場合だけ再利用すると確認した
- [ ] 新しい共通部品は画面実装より先に、実ノード・props・状態・設計値・テストを定義した
- [ ] 対象画面が使う `investigations` を0件にした、または承認済みの判断へ変えた
- [ ] 直書きの色、角丸、影、文字サイズを新しく増やさない計画にした
- [ ] 共通部品の変更が他画面へ届く範囲を `design:impact` で確認した

### 6-4. アクセシビリティと表示規則

- [ ] すべての操作にキーボードフォーカスが見える
- [ ] 入力欄にラベル、説明、エラーの関連付けがある
- [ ] モーダル・ドロワーのフォーカス移動、Escape、閉じた後の復帰を決めた
- [ ] 表見出しの `scope`、ボタン名、アイコンだけの操作の説明を決めた
- [ ] 文字と背景のコントラストを確認し、未達はPen.dev判断へ戻した
- [ ] 状態を色だけで伝えない
- [ ] 1440px・1920pxで横スクロールと不自然な改行を出さない設計にした

### 6-5. 実装と検証の合意

- [ ] 実装するルート・状態・部品と、実装しない範囲を明記した
- [ ] 機能テスト、型検査、ビルド、設計照合、負債検査の項目を決めた
- [ ] Pen.dev画像と実装画像を同じ状態・同じ幅で並べる方法を決めた
- [ ] 認証やデータで画像を再現できない場合、固定データの検証ルートを用意する計画にした
- [ ] 差分が残る状態は `unverified` とし、完了扱いしないと確認した
- [ ] 利用者が要件表と受け入れ条件を確認し、実装開始を承認した

## 8. 実装後の完了条件

開始条件を満たしても、次が終わるまで画面移行は完了ではない。

- [ ] Pen.devと同じ構造、文字、位置、寸法、色、余白、枠、角丸、影になっている
- [ ] 対象の通常・読込中・空・エラー・モーダル・ドロワー等をすべて確認した
- [ ] 1920pxでPen.devと実装を横に並べ、差を修正した後の画像を保存した
- [ ] 1440pxで崩れ、横スクロール、単語途中の改行がない
- [ ] 現在残すと決めた機能がすべて動く
- [ ] 新しい共通部品が `design-parts.json` の契約とテストへ入っている
- [ ] 共通部品変更の影響先を確認し、必要な基準画面を撮り直した
- [ ] 設計負債が増えておらず、減った項目は基準値を締め直した
- [ ] 機能テスト、全テスト、型検査、ビルド、設計照合が成功した
- [ ] PRのVisual Parity欄に実ノードと比較証拠、未確認状態を記録した
- [ ] 検証環境で同じ状態を確認した

ダッシュボードを最初の画面にする場合、契約済みのサマリーカードとボタンだけでは不足する。少なくとも、画面枠・カード見出し・通知パネル・プルダウン・編集ドロワー・QRダイアログ・読込中/空/エラー状態を、開始前に設計と機能へ対応付ける。

## 10. 推奨する土台整備の順番

1. 85件を「全画面共通・機能群共通・画面専用」へ分類し、一覧を契約へ追加する
2. 画面枠、正式共通メニュー、パンくず、ページ内タブを契約化する
3. 入力欄、複数行入力、プルダウン、検索を契約化する
4. 読込中、空、失敗、成功、入力不備、通知を契約化する
5. 標準確認、重要操作確認、右詳細パネルを契約化する
6. 一覧行・セル、表示件数、フォルダ、ツールバー、状態バッジを契約化する
7. 対象画面ごとに機能群共通部品を追加する

最初から7までを一度に実装しない。次に選ぶ1画面で必要な1〜6を先に整え、共通基盤の範囲を安全に広げる。

## 11. 証拠と制限

今回確認したもの:

- 現在開いているPencilファイルの再利用部品85件と実ノード名
