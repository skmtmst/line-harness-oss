## 1. 障害時の業務継続

出前館が配布するタブレットのオーダー管理アプリは、出前館のシステムと直接つながっています。
musubo はそこへ割り込まず、**連携したデータを受け取って調理指示・集計に使う側**です。

そのため musubo 側が止まっても、

- 注文の受け付け
- 店舗での受注の確認・承諾
- 配達の手配

はタブレットのアプリでそのまま続けられます。musubo が復旧したあとは、
止まっていた間の通知を出前館から再送してもらえば受信台帳へ取り込めます。
受信台帳は `UNIQUE (service, external_event_id)` で重複を弾くため、
**同じ通知が二重に届いても注文は増えません**（§10 の「再送」の行が実測値）。

                      └───────┬──────────────▲───────┘
                              ▼              │

Cloudflare Workers はリクエストごとに自動で並列実行される実行環境です。
musubo 側に常時起動のサーバ・ロードバランサ・台数の事前確保はありません（§6）。

### 注文を受け取るときの流れ

```
出前館            中継サーバ        musubo（Workers）          D1
  │                   │                    │                   │
  │ ① 注文の通知 ─────▶                    │                   │
  │                   │ ② そのまま転送 ────▶                   │
  │                   │                    │ ③ 送信元IPの照合  │
  │                   │                    │    （本文を読む前）│
  │                   │                    │ ④ 署名の検証       │
  │                   │                    │    HMAC-SHA256     │
  │                   │                    │ ⑤ 時刻ずれ5分以内  │
  │                   │                    │ ⑥ 受信台帳へ記録 ─▶ rt_delivery_events
  │                   │                    │    （重複はここで弾く）
  │                   │                    │ ⑦ 注文の取り込み ─▶ rt_delivery_orders
  │                   │                    │                    rt_delivery_order_items
  │                   │                    │ ⑧ 受信台帳を締める ▶
  │ ⑨ 200 を返す ◀────────────────────────┤                   │
  │                   │                    │                   │
```

**③〜⑧の中で外部サービスへ接続しません。** 応答時間が相手の都合で伸びない作りです（§10）。

守りは4つで、
1. 送信元IPの許可リスト（§7。設定されているときだけ）
2. サービスごとの合言葉による HMAC-SHA256 の署名検証
3. 5分の時刻ずれ制限
4. 受信台帳 `rt_delivery_events` の `UNIQUE (service, external_event_id)` による重複排除

署名が合わない通知は**本文を保存しません**。

### 店舗が操作するときの流れ

```
店舗の担当者     管理画面        musubo（Workers）      D1                中継     出前館
  │                 │                  │                │                 │        │
  │ ① 承諾を押す ───▶                  │                │                 │        │
  │                 │ ② API ──────────▶                │                 │        │
  │                 │                  │ ③ 注文の状態を更新 ▶ rt_delivery_orders  │
  │                 │                  │ ④ 送信の台帳へ ──▶ rt_delivery_dispatches│
  │                 │                  │ ⑤ 出前館へ送信 ────────────────▶────────▶
  │                 │                  │ ⑥ 結果を台帳へ ──▶ （符号だけ。本文は残さない）
  │                 │ ⑦ 結果 ◀─────────┤                │                 │        │
  │ ⑧ 画面が変わる ◀─┤                 │                │                 │        │
```

失敗したときは `rt_delivery_dispatches.status` を `failed` / `retryable_failed` / `exhausted` にし、
分類済みの符号（`error_code`）だけを残します。サービスから返った自由文・本文・例外は保存しません。
この失敗は §3 の監視が拾います。

## 3. エラーの監視

### 仕組み

管理画面の **設定 ＞ 緊急時 ＞ 稼働確認** にある「API・外部連携」の確認に、
デリバリー連携の3つの信号を畳んでいます。

| 信号 | 見ているもの | 範囲 |
| --- | --- | --- |
| 連携の切断・エラー | `rt_delivery_service_states.connection_status` が `error` | 現在の状態 |
| 送信の失敗 | `rt_delivery_dispatches.status` が `failed` / `retryable_failed` / `exhausted` | 直近1時間 |
| 受信の取り込み失敗 | `rt_delivery_events.status` が `failed` / `retryable_failed` | 直近1時間 |

- しきい値は **1件で注意、3件で危険**。
- 送信が `exhausted`（再試行を使い切った）まで進んだものは**重み3**として数え、1件でも危険へ上げます。
- サービスをまたいだ件数は `COUNT(DISTINCT service)` で数えるため、
  1サービスの連続失敗で他サービスの異常が埋もれません。
- 集計が落ちても確認そのものを `unknown` にしないよう、
  この集計だけを try/catch で囲み、失敗時は 0 件として他の外部連携（Webhook・Google Sheets）の判定を守ります。

実装：`apps/worker/src/services/operations-health.ts`（`deliveryIntegrationFailures`）
試験：`apps/worker/src/routes/operations.test.ts`「デリバリー連携のエラー監視（出前館QA#3）」12件

## 4. 障害時の連絡体制

**回答：はい。**

原因の切り分けの**手順**は用意があります（上のログの印、`rt_delivery_events` / `rt_delivery_dispatches`
の台帳、稼働確認の画面）。

連絡の受付体制は 2026-10-15 に運用担当が次のとおり決めました。

| 項目 | 内容 |
| --- | --- |
| 受付の手段 | メール（障害・仕様変更の連絡先として1つのアドレスを申請時に登録） |
| 受付日 | **365日**（土日祝日を含む） |
| 受付時間 | 24時間（受信は常時。返事は下の目安時間） |
| 一次返答の目安 | **9時〜21時は1時間以内**。それ以外の時間に届いた分は**翌朝**に一次返答 |
| 緊急電話 | 出前館へは渡しません（連絡はメールに集約） |

- 一次返答とは「受け取ったこと」と「切り分けの着手状況」の返事です。復旧の完了時刻の約束ではありません。
- 具体的な連絡先アドレスは、手順2「連携希望の連絡」のときに出前館へ届け出ます。
  この文書には書きません（公開リポジトリのため）。
- 当番は現在1名体制です。増えた場合はこの表を更新します。

## 5. 通信の暗号化

musubo は Cloudflare Workers 上で動き、公開ドメイン `api.musubo.jp` は Cloudflare 管理のTLSです。

- **受信（出前館 → musubo）**：Cloudflare は 2024年3月に全プランで TLS1.0 / 1.1 を廃止済みで、
  受け付けるのは **TLS1.2 以上**だけです。
- **送信（musubo → 出前館）**：Workers の `fetch` は TLS1.2 以上で接続します。
  接続先URLは `https://` のみ受け付け、`http://` は設定の読み取り段階で弾きます
  （`apps/worker/src/services/restaurant-delivery.ts` の `apiConfigFor`）。

## 6. 負荷への耐性と許容範囲

Cloudflare Workers は**リクエストごとに自動で並列実行**されます。
musubo 側で台数を見積もって事前に確保する必要がなく、瞬間的に増えた通知もそのまま並列で処理されます。
データの置き場（Cloudflare D1・R2）も同じ仕組みの上にあります。

### 備考欄に書く許容範囲

**1000 リクエスト/分**（1サービスあたり）

これは musubo 側で意図的に掛けている上限です。
`apps/worker/src/middleware/rate-limit.ts` の `AUTHENTICATED_MAX = 1000` / `AUTHENTICATED_WINDOW = 60_000`（60秒）。
上限を超えた分は 429 を返し、`Retry-After` で再送の時刻を伝えます。

この数字で足りるかは、出前館側の1店舗あたりのピーク通知数を伺って決めます。
足りない場合は設定値の引き上げで対応できます（作り直しは不要）。

## 7. 送信元IPによる制限

**できます。実装済みです。**

- 照合は**本文を読む前**に行い、許可していない送信元には 403 を返します。
  （本文のサイズ確認・署名の検証・台帳への記録はすべてこのあと）
- 設定は Worker の環境変数（秘密値ではないので値はここに書きません）。

| 環境変数 | 効く範囲 |
| --- | --- |
| `RT_DELIVERY_WEBHOOK_IP_ALLOWLIST` | 全サービス共通 |
| `RT_DELIVERY_DEMAECAN_WEBHOOK_IP_ALLOWLIST` | 出前館のみ（共通より優先。共通とは混ぜない） |

- 書き方は読点区切り。**IPv4 はまとまり指定（CIDR、例 `203.0.113.0/24`）**に対応、
  **IPv6 は1件ずつの指定**に対応します。
- 書き間違いの行はその行だけ飛ばし、他の行の判断を壊しません。
- 空欄・読点だけのときは「誰も通さない」にせず**制限なし**へ戻します。
  設定の書き損じで連携が全部止まるのを避けるためです。
- **未設定のときは制限しません。** 出前館から送信元IPを教えていただいた時点で設定します
  （コードの変更は不要）。

実装：`apps/worker/src/services/restaurant-delivery.ts`

## 9. データの利用目的

出前館から連携したデータ（注文情報等）は、**調理・配送・集計の3つの目的にだけ使います。**

- 広告・宣伝のための利用、第三者への提供・販売はしません。
- 店舗をまたいだデータの混在が起きないよう、受信台帳・注文・送信台帳・連携状態の
  **4つのテーブルすべてに契約者の識別子（`account_id`）を必須の列として持たせ**、
  読み取りは必ずこの列で絞り込みます。
- 送信の失敗記録には分類済みの符号だけを残し、サービスから返った本文は保存しません。
- 署名が合わない通知の本文は保存しません。

## 10. 応答時間

**1秒以内に応答できます。**

### 構造上の根拠

受信口は**応答を返す前に外部サービスへ接続しません**。
受け取って、署名を確かめ、台帳へ記録して、取り込んで、すぐ返します（§2 のシーケンス③〜⑨）。
応答時間が出前館以外の相手の都合で伸びることがありません。
この「外へ繋ぎに行かない」ことは試験で固定しています
（`expect(deliveryCalls).toHaveLength(0)`）。

再送された通知は受信台帳の重複排除で止まり、取り込みへ進みません。
出前館側の再送が重なっても応答は速いままです。

### 手元での実測値

同じコードを手元の SQLite に当て、**受信口に入ってから応答を返すまで**を計測しました。
署名を作るのは出前館側の仕事なので、要求は計測の前に組み立て終えています。

| 測ったもの | 件数 | 中央値 | 95% | 最大 |
| --- | --- | --- | --- | --- |
| 注文の取り込み | 20 | 0.1ms | 0.2ms | **0.3ms** |
| 注文の取り込み（品数が上限の100品） | 5 | 0.9ms | 1.1ms | **1.1ms** |
| キャンセルの取り込み | 20 | 0.1ms | 0.2ms | **0.4ms** |
| 再送された通知 | 20 | 0.1ms | 0.1ms | **0.3ms** |

約束の 1000ms に対して、最も重い「100品の注文」でも **1.1ms**。桁が3つ違います。

試験：`apps/worker/src/routes/restaurant-delivery.test.ts`「受信口の応答時間（出前館QA#10）」5件
（計測値は試験の実行ログに `[QA#10]` の印で出ます）

### この数字の読み方

**回線の往復と、遠隔のデータベース（D1）の呼び出しを含みません。**
配備した環境ではここに通信の時間が乗ります。上の数字は**下限**として読んでください。

1秒の約束を守れる根拠は数字そのものではなく、

1. 応答の前に外部サービスへ接続しない作り
2. 再送は台帳の重複排除で即返す作り

の2点です。配備後、検証環境（§8）での通信テストで実際の往復を含めて測り直し、
この節へ追記します。

## 11. Log4j

**使っていません。** 該当なし（CVE-2021-44228 の影響を受けません）。

musubo は TypeScript で書かれ、Cloudflare Workers（JavaScript の実行環境）で動きます。
**Java を使っていません。** リポジトリに `.java` のファイルは1つもなく、
Log4j への依存もありません。ログは Workers の標準の出力（`console`）を使います。

## 12. 送信の国

**日本です。**（※ 中継サーバの構築待ち）

Cloudflare Workers は世界中の拠点で動くため、**標準の構成では送信元の国を固定できません**
（国の固定は Enterprise 契約の Regional Services ＋ 専用の送信元IPの追加契約が必要です）。

そこで、**日本国内の中継サーバ（さくらのVPS等）を1台立て、出前館との通信をそこに通します。**
送信元の国は日本に固定されます。

musubo 側の作りは**接続先URLの差し替えだけ**で対応できる状態です。

- 接続先は環境変数 `RT_DELIVERY_DEMAECAN_API_BASE_URL` から読みます。
- `https://` のみ受け付け、末尾の斜線は重ねません。
- 中継サーバが立ったら、この環境変数を中継サーバの宛先へ向けます。
  **コードの変更もデータベースの変更も不要です。**

実装：`apps/worker/src/services/restaurant-delivery.ts`（`apiConfigFor`）

中継サーバの契約・構築は未着手です（利用者の予定）。
構築が済んだ時点で、サーバの所在地・固定IP・疎通の確認結果をこの節へ追記します。

## 13. 送信元IPの固定

**できます。**（※ §12 と同じ中継サーバの構築待ち）

§12 の中継サーバに割り当てた固定IPが、出前館から見た musubo の送信元IPになります。
Cloudflare Workers から中継サーバまでの経路は musubo の内側なので、
出前館へ届くリクエストは**常にその1つのIPから出ます**。

出前館側で送信元IPの登録が必要な場合は、中継サーバの構築後にそのIPをお伝えします。
