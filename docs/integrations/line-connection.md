# LINE公式アカウントの接続と確認

利用者向けの操作は[登録の手引き](../line-account-register.md)、画面の動きは[アカウント追加の説明](../../apps/web/src/v8/account-new/BEHAVIOR.md)を読む。見た目は承認済みの②とV8の決まりに従う。この文書はAPIの役割と残る確認の説明であり、配備済み・実環境合格の宣言ではない。

## 接続の入口

`POST /api/line-accounts/connect/check` はDBへ本登録する前の確認。**LINE側のWebhook登録、LIFFの作成・更新を伴う**ので、読むだけの検査として実行しない。本登録は `POST /api/line-accounts/connect`。既存IDの再開・保存版・二重登録の扱いを保ち、失敗や結果不明を成功扱いしない。

Messaging APIとLINEログインは同じプロバイダーのチャネルを使う。チャネルアクセストークンでボット情報・Webhook URLを確認する。プロバイダーの一致、Webhookの利用、LINEログインの公開と公式アカウントへのリンクなど、利用者がLINE Developersで確認する設定をトークンの発行成功だけで済にしない。秘密値は記録へ載せない。

## ②Step2と③接続確認の役割

②のStep2では、利用者が画面に表示されたWebhook URLをLINE Developersの「Messaging API設定」へ貼り付けて「更新」を押す。その後、Webhookの利用・再送・エラーの統計情報をオンにする。URLの貼り付けと3つの設定の計4項目を確認するまで、次へ進めない。承認済みv07（PR #1775）の画面は読み取り専用のURLとコピーボタンを備え、URLはAPIから取得する。未取得を推測したURLで埋めない。

③の接続確認では、musuboがWebhook URLを登録し直し、URLの一致と有効状態を読み直す。②の手作業と③の自動確認は別の段であり、両方を保つ。接続確認にはLINEへの書き込みがあるので、表示だけの点検で実行しない。過去のv06の「URLの入力は不要」「確認は3項目」という案内を現在の手順へ戻さない。

承認済みv07のURL枠は、共通Cardに縦横の余白を別々に渡して表示する（PR #1776）。余白をひとつのCSS変数へまとめて渡した旧形へ戻さない。枠の確認は実際の描画と共通Cardの動きで行う。

## 実装の入口

- 画面は `apps/web/src/v8/account-new/`。入口は `apps/web/src/app/accounts/new/page.tsx`。②は `step2-connect.tsx`。
- Workerの登録は `apps/worker/src/routes/line-accounts.ts`、接続の準備は `apps/worker/src/services/line-account-connect.ts`。
- 友だちの引き継ぎは `apps/worker/src/services/follower-import.ts` と同名の機能モジュール。先に保存した同じアカウントと進行を使い、古い実行者が新しい進行やプロフィールを上書きしない。
- LINE側が取り込みを許可しない場合は、その状態を表示する。403を友だち0人や取り込み成功へ読み替えない。途中再開の手元試験と、大量の実データでの確認を分ける。

## 登録できる役割（PR #1777）

登録・接続確認は現在の要件とAPIでオーナーだけが行う。管理者・閲覧のみには登録の手順を出さず、オーナーへ頼む案内と一覧へ戻る道を出す。登録一覧でも非オーナーに登録の入口を出さない。「並び順と親子を変える」など管理者に認められた操作は保つ。403の案内は、本人へ「管理者に頼む」と返さず「オーナーに頼む」にそろえる。

統合版では役割が未取得の間は読込み表示にし、下書き復元・接続確認・保存を起動しない。権限が確定する前のフォーム起動を避ける守りを維持した。サーバーの権限を広げていない。管理者への個別の鍵の付与・管理者全員への開放は、要件の変更が先であり、この整理では行わない。

PR #1777の引き継ぎにある特定の利用者のownerへの役割変更は、別の運用作業として扱う。F01では検証・本番のDB、アカウント権限、配備を変更しない。本番の接続確認・登録も実行しない。
