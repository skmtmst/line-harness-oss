# Lステップのリマインダ配信 — 実機調査と実装との差分

2026-08-20。`docs/lstep-scenario-research.md` と同じ形で、Lステップのリマインダ配信と
うちの `/reminders` を突き合わせる記録です。

この文書の目的は、**Lステップができることを正確に書き出し、うちの実装と突き合わせること**です。

**出どころ**：1. と 2.（Lステップ側）は一斉配信担当が本番アカウント（meauty渋谷店）で
読み取ったものです。読み取りのみで、登録・削除・送信はしていません。
3.（うちの実装）はこのセッションがコードを読んで書きました。

**既存の `lstep-feature-parity-matrix.md` と `lstep-gap-analysis.md` は当てにしていません。**
自動応答で「無い」と書かれていたものの半分が実装済みだったためです。実装を読んで書いています。

**分類の決めごと**（利用者の方針、2026-08-20）：

| 印 | 意味 |
| --- | --- |
| **残す** | こちらにあって、Lステップに無いもの。**消さない。画面から見えなくするのも消すに入る** |
| **足す** | Lステップにあって、こちらに無いもの |
| **寄せる** | 両方にあるが、Lステップのほうが良いもの（理由を書く） |
| **直す** | 壊れているもの |

画面そのものは作り変えてよい、というのが利用者の判断です。

## 1. Lステップの登録画面（`/line/episode/edit/new`）

```

フォルダ       [任意]  未分類 / 新規フォルダ
配信方式       [必須]  ○ 時刻で指定
                      ○ ゴール日時までの残り時間で指定
```

**通（ステップ）の編集画面は見ていません。** 登録しないと開けず、本番アカウントへの
書き込みになるためです。**「Lステップに無い」と書いた項目は、通の編集画面にある可能性が
残ります。**断定しないでください。

## 3. こちらとの差

### 3-1. 残す（こちらにあって、Lステップの登録画面には無い）

**消さないでください。**画面を作り変えるときも、入口を残してください。

| もの | 場所 | 補足 |
| --- | --- | --- |
| 予約が確定したときの自動登録 | `services/reminder-trigger.ts` | Lステップは「呼び出す側」が登録する作り。こちらは予約から自動で入る |
| イベント申込での自動登録 | 同上 | |
| 起点の時刻をずらす | `reminders.trigger_offset_minutes` | 施術後の追客など、終了時刻へ寄せるために使う |
| 送る時刻を固定する | `reminders.send_at_time` | 「予約が何時でも前日18時」を作れる。`resolveAnchor()` がJSTで日付を切る |
| タグで対象を絞る | `reminders.target_tag_id` | `enrollByTrigger()` が `friend_tags` を見る |
| 二重送信よけ | `friend_reminder_deliveries` の UNIQUE ＋ `INSERT OR IGNORE` | 落ちたときに黙って消えるより、重複を選ぶ作り |
| ブロック中の人を飛ばす | `reminder-delivery.ts`（`is_following`） | |
| 送信ログ | `messages_log` の `source='reminder'` | |
| KPI 4枚 | `/api/list-stats` | 件数・配信待ち・稼働中・今月の配信 |
| 手で1人を登録する | 友だち詳細 `single-friend-actions.tsx` | **壊れています（3-4 (a)）。機能としては残し、直す** |
| 名前での絞り込み | `/reminders` の検索欄 | Lステップにも検索があるので、これは同等 |

### 3-2. 足す（Lステップにあって、こちらに無い）

| もの | いま | 必要なもの |
| --- | --- | --- |
| フォルダ | 列が無い | `reminders.folder_id`。`folders` の `kind` には `reminder` が既にある。`folder-add-dialog.tsx` と `folder-panel.tsx` をそのまま使える |
| 並び替え | 列が無い。`created_at DESC` 固定 | 並び順の列 |
| 一覧の「配信方式」列 | 出していない | 3-3 の配信方式が入れば出せる |
| 一覧の「登録日」列 | カードに小さく出ている | 表にするなら列として |

`/reminders` の「フォルダを追加」「並び替え」は**押せない状態で置かれています**。
`ListToolbar` に渡しているフォルダ名 `['すべて','01_誕生日','02_定期便','未分類']` は
**べた書き**で、実データではありません。作り変えるときに落としてください。

### 3-3. 寄せる（Lステップのほうが良い）

**配信方式を最初に選ばせ、作成後は変えられない。**

Lステップは登録画面の3つ目で、**時刻で指定** と **ゴール日時までの残り時間で指定** の
どちらかを選ばせ、あとから変えられません。

こちらは `reminder_steps.offset_minutes`（分）しかありません。これだと運用者が
「3日前の10時に送る」と考えたときに、**ゴールの時刻ごとに違う数字を入れることになります。**

- ゴールが 15:00 なら `-4620`（3日と4時間30分前）
- ゴールが 10:00 なら `-4320`（ちょうど3日前）

同じ「3日前の10時」なのに、予約ごとに数字が変わります。Lステップが2つを**別の方式として
分けている**のは、混ぜると意味が変わるからです。こちらの `send_at_time`（送る時刻の固定）は
「時刻で指定」に近いものですが、**リマインダ全体に1つ**しか持てず、通ごとには決められません。

寄せ方の案：`reminders` に配信方式の列を持ち、`reminder_steps` の意味を方式で切り替える。
方式は作成後に変えられないようにする（変えると既存の通の意味が変わるため）。

**それと、一覧を表にする。** こちらはカードの格子で、開くとステップが出る作りです。
Lステップは表で、列は リマインダ名 / 配信方式 / 登録日。フォルダの縦パネルと合わせて、
共通情報・一斉配信と同じ形にそろえられます。

### 3-4. 直す（壊れている）

**(a) 友だち詳細の「リマインダを開始する」が通らない**

`api.reminders.enroll()` は本文なしで POST しますが、worker は `targetDate` を必須にしています。
本文が空なので `c.req.json()` の時点で落ちて **500** になります（400 ですらありません）。
一斉配信担当がコードで確認済みです。

**手動のリマインダは、画面からは一度も登録できていないはずです。**
起点の日時を画面から選ばせる欄ごと要ります。

**(b) 差し込みが効かない**

作成画面は「`{{name}}` や `{{予約日時}}` は一人ひとりの内容へ置き換わります」と書いていますが、
`reminder-delivery.ts` は本文をそのまま `pushMessage` に渡しています。

差し込みを通しているのは `step-delivery.ts`（シナリオ）・`broadcast.ts`（一斉配信）・
`auto-reply.ts`（自動応答）の3つで、**リマインダだけ通っていません。**
`{{name}}` が文字のまま届きます。一斉配信担当がコードで確認済みで、
**一斉配信でまったく同じものを今日直しています**（そのやり方をそのまま使えます）。

**(c) 「友だち情報欄の日付を起点にできます」が嘘になっている**

`/reminders` の説明文はこうです。

> ゴール日時までのカウントダウン配信を作ります。誕生日や次回お届け日など、
> 友だち情報欄の日付を起点にできます。

`trigger_type` は `manual` / `booking` / `event` の3つだけで、**その経路はありません。**
誕生日リマインダは作れません。

**利用者の判断は「説明文を実装に合わせるのではなく、実装のほうを作る」です。**
友だち情報欄の日付を起点にできるようにしてください。

**(d) 作成の入口が2つあって、作った結果が違う**

`/reminders` のカード内フォームと `/reminders/new` が、それぞれ別にリマインダを作ります。
項目も違います（前者は `triggerOffsetMinutes` を出し、後者は出さない代わりに1通目の本文を受ける）。
どちらから作ったかで中身が変わります。

**(e) 送れるのが text / image / flex の3種別だけ**

`reminder_steps.message_type` の CHECK が3つに縛られています。シナリオと一斉配信は
`services/line-message.ts` で8種別（テキスト・画像・動画・音声・スタンプ・位置情報・
カルーセル・Flex）を組み立てていますが、**リマインダはこれを使わず `buildMessage()` を
自前で持っています。**

寄せるなら `line-message.ts` に一本化するのが筋です。CHECK 制約の書き換え＝
表の作り直し（マイグレーション）が要ります。

**(f) デザイントークンに乗っていない**

`/reminders/page.tsx` は `bg-white`・`border-gray-200`・`text-red-600`・`bg-blue-100` などの
生の Tailwind が全面に残っています。`design-tokens.test.ts` は「自分たちの色が定義どおりの
名前で書かれているか」を見るもので、生の Tailwind を禁じてはいないため試験は通ります。
`/reminders/new/page.tsx` は `CreatePage` 経由でトークンに乗っています。

画面を作り変えるので、ここは自然に解消します。

## 4. 表の作り（いまの状態）

`packages/db/migrations/002_round3.sql` で作られた4つ。**v0.2 のころのまま、
ほとんど手が入っていません。**

| 表 | 中身 |
| --- | --- |
| `reminders` | 名前・説明・稼働。あとから `trigger_type` / `trigger_offset_minutes` / `send_at_time` / `target_tag_id` が足されている。**フォルダの列も並び順の列も無い** |

## 5. 順番の提案

判断は利用者に委ねますが、読んだ側の見立てを書きます。

1. **(b) 差し込み** を最初に直す。ここが通っていないと、種別を増やしても届くものは変わらない。
   一斉配信で今日直したものをそのまま持ってこられる
2. **(a) 手動登録** を直す。起点の日時を選ばせる欄を足す。いま画面から使えない機能が1つ消えている状態
3. **配信方式（3-3）** を入れる。表の列が増えるので、フォルダ・並び順の列も一緒に足すと
   マイグレーションが1回で済む
4. **画面の作り変え**（表＋フォルダの縦パネル、入口を1つに、トークンへ）
5. **(c) 友だち情報欄の日付を起点に**
6. **(e) 種別を8つに**（CHECK の書き換えなので、3. と同じ回にまとめられるなら一緒に）

**注意**：1. と 2. の壊れているものを、画面の作り変えより先に直してください。
先に画面を作り変えると、壊れたまま新しい画面に載ります。
