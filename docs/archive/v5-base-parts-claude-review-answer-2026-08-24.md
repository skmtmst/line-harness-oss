## 2. 5つの確認事項への回答

### 2-1. 共通部品はCSSモジュールにする → **採用（賛成）**

懸念された優先順位の不安定さは起きない。理由は実測で確認した。

ビルド後のCSSを調べると、**Tailwind v4 はすべてのユーティリティを
`@layer utilities` の中に出力している**（`.px-4` が層の範囲 13253〜106458 の
内側にあることを確認）。一方CSSモジュールは層に属さない。

CSSカスケード仕様では、**層に属さないスタイルは層に属するスタイルよりつねに強い**。
これはファイルの読み込み順に依存しない。したがって:

- 部品が持つプロパティは、呼び出し側のTailwindユーティリティで上書きできない
- この保証はビルドのチャンク分割順に左右されない

**Codexの 3-1 の懸念は解消される。** さらに、提案Bが求める「部品の自由度を制限する」
の一部は、追加の仕組みなしでカスケードが自動で守っている。

#### ただし、その裏返しの実害がある（§3-a）

部品が設定しているプロパティは、**呼び出し側から黙って効かなくなる**。

| 呼び出し | 意図 | 実際 |
|---|---|---|
| `className="w-full"` | 幅を広げる | **効く**（部品は `width` を持たない） |
| `className="mt-4"` | 外側余白 | **効く**（部品は `margin` を持たない） |
| `className="px-8"` | 内側余白を変える | 効かない（安全側・意図どおり） |
| `className="hidden"` | **条件付きで隠す** | **効かない**（`display: inline-flex` に負ける） |

最後の1件は実害。`hidden` や `lg:inline-flex` のような表示制御は正当な用途なのに、
エラーも警告も出ずに無視される。**投入前に対策が要る。**

#### 呼び出し側へ許可する境界について

提案Bに賛成。ただしカスケードが既に守っている部分と、まだ守れていない部分を分ける。

- **カスケードが守る**: 高さ、内側余白、色、角丸、影、文字（部品が宣言済み）
- **守れていない**: `display` の上書きが効かない問題、`className` に何を渡してよいかの明示

対策案は §5-1。

#### このリポジトリ内により適した既存方式があるか

`components/friend-attributes-v3/friend-attributes-v3-static.module.css` が唯一の
CSSモジュール前例。ただしこれは **ローカル変数 `--v3-accent: #08c654` を持っており**、
Pencil（`#06c755`）とも `globals.css`（`#06c755`）とも違う3つ目の色系統になっていた。

**技術の選択ではズレは止まらない**という証拠なので、これを手本にしてはいけない。
止めるのは契約テストのほう。

### 2-2. トークン値をPencil V5へ合わせる → **採用（賛成）**

コントラストを実測した。結果は「1つを除いて改善」。

| トークン | 地 | 変更前 | 変更後 | 判定 |
|---|---|---:|---:|---|
| `ink` 本文 | 白 | 17.14 | 16.83 | 微減。AA余裕 |
| `ink-secondary` 補足 | 白 | 6.61 | **7.56** | 改善 |
| `ink-faint` ラベル | 白 | **3.16** | **4.55** | **AA不可 → AA可** |

`ink-faint` は変更前が 3.16 で **WCAG AA（4.5）を満たしていなかった**。
今回の変更で 4.55 になり、初めてAAを満たす。読みにくくなる方向の変更ではない。

#### ただし1点、設計側の問題が見つかった

`ink-faint` を**白以外の地**に置くと、変更後もAAを下回る。

| 地 | 変更後の比 | AA(4.5) |
|---|---:|---|
| 白 `#ffffff` | 4.55 | 可 |
| 沈み面 `#f7f7f5` | 4.24 | **不可** |
| 表見出し `#fafafc` | 4.36 | **不可** |
| 緑 `#e8f8ee` | 4.13 | **不可** |

**Pencil V5 の表見出しセル `tPTMp` は、まさにこの組み合わせ**
（`$ink-faint` の文字を `$surface-pearl` の地に置く）で、12pxなので
「大きい文字」の例外も使えない。**設計そのものがAA未達。**

これはコード側の判断で変えるべきものではない。§4-3 でPencil側の判断項目に挙げる。

#### 分離すべき互換トークンがあるか

**不要と判断する。** 変更する4つはいずれも「本文・補足・ラベル・枠線」という
役割が明確で、意味が変わる使われ方は見つからなかった。互換トークンを作ると、
旧値が残る口実になり、提案Eの「旧基盤の出口」と矛盾する。

### 2-3. 表見出しから `uppercase` / `tracking-wider` を外す → **採用（賛成）**

実測した。**移行済みの見出し30種のうち、英字を含むものは0件。** 日本語見出しに
`uppercase` は効かないので、移行済み範囲では**見た目が1文字も変わらない**。

未移行分で `uppercase` が付いている見出しの文字列は5種。

| 文字列 | 外した場合 |
|---|---|
| `CV` `CVポイント` `URL` `エンドポイントURL` | 元から大文字。**変化なし** |
| `template` | **"TEMPLATE" → "template" に変わる** |

`template` の1件だけが実際に変わる。Codexの方針（英字表記はCSS変換ではなく
文字列自体で指定する）に従い、**移行時にソースを `TEMPLATE` に直す**のが正しい対応。

列幅への影響: `tracking-wider` は字間 0.05em。`CV` `URL` など2〜3文字の英字見出しで
数px縮むだけで、列幅は内容側で決まるため悪影響はない。日本語見出しは元から無影響。

### 2-4. `XywGr` と `mNUQ3` を統合する → **条件付き採用。ただし前提が不正確**

引き渡し書は「現在の差はラベル色、余白など」としているが、Pencilの実ノードを
読むと**3行目が色・大きさ・太さの3つとも違い、意味も違う**。

| | `XywGr` 共通サマリーカード | `mNUQ3` 配信KPIカード |
|---|---|---|
| 高さ | 100 固定 | `fill_container` |
| 余白 | `[14, 16]` | `18`（全周） |
| 並べ方 | `space_between` | `gap: 8` |
| ラベル色 | `$ink-secondary` | `$ink-faint` |
| 値 | `$ink` / 22px / 700 | **同じ** |
| 3行目 色 | `$ink-faint` | **`$accent`（緑）** |
| 3行目 大きさ | `$size-micro`(11) | **`$size-caption`(12)** |
| 3行目 太さ | normal | **500** |
| 3行目 内容 | 「総友だち 231人」＝説明 | 「本日 3件配信予定」＝**予定の告知** |
| バッジ | あり | なし |

3行目は、片方が「今の数の内訳」、もう片方が「これから起きること」で、
**役割が違う**。単に色が違うのではない。

#### 回答

- **統合には賛成。** ただし「完全に同じ見た目へ統一」は不可。3行目の意味が失われる
- **自由なvariantは作らない。** 名前付きで固定する。例: `tone="muted" | "accent"`。
  `muted` が `XywGr`、`accent` が `mNUQ3` の3行目に対応する
- ラベル色・余白・高さ・並べ方は `XywGr` に寄せる（差を残す理由が見つからない）
- Pencil側は **`mNUQ3` を削除ではなく「`XywGr` の状態違い」として定義し直す**のが妥当。
  削除すると配信12箇所の3行目の意味が記録から消える

#### 報告されていない3系統目がある

`app/emergency/page.tsx:121` に**ローカル定義の `SummaryCard`** がある。

```
function SummaryCard({ label, value, note }: { label: string; value: string; note: string })
```

- 値が **文字列**（"通常運用"、"最新結果"）。共通部品の `value: number | null` では受けられない
- **名前が共通部品と衝突している**。同じ名前のものが2つある

これは 3-4 の判断に直結する。`XywGr` を正本にするなら、**文字列の値を扱えるかどうか**を
先に決めないと、この画面は永久に統合できない。

## 3. 重大な見落とし（先に直さないと手戻りになるもの）

### a. `className="hidden"` が効かない — カスケードの副作用

`@layer` の性質上、部品が宣言した `display: inline-flex` は Tailwind の
`hidden`（`display:none`）につねに勝つ。**条件付きで部品を隠せない。**
エラーも警告も出ず、テストでも検出されない。

影響: ボタンやカードを画面幅や状態で出し分ける既存パターンが黙って壊れる。

### b. フォーカス指定が3部品とも0件

`summary-card.module.css` `button.module.css` `table.module.css` のいずれにも
`focus` の指定が無い（grep で 0 件を確認）。Tailwind preflight 下では
キーボード操作時の可視性がブラウザ既定に依存する。

引き渡し書の提案Gが「focus-visibleを共通部品に持たせる」と書いているとおり、
**部品を作った時点で入れるべきだった。**

### c. `Button` の `href` 分岐が他のpropsを捨てている

```
if (href) {
  return (<Link href={href} className={classes}>{children}</Link>)
}
```

`...rest` が使われていない。`disabled` `onClick` `aria-*` `target` が**黙って消える**。

`<Button href="/x" disabled>` は「無効のはずなのに遷移するリンク」になる。
提案Gの「disabledリンクを作らない」に正面から反する。型でも防げていない。

### d. 「35項目一致」は再現不能 — **引き渡し書 §5 の指摘は正しい**

この検証は、私がシェル上でその場限りのPythonスクリプトを書いて実行したもので、
**リポジトリには残っていない**（`apps/web/scripts/` には `build-release-log.mjs` と
`raw-color-baseline.mjs` の2本のみ。Pencil Node ID を参照する成果物は契約テスト1件のみ）。

契約テスト `v5-parts-contract.test.ts` が見ているのは **CSSソースの文字列**であって、
ビルド後の実CSSではない。したがって次は保証されていない。

- `var()` を解決した最終値がPencilと一致すること
- 呼び出し側 `className` との競合が起きていないこと
- ページ上で実際に適用されていること

**「35項目一致」を合格証拠として扱ってはいけない。** スクリプト化して
リポジトリへ入れ、CIで回るまでは「未確認」とすべき。

### e. `Th` の `scope` が `string` 型で既定値が無い

```
scope?: string
```

Reactの正しい型は `'col' | 'row' | 'colgroup' | 'rowgroup'`。既定値も無いため、
移行した9ファイル30箇所の見出しは**すべて `scope` 無し**になっている。
表の読み上げに影響する。`scope="col"` を既定にすべき。

## 5. コード側で先に直すもの

投入前に塞ぐ。いずれも部品3つの中だけで完結し、画面側の変更は不要。

### 5-1. `hidden` 問題（§3-a）

案を2つ挙げる。**案1を推す。**

- **案1: 表示制御をpropsで受ける。** `<Button hidden>` を部品側が解釈し、
  `display: none` を部品のCSSで当てる。`className` に表示制御を渡さない規約にし、
  契約テストで `className` に `hidden` / `flex` / `block` / `inline` が
  含まれていないことを見張る
- 案2: 部品CSSを `@layer components` に入れ、Tailwindの `utilities` より弱くする。
  カスケード順は正しくなるが、**呼び出し側から余白も色も上書きできるようになる**ため、
  提案Bの目的（自由度の制限）と衝突する。採らない

### 5-2. `focus-visible` を3部品へ入れる（§3-b）

Pencilにフォーカス状態の定義が無いため、**値をコード側で勝手に決めない**。
提案F・Iに従い、Pencil側へ「フォーカス時の見え方」を定義してもらってから入れる。
それまでの暫定として、ブラウザ既定の輪郭を消さないことだけ保証する。

### 5-3. `Button` の `href` 分岐（§3-c）

- `href` と `disabled` を**同時に受け取れない型**にする（判別可能ユニオン）
- `href` を渡したとき、`...rest` を捨てずに `Link` へ渡す
- 契約テストで「`href` 分岐で `rest` が使われていること」を見張る

### 5-4. `Th` の `scope`（§3-e）

型を `'col' | 'row' | 'colgroup' | 'rowgroup'` にし、既定を `'col'` にする。

### 5-5. `SummaryCard` の値の型（§2-4）

`app/emergency/page.tsx` のローカル部品を吸収するには文字列の値が要る。
ただし **`XywGr` の値は `$size-metric`(22px) の数字が前提**の設計なので、
文字列を入れると意味が変わる可能性がある。**Pencilへ確認してから決める。**
それまでは `emergency` を統合対象から外し、ローカル部品に非推奨コメントを付ける。
**少なくとも名前の衝突は先に解消する。**

## 6. PRの分割案

Codexの6段階に **0番** を足す。0番はコードの見た目を1pxも変えない。

| # | 内容 | 見た目の変化 | 戻し方 |
|---|---|---|---|
| **0** | 照合スクリプト＋影響レポートの仕組み | **なし** | 単独で戻せる |
| 1 | トークン変更のみ | 全ページで色がわずかに変わる | 単独で戻せる |
| 2 | 共通部品＋契約テスト（§5の穴を塞いだ版） | **なし**（まだ誰も使わない） | 単独で戻せる |
| 3 | カード移行 | カード寸法が揃う | 単独で戻せる |
| 4 | 表見出し移行 | 見出しの余白・行高が変わる | 単独で戻せる |
| 5 | ボタン移行 | ボタンの高さ・文字が変わる | 単独で戻せる |
| 6 | 残る部品を利用頻度順 | 部品ごと | 部品ごとに戻せる |

0番を先に入れる理由: **1番の効果と副作用を測る道具が、1番より先に要る。**
トークンを変えてから影響を調べる仕組みを作るのでは順序が逆になる。

依存: 2 は 1 に依存、3〜5 は 2 に依存、6 は 2 に依存。**逆流なし。**

現在の未コミット差分は 1〜5 が混ざった状態なので、
**`codex/development` から切り直して分割し直す**必要がある。

## 8. 変更影響の把握方法

提案A・Hに賛成。**3層に分けて作る。** 上から順に効果が高く、作るのも安い。

### 層1: 対応表をJSONにする（提案A）

`apps/web/src/lib/design-parts.json`（案）。

```json
{
  "XywGr": {
    "name": "共通 サマリーカード",
    "区分": "正本",
    "code": "components/shared/summary-card.tsx",
    "css": "components/shared/summary-card.module.css",
    "variants": ["muted", "accent"],
    "pencil使用回数": 24,
    "最終確認日": "2026-08-24"
  }
}
```

契約テストで次を検知する。

- JSONに書かれたコードのパスが存在すること
- JSONに無いCSSモジュールが `components/shared/` に増えていないこと
- `区分: 廃止候補` の部品が新たに使われていないこと

**Node IDの陳腐化検知**（§7-3の問い）: Pencil MCPで各Node IDを引き、
名前が変わっていないか・存在するかを確認するスクリプトを別に置く。
CIでは動かせない（Pencilはローカル）ので、**手動実行＋最終確認日で運用する**。

### 層2: ビルド後CSSの照合（§3-d の解決）

`apps/web/scripts/verify-design-values.mjs`（案）。私がその場で実行した処理を
そのままスクリプトにする。

1. `.next/static/css/*.css` から `:root` の変数を集める
2. CSSモジュールのクラス（`.summary-card_card__xxx` など）の宣言を集める
3. `var()` を解決する
4. **期待値はJSONに持つ**（Pencilの実ノードから写した値）
5. 一致しなければ終了コード1

これで「35項目一致」が再現可能な証拠になる。ビルド成果物が要るので、
テストではなく**ビルド後のチェックとしてCIに入れる**。

### 層3: 影響レポート（提案H）

`apps/web/scripts/design-impact.mjs <トークン名 or 部品パス>`（案）。
変更**前**に実行し、次を出す。

- そのトークン／部品を参照しているファイルとルート
- **共通部品を通らず直接値を書いている箇所**（`raw-color-baseline.json` と突き合わせ）
- 撮り直すべき基準画面（§2-5 の6画面のうち該当するもの）

「共通部品を直したのに一部だけ古い見た目が残る」の検知は、
**`raw-color-baseline.json` の仕組みをそのまま拡張するのが一番安い**。
既に「生の色は減る方向にしか変えられない」を強制できており、
同じ形で「直書きの `<th>` 数」「直書きボタン数」を足せばよい。

## 9. 新ルールの受け入れ手順

提案Iに賛成。判断基準を具体化する。

### 判断表

| 状況 | 判断 |
|---|---|
| 既存トークン・部品で**そのまま**表現できる | **Pencilを既存基準へ合わせ直す**。新ルールにしない |
| 既存の値と**5%未満**の差（例: 角丸12px と 13px） | 差に意味が無いとみなし、**Pencilを既存へ寄せる** |
| 差に意味があり、**2画面以上**で必要 | **正本へ追加**。トークンまたは部品を増やす |
| 差に意味があり、**1画面だけ** | 固有である理由を確認。理由・適用範囲・**終了条件**を記録した例外にする |
| 判断がつかない | **実装を止めて確認する。画面へ直接書かない** |

### 「意味がある差」の判定

次のどれかに当てはまれば意味がある。当てはまらなければ寄せる。

- 役割が違う（例: `mNUQ3` の緑の3行目は「予定の告知」で、説明ではない）
- 状態が違う（選択中・無効・エラー）
- 情報量が違う（列数、文字数の上限）

### 片方だけに存在する状態の検知

層1のJSONに `pencil使用回数` と `code` の両方を持たせ、次を未完了として扱う。

- `code` が空で `pencil使用回数 > 0` → **コード未実装**
- `code` があり `pencil使用回数 = 0` → **Pencil未使用**（廃止候補か、参照切れの調査対象）
