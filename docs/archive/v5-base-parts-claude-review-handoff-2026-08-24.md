# V5 デザイン基盤 Claudeレビュー引き渡し書

作成日: 2026-08-24
対象: `apps/web` のデザイントークン、共通部品、既存画面のV5移行
依頼内容: **実装はせず、設計・実装方針をレビューして結論と改善案を返す**

## 0. Claudeに最初に伝えたいこと

目標は、Pen.dev / Pencilで確定した画面を渡したとき、既存コードの古い色・余白・部品に引っ張られず、設計どおりに実装できる状態へ変えることです。

単に3個の共通部品を追加する作業ではありません。次の流れを今後の標準にするための基盤変更です。

```text
Pencilのトークンと実ノード
  → コードのトークンと共通部品
  → 各画面の表示層
  → 同じ状態・同じ横幅の画像比較
  → 差を直して合格
```

既存の機能、API、保存処理は残し、表示の基準をV5へ置き換えます。既存画面も最終的には新しい基準へ移行します。

特に実現したいのは、**修正箇所をできる限り少なくしながら、影響先へ漏れなく反映すること**です。

例えばPencilで共通ボタンの高さや色を変えた場合、コードを何十画面も個別修正するのではなく、次の状態にします。

1. 変更されたトークンまたは共通部品を特定する
2. Pencil上の使用画面とコード上の使用箇所を一覧化する
3. 影響する画面・状態・例外を変更前に報告する
4. 正本となるトークンまたは共通部品を原則1か所直す
5. 利用画面へ一括で反映される
6. 影響画面を画像比較し、意図しない差だけを修正する

Pencilで新しいルールや既存と違う値が見つかった場合、画面へ直接書いて済ませません。次のどちらかを先に判断します。

- 新ルールを共通基盤へ採用し、影響先をまとめて更新する
- 既存の基本設定へPencil側を合わせ直す

本当に画面固有の理由がある場合だけ、理由・適用範囲・終了条件を記録した例外にします。判断できない場合は実装を止め、基準変更かPencil修正かを確認します。

## 3. Codexが出した5点の結論

Claudeには、賛成・反対だけでなく、反対の場合の具体的な代案も求めます。

### 3-1. 共通部品はCSSモジュールにする

Codexの結論: **採用**。

- 共通部品の見た目はCSSモジュール
- ページ側の配置はTailwindのまま
- CSSモジュール内では`globals.css`のPencil由来トークンだけを参照
- 生の色、部品内ローカル変数、Tailwind任意値での上書きを禁止

確認してほしいこと:

- CSSモジュールと呼び出し側`className`の優先順位が不安定にならないか
- 幅や配置だけを呼び出し側へ許可する境界が適切か
- 状態、サイズ、余白を自由な`className`で再び崩せない設計になっているか
- CSSモジュールより適した既存方式が、このリポジトリ内にあるか

### 3-2. コードのトークン値をPencil V5へ合わせる

Codexの結論: **採用**。

変更対象には本文色、補足色、薄い文字色、枠線色が含まれます。トークンを使う全ページへわずかな色変更が波及します。これは今回の目的に含まれます。

確認してほしいこと:

- 一括変更で読みにくくなる状態色や古い画面がないか
- V5へ移行前の画面で、意味が変わる使われ方をしていないか
- トークン名と役割が十分明確か
- グローバルトークン変更前に分離すべき互換トークンがあるか

### 3-3. 表見出しから`uppercase` / `tracking-wider`を外す

Codexの結論: **外す**。

Pencilの表見出しセル`tPTMp`には大文字変換と文字間隔指定がありません。必要な英字表記は、CSS変換ではなく`ID`など文字列自体で指定します。

確認してほしいこと:

- 日本語・英語・数字が混ざる見出しでも問題がないか
- 文字間隔を外した結果、列幅や省略表示へ悪影響がないか
- 既存のアクセシビリティや可読性を落とさないか

### 3-4. `XywGr`と`mNUQ3`を統合する

Codexの結論: **`XywGr`を正本として統合し、`mNUQ3`は廃止候補にする**。

両者は「ラベル・数値・単位・補足」の同じ構造です。現在の差はラベル色、余白などで、配信だけ別規格にする明確な理由が見つかっていません。

確認してほしいこと:

- 統合すると失われる意味や状態があるか
- 1部品に自由なvariantを増やすより、完全に同じ見た目へ統一した方がよいか
- もしvariantが必要なら、許可する差を固定した名前付きvariantに限定すべきか
- Pencil側の`mNUQ3`を削除・非推奨・置換のどれにすべきか

### 3-5. 1本のPRにしない

Codexの結論: **段階投入**。

推奨順:

1. トークン変更だけ
2. 共通部品と契約テスト
3. カード移行
4. 表見出し移行
5. ボタン移行
6. 残る部品を利用頻度順に移行

確認してほしいこと:

- この分割で途中状態が壊れないか
- 各PRの依存関係とロールバック単位が適切か
- トークン変更を最初に入れるか、部品と同時に入れるべきか
- 103ページへの波及確認を現実的に行う最小の画面組み合わせは何か

## 4. Pencil側の部品表で直すこと

現行ハンドオフの「必ず使う部品」と、6機能85画面の実使用が一致していません。

- `AWHUI 標準一覧表`: 6機能でインスタンス利用0回
- `tPTMp 共通 表見出しセル`: 107回
- `n18zLK ツールバー`: 0回
- 実際の友だちツールバーは`tT9S1`
- ほかにも未使用部品が「必ず使う」に含まれている

単純な置き換えではなく、部品表を次の3分類にする案です。

1. **必ずインスタンス利用する部品**
2. **コピー元・完成見本として使うテンプレート**
3. **未使用・非推奨・廃止候補**

Claudeに確認してほしいこと:

- `AWHUI`は完成見本として残すべきか、実際に使える表コンテナ部品へ作り直すべきか
- 「0回」が本当に未使用なのか、コピー後に参照が切れた結果なのか
- 部品ID、用途、使用回数、コード側の受け皿、状態をどこで正本管理すべきか
- 次のPencil機能を作る前に、最低限どこまで直す必要があるか

## 5. 現時点で不足している保証

現在の契約テストは、主にCSSソースに期待する宣言が含まれることを確認しています。これは有効ですが、次までは保証しません。

- ビルド後にブラウザへ適用された最終スタイル
- Tailwindやページ側`className`との競合
- フォント、行高、内容量による高さの変化
- 1440px / 1920pxでの折り返しや横スクロール
- 通常、空、読込中、エラー、モーダルなど全状態の見た目
- Pencil画像との位置・寸法・色・余白・影の一致

`docs/v5-base-parts-handoff-2026-08-24.md`には「ビルド後の実CSSからvarを解決して35項目一致」とありますが、その検証を再実行できるスクリプトや成果物がリポジトリ内で確認できません。表現が正しいか、再現可能な証拠を追加すべきか確認してください。

## 6. 精度を上げるための提案

### 提案A: Pencil部品とコード部品の対応表を機械で読める形にする

Markdownだけでなく、次の情報をJSONなどで管理する案です。

- Pencil Node ID
- 部品名
- 正本・見本・非推奨の区分
- コード部品のパス
- 許可するvariant
- 使用画面
- 最終確認日
- 画像比較の証拠

Node ID変更や部品の廃止を契約テストで検知できるようにします。

### 提案B: 部品の自由度を制限する

`className`ですべてを上書きできると、再び寸法が分裂します。

- 呼び出し側に許可するのは幅、グリッド位置、外側余白だけ
- 高さ、内側余白、色、角丸、影、文字は部品側が所有
- 必要な差は`size="standard"`など名前付きvariantで固定
- 生の値を受け取るpropsは作らない

この境界をlintまたは契約テストで守ります。

### 提案C: 文字列テスト・計算後CSS・画像比較を分ける

1. トークンと部品APIの契約テスト
2. ブラウザ上のcomputed style確認
3. Pencilと実装の同一viewport画像比較

3段階を別の証拠として残し、どれか1つだけで「デザイン一致」と判定しないようにします。

### 提案D: 基準画面を決める

全103ページを毎回確認するのは現実的ではありません。トークンと部品を代表する基準画面を決めます。

- 通常の一覧
- KPIカード付き一覧
- 入力フォーム
- モーダルまたはドロワー
- データ量が多い表
- 空・読込中・エラー状態

各画面を1440pxと1920pxで確認し、変更対象の共通部品を使う画面は追加で確認します。

### 提案E: 古い基盤の出口を決める

現在も生の色が3267か所、表見出しとボタンの直書きが多数残っています。

- 新規追加を先に禁止する
- 利用頻度の高い部品から回収する
- 旧部品には非推奨コメントと置換先を付ける
- 生の色の基準値は減少だけ許可する
- 移行完了後に旧トークンや旧部品を削除する

追加と削除を同時に進めないと、新基盤の上に旧基盤が残り続けます。

### 提案F: 部品の状態を先に定義する

通常状態だけ一致しても、実画面では不十分です。

- default
- hover / focus-visible
- disabled
- loading
- error
- selected
- 長い日本語、長い数値、0件、値なし

Pencilに存在しない状態は、勝手にコードだけで確定せず、Pencil側へ戻して決めます。

### 提案G: アクセシビリティを設計契約へ含める

- ボタンとリンクを用途どおり使い分ける
- focus-visibleを共通部品に持たせる
- disabledリンクを作らない
- 表見出しの`scope`、空見出しの`aria-label`を決める
- 色変更後のコントラストを確認する

見た目の一致と操作可能性を同時に守ります。

### 提案H: 変更前に影響レポートを自動で出す

Pencilまたはコードの基準を変える前に、少なくとも次を出す仕組みを作る案です。

- 変更するトークン・部品・Node ID
- Pencil上の利用回数と利用画面
- コード上の利用ファイルとルート
- 影響する通常・空・読込中・エラー・モーダルなどの状態
- 共通部品を通らず直接値を書いている箇所
- 変更後に撮り直す基準画像
- 基本設定へ統合できない例外と理由

これにより、「ここを変えるとどこまで変わるか」を変更前に確認できます。共通部品を直したのに一部だけ古い見た目が残る状態も検知対象にします。

### 提案I: 新しいPencilルールの受け入れ手順を固定する

新しい画面で未登録の色、余白、角丸、文字サイズ、部品が見つかった場合は、次の順で扱います。

1. 既存トークン・部品で表現できるか照合する
2. 表現できる場合はPencilを既存基準へ合わせる
3. 表現できず、複数画面で必要なら新しい共通ルールとして正本へ追加する
4. 1画面だけ必要なら、固有である理由を確認する
5. 正本更新、コード更新、影響先更新、画像比較を同じ変更単位として記録する

Pencilとコードのどちらか片方だけに新ルールが存在する状態を未完了として検知します。

### 提案J: 修正回数と反映率を測る

基盤の効果を次の数で確認する案です。

- 1つのデザイン変更に必要だった修正ファイル数
- 共通部品経由で自動反映できた画面数
- 直接値が残る画面数
- 基準外variantと例外の数
- 画像比較で見つかった未反映数

目標は、同じ役割の変更を原則1か所で行い、利用画面の100%へ反映され、例外が一覧で説明できる状態です。

10. 同じ変更を複数画面で繰り返さず、原則1か所の修正へ集約するために不足している仕組みは何か

## 8. Claudeに求める回答形式

次の順番で回答してください。

1. **結論**: この方針で進めてよいか
2. **5つの確認事項への回答**: 採用・修正・不採用と理由
3. **重大な見落とし**: 先に直さないと手戻りになるもの
4. **Pencil側で先に直すもの**
5. **コード側で先に直すもの**
6. **PRの分割案**
7. **検証環境での確認項目**
8. **変更影響の把握方法**: Pencilの変更から影響先をどう列挙するか
9. **新ルールの受け入れ手順**: 基盤更新かPencil修正かの判断基準
10. **追加提案**: 費用対効果順
11. **次に実行する1タスク**

レビュー中にコードやPencilを変更しないでください。事実確認のための読み取りは可能です。不明点は推測で埋めず、「未確認」と明記してください。

## 9. 合格条件

この基盤変更は、次を満たしたときに完了とします。

- Pencilの必須部品表が実使用と一致している
- トークンの正本とコード値が一致している
- 同じ役割の部品が理由なく複数に分かれていない
- 1つの基準変更について、影響するPencil画面・コード・状態を変更前に列挙できる
- 同じ役割の変更を原則1か所のトークンまたは共通部品で実施できる
- 共通部品の変更が全利用画面へ反映され、未反映と例外を検知できる
- Pencilで新ルールが見つかったとき、基盤へ追加するかPencilを既存基準へ戻すか判断できる
- Pencilとコードの片方だけにルールが存在する状態を未完了として扱える
- 新規画面が生の色や任意値に戻らない仕組みがある
- 通常状態以外の部品状態も定義されている
- 1440pxと1920pxで横スクロールと意図しない改行がない
- Pencil実ノード画像と実装画像を同じ状態・同じ幅で比較している
- 差を修正した後の画像を合格証拠として残している
- 機能テスト、型検査、ビルドが成功している
- 旧基盤を減らして最終的に削除する順序が決まっている
